# Story 5.6: SMS Transactional Fallback (DLT-transactional) + 3-Retry × Exp-Backoff

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As any member whose primary channels (in-app push, WA) have failed for an alert,
I want a transactional SMS fallback delivered via DLT-transactional / PE-OE registered sender,
so that critical notifications still reach me even when modern channels are unavailable.

## Acceptance Criteria

**AC1 — the real SMS-DLT provider (AR-19 + AR-56 + Story 5.1 dispatcher):**
1. The SMS provider implements the **frozen** `ChannelProvider` port (`packages/channels/src/provider.ts`, channel `'sms'`, provider id `'sms-dlt'`) — replacing the Story 5.1 stub (`packages/channels/src/providers/sms-dlt.ts`) with a real telephony-gateway `send` integration, mirroring the Story 5.3 `whatsapp-business.ts` provider shape.
2. The provider sends **DLT-transactional templates registered with TRAI** (via the PE/OE-registered sender header). The rendered SMS body maps into the **registered DLT template's variable slot** (the single-variable shape, exactly mirroring WA's `bodyParam: rendered.body` — Story 5.3 Q1=A). The provider **never mutates** the frozen `render.ts` `sms` output.
3. `send` **resolves `accepted`** with the gateway message id on success and **resolves `rejected` (NEVER throws)** on any error — SMS **failure** (carrier reject, invalid number, DLT template not approved / content mismatch, gateway 4xx/5xx, network) is classified (no PII) via a new `sms-errors.ts` and encoded in the `SendResult.detail`. `getStatus` returns an honest `unknown` (the gateway gives no synchronous delivery receipt at accept time). **No further fallback below SMS in v1** (SMS is the terminal ladder rung).

**AC2 — DLT template registry (per-category, versioned):**
4. DLT templates are **versioned and registered per category that supports SMS fallback**. Architecture §3.4 (L1944-1948, "SMS preserved surfaces") defines SMS's fire *conditions* (OTP / step-up OTP / per-member WA-failure fallback) but does **not** enumerate a fixed SMS category list — that list is a v1 scope decision (BigDev, 2026-07-06, see Change Log): the DLT registry is populated for the **per-member transactional categories the `AlertCategory` enum actually has** — `deadline_reminder`, `contribution_confirmed`, `contribution_mismatch`, `claim_status_change`, `helpdesk_reply` — since SMS only fires as a fallback for a WA send that already exists. (Architecture §3.4's own prose examples — payment reminder, payout issued, claim accepted, expiry warning, membership lapse — are illustrative language, not schema identifiers; none map 1:1 onto the enum, so they are NOT the registered set — see Task 2 / Change Log.) This is a **derived v1 default, not an architecture-mandated list** — a category **not** in the registry is **not SMS-eligible** (the composition target/provider resolver returns `null` → no SMS send for it — mirrors WA's "no approved template ⇒ not WA-eligible"). Expanding the registry to other `AlertCategory` values is a later story once those categories' DLT content is TRAI-registered.
5. The **TRAI-assigned DLT template IDs** and the **PE/OE sender header** are resolved from **global** config / Secret-Manager NAME pointers at send time — **never hardcoded, never logged, never audited** (AI-4-3(c); mirror `pariwar_wa_config.access_token_secret_name` discipline). The registered content template text + version live in code (code-reviewed, matches the TRAI registration per the Story 0.1 runbook / AR-56).

**AC3 — retry × exponential-backoff cascade ladder (AR-19):**
6. A **retry / backoff / cascade primitive** WRAPS the per-channel send seam (the extension point `dispatch.ts` reserves for 5.6: *"Retry / backoff / cascade-on-failure (5.6) also WRAP the per-channel send seam without re-sequencing the canonical order or changing dispatch's public shape"*). It provides: (a) a **bounded retry** per channel with **exponential backoff** — **"3-Retry" means one initial send followed by three retry attempts using delays of 30s, 5m, and 30m** (i.e. 4 total sends per channel; the backoff schedule is injectable and its length is the retry bound), and (b) **cascade-down-the-ladder**: when a higher-tier channel is terminally undelivered (retries exhausted / `rejected`), advance to the next rung of `CANONICAL_CHANNEL_LADDER` (`push → whatsapp → sms`), with **SMS as the terminal rung**.
7. The cascade iterates **ONLY** `CANONICAL_CHANNEL_LADDER` and leaves the Telegram side-channel **independent** (no cascade on a Telegram failure). It **does NOT change** the frozen `dispatch` / `ChannelProvider` / `CANONICAL_CHANNEL_LADDER` / `DeliveryResolver` / `render.ts` surfaces, and it introduces **NO live `dispatch` call site** ([[project_channels_no_live_dispatch_yet]]) — it is a reusable, deterministically-testable primitive the (future) live fan-out drives. The backoff timing is behind an **injectable clock/sleep seam** (no real sleeps in tests).

**AC4 — per-member SMS rate-limit + eligibility (Story 1.14 + architecture §3.4):**
8. Per-member SMS **rate-limits prevent floods** (Story 1.14). Reuse the proven atomic Postgres bucket pattern (`otp_rate_buckets` — INSERT … ON CONFLICT DO UPDATE), but in a **dedicated `sms_rate_buckets` counter** keyed per **member** so a transactional-alert-SMS flood can **never** consume the security-critical OTP send budget (and vice-versa).
9. The composition layer exposes a reusable **`resolveSmsTarget(pariwarId, memberId)`** seam (mirror `resolveWaTarget`, **minus the opt-in gate** — SMS has no opt-in; the member's registered mobile from KYC is the address): decrypt the member's Tier-1 mobile **in the composition layer** (never in `dispatch` / the provider) → the E.164 `SendTarget.address`, or `null` when the member has no identity row. The **eligibility policy** (architecture §3.4: transactional-fallback SMS fires per-message only for members whose higher-tier channel failed after the retry window — **NOT** a blanket fallback for members with no higher-tier channel) is a documented constraint the live cascade site / cost-optimization wrapper (5.7) enforces; see Dev Notes "The §3.4 vs AR-19(c) eligibility tension".
10. Cost-optimization (Story 5.7) suppresses redundant SMS when the member has already acted in-app within the staleness window — this is a **later** wrapper (5.7); Story 5.6 only leaves the mechanism un-obstructed (do not build the suppression policy here).

### The DLT-template-matching constraint (the #1 SMS-reject cause)
DLT-transactional gateways **reject** any content that does not **byte-match a registered content template** (TRAI/DLT enforcement). So — exactly like WA's single-`{{1}}`-body-param shape — the frozen `render.ts` `sms` output (`` `${heading}: ${line}` ``) is mapped into the **variable slot** of a pre-registered DLT template; the fixed template wrapper (the registered header/body scaffolding + PE/OE sender) is the gateway's, not the renderer's. **Do not change `render.ts`** (it is determinism-gated). If the rendered body cannot fit the registered template's variable, that is a **`dlt-template-not-approved` / content-mismatch** rejection, classified and surfaced (never a fabricated success). Structured multi-variable DLT templates are an Epic-10 evolution — v1 is single-variable (mirror WA Q1=A).

### Retry-ladder durability — build the primitive, defer the durable substrate (DECIDED, BigDev 2026-07-06)
The 5.1 stub comment says *"the pg-boss retry ladder land in Story 5.6"* — but [[project_channels_no_live_dispatch_yet]] holds: there is still **no live `dispatch` call site**, so a durable pg-boss retry job would have **no real producer**. **Decision:** build the cascade/backoff as an **in-process, injectable-clock primitive** (deterministic, unit-tested) whose backoff schedule is a plain array — so the **durable** pg-boss wiring (retryLimit/retryBackoff or a dedicated `QUEUE_NAMES` entry) is a **thin adapter** the live fan-out adds later, exactly as WA's fallback and the multi-target fan-out were deferred. This keeps scope honest and avoids a registered-worker-with-no-producer.

> **Scope boundary — say it plainly so it is not read as an omission:** **Story 5.6 OWNS the retry *semantics*** — the attempt bound, the exponential-backoff schedule, and the cascade ordering are defined and tested here. **Durable retry *execution* (pg-boss scheduling / persistence / cross-restart resumption) is INTENTIONALLY out of scope** and lands with the future live-dispatch story that first drives a real fan-out. The absence of a pg-boss job in this story is a **deliberate deferral, not a gap** — the primitive is shaped (plain-array backoff schedule, injected clock) precisely so the durable adapter is thin. A later developer must not "fix" this by wiring a producer-less pg-boss worker.

### The §3.4 vs AR-19(c) eligibility tension (surface, default to architecture)
The epic AR-19 says SMS fires after: (a) push fails 3× backoff, **OR** (b) WA fails, **OR** (c) *"the member has no opted-in higher-tier channels."* **Architecture §3.4 (committed, L2092-2098)** is narrower: transactional-fallback SMS fires per-message **only** for members whose higher-tier channel **failed after the retry window**, and *"Members without active WA opt-in receive only in-app push for non-OTP notifications — **they do not receive transactional-fallback SMS**"* (the RA-29 no-bulk-SMS guardrail). These **conflict on case (c)**. Per [[feedback_architecture_vs_prd_boundary]], the architecture commits the constraint. **Resolution for 5.6:** this story builds the **mechanism** (provider + cascade + rate-limit + target resolver) and does **not** wire the eligibility **policy** (there is no live cascade site to wire it into). Record §3.4 as the default constraint the live cascade / cost-opt wrapper (5.7) will enforce; flag AR-19(c) as the divergence. Do **not** silently implement a blanket no-channel→SMS fallback.
