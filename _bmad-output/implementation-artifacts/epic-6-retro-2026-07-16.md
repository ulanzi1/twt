## 1. Epic Summary

Epic 6 is the **highest-stakes flow in the system** — ₹50L per decision (UX-DR39 earned its own story-level design budget at 6.10). When a member dies, the bereaved family (Ravi-mode, app on the deceased's phone) or a helpline-mediated path files a claim; both converge at a single canonical `claim_case_id` via the dual-path ICP. Death-certificate OCR runs a parity check. Peer mesh deterministically pings the 5 nearest members; ground inspection runs alongside (both, not either, per FR-40). Anita's ₹50L-budget verifier console loads the signals panel in ~5s via a compound read model; she adjudicates with a one-tap reason-code + rationale on the decision strip. A named human shepherd surfaces on the status page. The State Trustee freezes the cycle in a bulk-approval action (the Epic 7 pool-spawn trigger). Special cases route to R9 voting; concealment-flagged claims route to State Trustee review (flag, never auto-deny — R14 discipline preserved). Denials get a structured 3-stage internal appeal (District Admin reviewer ≠ original → State Trustee panel vote → Trustee discretion); reversed denials emit a `claim.reversed` publish hook for Epic 11b's Sahyog Vivran.

Story 6.1 landed the claim case object + event-replay state machine as the **primitive** (15 states, projector-only `current_state`, per-transition named events). 6.2/6.3 built the two intake surfaces; 6.4 the ICP convergence primitive (canonical-ID invariant, CI-asserted). 6.5 landed the stack's **first blob store** (`ClaimDocumentStorage` port + GCS adapter + `OcrProvider` abstraction). 6.6/6.7 the peer-mesh + ground-inspection signal pair. 6.8/6.9 claim-time nominee bank (dual-account) + DPDPA consent. 6.10/6.11 the verifier console + decision strip (first verifier writes). 6.12/6.13 human shepherd + cycle-freeze bulk approval. 6.14/6.15/6.16 R9 voting, concealment path, 3-stage appeal.

### The headline

> Epic 1: *enforced beats remembered.* Epic 2: *a gate is only as strong as the property it asserts.* Epic 3: *decay concentrates in the un-mechanized half of a split commitment.* Epic 4: *a corrosive family can be dissolved by architecture — but dissolution relocates the risk.* Epic 5: *you can build the gate and still miss the target — a control scoped to last epic's code protects none of this epic's.*
> **Epic 6's addition: a mechanized gate's SCOPE is a recurring per-epic tax, not a one-time fix. AI-5-1 extended the access-wrapper gate to Epic 5's surface — and Epic 6 promptly built the highest-stakes access surface in the system (`claims`/`nominee`/appeal) *outside* the scan roots. The convention half carried the epic again — and this time it caught a live wrong-data bug that DB-free tests structurally could not (the Story 6.6 Drizzle correlated-subquery tautology). The fix is to make gate-scope-extension a standing per-epic commitment, so the gate grows *with* the code.**

## 3. What Was Hard / What Leaked

### H-1 (headline) — The gate-scope tax is now standing
SCAN_ROOTS covers `validity-service` (`VALIDITY_ROOTS`, AI-4-3) + channels/apps-api-channel (`CHANNEL_ROOTS`, AI-5-1). Mechanization *did* happen this epic (two new dedicated claim gates), just not for the access-wrapper family. So the "extend the gate" action recurs every epic that adds an access surface: AI-4-3 aimed at Epic-4's package, AI-5-1 re-aimed at Epic-5's, and Epic 6's went uncovered again. → **AI-6-1.**

Every real defect landed in access / authz / audit / state-machine. Now at the highest stakes the system will ever carry.

### H-3 — DB-free tests structurally can't catch data-shape bugs
The 6.6 correlated-subquery tautology is the exemplar (green unit tests, wrong data). The 6.10 ~5s compound read model is the same class of risk and is un-covered by unit tests — and Epic 7's pool read models will be too. → **AI-6-3.**

### H-4 — Migration drift continued (~0058, hand-authored on 0020)
AI-5-4 correctly still parked as a pre-launch gate, but the drift is growing across a sixth epic ([[project_live_db_test_gotchas]]). → **AI-6-4** (carry).

### H-5 — Vendor facts still indicative
`OcrProvider` and the `kyc-provider-boundary` gate have no real vendor behind them (abstraction-first, no boundary gate until one exists). Live-integration risk carried — the same correct-for-pre-launch posture as Epic 5's external-API "indicative" fact sets.

### H-6 — W-6 is a strength *and* a signal
That several load-bearing invariants only closed on BigDev's manual second pass (6.13 needed **three** addenda) means the 3-layer review's coverage of load-bearing invariants is inconsistent story-to-story. The second pass shouldn't be the *only* place these are caught. → **AI-6-5.**

## 4. Key Insights / Lessons

### I-1 — A mechanized gate's scope is a recurring per-epic commitment
"Built a gate" is not "the gate reads the code this epic was about." Three epics running, the access-wrapper gate has covered the *previous* epic's surface. The clean fix isn't a bigger retro catch — it's to make **"extend access-wrapper SCAN_ROOTS to this epic's new access surface" a standing item in each epic's primitive (Story-1) checklist**, so the gate grows *with* the code instead of a retro catching the miss two epics later. This is [[feedback_mechanization_split_commitment]] at its next turn: the scope of a control is itself a commitment that decays if not re-made each epic.

### I-2 — The review layer earns its cost most where tests structurally can't reach
The 6.6 correlated-subquery bug is the cleanest proof to date: adversarial review caught what DB-free tests could not even in principle. Keep the 3-layer review; pair it with a targeted live-DB test class for compound-read-model / correlated-subquery shape so the catch isn't review-only.

### I-3 — Access-wrapper is still the family, at the highest stakes yet
Sixth epic, same family — which is exactly why I-1's per-epic scope extension matters *most* here. The cost of a miss on a ₹50L adjudication route is the highest in the system.

## 6. Next Epic Preview — Epic 7: Pool Engine & Cycle Spawn

**The math heart of PRD §9.1.** At trustee bulk-approval (cycle freeze, via Epic 6's 6.13), the engine atomically spawns N pools (one per approved claim), names them from a culture-rooted curated list, assigns every active member deterministically via `pool_index = hash(member_id + cycle_id) % N`, snapshots `fixed_amount`, and emits all events. Replay-verifiable, idempotent, partitioned for capacity; saga decomposition targets a **< 60s p95 envelope at N=50 / M=4L**.

### Dependencies
Epic 1 (event log + idempotency + pg-boss queue) · Epic 3 (active members at freeze) · Epic 4 (Validity Service — only valid members assigned) · **Epic 6 (approved claims trigger freeze via Story 6.13's `packages/contracts/pool-spawn-trigger` seam).**

### Two signals
1. **Epic 7 is the first consumer of 6.13's cycle-freeze trigger.** Worth confirming the `pool-spawn-trigger` contract is wired and actually fires from the bulk-approval action — the same "first live caller" caution that AI-5-2 handled for `dispatch`. (6.13 shipped `cycle.freeze` @ `dimension:'pariwar'` with the `state_trustee` gating deferred to Epic 3; v1 actor is `pariwar_admin`-as-Trustee-Lite.)
2. **Epic 7 shifts the risk family** — away from access-wrapper (I-3, six epics) toward **determinism / replay / saga-atomicity / measured-performance**. Story 7.9's pre-launch measured-validation gate (Sprint Change Proposal Item 15) is a **P0 launch-blocker**, and it is the same *class* as the parked AI-4-1 (concurrent-load p95 harness) and AI-4-2 (determinism-gate real-path scope). → **AI-6-2** pulls them forward into a single shared framework.
