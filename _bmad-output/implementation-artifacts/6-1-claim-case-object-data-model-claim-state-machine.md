## Story

As Solo Builder authoring the claim case primitive that the **entire Epic 6 flow** (dual-path intake → ICP convergence → OCR parity → peer mesh + ground inspection → verifier console → State Trustee freeze → R9 voting → 3-stage appeal) consumes,
I want a claim case object data model + state machine that consumes Story 1.3's `@twt/events` event-log primitive — where the persisted `claims.current_state` column is *derived from* event replay and is never directly mutated,
So that the §1.14 / §1.9 source-of-truth commitment (architectural-freeze row 2) is enforced **by construction** for the **highest-stakes flow in the system** (₹50L/decision).

This is the FIRST story of Epic 6 and a pure `[PRIMITIVE]` — the exact claim-lifecycle twin of the already-merged **Story 3.1** (member lifecycle). It builds the `claims` table, the state machine, the pure reducer, the `claim.*` event vocabulary, the persisted-state projector, the two enforcement guards (DB trigger + CI gate), and the audit-emission surface. **It does NOT build any UI, any HTTP route, any intake flow, ICP convergence, OCR, peer mesh, or verifier console** — Stories 6.2–6.16 emit the events defined here. The claim *aggregate* consistency boundary (spawn → settlement, §1.9) is Epic 7+; 6.1 declares the states/events as legal + replay-safe only.

**⚠️ The single most load-bearing constraint in this story:** the already-merged Story 3.1 `account-frozen` overlay (`packages/domain/src/member/overlay.ts`) is a **built, waiting consumer** of *this* story's events. It pins an exact contract — the claim intake event MUST be named `claim.intake_initiated` (single-dot, snake_case) carrying `deceased_member_id` in its payload; the overlay-clearing events MUST be named `claim.settled` and `claim.denied_no_appeal`. The epics.md AC lists these with a DIFFERENT (double-dot) spelling. **Follow the seam contract, not the epic's illustrative spelling** — a mismatch silently breaks the account-frozen overlay across Epic 12 (Module Shelf suppression) and every future consumer. See Dev Notes "Event naming — the pinned seam contract."

**AC3 — State-mutation invariant (this story's load-bearing commitment).**
**Given** the state-mutation invariant (same pattern as Story 3.1)
**When** the persisted `claims.current_state` column is examined
**Then** it is **derived from event replay only** — never directly `UPDATE`d by any code path except the single projector (`packages/domain/src/claim/project.ts`)
**And** state replay is **deterministic, idempotent, and prefix-consistent** (pure reducer — no clock, no randomness, no I/O, no mutable module state):
  · *deterministic + machine-independent* — replaying events 1..N produces the same final state every time, on every machine;
  · *idempotent* — replaying the same 1..N twice yields identical results (no accumulation);
  · *prefix-replay determinism* — for ANY k ≤ N, folding events 1..k yields EXACTLY the state the incremental step-by-step fold held after event k (`fold(rows[0..k]) === rows[0..k].reduce(step, initial)`); i.e. `fold` and repeated `step` never diverge, and a truncated replay (as `getClaimStateAt` does at a timestamp boundary) is always a valid intermediate state, never a torn one
**And** a CI gate (`scripts/claim-state-invariant/`) statically asserts no code outside the projector allowlist writes to `claims.current_state`
**And** a DB-layer `BEFORE UPDATE` trigger on `claims` rejects any `current_state` change not issued under the projector's session guard (`app.claim_state_writer`), surfacing as a typed `ClaimStateDirectWriteError` at the `@twt/domain` barrel (P0 architectural-violation audit line emitted by the catching application boundary, NOT the trigger — see Dev Notes "Why the trigger can't write audit")

**AC4 — Audit trail on every transition.**
**Given** Story 1.10 audit log
**When** any claim state transition occurs (via the projector)
**Then** an audit-capable record exists carrying the transition with full event metadata + `claim_case_id` + `from_state`/`to_state`; the projector is audit-transparent (caller-supplied `auditId` threaded, transport-free — consumer owns the audit-or-throw obligation, mirroring `consent`/`member`)
**And** every `claim.*` event payload carries the §1.14 audit shape: `from_state`, `to_state`, `trigger`, `actor` (`member | operator | trustee | system`), plus event-specific fields (`timestamp` + `pariwar_id` are `events_log` columns — do NOT duplicate in payload)

**AC5 — `account-frozen` overlay seam is honored by construction (the pinned contract).**
**Given** the already-merged Story 3.1 `account-frozen` overlay (`member/overlay.ts`) — a built consumer that queries `events_log` for `claim.intake_initiated` (freeze) / `claim.settled` + `claim.denied_no_appeal` (unfreeze) events matching `payload ->> 'deceased_member_id'`
**When** this story emits claim lifecycle events
**Then** the `claim.intake_initiated` payload carries `deceased_member_id` (the deceased member's id) and the event names EXACTLY match `ACCOUNT_FREEZE_EVENT_TYPE` / `ACCOUNT_UNFREEZE_EVENT_TYPES` in `member/overlay.ts` — no re-implementation of the overlay, no edit to `overlay.ts`
**And** an integration test proves the seam end-to-end: a `claim.intake_initiated` naming member M flips `getMemberAccountOverlay(db, M, now)` → `accountFrozen: true`; a subsequent `claim.settled` (or `claim.denied_no_appeal`) clears it → `accountFrozen: false`; a claim in a different Pariwar naming a member does not affect a cross-tenant member's overlay (RLS + pariwar-scoped events)

**AC6 — v1 scope-boundary non-adds (architecture-spec assertions).**
**Given** §1.13 Hook 2 (payout-destination reserved-not-built) + §1.9 (claim aggregate = death-support nominee claims only)
**When** the `claims` schema + migration are authored
**Then** there is **no** `payout_destination_id` column on `claims`, **no** `payout_destinations` table, **no** accident-assistance / `reserve`-mechanism / disbursement columns, and **no** benefit-mechanism branch in the claim schema — the v1 `claim` schema is death-support-only; future Durghatana Sahayata uses a **separate** request/case entity (greenfield, never a column addition to `claims`)

- [x] [Review][Patch] (resolved decision) `trigger: z.string().min(1)` (`packages/domain/src/claim/events.ts`) is unconstrained freeform text across all 20 event payloads with no enum/allowlist defined anywhere in the spec. **Decision (2026-07-08): leave freeform, document why** — added a comment on `auditShape.trigger` documenting it as a deliberately unconstrained human-readable audit note.
- [x] [Review][Patch] AC3's two-guard invariant has a structural gap at INSERT time: the DB trigger (`packages/domain/migrations/0051_claims-lifecycle.sql`) is `BEFORE UPDATE` only — never fires on row creation — and the AST gate (`scripts/claim-state-invariant/lib.ts`) only pattern-matches `.set(...)` chained off `.update()/.insert()` or the `set:` object inside `onConflictDoUpdate(...)`; a bare `.insert(claims).values({ currentState: 'x' })` with no further chaining is invisible to both. Not hypothetical: `packages/domain/tests/integration/_helpers.ts`'s `seedClaim` helper already uses exactly this unguarded shape. **Fixed both layers:** trigger is now `BEFORE INSERT OR UPDATE` (branches on `TG_OP`), re-applied to the local :5433 test DB; scanner now also flags a bare `.insert(claims).values({ currentState })`. `seedClaim` updated to set/reset the projector's session guard around its direct seed insert (and the RLS-regression test that deliberately exercises an unguarded mismatched-tenant insert now sets the guard too, so it isolates the RLS check from the AC3 trigger).
- [x] [Review][Patch] AST gate has two further pattern-matching blind spots in `scripts/claim-state-invariant/lib.ts`: (a) `chainTargetsClaims` only recognizes a bare `Identifier` named `claims` — a namespaced reference like `schema.claims` (the codebase's own dominant import style elsewhere in `packages/domain/src`) is not recognized; (b) `objectHasStateKey` only inspects `PropertyAssignment`/`ShorthandPropertyAssignment` with `Identifier`/`StringLiteral` keys — a computed property or a variable/spread-built object literal evades it entirely. **Fixed:** both `chainTargetsClaims` and the direct-assignment check now resolve the table name via a shared `tableNameOf` helper (identifier OR property-access); `objectHasStateKey` now also recognizes a `ComputedPropertyName` whose key is the literal string `'currentState'`. 5 new fixtures in `lib.test.ts` prove the previously-invisible bypasses are now flagged (and that a same-shaped `schema.members` write still correctly passes).
- [x] [Review][Patch] `packages/domain/src/claim/state.ts:61` re-declares a local `decisionSchema` instead of importing the canonical `appealReviewDecisionSchema`/`appealFinalDecisionSchema` from `claim/events.ts` — two hand-maintained copies of the same vocabulary (unlike `CLAIM_LIFECYCLE_STATES`'s single-tuple discipline), and the reducer alone doesn't reject an illegal stage-3 `'advance'` if `replayClaimState` is ever called without going through the projector's stricter payload validation first. **Fixed:** `state.ts` now imports `appealReviewDecisionSchema` from `events.ts` instead of re-declaring it.

### Why `claim_case_id` is caller-supplied (NO `gen_random_uuid()` default)
`claim_case_id` IS the claim's `events_log.stream_id` — **one event stream per claim** (`stream_id = claim_case_id`, mirroring `member_id = stream_id`). The id must therefore exist *before* the first event so it can BE that event's `stream_id`: the intake flow (Story 6.2 member-app / 6.3 helpline / trustee-initiated) mints the UUID, uses it as the `stream_id` of the first `claim.intake_initiated` append, and the projector's first-event INSERT writes the `claims` row under that same id. A `DEFAULT gen_random_uuid()` on the column would mint a *second, independent* id at row-insert time that has no relationship to the stream — you could then have a `claims` row whose `claim_case_id` matches no event stream (source-of-truth violation) or a stream with no row. Removing the default makes that state **structurally impossible**: a `claims` row can only come into being via the projector, which is handed the id that is already the stream head. This is the identical invariant `schema/members.ts` documents for `member_id`.

**ICP immutability (forward ref, not this story's job):** the AC calls `claim_case_id` "canonical, immutable post-ICP per Story 6.4." Dual-path intake (app + helpline) can create *two* streams for the same death; ICP convergence (6.4) picks ONE canonical `claim_case_id` and emits `claim.intake_converged`. 6.1 only commits that the id is caller-supplied + immutable once written; the dedup/merge policy (which id wins, how the loser stream is tombstoned) is entirely Story 6.4's — do NOT build convergence logic here.

### Appeal-review branching — the `decision` disambiguator (read before Task 3)
**The trap:** every other transition in the graph is a clean `(state, event.type) → state` mapping — e.g. `verifier_review` has two distinct event types (`verifier_approved`/`verifier_denied`) for its two outcomes. The three appeal-review rows are different: `appeal_stage1_reviewed` (and its stage-2/stage-3 twins) each map to **three** possible target states (`advance-to-next-stage | reversed | denied`) from the SAME source state, with a SINGLE event type. A reducer that (correctly, per the total-reducer contract) derives next-state from `(current_state, event.type)` alone cannot resolve this — it needs a third input.

**The fix:** each `appeal_stageN_reviewed` payload carries `decision: 'advance' | 'reversed' | 'upheld'` (Task 2). The reducer's handling of these three event types is the ONE place it also branches on payload content, not just `(state, type)`:
- `decision: 'advance'` → `appeal_stage_2` (from stage 1) / `appeal_stage_3` (from stage 2) — stage 3 has no "advance" (Trustee discretion is final; `advance` is not a legal `decision` value for `claim.appeal_stage3_reviewed` — validate this in the Zod schema, e.g. a discriminated union keyed by stage).
- `decision: 'reversed'` → `reversed` (all three stages)
- `decision: 'upheld'` → `denied` (all three stages)

This is why there is no standalone `claim.reversed` event in the AC2 vocabulary (an earlier draft listed one; it was never wired into the transition graph and is dropped — entering `reversed` is always via an `appeal_stageN_reviewed` event with `decision: 'reversed'`). Cover all three `decision` branches per stage in the Task 9 unit tests.

### `state_trustee_approved` vs `approved` — a distinct event, NOT a pure replay state
**Decision:** `approved` is entered by its **own named event, `claim.approved`** — it is NOT a bookkeeping/derived roll-up of `claim.state_trustee_approved`. The two are semantically distinct milestones and the reducer keeps them as separate steps:
- `claim.state_trustee_approved` → state `state_trustee_approved`: a **per-claim** trustee vote cast *during* an open cycle-freeze session. The claim is approved-in-principle but the freeze is still open and reversible.
- `claim.approved` → state `approved`: the **cycle-freeze bulk-approval commit** (Story 6.13) finalizes every voted claim in one atomic step. This is the clean, single milestone Epic 7 (pool binding) and Epic 9 (reconciliation) key off — they must not have to distinguish "voted" from "committed."

This honors AC2's invariant that **every non-initial state has at least one entering event** (reachability, not a 1:1 mapping — several states, e.g. `denied`, have multiple legal entering event types, and the three `appeal_stageN_reviewed` events each fan out to more than one target state via `decision`, see "Appeal-review branching" above; the one hard constraint is that a state reachable only by "replay bookkeeping" with no event would be unreachable by the append-only projector — the projector only ever *appends an event then replays*, so a state with no entering event at all can never be written to `current_state`). The AC's event list ends with "…etc." and is explicitly non-exhaustive, so adding `claim.approved` completes the graph rather than contradicting it. Do NOT make `approved` a silent alias of `state_trustee_approved`; that would leave one enum label unreachable and the other overloaded.
