## Story

As Solo Builder authoring the feature-flag primitive,
I want per-cohort feature flags with a capability bar + a governance-boundary invariant that makes it structurally impossible for a flag to bypass audit, consent, validity, RBAC, or any other frozen governance control,
so that staged rollout is safe, the DigiLocker hard-mandatory cutover has a real mechanism instead of an ad-hoc config edit, and every architectural invariant holds identically across all flag states.

## Scope Boundary (read first — prevents over-build AND under-build)

**This is a `[PRIMITIVE]`, but NOT the pure-domain-only kind 10.6 was.** 10.6 shipped a domain harness with no table, no route, no admin UI, and no RBAC key, because a bulk-op harness has no state of its own. 10.8 *does* have state (a flag is a durable, versioned, tenant-scoped, audit-anchored record) and two of its ACs are **visibility** properties — "flag inventory visible to Pariwar Admin and above" and "no secret flags" (`prd.md:892`, `architecture.md:325-326`). A flag store with no inventory surface literally cannot satisfy "no secret flags." So 10.8 = **domain module + migration + contracts + a NEW repo-global CI gate + `apps/api` routes + a minimal `apps/admin` inventory console + ONE real consumer wired**.

**The three things that make this story hard are not the CRUD.** They are:
1. **The governance-boundary invariant must be MECHANIZED, not asserted.** The AC (`epics.md:3520`) names a `governance_boundary.yaml` allowlist and a CI test. That file does not exist anywhere in the repo — you are authoring it plus its gate. Per [[feedback_mechanization_split_commitment]] and [[project_gate_scope_semantic_coverage]], a gate that only checks "every flag key appears in a YAML list" is **vacuous** — it proves nothing about bypass. The load-bearing leg is the *source-scan* leg (AC5b) that proves no flag read reaches inside a governance module. Ship it with a revert-sanity negative control or it has no teeth.
2. **"Capability bar" means two different things in the source artifacts and you owe BOTH.** See Decision 2. Getting this wrong under-delivers half the story silently.
3. **A producer-less flag store is the anti-pattern this repo has already called out twice** (Story 5.6 producer-less pg-boss worker; Story 5.7 producer-less toggle column — `deferred-work.md:2066`). Three consumer seams are already sitting in the codebase with comments pointing at *this story*. Wire exactly one end-to-end (Decision 8).

## Acceptance Criteria

**AC1 — The flag primitive: versioned, tenant-scoped, replay-safe rows (Decision 3).**
Given FR-58C + Cross-Cutting #15 (`architecture.md:325-326`) + the Item 9 capability bar (`architecture.md:200-229`),
When the feature-flag primitive is authored in `packages/domain/src/feature-flags/` + `migrations/0087_feature-flags.sql`,
Then a flag version row carries: `flag_key`, `pariwar_id` (**nullable** — null = global), `version`, `cohort_definition` (the Decision-5 bounded predicate, JSONB), `state` (`off | canary | rollout | full | rolled_back`), `fallback_default` (boolean — the offline-resilience default required by `architecture.md:217-219`), `owner` + `dead_by` (the lifecycle-accountability pair required by `architecture.md:220-221` + `:4094-4098`), `audit_id`, `effective_from`, `effective_until` (nullable), `actor_who_flipped`, `superseded_by_version` (nullable forward-pointer), `created_at`;
And **version rows are immutable** (the 10.1 posture): a flip INSERTs a new version; prior rows are never mutated except the `superseded_by_version` forward-pointer, so `(pariwar_id, flag_key, version)` is an unambiguous replay pin and *"historical flag states are queryable for past evaluations"* (`architecture.md:214-216`) is satisfied by a row read, not a projector;
And `flagVersionInForce(db, flagKey, pariwarId, at)` resolves the version whose `effective_from <= at` and (`effective_until` is null or `> at`), preferring a per-Pariwar override over the global row, else the code-default; `flagVersionForVersion(...)` reconstructs any historical version for replay;
And a live-DB test proves tenant isolation **including the nullable-`pariwar_id` carve-out**: tenant A cannot read tenant B's override, both can read the global row, and an unset scope reads zero (the `report-exports-policy-regression` spec shape — this table's own pos/neg/withCheck/fail-closed regression is mandatory, not optional; it was the one real gap the 10.7 review found).

**AC2 — Deterministic, pure, replay-identical evaluation (Decision 4, 5).**
Given the Item 9 property *"same cohort + same flag identity + same version yields the same result; output is reproducible for replay"* (`architecture.md:207-210`) + NFR-FR58C `< 5 ms` (`prd.md:891`),
When `evaluateFlag(flagDoc, memberContext)` runs,
Then the resolver is **PURE** — the 10.1 `resolveRoute` contract: `cohort_definition.clauses` is a plain **array** whose explicit order is the ONLY precedence source; no `Object.keys()`/`Map`/`Set` iteration decides the outcome; no clock, no randomness, no I/O, no async, no mutable module state; the returned `FlagDecision` carries `{ enabled, flagVersion, matchedClauseIndex, reason }` so the decision is audit-replayable;
And time-dependence is **split out** of the pure core exactly as `computeTicketSlaDueDates` is split from `resolveRoute`: `effective_from`/`effective_until` windowing happens in the *version-in-force lookup* (AC1), never inside `evaluateFlag`;
And a determinism test runs the same `(flagDoc, memberContext)` 100× and asserts byte-identical decisions (the `ladder.ts` / Story 4.6 rule-order precedent); a fixture-pinned hash test pins the seeded capability bar + the default flag documents (the `default-policy-hash.test.ts` precedent);
And the cohort predicate is a **bounded declarative form**, not an expression language (Decision 5): a flat array of clauses `{ dimension: 'pariwar_id'|'member_state'|'district'|'block'|'role'|'cohort_tag', op: 'in'|'eq', values: string[] }` evaluated as first-match; an unknown dimension or op **fails closed** to the flag's `fallback_default` with a typed reason, never throws into the caller's request path.

**AC3 — Every flag change is audit-logged; the flip write path (Story 1.10).**
Given `epics.md:3513` + `architecture.md:214-216` (*"every flag-state change emits a tamper-evident audit line (§1.5 hash chain)"*),
When an actor creates or flips a flag version,
Then the write follows the 10.1 narrow-write posture — `CreateFlagVersionInput.auditId` is a **pre-generated anchor** stamped on the row, and the caller writes the audit LINE via `writeAuditEntry` with a dotted action (`feature_flag.version_created` / `feature_flag.rolled_back`), `actorId`/`actorRole` from the flipping admin ([[project_admin_display_name_attribution]] — `users.display_name` is the attribution source; a missing name blocks the action with a typed error, no email-derived fallback), and `requestPayloadHash` = sha256 of the canonical input (never the raw `cohort_definition`);
And the audit context is NON-PII and records **`flag_key`, prior version, new version, prior state, new state, and the rationale string** — FR-58C requires *"flag changes audit-logged with actor + rationale"* (`prd.md:890`), so `rationale` is a REQUIRED, bounded, non-empty field on the write contract, not optional;
And a concurrent double-flip loses on the `(pariwar_id, flag_key, version)` unique index → `FlagVersionConflictError` → `409`, never a silent overwrite (the `RoutingPolicyVersionConflictError` shape).

**AC4 — Inventory visible to Pariwar Admin and above; no secret flags.**
Given `prd.md:892` (*"No 'secret' flags — flag inventory is visible to Pariwar Admin role and above"*) + `architecture.md:325-326`,
When an authorized admin opens the flag inventory,
Then `GET /api/v1/global/feature-flags` (catalog) and `GET /api/v1/p/<pariwar_id>/feature-flags` (this tenant's effective flags, each showing global-vs-override provenance) return the **complete** flag set for that scope — there is no `hidden`/`internal` field and no code path that omits a registered flag from the inventory response;
And `apps/admin/src/modules/feature-flags/` renders that inventory (key, state, cohort summary, owner, dead-by, effective window, last flip actor + rationale) plus the flip form, reusing the 6.3 admin shell (the 10.3/10.4/10.5/10.7 `apps/admin/src/modules/*` precedent);
And a test asserts the **no-secret-flags property with teeth**: every key in the domain flag registry appears in the inventory response for an authorized actor — a flag registered but omitted from inventory fails the test.

**AC5 — The governance-boundary invariant, MECHANIZED (this story's load-bearing commitment).**
Given `epics.md:3516-3522` + the Architectural Freeze Boundaries table (`epics.md:510-543`),
When any feature flag is defined or evaluated,
Then **(a) conformance leg** — `governance_boundary.yaml` at repo root declares the capability bar (the allowlist of flag-toggleable behaviors, each `{ kind, artifact, rationale, adr }` per the `fr-100-non-add.yaml` entry shape) plus the prohibited-behavior patterns; the gate asserts **every registered flag key resolves to exactly one allowlist entry**, an unlisted key fails, and a `count` cross-check catches a silently-dropped entry (the `bank-allowlist.ts:78-80` revert-sanity trick);
And **(b) the load-bearing source-scan leg** — the gate asserts that **no flag-evaluation import reaches inside a governance module**: scanning `packages/domain/src/audit/`, `packages/domain/src/rbac/`, `packages/domain/src/consent/`, `packages/validity-service/src/`, `packages/domain/src/contribution/` (where `CONFIRMED_EVENT_TYPE` and the confirmed-truth reads live — the actual enforcement roots the 9.5 `canonical-financial-truth.test.ts` fence itself scans, not the test file), and `scripts/*/` (the CI gates themselves), **any import of `@twt/domain`'s feature-flags namespace or of `evaluateFlag` is a gate failure** — this is what makes prohibitions (a) disable audit logging, (b) bypass Story 2.7 consent, (c) override Validity Service eligibility, (d) escalate RBAC, (f) disable a 1.16a-d gate, and (g) bypass the canonical-financial-truth fence *structurally impossible* rather than merely documented. **A green run of leg (a) alone proves nothing — leg (b) is the invariant with semantic coverage** ([[project_gate_scope_semantic_coverage]]);
And prohibition (e) *"altering any architectural freeze table row"* is covered by the allowlist's rationale requirement: an `allow` entry naming a frozen-table behavior (`epics.md:518-532`) is rejected by the parser with the freeze-row cited;
And **(c) the audit-outside-the-cache leg** — flag evaluation cannot suppress its surrounding audit: the cached core is the *decision computation only*, and any audit/observation the caller performs sits OUTSIDE it, so it fires on a cache HIT exactly as on a miss (the Story 4.8 D5-A structure, `packages/validity-service/src/cache.ts:22-26`). A test asserts the audit fires on both paths;
And the gate ships with a **revert-sanity negative control** in `lib.test.ts`: a fixture flag key absent from the allowlist fails leg (a), and a fixture governance-module source importing the evaluator fails leg (b). A gate that cannot be made to fail has no teeth.

## Load-Bearing Decisions

Each carries a firm recommendation + the rejected alternative (the 10.4–10.7 house style).

**Decisions 2, 4, and 6 — the three that were open — are CONFIRMED by the product owner (2026-07-31). Implement the recommendations as written; their rejected alternatives are closed.** Concretely that ratifies: the flag tool is **in-house Postgres-backed** and `ADR-0036` records it against Item 9's seven properties (D2); "cached per Story 4.8 pattern" means 4.8's **invariants**, not its table + cohort-epoch machinery (D4); and AR-64's **automatic** error-spike rollback ships as a recorded absent seam rather than a fabricated signal (D6). The remaining decisions were firm recommendations, not open questions. All per-decision text below is retained as the rationale of record — why the primitive is shaped this way — not as live debate.

1. **Story shape — RECOMMEND a `[PRIMITIVE]` that ships persistence + a thin surface, NOT 10.6's pure-domain-only shape.** 10.6 correctly shipped no table/route/UI because a bulk-op harness holds no state. A flag *is* state, and two ACs are visibility properties ("inventory visible to Pariwar Admin and above"; "no secret flags") that a headless module cannot satisfy. So: domain + migration + contracts + gate + API + a minimal admin console + one wired consumer. *Rejected:* a pure-domain flag module with the surfaces deferred — rejected because it would ship a store nobody can see or use, failing AC4 on its face and repeating the producer-less anti-pattern.

2. **"Capability bar" is overloaded — RECOMMEND producing BOTH artifacts, because the epic requires both and they are different lists.** Sprint Change Proposal Item 9 (`architecture.md:200-229`) defines a *vendor-selection acceptance-criteria bar*: seven properties a chosen tool must demonstrate (deterministic evaluation, tenant isolation, replay safety, auditability, offline resilience, lifecycle accountability, DPDPA posture). Story 10.8's AC (`epics.md:3512`) defines a *runtime allowlist of flag-toggleable behaviors*. `epics.md:4423` merges both into one ADR obligation: *"capability bar ADR documents what's flag-toggleable + governance-boundary invariant + selection criteria for vendor."* So this story produces `governance_boundary.yaml` (runtime bar) **and** `ADR-0036` (vendor bar, demonstrating the seven properties against the in-house implementation). *Rejected:* treating them as one list — rejected because it silently drops half the commitment, and because the seven properties are *acceptance criteria for the implementation*, not entries in a toggle allowlist. **Sub-recommendation (CONFIRMED 2026-07-31):** select **in-house Postgres-backed** as the v1 tool. Tenant isolation, DPDPA "flag evaluation does not require PII outbound," and offline resilience all argue against a SaaS flag vendor, and §1.4 already commits Postgres-only (no Redis). This is a real governance call — it closes ADR slot row 24 and dispositions launch-gate Row 12. Write `ADR-0036` as a *selection* ADR (in-house is a selection, not a deferral): per [[feedback_architecture_vs_adr_boundary]] the architecture already committed the properties at `:200-229`, so the ADR's job is to name the control and demonstrate the seven properties against shipped code — not to restate the bar.

3. **State model — RECOMMEND immutable versioned rows (the 10.1 routing-policy shape), NOT a 6th event-derived-state primitive.** The repo has five event-derived-state primitives (members, claims, pools, alerts, helpdesk_tickets), each carrying a projector-only `current_state` + a DB trigger + its own CI gate. The temptation is to make flags the sixth. **Don't.** The architectural requirement is *replay safety* — *"historical flag states are queryable for past evaluations; flag changes carry version + effective-at timestamps"* (`architecture.md:214-216`) — and immutable version rows deliver exactly that, with `(pariwar_id, flag_key, version)` as the replay pin. A flag's `state` is an **authored attribute of a version**, not a lifecycle derived from external events: nothing outside the admin write path ever moves a flag, so there is no projector-vs-writer divergence for a gate to police. Story 10.1 faced the identical choice and split it correctly — its *tickets* are event-derived-state, its *routing-policy registry* is versioned-immutable-rows. A flag is the registry, not the ticket. *Rejected:* a 6th `current_state` + trigger + `feature-flag-state-invariant` gate — rejected as cost with no property gain, and it would dilute the meaning of the five existing state gates. ⚠ **The one real cost of this choice:** `pariwar_id` is nullable (global flags), so the standard RLS predicate needs an explicit `OR pariwar_id IS NULL` read leg. That is a deliberate, tested carve-out (AC1) — call it out in the migration comment so a future reader doesn't "fix" it.

4. **Caching — RECOMMEND adopting Story 4.8's POSTURE and invariants, and the cheapest cache that meets `< 5 ms`; DEFER 4.8's table + cohort-epoch machinery.** The AC says *"deterministic + cached per Story 4.8 pattern"* (`epics.md:3514`). The load-bearing parts of 4.8 are its *invariants*, and you must inherit all of them: cache-optional/correctness-mandatory; reads degrade to recompute; writes best-effort and non-blocking; and — critically for AC5c — **the audit/access layer stays OUTSIDE the cached core** (`cache.ts:22-26`, D5-A). What you should *not* automatically clone is 4.8's `member_validity_cache` table + `cohort_invalidation_epochs` + the `events_log` AFTER-INSERT trigger: that machinery exists because a validity recompute is expensive over a large rule registry. A flag lookup is one indexed row from a table with tens of rows. Start with per-request memoization + a short-TTL in-process snapshot keyed by `(flag_key, pariwar_id)`, measure, and record the full cache-aside table as a seam if `< 5 ms` is ever at risk. *Rejected:* cloning 4.8's full cache substrate now — rejected as premature; a second cache table + epoch bump + trigger is a meaningful maintenance surface bought for a read that is already sub-millisecond. **This is a deliberate narrowing of the epic's "per Story 4.8 pattern" wording to 4.8's invariants rather than its implementation — CONFIRMED 2026-07-31.** Record the narrowing explicitly in the Dev Agent Record so the epic-vs-implementation delta is legible to a later reader ([[feedback_closure_language_precision]]): the invariants are *adopted*, the cache substrate is *deferred pending measurement* — neither is "not addressed."

5. **Cohort definition — RECOMMEND a bounded declarative predicate, NOT an expression language.** `epics.md:3511` says `cohort_definition` is a *"rule expression evaluable against member context."* The nearest existing precedent is Epic 11c's module `eligibility_filter` (`epics.md:4018`), which is likewise unspecified. Specify it *narrowly*: a flat, ordered array of clauses `{ dimension, op: 'in'|'eq', values[] }` over a **fixed dimension enum** (`pariwar_id`, `member_state`, `district`, `block`, `role`, `cohort_tag` — matching FR-58C's stated gating axes at `prd.md:886`), ANDed within a clause, first-match across clauses, unknown dimension/op fails closed to `fallback_default`. *Rejected:* JSONLogic, a mini-DSL, or any `eval`-backed evaluator — rejected because it makes determinism unprovable, makes the rule un-reviewable in a trustee-attested PR, executes data as code, and would need its own parser + fuzz surface. The niyamavali engine's rule holds here too ([[project_niyamavali_precedence_is_provenance]], `ladder.ts:11-26`): the engine interprets DATA, never hardcodes logic — but the data's *shape* must be bounded.

6. **Canary auto-rollback — RECOMMEND shipping the state machine + a manual audited rollback + a declared `FlagHealthSignal` port; DEFER automatic error-spike detection as a first-class absent seam.** AR-64 requires *"automatic rollback on error-rate spike."* There is **no error-rate metrics substrate in this repo** — no observability package, no metrics sink; AR-31's vendor is itself a deferred ADR. Building a synthetic error-rate pipeline inside a feature-flag story would be inventing a producer to satisfy a consumer, which is the exact anti-pattern Story 5.6 rejected. Ship what is real (the five-state machine, the audited manual `rolled_back` flip that takes effect with zero consumer code change) and record the detector honestly as un-built with an AR-31 re-trigger. *Rejected:* implementing a naive in-process error counter and calling AR-64 satisfied — rejected under [[feedback_record_unattested_no_backfill]]: a fake signal that auto-flips production behavior is worse than an honest absence, and it would make a rollback mechanism whose trigger nobody trusts. **This is a knowing partial delivery of AR-64 — CONFIRMED 2026-07-31.** Because it is knowing, it must be recorded as such and carried as risk, never quietly closed ([[feedback_record_unattested_no_backfill]]): the `deferred-work.md` entry names AR-31 observability as the re-trigger, and the ADR's offline-resilience/auditability sections state plainly that the *manual* rollback path is what ships. An un-gated re-commitment decays — tie the seam to the AR-31 observability story rather than leaving it as an open intention.

7. **Authorization — RECOMMEND two new keys, no umbrella.** Mint `feature_flag.view` (inventory read — granted to `pariwar_admin` and above per `prd.md:892`, plus `auditor`) and `feature_flag.flip` (the write, narrower). Catalog **v26 → v27** (verified: `permissions.ts:293` is 26 at HEAD). Both are `dimension: 'pariwar'`; per [[project_rbac_geo_scope_containment]] a district-ceiling grant cannot satisfy a pariwar-dimension check, so **do not grant these to `district_admin`** — that would be an inert capability, the exact trap 10.3 and 10.4 documented. *Rejected:* one `feature_flag.manage` umbrella key — rejected: it collapses "everyone at Pariwar-Admin-and-above can *see* the inventory" (a transparency property) into "everyone who can see can also flip" (a governance authority). The visibility requirement is deliberately broader than the write requirement; one key destroys that.

8. **Consumer wiring — RECOMMEND wiring exactly ONE seam (FR-2 DigiLocker) end-to-end; record the other two.** All three seams carry comments pointing here, and `deferred-work.md:2066` explicitly re-triggers the cost-optimization toggle at "the Epic 10 FR-58C feature-flag story." But FR-2 is the *canonical* use case in every source artifact (PRD FR-58C consequence #1, `epics.md:1663/1677`, the Epic-10 demoable closure, and the ADR's decision-gate acceptance case), and wiring it proves the whole chain: flag → cohort → evaluation → per-tenant behavior change → no consumer code edit. *Rejected (a):* wire zero and ship a headless store — rejected as the producer-less anti-pattern. *Rejected (b):* wire all three — rejected on scope; the cost-optimization toggle also needs its per-Pariwar admin form (`architecture.md:2082-2095`), which is its own surface. Leave both returning fail-safe defaults with a `deferred-work.md` entry.

9. **The "beta UX patterns" seed entry — RECOMMEND dropping it from the initial capability bar and recording why.** `epics.md:3512`'s seed list is `e.g., DigiLocker hard-mandatory, alternative KYC provider, beta UX patterns`. The first two trace to concrete FRs (FR-2, AR-43/`epics.md:530`). **"Beta UX patterns" appears exactly once in the entire corpus** with no supporting FR, AR, or UX-spec entry — the UX spec has zero FR-58C content. Seeding an allowlist entry for an undefined behavior would create exactly the silently-expandable bar AC6 prohibits. Seed the bar with behaviors that have a named owner and a real consumer: `kyc_manual_fallback` (FR-2, wired in AC8), `kyc_provider_selection` (AR-43 seam), and — as recorded-but-unwired entries with their re-trigger stories — `wa_cost_optimization` (AR-18) and `telegram_mirror` (FR-73). *Rejected:* seeding `beta_ux_patterns` to match the epic's prose literally — rejected: an allowlist entry with no definable artifact cannot be gate-checked, and admitting it now normalizes exactly the silent expansion the story exists to prevent.

## Dev Notes

### Read this first: the two traps specific to 10.8

**Trap 1 — the vacuous gate.** It is very easy to ship `governance_boundary.yaml` + a gate that checks "every flag key is listed" and declare AC5 done. That gate is green from the moment it lands and stays green while someone adds a flag read inside the RBAC module. The list-conformance leg is bookkeeping; **the source-scan leg (AC5b) is the invariant**. [[project_gate_scope_semantic_coverage]] is the exact lesson (the AI-5-1 trap: a green scan proves nothing without meaningful semantic coverage of the new surface), and [[feedback_mechanization_split_commitment]] is the companion (decay concentrates in the un-mechanized half). Build leg (b) first, prove it fails on a planted violation, then build leg (a).

**Trap 2 — half the capability bar.** Two artifacts, two meanings, one word. See Decision 2. If you only produce `governance_boundary.yaml`, you have silently dropped the ADR obligation at `epics.md:4423` and left launch-gate Row 12's predicate live.

### Why versioned rows and not a 6th state primitive (Decision 3, restated because it's the biggest structural call)

Five tables in this repo carry a projector-only `current_state` with a DB trigger and a dedicated CI gate. Flags look superficially similar — they even have a five-value state set. But those five exist because an *external* event stream moves the state and a writer might diverge from the projector; the gate polices that divergence. Nothing external moves a flag: an admin authors a version, and the version *is* the state. Story 10.1 already made this exact split correctly — helpdesk *tickets* are event-derived-state, the helpdesk *routing-policy registry* is versioned-immutable-rows. **A flag is the registry, not the ticket.** Adding a sixth state gate here would buy no property and dilute what the five existing gates signal.

### The pure-resolver contract (copy it, don't paraphrase it)

`packages/domain/src/helpdesk/routing.ts:1-16` states the determinism contract this codebase means by "pure resolver," and `packages/niyamavali-engine/src/ladder.ts:11-26` states the companion rule (interpret DATA; never `switch (id)`). Both apply verbatim. The subtle one is the **time split**: `resolveRoute` is time-independent and `computeTicketSlaDueDates` is the separate time-dependent derivation. Your `effective_from`/`effective_until` must live in the version-in-force *lookup*, not inside `evaluateFlag` — otherwise the evaluator takes a clock and replay determinism is gone.

### Audit must survive the cache (AC5c)

`packages/validity-service/src/cache.ts:22-26` (Story 4.8 D5-A) is the structural answer to `epics.md:3522`: only the *compute core* is cached; the access/audit layer sits outside it, so the audit fires on a HIT exactly as on a miss. Build the flag cache the same way. If you find yourself putting the audit inside the memoized function, you have built the thing this AC exists to prevent.

### Audit-action naming

`writeAuditEntry`'s `action` is a free-form dotted lowercase string with **no central registry** (`write.ts:99-102` is the only validation). Use `feature_flag.version_created` / `feature_flag.rolled_back`. Keep it distinct from RBAC permission keys (imperative verbs) and from `packages/events` names (past-tense event types). `rationale` is required by FR-58C (`prd.md:890`) — a bounded non-empty string in the audit context, never free-text PII.

### Migration hygiene

Hand-author `0087`; never `db:generate` (snapshots stop at 0020; drizzle skips by journal `when` → `42P07`, [[project_live_db_test_gotchas]]). Mirror `0084`'s tenant-table body. The nullable-`pariwar_id` global-flag row is the one place you deviate from the standard RLS predicate — comment it, test it, and add the policy to the inventory the `schema-diff` gate reads.

### Contracts hygiene

`packages/contracts/src/feature-flags/README.md` already commits your route shapes and forbids type-shadowing in `apps/api/src/modules/feature-flags/`. Pure-Zod `.strict()`, snake_case wire, no `@twt/domain` source import ([[project_contracts_domain_bundle_boundary]] — a source import leaks `pg`/`node:async_hooks` into the RN Metro bundle; the sync-guard is a TEST-only cross-import). ### Debug Log References

Five real defects surfaced during development. All were found by tests, not by inspection:

1. **`drizzle 0.45` exposes `nullsNotDistinct()` only on `unique()`, not `uniqueIndex()`.** The first `db:migrate` failed with `uniqueIndex(...).on(...).nullsNotDistinct is not a function`. Switched the declaration to a UNIQUE **constraint** so the schema can actually express the null semantics — a declaration that cannot state them would silently misdescribe the DB. Verified live that without `NULLS NOT DISTINCT` Postgres accepts a duplicate `(NULL,'x',2)` (2 rows), so RLS spec case (g) has real teeth.
2. **`db.execute(sql\`select now()\`)` returns a STRING, not a Date.** `<{ now: Date }>` typechecks and then crashes inside drizzle's timestamp encoder (`value.toISOString is not a function`) — but ONLY on the path where the caller omits `effectiveFrom`, which is why a suite that always passes it would never catch it. Fixed with explicit coercion. ⚠ **`helpdesk/registry.ts:258` has the identical latent bug**; recorded in `deferred-work.md` rather than changed out of scope.
3. **`/api/v1/global/feature-flags` 404'd.** `scopeResolutionHook` resolves the tenant from the `:pariwarId` PATH PARAM; a route without one reads `''` and 404s. Re-gated the cross-tenant catalog on `requireGlobalPermission` (super_admin). See Completion Note 4 — this is a boundary decision, not a workaround.
4. **The `config.digilocker.manualFallbackEnabled` fallback was unreachable.** A registered flag ALWAYS resolves (tier 3 = the code default), so "no version in force" never surfaces as a null and the code default would silently override a deployment whose config had manual disabled — dead configuration that still looks live. 5. **`getActiveKycProvider` became async**, breaking three call sites and three unit tests (all updated).
