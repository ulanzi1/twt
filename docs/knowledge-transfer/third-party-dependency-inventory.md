# Third-Party Dependency Inventory

The canonical inventory of every external dependency the project relies on, with vendor / contract / renewal cadence / monitoring owner / vendor contact captured per row. Authority: PRD §9.1.1 paragraph 5 ("third-party dependency inventory with renewal dates") commits the inventory; architecture §Critical External Dependencies (lines 240-269) + §3.10 (External-API deprecation monitoring) commit the named-monitoring-owner property; Story 0.5 Task 6 authors this inventory.

This file is the **operating-discipline-focused** dependency surface. It captures the renewal cadence + the monitoring owner + the vendor contact so a future engineer or trustee can renew a contract / respond to a deprecation notice / contact a vendor without Solo Builder consultation. Per architecture §3.10: every external API has an accountable monitoring owner; **no integration is "set and forget."**

## Schema

Every row records:

- **Dependency class** — the named external dependency
- **Provider** — the current vendor / OR `pending-ADR-selection` per `docs/knowledge-transfer/adr-index.md`
- **Usage** — 1-line description of what the project uses the dependency for
- **Architectural authority** — the architecture section that grounds the dependency
- **Owning Story** — the sprint-status story key that operationally instantiates the dependency
- **Renewal or contract event** — what triggers a renewal action (annual subscription / per-partner contract / partner-deprecation notice / Apple/Google account renewal / DLT registration / Meta template approval / regulatory cycle / monthly billing)
- **Next renewal date** — concrete date OR `pending-contract-signature` OR `per-rotation-cadence-ADR` OR `monthly-billing` (continuous)
- **Monitoring owner** — the named owner per §3.10 (Solo Builder default at v1; Trustee Panel for regulatory-gate rows; legal counsel per Story 0.13 for legal-flagged events)
- **Vendor contact** — support portal URL OR escalation-contact-as-recorded-in-credential-envelope OR `pending-vendor-onboarding`
- **Cross-link** — `docs/escrow/credential-inventory.md` row reference where the dependency has a corresponding credential envelope; OR `pending` if the credential envelope is `pending-system-availability`
- **Status** — `active` | `pending-system-availability` | `pending-ADR-selection` | `deferred-with-ADR`

## Status legend

| Status | Meaning |
|---|---|
| `active` | The dependency is contracted + operational; the row's renewal cadence is currently tracked. |
| `pending-system-availability` | The dependency is committed but the owning Story has not closed yet; the row is reserved with the renewal cadence + monitoring-owner schema in place. |
| `pending-ADR-selection` | Multiple candidate vendors are deferred to an ADR; the row records the candidate set + the ADR slot from `docs/knowledge-transfer/adr-index.md`. |
| `deferred-with-ADR` | The dependency category exists but no concrete instances yet; the row is reserved for a future onboarding event (e.g., first Module Marketplace partner). Transitions to `active` when the first concrete instance onboards (e.g., first partner contract signed); a `.decision-log.md` `[CONTINUITY]` entry records the onboarding event and the row is updated. |

## Forbidden-removal rule

Rows are **never removed**. Supersession is the only allowed lifecycle exit. A dependency that is decommissioned (e.g., a provider deprecation that removes the API entirely) is marked `superseded` with a cross-link to the replacing dependency's row; the prior row is preserved as the integration-evolution record.

## Cross-link discipline

Every row that has a corresponding credential envelope in `docs/escrow/credential-inventory.md` cross-links to the envelope row. The KT pack dependency inventory does NOT duplicate the credential inventory — it cross-references it. A dependency that has no credential envelope at v1 (e.g., bot APIs, free-tier SaaS) shows `n/a` in the Cross-link column.

## Periodic review cadence

Per `docs/knowledge-transfer/README.md` §6 fallback:

- **Quarterly** — every row reviewed for renewal-date currency; rows whose `Next renewal date` is within 60 days are surfaced in `kt-pack-ledger.md` "Periodic re-attestation log" with the monitoring owner notified.
- **Annual** — every row reviewed for provider-status changes; rows where the provider has announced deprecation OR pricing changes OR DPDPA-impacting policy changes are surfaced.
- **On-deprecation-notice** — when a monitoring owner detects a deprecation notice per §3.10 monitoring duty, the row is updated immediately (`Status` flip OR Notes append) + the response procedure is recorded in `docs/runbooks/` (provider-deprecation-response runbook per architecture §5.15 inventory).
