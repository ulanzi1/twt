## Story Classification

**`[SURFACE]`** — the **first WRITE** on the verifier surface. Story 6.10 shipped the **READ-ONLY** console and deliberately left a **sticky-bottom composition slot** (`decisionSlot`) for exactly this story. 6.11 mounts `<VerificationDecisionStrip>` into that slot and adds the **adjudication write path**: emit the `claim.verifier_*` lifecycle event, persist the **decision read model** that 6.10's D6 dependency contract pinned (outcome · reason-code · rationale · human-actor display attribution · timestamp · claim id · Pariwar scope), write the audit-sink line, and turn on 6.10's two `not_available_yet` sections (e)/(f) by **flipping `VERIFIER_DECISION_READ_MODEL_AVAILABLE` and wiring the real queries**.

6.11 is the **consumer that fulfils five explicit 6.10 seams**: (1) the `decisionSlot` slot; (2) the `VerifierDecisionRecord` read-model contract + the pure `orderPriorDecisions`/`selectRecentInScopePrecedents` helpers in `verifier-console-read.ts`; (3) the reducer's `claim.verifier_reviewing`/`verifier_approved`/`verifier_denied` events (already defined, owner-labelled "Story 6.11"); (4) the CI gate's **`COVERAGE_SET`**, which 6.11 **must extend** with its approve/deny/escalate route; (5) the existing `claim.approve` WRITE permission key (6.10 repeatedly calls it "the 6.11 WRITE key").

**Seven seam decisions (D-A … D-G) + all four residuals are RATIFIED by BigDev (2026-07-11)** and firm; each is wired into the ACs + tasks. See "BigDev directives" in Dev Notes for the ratified calls (escalate = identity annotation with its own guard; no `claim.approve` grant to the verifier role; same-outcome revision via a dedicated annotation + atomic supersession; Tier-1-encrypted rationale) and the three sharpenings (two-authority split, escalation-excluded precedents, actor-display snapshot, idempotency, outcome↔reason-code compat). **R5 (`actor_display` source) is also RATIFIED (BigDev 2026-07-11): a new `users.display_name` — controlled staff-attribution personal data, never derived from the encrypted email — snapshotted server-side into a REQUIRED `claim_verifier_decisions.actor_display` at decision time; a missing display name BLOCKS adjudication with a typed error (no fallback of any kind).**

## Story

As **Anita** (a verifier at the District-Admin level) making a verification decision — **approve / deny / escalate**,
I want **a Verification Decision Strip with a one-tap structured reason-code dropdown, a brief rationale free-text field, and an immediate audit-trail entry**,
so that **every ₹50L decision is fast, structured, attributable, and traceable for trustee review and as a future precedent — a 90-second informed judgment, not a two-hour investigation.**

## Acceptance Criteria

<!-- All five residuals RATIFIED by BigDev 2026-07-11 + eight directives baked in. See "BigDev directives" in Dev Notes. -->

**AC0 — Two authorities, never conflated (the load-bearing framing — BigDev directive "clarify lifecycle-event authority vs decision-metadata authority").**
Every decision writes to **two stores with two distinct authorities**:
- **The `claim.verifier_*` event in `events_log` is the LIFECYCLE authority** — the reducer derives claim STATE from event replay (Story 6.1 §1.14 freeze). It carries **`auditShape` only**; state is *never* derived from the decision table.
- **The `claim_verifier_decisions` table is the DECISION-METADATA authority** — reason-code, rationale, actor display-attribution, precedent history, and the trustee audit query. Reason text is *never* in `events_log`.
Neither store is a projection of the other; both are written in the same transaction so they cannot diverge. Any code that tries to derive state from the table, or read a reason from the event, is wrong.

**AC1 — The decision strip surface (UX-DR40 `<VerificationDecisionStrip>` + UX-DR43 `<ReasonCodeDropdown>` + UX-DR44 `<AuditTrailEntry>`).**
Mounted into the 6.10 `<VerificationConsoleShell>` `decisionSlot` (the sticky-bottom composition seam), the strip surfaces:
- **(a)** a `<ReasonCodeDropdown>` with **structured, bounded reason codes** (domain enum — e.g. `r5_d_natural_death`, `r8_90pct_met`, `concealment_flag_uphold`, `concealment_flag_override`, `r9_routed_to_voting`, plus an **`other`** value requiring mandatory free-text) — agreed-upfront categories, **not** free text (UX §11). The dropdown offers **only the reason codes compatible with the chosen outcome** (AC8);
- **(b)** a **brief rationale free-text** field, **max 500 chars**, required on `other` and on Deny (mandatory before Reject submits — UX §"Verification Console pattern"). This text is **Tier-1 PII-capable** (D-G) — the field carries a UX note that it will be encrypted + access-controlled;
- **(c)** **"Approve" (primary) · "Deny" (opens reason-code) · "Escalate to State Trustee"** buttons, keyboard-operable (number shortcuts, sticky-bottom, confirmation modal for irreversible actions);
- **(d)** the irreversible-action **confirmation modal is the attestation** (BigDev directive: "remove or define the vague attestation field") — there is **no separate attestation data field** in v1; the epic's "(d) any required attestations" is satisfied by the explicit confirm-before-submit step. If a structured attestation is later required it is additive.

**UX-DR40 anatomy variance (deliberate — the epic AC narrows the UX spec):** UX §DR40 (L2041-2048) lists a FIVE-action anatomy — Approve · Approve-with-note · **Hold for clarification** · Reject · Escalate. 6.11 ships the epic's **three-action** strip: (1) **Approve-with-note is subsumed by Approve** — the optional rationale field on an Approve *is* the note (no separate secondary button/modal); (2) **"Hold for clarification" is NOT in scope** — there is no `hold` lifecycle state, event, or backend anywhere in the substrate; do **not** invent one (a claim not yet decided simply stays in its current state); (3) the Trustee-level variant ("freeze pool" option) is **Story 6.13**. Keyboard shortcuts are 1-N over the actions actually rendered. Similarly, UX Pattern 3's "brief undo window" (L2325-2329) is **not built in v1**: the recovery paths are same-outcome revision (AC5, this story) and appeal (Story 6.16) — do not build an undo timer.

**AC2 — Approve / Deny emit the lifecycle verdict event; escalation is separate (Story 6.1 reducer; D-C, D-D).**
- **Approve** → `claim.verifier_approved` (reducer: `verifier_review → verifier_approved`).
- **Deny** → `claim.verifier_denied` (reducer: `verifier_review → denied`).
- **Entry-into-review precondition (D-C) — approve/deny ONLY:** the verdict events fire only from `verifier_review`, but a claim gathering signals sits in `verification_in_progress`. The **approve/deny** handler **first emits `claim.verifier_reviewing`** (`verification_in_progress → verifier_review`) when not yet in review, **then** the verdict — in **one transaction**. The reducer stays **total**; the precondition is a **write-path guard** (`ClaimNotInVerifierReviewError`, the `GroundInspectionClaimNotInVerificationError` precedent), never in the reducer.
- **The `claim.verifier_*` payloads carry `auditShape` only** — no reason-code, no rationale in `events_log` (AC0).

**AC3 — Escalation is its own action with its own state-window guard (D-D — BigDev directive "treat escalation separately").**
- **Escalate to State Trustee** → `claim.verifier_escalated`, a **new identity-transition annotation event** (`from_state === to_state`; the reducer has **no `escalated` state** and gains none). **No lifecycle-state change, no queue mutation.**
- Escalation has its **OWN explicit state-window guard** — an allowlist of the pre-verdict states it is valid from (**`verification_in_progress` and `verifier_review`**), rejecting terminal/resolved claims. It **must NOT auto-emit `claim.verifier_reviewing`** — escalating does not "enter review". (Contrast the approve/deny path, which does.)
- A decision-table row is written with outcome `escalated` for attribution/audit, but escalated decisions are **NOT resolved precedents** — they are excluded from `getRecentInScopePrecedents` (AC6).
- The exception **queue/assignment** (who at State level picks it up) remains 6.12/6.13; 6.11 emits the event + audit line only.

**AC4 — The decision read model (D-A — fulfils the 6.10 D6 dependency contract) + `<AuditTrailEntry>` + trustee-side audit UI.**
- A new **`claim_verifier_decisions`** table (migration `0059`) is the DECISION-METADATA store (AC0). Per decision: **outcome · reason_code · rationale (Tier-1 ciphertext, D-G) · actor_id · actor_display (a decision-time SNAPSHOT — see AC7) · decided_at · claim_case_id · pariwar_id** (+ the revision linkage, D-E). Scope-safe (RLS + explicit `pariwar_id`).
- **Flip `VERIFIER_DECISION_READ_MODEL_AVAILABLE = true`** and wire `getPriorVerifierDecisions` (full ordered history for the current claim → 6.10 section (e)) and `getRecentInScopePrecedents` (latest-3 **resolved** in-scope precedents, exclude current + exclude escalated/superseded → section (f)) via the existing pure helpers `orderPriorDecisions`/`selectRecentInScopePrecedents`. Sections (e)/(f) now return `present`/`empty` where they returned `not_available_yet` — **`empty` (`[]`) now legitimately means "genuinely no records"**, distinct from the retired `not_available_yet` (the 6.10 AC7 four-state vocabulary — never collapse).
- **`VerifierDecisionRecord.rationale` is surfaced only after authorization + decrypt-at-route** (D-G): the read model returns plaintext to the authorized console (the `<VerifierReviewPanel>` decrypt-at-route precedent); it is **never** in events, audit context, logs, indexes, or searchable filters.
- A `<AuditTrailEntry>` **appears immediately** after a decision (semantic verb — "Approved by Anita", not "status changed").
- **Trustee-side audit UI**: "show me all decisions Anita made last month with reason-code X" queries the decision table filtered by **`actor_id + reason_code + time_range`** — all three are **non-PII, indexable** columns; the rationale is **not** a filter/index (D-G).

**AC5 — Revision: same-outcome correction only, dedicated annotation event, atomic supersession, step-up-gated (D-E).**
- Revision corrects **only** the **reason-code and/or rationale of the SAME outcome**. **Cross-outcome reversal (denied → approved) is out of scope — it remains Story 6.16 (appeal).** Do **not** invent a `denied → verifier_approved` reducer edge.
- A revision emits a **dedicated `claim.verifier_decision_revised` identity-transition annotation event** (`from_state === to_state`) — it **does NOT replay** `claim.verifier_approved`/`denied` (BigDev directive). Claim state is unchanged.
- **Atomic supersession:** the prior decision row is superseded and the new row inserted in one transaction, guarded so a concurrent double-revision cannot produce two live current decisions (a conditional `UPDATE … WHERE superseded_at IS NULL RETURNING` + a partial-unique "one live decision per claim" invariant — see Task 3). The new row carries `supersedes_decision_id`; the audit trail shows **both** with the linkage visible.
- **Explicit state allowlist:** revision is valid only while the claim is in the post-verdict, pre-freeze window (**`verifier_approved` or `denied`**, and **not** yet `state_trustee_freeze`/terminal). Outside it, fail closed with a clear reason.
- Revision **requires step-up** — `requireStepUp(deps, 'claim_decision_revise')` (Story 1.9 admin session step-up; fresh ~5-min elevation bound to this exact action context).

**AC6 — Precedents exclude escalations and superseded rows (BigDev directive "treat escalation separately from resolved approve/deny precedents").**
`getRecentInScopePrecedents` returns **resolved approve/deny decisions only** — it **excludes** `outcome = escalated` and any `superseded_at IS NOT NULL` row, in addition to the existing exclude-current + same-Pariwar + latest-3 rules. Section (e) (this claim's transcript) *does* show the full history including escalations + superseded rows (with linkage) so the audit trail is complete.

**AC7 — Actor display is a decision-time snapshot (BigDev directive).**
`actor_display` is captured **at decision time** and stored on the row — it is **not** re-resolved live at read time. A later name/role change never rewrites the historical decision's attribution. The read model surfaces the stored snapshot; `actor_id` (the raw id) is the join/query key, `actor_display` is the frozen human-readable attribution.
**Source (R5, RATIFIED):** the display string comes from a **new `users.display_name` column** — **controlled staff-attribution personal data** (plaintext by deliberate decision: its purpose is to be displayed on audit surfaces), **never derived from the encrypted admin email**. The adjudication handler resolves it **server-side** from the authenticated actor's `users` row and snapshots it into the **required (NOT NULL)** `claim_verifier_decisions.actor_display`. **A missing/empty display name BLOCKS adjudication with a typed error (`AdminDisplayNameMissingError`) — fail-closed BEFORE any event or row is written. There is NO fallback: not the email, not the UUID, not a role/district label, not a generic placeholder, and never client input** (the request DTO does not carry `actor_display`; the contract is `.strict()`).

**AC8 — Outcome↔reason-code compatibility, enforced in BOTH domain and contract (BigDev directive).**
A reason code is only valid for certain outcomes (e.g. `concealment_flag_uphold` → deny; `concealment_flag_override` → approve; `r9_routed_to_voting` → escalate; `r8_90pct_met`/`r5_d_natural_death` → approve; `other` → any). The compatibility map is a **single domain source of truth** (`packages/domain`), enforced by:
- the **contract** (`packages/contracts` zod `superRefine`) — a rejected combination is a 400 at the boundary;
- the **domain write-path** (defense-in-depth) — the handler re-checks before persisting;
- the **UI** — the `<ReasonCodeDropdown>` offers only compatible codes for the chosen outcome.

**AC9 — Duplicate-submission / idempotency is explicit (BigDev directive).**
A decision POST advances a ₹50L claim; a double-submit must not create two events or two decision rows. Layers: (1) a transaction-scoped advisory lock on `(pariwarId, claimCaseId)` serializes concurrent decisions on one claim (the intake precedent); (2) the write-path state guard (AC2/AC3/AC5) means a second verdict finds the claim no longer in `verifier_review` and is rejected — the natural idempotency for approve/deny; (3) the `events_log (stream_id, event_version)` unique index backstops a duplicate append (`ClaimStreamConcurrencyError`); (4) the partial-unique "one live decision per claim" invariant (AC5) backstops a duplicate row. A retried identical submit returns 409, never a silent duplicate.

**AC10 — Human-actor invariant: runtime control + extend the 6.10 CI gate (the commitment 6.10 handed forward; D-B).**
- **Runtime is the security control:** every approve/deny/escalate/revise route requires an authenticated **human** admin actor, the **`claim.approve`** WRITE key (D-B — **NOT** granted to the technical `verifier` role; the `claim.verify` read vs `claim.approve` adjudication separation is preserved, and Anita adjudicates as a **District Admin**), the deceased member's **server-derived district** scope (never client-submitted — the 6.10 `resolveVerifierConsoleDistrict` pattern), tenant match, session posture — fail-closed, audited.
- **Extend the CI gate:** add the 6.11 route file + `pathSubstrings` (`verifier-decision`, or `['approve','deny','escalate','revise']`) to `scripts/claim-adjudication-human-actor-invariant/check.ts`'s `COVERAGE_SET`. An unlisted adjudication route is invisible to the gate; a coverage entry matching no route is a hard failure.
- **The runtime assertion 6.10 explicitly deferred to 6.11 now lands:** a live-DB test proving **no approve/deny/escalate/revise endpoint accepts a "system"/service/null actor** — only an authenticated human with `claim.approve` at the resolved district.
- Per epics.md:2280 the AR-61 staff-fallback path is **referenced** from Story 0.7's ledger, **not re-implemented** here.

### D-E — Revision: dedicated `verifier_decision_revised` annotation + atomic supersession + step-up (RATIFIED, directive 3)

Store it as `rationale_ciphertext = piiColumn(1,'verifier_decision')` (the ground-inspection-notes precedent), **decrypt only after authorization**, at the route (never the accessor — the 6.10 ciphertext-as-stored rule). It is **never** placed in: the `claim.verifier_*` event payload (`auditShape` only — the codebase invariant, the DPDPA-revoke precedent), the audit-sink context, application logs, any **index**, or any **searchable filter**. The **reason-code** (bounded non-PII enum) and **outcome** may ride the audit-sink context + the trustee query filter; the **rationale may not**. The trustee "actor + reason-code + time_range" audit query (AC4) filters only the non-PII columns — the rationale is returned decrypted **only** to an authorized reader of a specific decision, never as a filter/search dimension.
