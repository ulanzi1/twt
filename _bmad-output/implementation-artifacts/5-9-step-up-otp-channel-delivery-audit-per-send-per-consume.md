# Story 5.9: Step-Up OTP Channel Delivery + Audit-Per-Send-Per-Consume

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As any member at a step-up-OTP-gated action (Story 3.2 member auth) or a member logging in (Story 3.2 login OTP),
I want the OTP delivered via SMS-DLT-transactional with audit logging per send AND per consume,
so that OTP delivery is regulator-compliant (DLT/PE-OE), audit-traceable, and the gating logic (which lives in the auth surfaces, not here) can rely on a clean delivery primitive.

## Acceptance Criteria

> **Scope framing (read before the ACs — this is the load-bearing decision). This is a `[SURFACE]`/CONSUMER story that WIRES an existing seam, NOT a green-field build.** Four facts fix its shape:
>
> 1. **The OTP mechanism (generate → hash → store → verify → burn → rate-limit) and the send/consume/failure AUDIT already exist** — built by Story 1.9 (admin `step_up.*`) and Story 3.2 (member `member_login.otp_*` + `member_step_up.*`). The `StepUpOtpDeliveryPort` seam (`apps/api/src/modules/auth/shared/step-up-delivery.ts`) is the ONLY thing that is a stub today (`createLogStepUpDelivery`). 5.9 replaces that stub with the **real SMS-DLT delivery adapter** and augments the *existing* send-audit with delivery metadata. **Do NOT rebuild OTP generation, storage, verification, rate-limiting, or the consume/failure audit — they are done.**
> 2. **`step_up_otp` cannot flow through `dispatch(alert)`.** The frozen `Alert` payload for `step_up_otp` carries `{ purpose, ttl_seconds }` and render.ts emits *"A code was requested for {purpose}"* — it deliberately **carries NO code** (alerts are deep-frozen + audited + HMAC-hashed; a secret OTP must never enter that pipeline). So delivery is a **DIRECT SMS-DLT provider send** (the transport Epic 5 built in Story 5.6), classified `step_up_otp`/time-critical, with the code in a **dedicated OTP DLT template body** — **not** a `dispatch()` fan-out. This honours *there is still NO live `dispatch` call site* ([[project_channels_no_live_dispatch_yet]]).
> 3. **Delivery target is a MEMBER mobile.** Members carry a KYC-registered Tier-1 mobile (`resolveSmsTarget` / `decryptMobile` — Story 5.6). **Admins carry email only — there is NO admin mobile column** (`admin_credentials.ts` has `email_ciphertext`/`email_blind_index`, no phone). So SMS-OTP delivery is **member-scoped for v1**; admin step-up OTP-over-SMS delivery is **DEFERRED pending an admin-mobile substrate** (see Dev Notes "The admin-scope reconciliation" — flagged for BigDev). Admin step-up keeps the dev/reveal log stub until then.
> 4. **This is the FIRST live caller of the real SMS gateway.** Story 5.6 built `createSmsDltProvider` / `SmsMessagingHandle` (`sms-app.ts`) / `sms-errors.ts` with NO live caller. 5.9 is the first real send — but only the **single-target OTP path**, reusing 5.6's gateway client + error classifier, on the **OTP rate budget** (`otp_rate_buckets`), never the transactional `sms_rate_buckets`.
>
> Net: build the **real `StepUpOtpDeliveryPort` SMS-DLT adapter** (member-mobile resolution + a dedicated OTP DLT template + 5.6's gateway send + honest accept/reject) **AND** wire it as the prod default for the **member** call sites only in `deps.ts` (dev/CI keeps the reveal stub for members; admin keeps the reveal stub in ALL environments, on its own separate dependency key — see Task 5) **AND** augment the *existing* send-audit with `delivery_channel`/`delivery_status`. **Do NOT** touch OTP gating/mechanism/verification, add a live `dispatch` call site, change the frozen channel core, or add an admin-mobile column.

**AC1 — the real SMS-DLT step-up/login OTP delivery adapter (AR-24 + AR-56 + Story 5.6 SMS provider):**
1. A new adapter implements the **frozen** `StepUpOtpDeliveryPort` interface (`apps/api/src/modules/auth/shared/step-up-delivery.ts`) — a real SMS-DLT delivery replacing `createLogStepUpDelivery` as the **production** default. It takes a `StepUpOtpDelivery` payload widened with `intent: 'login' | 'step_up'` (Task 2). **Mobile resolution is per-intent, NOT a single uniform decrypt path** — the two call sites hand the adapter different things, and the two new fields are **intent-specific, not arbitrary optionals** (do not treat `resolvedMobile`/`pariwarId` as a free-for-all bag either caller may populate — see the discriminated-shape note in Task 2):
   - **`login`** (`member-auth.handlers.ts:130-155`): at OTP-request time no member is resolved yet (enumeration-safety — `actorId` there is a **mobile blind index**, not a `MemberId`), so `getMemberMobileCiphertext` cannot be called. The caller already holds the canonical E.164 mobile (`canonical = normalizeMobile(body.mobile)`, line 133) — thread that value itself into the delivery payload as a new field (`resolvedMobile`, **required** for `login`, **forbidden** for `step_up`), distinct from the existing masked `destinationHint`. The adapter uses it directly; no decrypt.
   - **`step_up`** (`member-auth.handlers.ts:397-411`): `actorId` IS a real `MemberId`, and `pariwarId` is available at the call site (`request.requestContext.pariwarId`) but is **not currently in the delivery payload** — add it (**required** for `step_up`, **forbidden** for `login`). The adapter resolves via the Story 5.6 `resolveSmsTarget` decrypt path — `getMemberMobileCiphertext(db, { pariwarId, memberId })` + `decryptMobile`, decrypted **only** in this composition layer, never logged.

   Either way, the adapter renders the OTP SMS body **containing the code** via the dedicated OTP DLT template (AC2), and posts via the Story 5.6 **`SmsMessagingHandle`** gateway client (`providers/sms-app.ts`).
2. **The response must reflect ACTUAL acceptance.** On gateway accept, `deliver` resolves (optionally returning the channel + gateway message id for the send audit — see AC3). On any non-accept (invalid number, DLT template not approved / content mismatch, carrier reject, gateway 4xx/5xx, network) the adapter **throws** a classified `StepUpDeliveryError` (no PII, classified via 5.6's `sms-errors.ts`) — so the **existing** caller catch-path fires: `member_*` handlers already audit a `*.failure` line (`reason: 'otp_delivery_failed'`) + call `onPrimaryDeliveryFailure` + propagate a retriable error (member-auth.handlers.ts:149-155, :404-411). A rejected OTP send must **never** surface as `{ sent: true }` — the member did not get the code. **Do NOT copy Story 5.6's provider "never throws / resolve rejected" posture here** — that posture is for a best-effort fan-out where a lower rung is tried next; an OTP send has no lower rung and its success/failure is load-bearing for the member's next step. **"Retriable" here means the user re-requests (a brand-new code, via the existing endpoint) — the adapter itself never auto-retries the failed send** (see Dev Notes "Load-bearing constraints").
3. **OTP delivery is direct + time-critical — it bypasses the cost-optimization (5.7) and degraded-mode (5.8) wrappers entirely.** OTP is never batched, suppressed, or deferred. The adapter calls the SMS gateway directly; it does **not** go through `dispatch`, `evaluateCostOptimization`, or `evaluateDegradedModeBridge`. (This is what the epic AC means by *"category `step_up_otp` + `time_critical = true` (bypasses cost-optimization)"* — the classification, not a literal `dispatch(alert)`; see Dev Notes "Reconciliation R1".)
4. On the **OTP rate budget**, never the transactional one: OTP send throttling is **already enforced** by the Story 3.2 per-phone `otp_rate_buckets` pre-handler (`apps/api/src/modules/auth/member/otp-rate-limit.ts`). 5.9 **reuses** it and **must NOT** consume, share, or touch the `sms_rate_buckets` transactional budget (5.6) — an alert-SMS flood must never drain the security-critical OTP budget, and vice-versa ([[project_channels_no_live_dispatch_yet]] sibling: 5.6 Dev Notes "OTP is NOT this story"). No new rate-limit code.

**AC2 — the dedicated OTP DLT templates (per AR-56; distinct from the 5.6 transactional registry):**
5. `step_up_otp` and the member **login** OTP each deliver via their **OWN separately TRAI-registered OTP DLT-transactional template — TWO templates, keyed by intent** (`login` vs `step_up`; BigDev decision 2026-07-07) — **NOT** the Story 5.6 per-category transactional registry (which **deliberately EXCLUDED** `step_up_otp`: `sms-dlt-registry.ts` L19 *"OTP delivery is Story 5.9, on its OWN rate budget (never this transactional path)"*). Add an OTP template definition keyed by intent — the registered content template TEXT + version in code (code-reviewed, byte-matching each TRAI registration per the Story 0.1 runbook / AR-56), with the **per-intent TRAI template id + PE/OE sender header resolved from GLOBAL config / Secret-Manager NAME pointers at send time** — **never hardcoded, never logged, never audited** (AI-4-3(c); mirror `pariwar_wa_config.access_token_secret_name` + the 5.6 `dltTemplateIdConfigKey` NAME-pointer discipline).
6. Each OTP template's single variable slot carries the **6-digit code** (mirror the 5.6 single-`{{1}}`-variable DLT shape — WA Q1=A). The body is a fixed registered wrapper (e.g. login: *"{{1}} is your <platform> login code. Valid 5 min. Do not share."*; step-up: *"{{1}} is your <platform> verification code for <action>. Valid 3 min. Do not share."*) — the exact registered text lives in code and must byte-match its TRAI registration or the gateway rejects it (`dlt-template-not-approved` / content-mismatch, classified by `sms-errors.ts`). The two templates carry the two committed TTLs (login 5 min, step-up 3 min — R2). **The OTP code is NOT PII in the alert-payload sense but IS a secret** — it appears only in the outbound SMS body, never in a log / audit / render-hash / the `step_up_otps` row (only the hash persists, §2.2).

**AC3 — audit-per-send AND audit-per-consume (Story 1.10; AUGMENT what exists, do not rebuild):**
7. The **send** and **consume/failure** audit lines **already exist** (Story 1.9 admin `step_up.send`/`.consume`/`.failure`; Story 3.2 member `member_login.otp_send`/`.otp_consume`/`.failure` + `member_step_up.send`/`.consume`/`.failure`), each already carrying `actor_id`, `action_context` (where applicable), the **HMAC-keyed `otp_audit_tag`** (`hmacOtpAuditCorrelation`, the non-invertible send↔consume correlation form — this IS the AC's *`otp_hash` (NOT plaintext)* that *"matches a previous send"*), and `sent_at`/timestamp. 5.9 **augments the SEND audit** to record `delivery_channel: 'sms'` + `delivery_status` (the gateway outcome: `accepted`) on a successful real send, so the audit trail reflects *how* the OTP was delivered. The consume + failed-verification audits are **already complete** — do NOT duplicate them.
8. **Harmonize the admin send-audit to the HMAC posture.** The admin `step_up.send` line currently records the **plain SHA-256 `otp_hash`** (step-up.handlers.ts) whereas the member paths record the **HMAC-keyed `otp_audit_tag`**. Plain SHA-256 of a 6-digit code is brute-forceable in <1ms (the codebase's own P28/otp.ts note). Change the admin send + consume audits to use `hmacOtpAuditCorrelation(otpHash, deps.config.auditOtpCorrelationKey)` (the linkable, non-invertible form) so admin matches member and satisfies the AC's *"otp_hash (NOT plaintext)"* + *"matches a previous send"* linkage. (This is an audit-quality reconciliation; the gating/mechanism is untouched.)

**AC4 — delivery-only, not gating-logic (explicit scope wall):**
9. **The gating decision — which actions require step-up, and the elevation window — is owned by Story 1.9 (admin) + Story 3.2 (member) and does NOT change here.** The gating middleware (`requireMemberStepUp`, `member-step-up.gate.ts`; the admin session elevation) calls the *existing* request/verify handlers; those handlers call **this story's** delivery adapter for transport. 5.9 owns **only** *how the OTP reaches the user* (SMS-DLT transport) and the *send-audit delivery metadata*. Do not add, remove, or re-scope any step-up-gated action.
10. **Freeze discipline + no live wiring beyond delivery.** Do NOT touch the frozen channel core: `dispatch.ts`, `provider.ts`, `CANONICAL_CHANNEL_LADDER`, `DeliveryResolver`, `render.ts`, `LifecycleSuppressionHook`, the `step_up_otp` alert variant / render case / deep-link-null — all frozen ([[project_channels_no_live_dispatch_yet]]). Do NOT add a live `dispatch` call site. Do NOT add an admin-mobile column (admin OTP-over-SMS is deferred — AC scope framing #3 / Dev Notes). Reuse 5.6's `sms-app.ts` + `sms-errors.ts`; do not fork a second gateway client.

### Load-bearing constraints (DO NOT violate)
- **Frozen channel core + no live dispatch** ([[project_channels_no_live_dispatch_yet]]): `dispatch.ts`, `provider.ts`, `CANONICAL_CHANNEL_LADDER`, `DeliveryResolver`, `render.ts`, `LifecycleSuppressionHook`, and the `step_up_otp` alert variant / render case / deep-link-null are **already correct and must not change**. 5.9 delivers via a **direct SMS gateway send** (5.6's `SmsMessagingHandle`), NOT `dispatch`. - **Gating is NOT this story** (AC4): the set of step-up-gated actions + the elevation window belong to Story 1.9/3.2. 5.9 owns transport + send-audit delivery metadata only.
- **OTP is a secret, distinct from alert-payload PII**: the code appears ONLY in the outbound SMS body (via the OTP DLT template variable), NEVER in a log / audit / render / the `step_up_otps` row (only the hash persists, §2.2). "Resend" is entirely a **caller-driven** action: the user re-hits the same `/otp/request` or `/step-up/request` endpoint, which calls `requestOtp` again. `requestOtp` (`member-otp.service.ts:33`, `invalidateLiveOtps`) **invalidates the previous live OTP and mints a brand-new code** on every call — so a resend is never "retry sending the identical code," it is always a fresh code, gated by the same `otp_rate_buckets` limiter (Story 3.2). Do not build a same-code redelivery path.

### The reconciliations this story resolves (surface them, resolve them)
