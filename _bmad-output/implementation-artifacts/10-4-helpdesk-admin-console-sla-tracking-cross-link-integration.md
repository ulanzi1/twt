# Story 10.4: Helpdesk Admin Console + SLA Tracking + Cross-Link Integration `[SURFACE]`

## Story

As a helpdesk responder or designated assignee (District Admin is NOT a `helpdesk.respond` holder — see AC6's deferral),
I want a helpdesk **responder console** — a scope-respecting ticket queue with live SLA timers, derived severity, and cross-link badges — where I can pick a ticket up, reply to the member, put it in `awaiting_member`, or resolve it, **and where a member reply / a staff reply drives the round-trip notification**,
so that I can resolve tickets efficiently with full context from the rest of the system, and the member sees the response without WhatsApp or a phone call.

## Scope Boundary (read first — prevents over-build)

This is the story that **10.3's scope table and 10.2's Dev Notes explicitly deferred here** — the two rows read verbatim: "Admin helpdesk **console / queue / SLA-tracking / SLA-breach alerts / cross-link navigation** → **Story 10.4**" and "Member/staff **reply-append WRITE** + `helpdesk_reply` push EMITTER → **Story 10.4**." Epic-10's demoable closure adds the load-bearing sentence: **"admin replies; member receives reply push."** So 10.4 is genuinely large: it closes the ticket **lifecycle** (the transition emitters + the transition projector that Story 10.1 authored the reducer for but deliberately did **not** emit), the **reply round-trip** (the message-bearing events `replayTicketThread` was already built to read), the **notification** (`helpdesk_reply`, whose Alert variant + deep-link are already wired end-to-end — only the emitter is missing), and the **admin responder UI** (queue + SLA + severity + cross-link nav).

**The substrate is almost entirely built. 10.4 emits into it and surfaces it — it does NOT re-author primitives.** Read [[project_helpdesk_primitive_substrate]], [[project_alert_primitive_substrate]], [[project_channels_no_live_dispatch_yet]] (retired), [[project_contribution_event_name_contract]].

## Acceptance Criteria

**AC1 — The scope-respecting responder queue with SLA timers + severity.**
Given FR-52 + AR-47 + Story 10.1's helpdesk subsystem,
When the admin console is implemented,
Then a responder holding `helpdesk.respond` opens `/p/:pariwarId/helpdesk/queue` (tenant-scoped, session-gated like every `/p/$pariwarId/` admin route) and sees the Pariwar's tickets **newest-first, paginated**, filterable by lifecycle state, scope-respecting (RLS + the pariwar predicate; v1 shows the Pariwar's tickets, with a role-match "my queue" filter over `routed_to_role`);
And each row surfaces the **live SLA timers** — first-response due + resolution due — with a derived **severity** (breached ≻ due-soon ≻ on-track) and the ticket's `current_state`, category, subject, and `created_via`;
And the queue read is a real paginated read in `helpdesk/read.ts` (state filter + `clampLimit`), NOT the capped-200 `listTicketsForPariwar` diagnostic (whose 10.1 header names this story as the owner of the paginated queue).

**AC2 — Pick up, reply, await, resolve — the lifecycle emitters + transition projector.**
Given Story 10.1 authored the full reducer (`helpdesk/state.ts`) + the transition payload shapes but emitted only the genesis (`projectTicketGenesis`),
When a responder acts on a ticket,
Then the console can `pick up` (`open`/`reopened` → `in_progress`), `reply asking for info` (`awaiting_member`), `resolve` (`in_progress`/`awaiting_member` → `resolved`), each emitting the matching `helpdesk.*` event through a NEW `projectTicketTransition` (the sibling of `projectTicketGenesis`): it appends the transition event to the ticket's `events_log` stream, re-projects `current_state` under the `app.helpdesk_state_writer` guard, and is concurrency-safe on `(stream_id, event_version)` (the same posture the genesis projector uses);
And an illegal transition (e.g. `resolve` a `closed` ticket) is rejected at the API layer BEFORE the write (the reducer is total/identity by design, so the API must guard — a no-op reducer must not silently swallow a bad request into a 200);
And the transition event types (`helpdesk.picked_up` / `helpdesk.awaiting_member` / `helpdesk.member_replied` / `helpdesk.resolved`) are registered in `packages/events/src/registry.ts` (10.1 registered only the genesis).

**AC3 — The reply thread round-trips; the member is notified.**
Given a ticket a member filed (or an operator filed on their behalf),
When a responder replies (an `awaiting_member` "we need X" or a `resolved` closing message, carrying a `message`),
Then the reply appends as a message-bearing event and surfaces in BOTH the admin thread and the member's own `GET …/member/helpdesk/tickets/:ticketId` thread via the UNCHANGED `replayTicketThread` reader (the author is a ROLE label — `staff` vs `member` — NEVER a named individual, per [[project_admin_display_name_attribution]] and the 10.2 thread rule; the FILING operator's name from 10.3 is the only named exception, and it is not a reply author);
And a `helpdesk_reply` notification is emitted (`Alert` category `helpdesk_reply`, payload `{ ticket_id }`) and dispatched to the member via the shipped fan-out — v1 delivery is a log-only fixture (providers unwired), the deep-link resolves to `tickets/:ticket_id` (already wired), the emit + dispatch is the deliverable;
And when the member replies from their app (`helpdesk.member_replied`, `awaiting_member` → `in_progress`), the message appears in the responder's thread and the ticket returns to the responder's active queue.

**AC4 — SLA timers stop on `awaiting_member` / `resolved`; breaches surface.**
Given per-ticket `sla_first_response_due` + `sla_resolution_due` (materialized at creation, calendar-aware),
When the console renders a ticket,
Then the SLA timer is **running** only while the ticket awaits staff action (`open` / `in_progress` / `reopened`) and is **stopped/paused** once `current_state ∈ { awaiting_member, resolved, closed }` (a pure derivation from the state — no new column; the reducer already encodes `awaiting_member` as "resolution SLA pauses");
And a **breach** (`due < now` while running) surfaces a visible breach indicator + escalates the row's derived severity; the queue can filter/sort by severity so breached tickets surface first;
And breach is **console-surfaced only** in 10.4 — a proactive breach → assignee-notification **sweep job is a documented seam** (PM-confirmed deferral; the 9.10 hourly-sweep precedent is the home when it lands), NOT built here.

**AC5 — Cross-link badges + navigation into the rest of the system.**
Given the four nullable cross-link refs on the ticket (`claim_case_id`, `pool_id`/reconciliation, `module_id`, `validity_lookup_id`) — settable via the existing `CreateTicketRequest` (all `.optional()`) though no v1 producer populates them yet,
When a ticket carries a cross-link,
Then the console renders the matching **badge** and a navigation affordance: claim → `VerifierConsoleRoute` (Story 6.10) for that claim; reconciliation → `ReconciliationReviewRoute` (Story 9.8) for that case; validity-service → `member-status` / `MemberSearchRoute` (Story 4.7 `MemberStatusPanel`); partner-module → **Story 12.x module lead (documented seam — no target route exists yet, the badge renders but nav is disabled/pending)**;
And because no v1 producer sets these refs, the badge + nav logic is **built defensively and unit-tested with synthetic cross-linked rows** — it lights up for free the first time a producer (a future claim/reconciliation integration) populates a ref.

**AC6 — RBAC: mint + grant + gate `helpdesk.respond` (closing the responder-authz gap).**
Given the responder console + all transition/reply routes need an authorization gate distinct from 10.3's `helpdesk.create` (filing ≠ responding),
When this story is implemented,
Then a `helpdesk.respond` permission key is minted (catalog `PERMISSION_CATALOG_VERSION` 23 → 24, dimension `pariwar` — value = `scopeTx.pariwarId`, the `helpdesk.create` / `reconciliation.review` pariwar-wide precedent) and gates the queue-read + every transition/reply route (`[requireAdminSession, scopeResolutionHook, requirePermissionHook(deps, HELPDESK_RESPOND_KEY, { dimension: 'pariwar' })]`);
And it is granted to the roles the default routing policy routes to — `helpline_operator`, `finance_officer`, `it_cell`, `pariwar_admin` (`super_admin` auto-derives); **`district_admin` is deliberately NOT granted** — a district-ceiling grant can never satisfy a `pariwar`-dimension check ([[project_rbac_geo_scope_containment]]), the exact asymmetry 10.3 encoded for `helpdesk.create` (documented deferral, acceptance condition: enable only if a helpdesk ticket gains a server-derived district AND the gate moves to `dimension:'district'`);
And an actor **without** the grant is fail-closed (audited 403); an actor **with** it succeeds — both asserted as a revert-sanity pair (removing the grant flips the 200 test to 403).

**AC7 — Tests + gates green.**
Given the merge gate is `pnpm ci:local` (`--concurrency=4`, DB on :5433),
Then live-DB integration tests cover: the queue read (paginated, state-filtered, scope-respecting; **assert membership, not counts** per [[project_live_db_test_gotchas]]); each transition emitter (pick-up / awaiting_member / member_replied / resolved) advances `current_state` correctly AND an illegal transition is rejected pre-write (a reducer no-op does NOT become a silent 200); a staff reply appends a message-bearing event that the member's 10.2 read surfaces in its thread; **the reverse direction — a member reply via `POST …/member/helpdesk/tickets/:ticketId/reply` appends `helpdesk.member_replied`, advances `awaiting_member → in_progress`, and surfaces in the admin thread + active queue** (AC3's third clause); the `helpdesk_reply` emit fires (fixture-level) on a staff reply; the RBAC 403-without-key / 200-with-key **revert-sanity pair** + the `district_admin`-denied pin;
And domain unit tests cover the pure derivations (SLA-stop by state, breach, severity) + the transition projector (state advance + concurrency + writer-guard) + the message-bearing reply thread;
And admin UI component/interaction tests cover the queue (SLA/severity/cross-link render) + the detail actions (pick-up → reply → resolve → confirmation) following the `claim-verification`/`helpline-claims` module test conventions;
And `emit-openapi.ts` + `openapi/v1.yaml` are regenerated for the new admin queue/transition/reply DTOs; en/hi parity holds for any new member-facing copy (the reply/notification strings that render in the mobile app); `pnpm ci:local` is green.

## Load-Bearing Decisions (RESOLVED — PM-confirmed 2026-07-29)

1. **Reply representation — RESOLVED: no new event type.** A staff reply rides the `awaiting_member` / `resolved` transition; a member reply rides `member_replied`. Extend ONLY those three payload schemas with a bounded `message` (`z.string().min(1).max(5000)` — matching the genesis `body` bound); leave `picked_up` / `closed` / `reopened` message-free. This satisfies "admin replies; member receives reply push" with zero new vocabulary and lights up `replayTicketThread` for free (it already reads `message`/`body`). A standalone in-progress note (reply w/o state change) is a **documented seam** (would need a self-loop `helpdesk.staff_replied` event + reducer arm) — NOT built in v1.
2. **SLA-breach notifications — RESOLVED: console-surfaced only; sweep DEFERRED.** The console-surfaced breach badge (AC4) is the whole of 10.4's breach handling. The proactive breach → assignee-notification sweep (the 9.10 hourly-sweep pattern in `apps/jobs`) is **deferred to a small follow-up job story** — do NOT build it here (it roughly doubles the API/jobs surface). Leave the documented seam only.
3. **Push-emit call site — RESOLVED.** The `helpdesk_reply` dispatch fires inline on the staff-reply write (synchronous, unlike the scheduled contribution-notify). Reuse the shipped dispatch fan-out composition rather than re-implementing it; v1 delivery is log-only (providers unwired), so this is emitter wiring, not vendor work.

### 10.1 built the reducer; 10.4 emits into it — the single most important fact

Story 10.1 **authored the complete 6-state reducer and all transition payload shapes but deliberately emitted only the genesis** (`state.ts` header: "author-all-arms, emit-genesis"; `project.ts` header: "a general transition-append projector is a later-story addition"; `events.ts`: each transition's "Owner: Story 10.4/10.2/auto-close job"). If you find yourself editing the reducer's transition arms, stop — they are correct and frozen; you emit into them. [[project_helpdesk_primitive_substrate]].

### The reply thread was built forward-compatible in 10.2 — you add the message field, not a reader

`replayTicketThread` (`helpdesk/read.ts:158`) is ONE total reader: the genesis becomes the opening entry; **any non-genesis event carrying a non-empty `message`/`body` becomes a reply entry** (`read.ts:142-151` literally documents "10.4 has not yet fixed the reply payload's field name, so BOTH `message` and `body` are accepted"). So 10.4's reply work is a **schema delta, not a reader delta**: add a bounded `message` to the `awaiting_member`/`resolved`/`member_replied` payloads (Decision 1) and the thread lights up. The author is a ROLE label (`threadAuthor` collapses everything non-member to `staff`) — NEVER a named individual ([[project_admin_display_name_attribution]]); the 10.3 filing-operator name is a create-time header, not a reply author.

### `helpdesk_reply` is a 5.1 NOTIFICATION, not an alerts-table row

Do NOT route the reply notification through the alerts-table primitive (`mintAndOpenAlert`/`openCycleAlert` in `alert/project.ts`) — that primitive is **cycle-keyed** (`deriveAlertId(cycleId)`, 1:1 with a contribution cycle). The `helpdesk_reply` is a per-ticket **5.1 notification**: an `Alert` **contract** object (`packages/contracts/src/alerts/alert.ts:149`, variant `helpdesk_reply` with `{ ticket_id }`) handed to the **dispatch fan-out**. The deep-link (`deep-link.ts:108`) already maps `helpdesk_reply` → `tickets/:ticket_id`; the mobile screen already exists (10.2/10.3).

### SLA is a pure derivation off `current_state` — no new column, no timer table

### Illegal transitions must be guarded at the API, not swallowed by the reducer

The reducer is **total** — an inapplicable event returns state unchanged (identity, `state.ts:14-17`). That is correct for replay safety, but it means the API layer MUST reject an illegal `(current_state, action)` request **before** the write (else a "resolve a closed ticket" call appends a no-op event and returns 200, corrupting the audit + the client's mental model). Guard legality in the handler (load current_state, check the action is legal for it, else typed 409/422). This is the analogue of the alert/pool "the emitter owns whether a transition SHOULD fire; the reducer owns what it DOES."
