# Terraform `terraform plan` expectations

Reference document — captures the expected resource-add count for each
substrate Story's IaC delta. Cross-reference for BigDev when executing the
deferred live-provisioning legs (D1-1.2, D1-1.5, Story 1.15).

## Story 1.5 — Cloud KMS substrate

Running `terraform plan` against the existing Story 1.2 dev state with
`var.app_service_account_email` left at its default (`null`) should produce:

```
Plan: 3 to add, 0 to change, 0 to destroy.
```

With the 3 resources being:

1. `google_kms_key_ring.twt_dev` — `twt-dev-keyring` in `asia-south1`.
2. `google_kms_crypto_key.pii_tier_1_kek` — HSM-backed AES-256 KEK.
3. `google_kms_crypto_key.pii_tier_2_hmac` — HSM-backed HMAC-SHA-256 key.

When `var.app_service_account_email` is set (Story 1.15 substantive populate),
the plan adds 2 additional IAM member resources (`google_kms_crypto_key_iam_member`,
one per key — additive semantics):

```
Plan: 5 to add, 0 to change, 0 to destroy.
```

Verification:

```sh
cd infra/gcp
terraform init
terraform plan -out=tfplan-story-1.5
# Resources to add: 3 (or 5 with IAM bindings).
# Resources to change: 0.
# Resources to destroy: 0.
```

**Story 1.5 closure does NOT apply this plan.** Live provisioning is D1-1.5.

## Story 1.15 — module extraction + staging/prod + WIF (D3-1.2 / D4-1.2)

### Module-address migration (already-applied dev)

The Cloud SQL resources moved into `module.cloud_sql_dev`. Re-running `plan` against
the existing dev state (var.environment=dev) WITHOUT a `state mv` would show
`5 to add … 5 to destroy` (same config, new address). Migrate in-place FIRST so the
plan is clean:

```sh
terraform state mv 'random_password.app_password'                'module.cloud_sql_dev[0].random_password.app_password'
terraform state mv 'google_sql_database_instance.main'           'module.cloud_sql_dev[0].google_sql_database_instance.main'
terraform state mv 'google_sql_database.app'                     'module.cloud_sql_dev[0].google_sql_database.app'
terraform state mv 'google_sql_user.app'                         'module.cloud_sql_dev[0].google_sql_user.app'
terraform state mv 'google_secret_manager_secret.conn_string'    'module.cloud_sql_dev[0].google_secret_manager_secret.conn_string'
terraform state mv 'google_secret_manager_secret_version.conn_string_v1' 'module.cloud_sql_dev[0].google_secret_manager_secret_version.conn_string_v1'
# Then: terraform plan  → "No changes." (behaviour-preserving — D3-1.2 baseline still valid.)
```

### STAGING — fresh apply (`-var-file=terraform.staging.tfvars`, github_repository set)

```
Plan: 13 to add, 0 to change, 0 to destroy.
```

network (2: PSA range + connection) + cloud-sql module (6: random_password +

does NOT run this.

### PROD — fresh apply (`-var-file=terraform.prod.tfvars`)

Same shape as staging (the same module + WIF), REGIONAL Cloud SQL, the strictest WIF
attribute condition (`wif_prod_workflow_ref`). Apply is gated behind the
`production` GitHub Environment ≥2-reviewer rule for the deploy workflow (§5.4); the
`terraform apply` itself is run by the operator with the escrow-sealed prod creds.

**Story 1.15 closure does NOT apply any of these plans** (D3-1.2 / D4-1.2 — operator
activation leg). The dev agent authored + CI-validated the HCL; `terraform validate`
+ `plan` are the operator's first live step.
