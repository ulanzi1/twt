**Source:** Epic 8 retrospective (`epic-8-retro-2026-07-25.md`, H-1 + §7 AI-8-3 + §8) — **CONFIRMED BigDev 2026-07-25, ELEVATED to pre-Epic-9 critical path.**

**Status:** done

> **Retro ask (verbatim, §7 AI-8-3):** *"Wire the real per-Pariwar delivery providers before Epic 9. 8.8 shipped the first live `dispatch()` call site but `resolveProviders` is unwired in `boot.ts` (log-only fixtures, no real bytes). Resolve the `apps/api ↔ @twt/channels` package-cycle constraint (a jobs-side provider seam or a shared provider package) so 9.5's `contribution_confirmed` push delivers live bytes during Epic 9 dev (H-1)."*

## 1. Context — the risk this closes (H-1, headline of the Epic 8 retro)

Story 8.8 landed **the stack's first live `dispatch()` call site** (`apps/jobs/src/scheduler/contribution-notify.ts`), ending Epic 5's nine-story "future live fan-out" deferral ([[project_channels_no_live_dispatch_yet]] — the deferral has ENDED, that memory records the live seam). A deployed worker now composes the full ladder (bridge → cost-opt → cascade over `dispatch`), writes both audit families, and honestly maps every outcome.

**But `resolveProviders` is left unwired in `boot.ts` (lines 506–523).** With the seam omitted, `dispatch` resolves its own `DEFAULT_PROVIDER_REGISTRY` — the **log-only fixtures** (`packages/channels/src/providers/index.ts:111`). Those unconditionally return `status:'accepted'` and send **no real bytes**. So today a deployed worker composes + audits a complete fan-out that **delivers nothing**.

This is the retro's headline hard-truth **H-1**, disclosed (not silent) in the 8.8 Dev Agent Record and `deferred-work.md`. BigDev **elevated it to pre-Epic-9 critical path**: Story 9.5 emits `contribution.confirmed` and enqueues the confirmed-push (the 8.8 Epic-9 seam, `registerContributionNotifyWorkers`' confirmed enqueue) — that push must deliver **real bytes end-to-end during Epic 9 dev**, not fixtures. AI-8-3 wires the real providers so it does.

## 2. The load-bearing reconciliation — the "cycle" is narrower than the retro's shorthand (surface it; do NOT invent a package)

The retro names the constraint "the `apps/api ↔ @twt/channels` package-cycle". **Read the graph before choosing a fix** — the real constraint is subtler, and getting it right picks the cheapest correct home.

**Package dependency facts (verified this session):**

| Fact | Source |
|---|---|
| `apps/jobs` depends on `@twt/channels` **and** `@twt/domain` | `apps/jobs/package.json` |
| `apps/api` depends on `@twt/channels`, `@twt/domain`, **and `@twt/jobs`** | `apps/api/package.json:25,27,30` |
| `@twt/channels` depends on `@twt/domain` (already imports `audit`, `canonicalJsonStringify`, `encryption`) | `packages/channels/package.json`; `packages/channels/src/audit.ts:19`, `cost-optimization.ts:43` |
| `@twt/domain` **cannot** import `@twt/channels` (would cycle `channels→domain→channels`) | why 8.8 relocated the *target* resolvers to domain as `SendTarget`-structural, never importing channels |

So there are **two different cycles**, and the 8.8 comment conflates them:

1. **`apps/jobs → apps/api` is forbidden** because `apps/api → @twt/jobs` already exists. This is why the composition can't just be *imported from apps/api* by jobs. ✅ real.
2. **The provider composition can't go into `@twt/domain`** because it must call `createWhatsappProvider`/`createSmsProvider`/`createTelegramProvider`/`createPushProviders` and return `ChannelProvider` — all `@twt/channels` symbols, and domain can't import channels. ✅ real (this is the true blocker, distinct from #1).

**The resolution both facts point to:** the provider composition's only real dependencies are `@twt/domain` (the `channelConfig` reads) **and `@twt/channels`'s own provider factories**. **`@twt/channels` already depends on `@twt/domain`.** Therefore the composition's natural home is **`@twt/channels` itself** — the package that already owns the provider factories and already reads domain. Both `apps/api` and `apps/jobs` already depend on `@twt/channels`, so both can consume it with **zero new package** and **zero new dependency edge**.

This is the exact shape of 8.8's own move (relocate the delivery *target* resolvers into `@twt/domain` because that's the lowest shared layer that satisfies their deps; leave a thin re-export so no call site changes). AI-8-3 does the twin move one layer up: relocate the provider *composition* into `@twt/channels` because that's the lowest shared layer that satisfies **its** deps.

**Do NOT create a new `@twt/channel-composition` package.** A second consumer exists (`apps/api` tests + `apps/jobs`), so a shared home is justified — but `@twt/channels` **is** that shared home already. A new package would be ceremony that duplicates the layer that already exists ([[feedback_no_premature_package]]: prefer the existing shared package over a new one; the rule is against *premature* extraction, and here even a non-premature extraction is unnecessary because the right package is already in the graph).

Record this reconciliation in the Dev Agent Record per [[feedback_closure_language_precision]] — the retro's "apps/api ↔ @twt/channels cycle" shorthand is corrected to "the composition needs `@twt/channels`, `@twt/domain` can't host it, and `@twt/channels` already reads `@twt/domain` ⇒ it lives in channels."

## 4. The push trap — the fixture push short-circuits the whole cascade (why "wire providers" is really "wire real PUSH")

This is the single most important behavioural fact in the story. The cascade (`runChannelCascade`, AR-19) is **push → WA → SMS, stop at first `sent`**. `dispatch`/the cascade delivers on the **first accepting rung**. The **fixture push provider always returns `accepted`** (`fixture-push.ts`). Therefore:

> If `resolveProviders` returns the fixture push (even while WA/SMS are real), **every member "delivers" on the fixture push and the ladder never advances** — no real bytes, ever. Wiring real WA/SMS while leaving push on the fixture delivers **nothing real**.

So "wire the real providers" **requires wiring real push** (the cascade's first, primary rung) — or nothing downstream is ever exercised. This must not be discovered at Epic 9; it is the crux of the story.

**Push provisioning gap (verified):** there is **no per-Pariwar push/Firebase config table** (no `pariwar_push_config`, no service-account secret NAME column — grep confirms only WA/Telegram config tables exist). `createFirebaseAppCache().messagingFor(pariwarId, serviceAccountJson)` needs a service-account JSON per Pariwar, and there is no substrate that supplies one.

**D3 (✅ RATIFIED — global v1):** wire push against a **GLOBAL Firebase service-account secret** (one Secret-Manager NAME + env-fallback, e.g. `FIREBASE_SERVICE_ACCOUNT` / `PUSH_FIREBASE_SA_SECRET_NAME`), passed as the `serviceAccountJson` for **every** Pariwar's `messagingFor(pariwarId, sa)` call (the cache still isolates one Firebase `App` per pariwar_id by name, but they share one project's credential). **Absent secret ⇒ fixture push** (the opt-in-real convention). This mirrors SMS's own "global gateway, **no per-Pariwar dimension**" posture (`composition.ts:258-271`) exactly — SMS is already global, so a global-credentialed push v1 is consistent, needs **no migration**, and unblocks Epic 9's real-bytes goal. A genuinely per-Pariwar Firebase project (its own config table + secret-name column + admin surface) is a **separate future story**, flagged here, not built now (adding a producer-less config column repeats the anti-pattern 5.6/5.7 called out). See §9 D1.

## 6. The scoping subtlety — `resolveProviders` must open its OWN tenant scope (and should memoize)

`resolveProviders` is invoked **inside `fanOutAlert`** (`contribution-notify.ts:235-237`) with only `{ pariwarId, category }` — it is **not** handed the pre-scoped `db` that `resolveMemberDeliveryContext` gets (that one runs under `withPariwarScope` at `fanOutAlertToMembers` `:439`). The relocated composition functions read `channelConfig.getWaConfig` etc., which are **RLS-scoped** reads. So the resolver **must open its own `withPariwarScope(servicePool, pariwarId, db => ...)`** for the config reads. Missing this ⇒ the config read runs unscoped ⇒ RLS returns nothing ⇒ every channel silently resolves to the fixture (a green-but-vacuous wiring — the exact failure mode this story exists to prevent).

**Efficiency (D3, ✅ RATIFIED — memoize):** `fanOutAlert` calls `resolveProviders` **once per member**. For a 4-lakh-member cycle that is ~400k invocations, each doing a config DB read + `resolveApprovedTemplate` read + a `resolveSecret`/`resolveConfig` round-trip — for values that are **identical across every member of the same `(pariwarId, category)`**. The app caches already memoize the *clients* by pariwar_id, but the **config + secret reads repeat per member**. The resolver **memoizes its result per `(pariwarId, category)`** (a `Map` populated on first miss) — so config is read once per `(pariwarId, category)`, not once per member. This lives **inside `createContributionProviderResolver`** (do NOT touch the frozen `fanOutAlert` to hoist the call — that changes 8.8's signature). Task 3 proves the memoization with a call-count spy.

**Cache-invalidation posture — CORRECTED during story validation (was inconsistent, now matches what's actually buildable):** `createContributionProviderResolver(bootDeps)` is constructed **once**, in `boot.ts`, at process startup (Task 4), and its returned resolver is registered **once** via `registerContributionNotifyWorkers`. `resolveProviders({pariwarId, category})` carries no batch/job/cycle id (§ signature above) — the resolver has **no way to know when "one fan-out" starts or ends**, so its memo `Map` is necessarily a **process-lifetime** cache, not a per-cycle one. Concretely: disabling a channel's admin toggle, rotating a WA/Telegram/SMS credential, or approving a new template does **not** take effect for an already-memoized `(pariwarId, category)` until the **worker process restarts** — this is the exact same "restart-required-on-rotation" posture the app caches already document (`firebase-app.ts`/`whatsapp-app.ts`/`telegram-app.ts` headers), not a "next cycle" freshness guarantee. State this explicitly in the Dev Agent Record; do NOT describe it as "picked up next cycle."

### Review Findings

_bmad-code-review, 2026-07-25 (3 parallel layers: Blind Hunter, Edge Case Hunter, Acceptance Auditor). The Acceptance Auditor traced the §9a-i 5-state invariant only within `provider-composition.ts` against its unit-test fakes (which correctly model a nullable `resolveConfig`) and reported clean; both other layers independently found that the REAL boot-time `resolveConfig` wiring breaks that contract — a blind spot worth noting for future acceptance-auditor prompts on this codebase._

- [x] [Review][Decision] `resolveConfig` is aliased to the same throw-only function as `resolveSecret`, collapsing "not provisioned" into "infra outage" — one missing per-category secret rejects the WHOLE 4-channel registry, not just SMS — This is the single highest-severity finding, confirmed independently by both the Blind Hunter and Edge Case Hunter layers, and further confirmed by tracing `resolveSecretValue` directly. `apps/jobs/src/scheduler/contribution-providers.ts:107,111` binds BOTH `resolveSecret` and `resolveConfig` to the same `resolveChannelSecret` (`:56-60`), which calls `resolveSecretValue` (`packages/domain/src/secrets.ts:101-132`) — a function whose type is `Promise<string>` and which **always throws**, never returns `null`/empty, whether the cause is a genuine Secret-Manager outage OR a secret that was simply never provisioned (verified: no `.code`/gRPC-status branching in `resolveSecretValue`; both a `NOT_FOUND` and an `UNAVAILABLE` from the underlying client surface as the same generic thrown `Error`). ### 9a. Two BigDev hardening asks (both binding — encode as teeth)

**(i) The 5-state outage/fixture matrix — the honesty invariant's highest-risk boundary.** "Not configured" and "configured but the infra is down" are **fundamentally different**, and collapsing them is how honest delivery reporting silently rots (a masked outage becomes a fake fixture "success"). Task 3 MUST prove all five, per channel where applicable:

| State | Expected | Why |
|---|---|---|
| Configuration **absent** (no config row) | → **fixture** | not provisioned |
| Configuration **disabled** (`enabled=false`) | → **fixture** | admin opted out |
| Secret **missing by design** (blank credential/template NAME, `isConfigured()===false`) | → **fixture** | not provisioned |
| **Secret Manager outage** (`resolveSecret`/`resolveConfig` **throws**) | → **failure (propagates)** | infra down ≠ unconfigured |
| **Database outage** (the scoped `channelConfig` read **throws**) | → **failure (propagates)** | infra down ≠ unconfigured |

The first three resolve to the log-only fixture (opt-in-real); the last two **must reject** the resolver so the pg-boss job fails and retries — never degrade to a fixture. This is the load-bearing distinction the composition head-comment (`composition.ts:23-29`) already encodes for a single channel; AI-8-3 must hold it **across the assembled registry** and prove it explicitly.

**(ii) The full-ladder-advances-on-reject end-to-end test — permanent regression armor for the push trap (§4).** Because the fixture push always accepts, a partially-wired system can look healthy while never sending a real notification. Task 5 MUST drive the **8.8 `fanOutAlert`** (unchanged) with a `resolveProviders` built from **provider doubles only (no network)** and prove the ladder advances on each reject:

- **real push `rejected` → WhatsApp attempted**, **WhatsApp `rejected` → SMS attempted**, and **SMS is the TERMINAL rung** (`CANONICAL_CHANNEL_LADDER = ['push','whatsapp','sms']`, `cascade.ts:18-20`): SMS `sent` ⇒ delivered-on-SMS; SMS `rejected` ⇒ ladder **exhausted** ⇒ member undelivered ⇒ the caller fails the job (pg-boss retry). Assert the trail is `push→whatsapp→sms` in order with the reject outcomes recorded honestly.
- **Ladder-shape reconciliation (correct BigDev's "SMS → Telegram" phrasing, per [[feedback_closure_language_precision]]):** **Telegram is NOT the 4th rung.** The cascade iterates ONLY `push→whatsapp→sms`; **Telegram is an INDEPENDENT fire-and-forget mirror** (`cascade.ts:29-31`; `contribution-notify.ts` step 4) that fires in parallel **only when the category is Telegram-eligible** (`isCategoryEligible('telegram', category)`) **and** a chat_id is on file — a Telegram failure triggers **no** cascade and never affects the ladder outcome. Note the eligibility corollary: the contribution-loop **deadline-reminder / contribution-confirmed** categories are **NOT** Telegram-eligible (only the cycle-open **`alert_published`** announcement is), so the mirror is silent for exactly the Epic-9 confirmed-push this story unblocks. The test asserts (a) the ladder advances push→WA→SMS independently of Telegram, and (b) for a Telegram-eligible category with a chat_id, the mirror fires **once, independently**, and its failure leaves the ladder outcome unchanged.

This test permanently protects the exact regression the story exists to eliminate: it goes RED the day someone leaves push on the fixture (push would "accept" and the trail would stop at push, never reaching WA/SMS).
