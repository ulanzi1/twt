# Story 10.1: Helpdesk Subsystem Data Model + Routing-Policy Registry `[PRIMITIVE]`

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As Solo Builder authoring the first-class helpdesk subsystem,
I want the helpdesk data model + a registry-driven routing-policy primitive that deterministically routes tickets by category × scope,
so that routing decisions are reproducible, audit-replayable, and modifiable via the policy registry (not engine code) per AR-47 §3.5a.

## Scope Boundary (read first — prevents over-build)

This is a `[PRIMITIVE]` story. It lands the **substrate** the Epic-10 helpdesk surfaces consume. It does **NOT** build UI:

| In scope (10.1) | Out of scope → owning story |
|---|---|
| `@twt/contracts/helpdesk` transport types (`.strict()`) | — |
| `@twt/domain` `helpdesk` namespace: schema, event vocab, **complete** ticket-state reducer, deterministic routing resolver, versioned routing-policy registry (read/write), projector, reads | — |
| Migration `0084` (tickets table + routing-policy-versions table) | — |
| `helpdesk.*` genesis event registration + default routing-policy **v1 seed** | — |
| API `apps/api/src/modules/helpdesk/` **create-ticket primitive** route (tenant-scoped) + audit emission | — |
| Determinism CI test (load-bearing) | — |
| Member ticket-filing UI | **Story 10.2** (`apps/mobile`) |
| Helpline operator call-to-ticket surface | **Story 10.3** |
| Admin console, queue, SLA-breach alerts, cross-link navigation | **Story 10.4** (`apps/admin/src/modules/helpdesk/`) |
| Emitting the non-genesis transitions (pick-up, resolve, awaiting-member, close, reopen) | 10.2 / 10.4 + auto-close job |

The state reducer authors **all** transition arms now (total, forward-compatible), but this story **emits only the genesis** (`helpdesk.ticket_created` → `open`) + the routing decision. This is the exact **alert/state.ts precedent** ("author the complete reducer, emit only the cycle-open arms"). Cross-link ref columns are defined **nullable seams** now; the navigation that reads them is 10.4.

## Acceptance Criteria

**AC1 — Modules + ticket schema exist (structural).**
Given FR-52 + AR-47 §3.5a + AR-46 per-Pariwar configurability registry,
When the helpdesk subsystem is authored,
Then the following exist and typecheck across the workspace:
- `packages/contracts/src/helpdesk/` — substantive `.strict()` transport contracts (replaces the reserved README-only placeholder).
- `packages/domain/src/helpdesk/` — the primitive (events/state/routing/registry/project/read/errors/index — **no `schema.ts` here**; the Drizzle table defs live in `packages/domain/src/schema/` per Task 2, the convention every other namespace (`alert/`, `pool/`, `claim/`, `niyamavali/`, `reconciliation/`) follows), exported as `export * as helpdesk from './helpdesk/index.js'` in `packages/domain/src/index.ts`.
- `apps/api/src/modules/helpdesk/` — the tenant-scoped create-ticket primitive route.
- **Not** `apps/member/modules/helpdesk/` (epics prose drift — the member surface is `apps/mobile`, and it is **Story 10.2**, not this story).

And the **ticket record** carries: `ticket_id`, `pariwar_id`, `subject_member_id` **OR** `subject_actor_id` (exactly one non-null), `category` (enum from registry), `subcategory` (registry-driven, nullable), `body`, `attachments[]`, `current_state` (**projector-only** — see AC4), `routed_to_scope` (RBAC `(dimension, value)`), `routed_to_role`, `routed_to_actor_id` (nullable), `routing_policy_version`, `member_scope_context` (the routing inputs snapshot), `assigned_at`, `sla_first_response_due`, `sla_resolution_due`, `audit_id`, `created_via` (`member_app | helpline_call`), `operator_attribution` (nullable), plus nullable cross-link refs `claim_case_id`, `pool_id`, `module_id`, `validity_lookup_id`.

**AC2 — Routing-policy registry (versioned + audit-logged, per-Pariwar).**
Given the FR-7 / Story 2.3 versioned-registry pattern,
When the registry is authored,
Then it exposes a resolver `(category, sub_category, member_scope_context) → (target_role, target_scope, sla_first_response, sla_resolution)`;
And entries are **versioned** (a policy update INSERTs a new version row; prior rows are never mutated except a `superseded_by_version` forward-pointer — the `clause_versions` immutability posture) and **audit-logged** on write;
And a **default routing-policy v1 is seeded** covering the FR-52 v1 categories: `kyc-trouble`, `payment-failed`, `utr-mismatch`, `claim-status`, `profile-update`, `niyamavali-question`, `partner-module-issue`, `complaint`, `other`;
And per-Pariwar overrides are allowed (default policy applies when a Pariwar has no override — AR-46).

**AC3 — Deterministic, audit-replayable routing (this story's load-bearing commitment).**
Given a ticket created with inputs `(category, sub_category, member_scope_context, routing_policy_version_at_creation)`,
Then the routing decision is **deterministic** — same inputs + same policy version produce the same outputs on every machine, every replay;
And the routing is **audit-replayable** — the audit line records inputs + the policy version used + the resulting target role/scope; replaying with the same inputs + same policy version reproduces identical routing;
And policy changes are **non-retroactive** — a routing-policy update creates a new version; existing tickets keep the routing under the version in force **at their creation** (they store `routing_policy_version` and are never re-routed);
And a **CI test asserts** determinism: same `(category, sub_category, member_scope_context)` yields identical routing across replay runs; hash-map iteration order, async scheduling, or parallel execution cannot vary the outcome (the **Story 4.6 rule-order determinism** analog).

**AC4 — Ticket state is event-derived (§3.5a + Cross-Cutting #4).**
Given the architecture commitment that persisted ticket state is an optimization, not the source of truth,
Then ticket lifecycle state is derived by replaying the `helpdesk.*` event stream (`stream_id = ticket_id`) through a **pure/deterministic/idempotent/total reducer** (twin of `alert/state.ts`);
And `helpdesk_tickets.current_state` is **projector-only** (maintained by the projector/DB trigger; never written directly by feature code — a CI gate enforces this, mirroring `members.state` / `alerts.current_state`).

**AC5 — Audit on create/route (Story 1.10).**
Given the tamper-evident audit log,
When any ticket is created or routed,
Then an audit line records the routing decision with full inputs + policy version + outputs, via `writeAuditEntry` (hash-chained).

### ⚠️ Load-bearing decision — the lifecycle state set (PRD↔epics drift; needs ratification)

The two authoritative docs disagree, and **each is individually incomplete** — the exact situation `rbac/scope.ts` resolved for scope dimensions (ratified in ADR-0008):

| Source | State set | Missing (but its own prose requires) |
|---|---|---|
| **PRD FR-52** (prd.md:822) | `open · in_progress · awaiting_member · resolved · reopened` | `closed` — yet FR-52 prose says "auto-close on `resolved` after 7 days" and "reopen … within 30 days **post-close**" |
| **epics.md 10.1** (AC) | `open · in_progress · awaiting_member · resolved · closed` | `reopened` — yet the reopen path is a committed FR-52 consequence |

Architecture §3.5a says "the state set and transitions are committed in PRD FR-52" — but FR-52's own auto-close/reopen prose needs a state its enum omits. **RATIFIED by BigDev 2026-07-28 (bmad-create-story): the union the requirements structurally need** —
`open → in_progress → awaiting_member → resolved → closed → reopened`, transitions:
- `open → in_progress` (assignee picks up)
- `open|in_progress → awaiting_member` (needs member input; SLA resolution timer pauses)
- `awaiting_member → in_progress` (member replies)
- `in_progress|awaiting_member → resolved` (assignee resolves; resolution timer stops)
- `resolved → closed` (auto, 7 days no member reply)
- `resolved|closed → reopened` (member reopens within 30 days post-close) `→ in_progress`

This mirrors `alert/state.ts` (linear-plus-arms, total reducer). It is the primitive's **replay identity** — changing it later re-shapes every downstream surface (10.2/10.3/10.4). The decision is ratified; **record it in an ADR/decision-log note** (ADR-0008 scope-dimension-union precedent) as part of this story so the divergence-from-both-sources is documented. Do **not** silently follow either single source. `[[feedback_architecture_vs_prd_boundary]]`.

### Event-derived-state primitive — the 5th one

Ticket state is **event-sourced** (§3.5a explicit). This is the FIFTH event-derived-state primitive after member/claim/pool/alert. Copy the shape exactly:
- **Source of truth** = replaying the `helpdesk.*` stream (`stream_id = ticket_id`, PK-ordered by `event_version`) through the reducer. `helpdesk_tickets.current_state` is a **projection** (an optimization), never authoritative.
- **Reducer contract** (`packages/domain/src/alert/state.ts:9-28` verbatim template): pure, deterministic, idempotent, **total** — an inapplicable event returns state unchanged (identity), never throws. Replaying 1..N twice yields the same state. Whether a transition *should* emit is the emitter's concern, not the reducer's.
- **Projector-only column** — mirror `members.state` / `alerts.current_state`: a DB trigger/projector maintains `current_state`; a CI gate forbids direct writes by feature code. `[[project_alert_primitive_substrate]]`, `[[project_member_lifecycle_domain_substrate]]`.
- `ticket_id` is a plain `gen_random_uuid()` (unlike `alert_id`, it has no natural key to derive from — there is no `deriveTicketId`). If helpline-call create needs idempotency, use a keyed idempotency store, not a derived id.

### Versioned routing-policy registry = the clause_versions posture

The routing-policy registry is the **Story 2.3 niyamavali registry** pattern applied to routing rules (`packages/domain/src/niyamavali/write.ts` is the exemplar):
- A version row is **append-only**; the only legitimately-mutable column is `superseded_by_version` (the forward-pointer). Never UPDATE `policy_document`/`version`.
- A policy update INSERTs `version + 1` and points the prior row's `superseded_by_version` at it — all in the caller's transaction (narrow-write posture: no HTTP, no auth in the domain fn; those live at the route).
- **Non-retroactivity** = the `lock_in_days_at_join` snapshot pattern (FR-8): the ticket stores `routing_policy_version` at creation; existing tickets are **never** re-routed when a new version publishes. `[[project_niyamavali_precedence_is_provenance]]`.
- Per-Pariwar override + default (AR-46): `routingPolicyVersionInForce` resolves the Pariwar's own latest-effective version, falling back to the seeded default policy.

### Deterministic routing = the Story 4.6 rule-order analog

`resolveRoute(inputs, policyDocument)` must be a **pure first-match** over an **explicitly-ordered** rule array. The determinism killers to avoid (the CI test must catch each): `Object.keys()`/`Map`/`Set` iteration order deciding precedence, `Date.now()`/randomness, async scheduling affecting outcome, parallel execution. `member_scope_context` supplies the geo values that fill the target scope's `value` (e.g. `kyc-trouble` + subject in `district=Patna` → `(district_admin, {dimension:'district', value:'Patna'})`). The resolver returns `(target_role, target_scope, sla_first_response, sla_resolution)`; SLA budgets are read from the matched rule. `[[project_pool_assignment_engine]]` (version-pin gates the whole algorithm, not just a hash) is the discipline: the `routing_policy_version` pins the entire rule list + first-match semantics, and that is the replay identity.

### RBAC target scope shape (Story 1.8)

`target_scope` is a `GrantScope` `(dimension, value)` from `packages/domain/src/rbac/scope.ts`. Canonical dimensions: `global | pariwar | state | district | block | self`. `target_role` is one of the seeded roles in `packages/domain/src/rbac/roles.ts`: `super_admin | pariwar_admin | state_trustee | district_admin | block_admin | … | helpline_operator`. 10.1 only **derives + records** the target; queue-visibility filtering (does this admin see the ticket?) is **Story 10.4** and uses `scopeContains`. Note: the geo-tree containment resolver was a deferred seam (default deny-deeper) until Epic 3 — Epic 3 is done, but recording a target scope does not require containment resolution, so this is not a blocker for 10.1. `[[project_rbac_geo_scope_containment]]`.

### Audit (Story 1.10) — use `withCompensatingAudit`, not a bare `writeAuditEntry` call

`AuditEntryInput` (`packages/domain/src/audit/write.ts:71-88`) has **no free-form content field** — it takes `pariwarId`, `actorId`, `actorRole`, `action` (dotted lowercase `resource.action`, e.g. `helpdesk.ticket_created`), `resourceLocator` (e.g. `` `ticket/${ticketId}` ``), `requestPayloadHash` (a **SHA-256 hex digest you compute**, never the raw payload — "never the payload itself" per the file's own doc comment), and `responseStatus`. Compute the digest the way `packages/domain/src/pool/names.ts` does: a local `createHash('sha256').update(canonicalInput, 'utf8').digest('hex')` helper over a canonicalized JSON string of `{ticket_id, category, sub_category, member_scope_context, routing_policy_version, target_role, target_scope, sla_first_response_due, sla_resolution_due}` (local, not imported — the packages that already export a `sha256Hex` idiom depend on `@twt/domain`, so importing one would cycle).

Per ADR-0030 (`packages/domain/src/audit/compensating.ts` header), `withCompensatingAudit` / `writeRolledBackAudit` are the **sole sanctioned callers** of `writeAuditEntry` for a mutation+audit pairing — a bare direct call is non-conformant, not merely a fallback option. Use `audit.withCompensatingAudit(servicePool, { auditIntent, mutate })`: it writes the intent audit line first (giving you `auditId` to thread into the ticket row, the Story 2.4 pre-generate pattern), then runs `mutate`, firing the compensating `_rolled_back` line on failure. Note: the AI-5-3 CI gate that catches bare `writeAuditEntry` calls (`scripts/access-wrapper-invariants/check.ts`) is currently scoped to `CHANNEL_ROOTS`/`CLAIM_ROOTS` only — it will **not** catch a violation under `apps/api/src/modules/helpdesk/` or `packages/domain/src/helpdesk/`, so this is a silent-failure risk if skipped, not a build-breaker.
