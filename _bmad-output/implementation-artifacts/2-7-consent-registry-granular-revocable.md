## Story

As **Solo Builder authoring the consent primitive that Epic 6 (claim-time DPDPA consent) and Epic 3 (T&C acceptance + medical-disclosure ack) will both consume**,
I want **a granular, revocable consent-registry data model + domain API surface**,
so that **every consent transaction is independently auditable, revocable, and resolvable to a specific version of the artifact consented to**.

## Context & boundaries (read first)

This is the **fourth and final Epic-2 substrate landing** — and, unlike 2.3–2.6, it is a **pure `[PRIMITIVE]`**: a `@twt/domain` registry + RLS + migration + accessors, plus the `@twt/contracts` transport DTOs that future consumers import. **There is NO surface in this story** — no `apps/api` routes, no `apps/admin` UI, no `apps/public` page, no member-facing copy. The actor-facing flows that *record* consent are built later:

- **Epic 3** records `tc_acceptance`, `medical_disclosure_ack`, `nominee_share_split` at signup (consumes `recordConsent`).
- **Epic 6** records `claim_time_dpdpa` at claim time (epic AC3 — "Story 2.7's primitive is the only API touched").
- **Epic 5 / 11b** consume `consentExists(...)` as the canonical "did this member have valid X consent at time Y?" gate (WhatsApp opt-in, Sahyog Vivran / In-Memoriam publication).

**This story mirrors the 2.6 substrate slice, minus the surface layers.** The schema + RLS + migration mirror `terms_and_conditions_versions.ts` (2.6) / `clause_versions.ts` (2.3); the accessor module mirrors `terms-and-conditions/{read,write,errors,index}.ts`; the contracts DTOs + the `pgEnum` ↔ `z.enum` lockstep mirror `terms-and-conditions/tc-version.ts` + its lockstep test. **You are not inventing patterns; you are following the ones already in the tree.** Cite them and match them.

**The "API surface" in the user story = the `@twt/domain` exported-function surface** (`recordConsent` / `revokeConsent` / `listConsents` / `consentExists`), exactly as the epic AC2 enumerates it — NOT an HTTP surface. The audit-or-throw HTTP wrapper is the *consumer's* responsibility (Epic 3/6 route, which owns the actor session): those accessors take a **caller-supplied `auditId`** (mirror `createTcVersion`'s caller-supplied `auditId`) so the consumer writes its audit line first and threads the id in.

### Settled decisions (BigDev, 2026-06-24) — these are firm, not open
1. **Scope = `@twt/domain` primitive + `@twt/contracts` DTOs only.** NO `apps/api` routes, NO new RBAC permission keys, NO `PERMISSION_CATALOG_VERSION` bump, NO OpenAPI path registration, NO public/admin surface, NO i18n namespace, NO domain-event emission. The consumers (Epic 3/6) own the routes + audit-or-throw + any events. (Follows the 2.6 scope-fence discipline: do not add routes speculatively for flows that do not yet exist.)
2. **`consent_type` is a `pgEnum` with the AC1-listed 7 values only**, lockstep-asserted against a `@twt/contracts` `z.enum` (mirror `tc_legal_review_status` ↔ `TcLegalReviewStatusSchema`). New consent types (e.g. `whatsapp_opt_in`, `sahyog_vivran_publication`, `in_memoriam_listing`, `module_lead_handoff` — referenced in later epics) are added by their **own consumer epic** via an additive `ALTER TYPE … ADD VALUE` migration. Do NOT seed types for surfaces that do not exist yet.
3. **Two revoke-side columns are added beyond the epic's literal column list: `revocation_reason` (text, nullable) + `revoked_audit_id` (uuid FK, nullable).** This is a deliberate variance from epics.md L1554 (which lists only `audit_id` + `revoked_at`): `revokeConsent(consent_id, reason)` takes a reason and the revoke transition needs its OWN audit line, so the row carries a durable on-row link for BOTH transitions (grant `audit_id` + grant `granted_at`; revoke `revoked_audit_id` + `revocation_reason` + `revoked_at`). Keeps "every consent transaction is independently auditable" literally true on the row. Record the variance in the ADR.

## Acceptance Criteria

Derived from epics.md §Story 2.7 (L1544–L1563); expanded for implementation precision. Source for AC1/AC2 = epic AC block 1; AC3 = block 2; AC4 = block 3.

1. **AC1 — `consent_records` table + two `pgEnum`s.** The table carries: `consent_id` (uuid PK, branded `ConsentId`, `gen_random_uuid()` default), `subject_id` (uuid, NOT NULL — the member-or-pre-member-applicant id; **NO FK, NO brand** — polymorphic, and the `members` table does not exist until Epic 3; see Dev Notes), `pariwar_id` (uuid, NOT NULL, branded `PariwarId`, RLS predicate column), `consent_type` (`pgEnum` `consent_type` — the 7 AC1 values), `consent_artifact_ref` (text, **nullable** — e.g. a `tc_version_id` or `clause_version_id`; null for consents with no versioned artifact such as `marketing`), `granted_at` (timestamptz NOT NULL, default `now()` — DB-authoritative §1.11), `revoked_at` (timestamptz, nullable), `granted_via_actor` (`pgEnum` `consent_granted_via` — `member_self | staff_assisted | inherited`), `consent_payload` (jsonb NOT NULL — context: checkbox text shown, locale at consent time, IP, user-agent), `audit_id` (uuid, nullable, FK → `audit_log_entries` — the GRANT-event audit line), plus the two variance columns `revocation_reason` (text, nullable) + `revoked_audit_id` (uuid, nullable, FK → `audit_log_entries` — the REVOKE-event audit line). DB columns snake_case; TS fields camelCase. Indexed on `(pariwar_id, subject_id, consent_type)` (the `consentExists` / `listConsents` lookup). Tenant-isolated RLS (NOT cross-readable — mirror `clause_versions` / `terms_and_conditions_versions`). Migration generated once + hand-supplemented (GRANT + FORCE RLS + the two `CREATE TYPE` enums + the two FKs), **never regenerated**.

2. **AC2 — Domain accessors (the epic's "API exposes …").** `recordConsent(db, input)` inserts a grant row (`consent_payload`, `granted_via_actor`, optional `consent_artifact_ref`, caller-supplied `auditId` + optional `consentId` for the consumer's audit-first path); `revokeConsent(db, input)` sets `revoked_at` (DB `now()` default), `revocation_reason`, `revoked_audit_id`; `listConsents(db, pariwarId, subjectId, opts?)` returns a subject's consents newest-first with optional `consentType` filter + Story 1.14 forced-pagination ceiling; `consentExists(db, pariwarId, subjectId, consentType, validAt?)` returns a boolean — the canonical query — where `validAt` defaults to **DB `now()`** (§1.11 DB-authoritative time, never an app-server clock) and the predicate is `granted_at <= validAt AND (revoked_at IS NULL OR validAt < revoked_at)`. A `resolveConsentById(db, pariwarId, consentId)` read backs the revoke guard. Every accessor takes explicit `pariwarId` (indexed predicate + cross-tenant defense-in-depth) alongside RLS.

3. **AC3 — Revoke preserves history; the time-travel query honors it.** When `revokeConsent` is called: `revoked_at` is set, `revocation_reason` + `revoked_audit_id` are recorded, and the **row is NOT deleted** (historical proof preserved). Revoking an already-revoked consent throws a typed `ConsentStateError`; revoking a non-existent `consent_id` throws `ConsentNotFoundError`. Downstream `consentExists(...)` at a **current** timestamp returns false after revocation; at a **pre-revocation** timestamp returns true. A re-grant after revocation is a NEW `recordConsent` row (new `consent_id`) — there is no unique constraint on `(subject_id, consent_type)`; multiple rows over time are expected, and `consentExists` resolves the one valid at the queried instant. (This is the AC2/AC3 crux — test it explicitly: grant→revoke→consentExists at pre/post timestamps; grant→revoke→re-grant→consentExists true again.)

4. **AC4 — Full-provenance, single-touch primitive (epic AC3).** Every consent is queryable with full provenance from any later audit context: which artifact (`consent_artifact_ref`), what checkbox text + locale (`consent_payload`), how it was granted (`granted_via_actor`), when granted/revoked (`granted_at`/`revoked_at`), and the audit lines on both transitions (`audit_id` / `revoked_audit_id`). A future Epic 6 claim-time DPDPA flow records consent by touching **only** `recordConsent` (no bespoke consent table elsewhere). 2.7 ships the primitive; it does NOT itself record any real consent.

5. **AC5 — RLS tenant-isolated (NOT cross-readable) + migration discipline.** A `consent-records-rls.ts` policy file mirrors `terms-and-conditions-versions-rls.ts`: tenant-isolation SELECT + write (`for: 'all'` — insert on grant, update on revoke; NO delete), using the exact fail-closed `pariwar_id = nullif(current_setting('app.pariwar_id', true), '')::uuid` construct. Migration `0017_*.sql` is generated ONCE then hand-supplemented (GRANT SELECT, INSERT, UPDATE — **NOT DELETE**, consent rows are never row-deleted; FORCE ROW LEVEL SECURITY; the two `CREATE TYPE`s + two FKs are drizzle-kit-emitted — confirm present) with the `⚠ DO NOT REGENERATE` banner. `db:check` passes (snapshot tracks the new table + 2 policies + 2 enums).

6. **AC6 — Contracts DTOs + dual lockstep (no endpoint).** `@twt/contracts` exposes `ConsentRecordResponse`, `RecordConsentRequest`, `RevokeConsentRequest`, `ConsentTypeSchema` (`z.enum`), `ConsentGrantedViaSchema` (`z.enum`). A contracts test lockstep-asserts BOTH `z.enum`s against their domain `pgEnum.enumValues` (mirror the `BenefitMechanism` / `TcLegalReviewStatus` discipline; contracts→domain is the legal import direction). Contracts MUST NOT import `@twt/domain` (browser-bundle constraint). **No `.openapi()` registration and no `openapi/v1.yaml` change** — there are no endpoints in this story; the DTOs exist for Epic 3/6 to import and for the lockstep guard. Do NOT add speculative OpenAPI paths.

7. **AC7 — Scope fences hold (the primitive stays a primitive).** No `apps/api` module, no `apps/admin`/`apps/public` change, no new RBAC keys / catalog bump, no domain-event emission, no i18n namespace, no friction-budget/microcopy/pii-scrape touch. An ADR (next number after ADR-0023 = **ADR-0024**) records: the consent-registry shape, the two `pgEnum`+lockstep choices, the `revocation_reason` + `revoked_audit_id` variance (vs the epic's literal column list), the `subject_id` polymorphic-no-FK rationale, the RLS-tenant-isolated posture, the "row is never deleted — revoke is a mutate" append-mutate invariant, and the domain+contracts-only scope (consumers own routes + audit-or-throw). `adr-index.md` counts updated; ratification recorded **un-attested-pending** (no fabricated trustee session).

### `subject_id` — polymorphic, NO FK, NO brand (the one real shape decision)
`subject_id` is "member OR pre-member applicant id" (epics.md L1554). It is **not** FK-able: the `members` table is built in Epic 3 (it does not exist yet), and a pre-member applicant id is minted at signup-initiate before any member row exists. So `subject_id` is a plain `uuid NOT NULL` with **no FK** and **no branded type** (a brand implies a single owning entity; this column is intentionally polymorphic). Document this in the schema header. Referential integrity for the subject is the consumer's concern (Epic 3 ties applicant→member). Do NOT introduce a `members` FK "to be safe" — it will not compile (no table) and would wrongly forbid pre-member consents.

### `consent_type` + `consent_granted_via` — two `pgEnum`s, both lockstep-guarded
Both are `pgEnum` (not raw text, not a CHECK) so each yields a `CREATE TYPE` in the migration and a DB-level guard, exactly like `tc_legal_review_status` / `benefit_mechanism`. `@twt/domain` must NOT import `@twt/contracts` (turbo cycle), so the literal lists are duplicated in the `z.enum`s and the **contracts test** is the anti-drift guard (contracts→domain is the legal import direction). Seed `consent_type` with the **7 AC1 values only** — `tc_acceptance`, `dpdpa_data_processing`, `dpdpa_data_sharing`, `marketing`, `medical_disclosure_ack`, `nominee_share_split`, `claim_time_dpdpa`. Later epics add their own values (`whatsapp_opt_in` Epic 5, `sahyog_vivran_publication`/`in_memoriam_listing` Epic 11b, `module_lead_handoff` Epic 12) via additive `ALTER TYPE … ADD VALUE` migrations in those stories — do NOT seed them here (the 2.6/RBAC "seed exactly what the artifacts reference, do not manufacture for surfaces that don't exist" discipline).

### `consentExists` — the canonical query, on DB-authoritative time
`consentExists(subject, type, validAt?)` is the whole point of the registry (epics.md L1555: "did this member have valid X consent at time Y?"). It mirrors `getEffectiveTc`'s effective-window construction: `validAt` defaults to DB `now()` (NOT an app clock — §1.11), predicate `granted_at <= validAt AND (revoked_at IS NULL OR validAt < revoked_at)`. Return a boolean (`SELECT 1 … LIMIT 1` / `EXISTS`), not the row. There is **no unique constraint** on `(subject, type)`: grant→revoke→re-grant produces multiple rows over time, and the window predicate resolves the one valid at `validAt`. This is exactly why revoke must NOT delete — a deleted row would make a pre-revocation `consentExists(... , pastTimestamp)` wrongly return false (AC3 explicitly requires it return true).

### Revoke is a mutate, never a delete (compliance invariant) + the two variance columns
Revocation sets `revoked_at` + `revocation_reason` + `revoked_audit_id` on the existing row; the row is **never deleted** (DPDPA "historical proof preserved", epics.md L1559). Hence the migration GRANT is `SELECT, INSERT, UPDATE` — **no DELETE** (mirror the `terms_and_conditions_versions` grant rationale). The two revoke-side columns (`revocation_reason`, `revoked_audit_id`) are a deliberate variance from the epic's literal column list (which names only `audit_id` + `revoked_at`): they make the row symmetric — grant carries `audit_id`+`granted_at`, revoke carries `revoked_audit_id`+`revocation_reason`+`revoked_at` — so BOTH transitions have a durable on-row audit link ("every consent transaction is independently auditable", epics.md L1550). Record the variance in ADR-0024 (mirror how 2.6's link-table variance was ADR-recorded).

### Audit linkage — a CONSUMER obligation, not built here (and why the domain tests pass `null`)
The `audit_id`/`revoked_audit_id` FKs point at the Story 1.10 hash-chain (`audit.writeAuditEntry(servicePool, …)`). The audit-or-throw orchestration — write the audit line FIRST (it needs the actor session), then thread its id into `recordConsent`/`revokeConsent`, throw → scope tx rolls back → no consent without an audit line — is the **consumer route's** job (Epic 3 signup, Epic 6 claim). 2.7 has no route and no actor session, so its accessors merely *accept* a caller-supplied `auditId`/`revokedAuditId` (mirror `createTcVersion`'s caller-supplied `auditId`). The domain integration tests pass `null` for these (the columns are nullable; a random non-null uuid would violate the FK, and writing a real chained audit line via `servicePool` would commit on a separate connection while the test's `BEGIN/ROLLBACK` tx discards the consent row — a mismatch). The FK guarantees referential integrity structurally; the audit-or-throw behavior is tested where it lives, in the consumer epic. **Flag this loudly for Epic 3/6**: they MUST write the audit line first and thread the id, or the consent row will carry `audit_id = NULL` (a compliance gap the FK alone cannot force).

### RLS posture — tenant-isolated, NOT cross-readable
Mirror `terms-and-conditions-versions-rls.ts` / `clause-versions-rls.ts` (ADR-0020 rationale), NOT the `pariwar_passport` cross-readable carve-out. Consent is per-tenant; a member's consents are read under that Pariwar's `app.pariwar_id`. Use the exact fail-closed `pariwar_id = nullif(current_setting('app.pariwar_id', true), '')::uuid` construct (unset scope → 0 rows). `for: 'all'` covers the grant INSERT + the revoke UPDATE; `withCheck` defends an INSERT/UPDATE from creating/moving a row into another tenant.

### `consent_payload` — internal-only jsonb (PII note)
`consent_payload` holds operational context (checkbox text shown, locale, IP, user-agent) — it is **never publicly rendered** (no public surface in this story; the consent registry is audit/admin-queried). It is not a Tier-1 PII column under AR-12 (which lists mobile/email/Aadhaar/DOB/address/nominee-bank/medical), so it is stored clear jsonb. If a future consumer ever places Tier-1 PII into the payload, Story 1.5 envelope-encryption applies — but checkbox text / locale / IP / UA do not warrant it. Keep the jsonb permissive but type it (`ConsentPayload`) so consumers populate it consistently.

### No events, no idempotency, no surface (scope fences)
- **No domain event.** 2.7 records to `consent_records` + audit only. Consumers emit their own events that *reference* a `consent_id` (e.g. Epic 3 `medical.disclosed` referencing the `medical_disclosure_ack` consent, epics.md L1714) — that is their concern, not this primitive's.
- **No idempotency.** Re-recording is a new row by design (AC3). Idempotency keys (Story 1.12) are the consumer route's concern if it needs them.
- **No HTTP / RBAC / OpenAPI / i18n / seed.** See the mirror table. The `RevokeConsentRequest`/`RecordConsentRequest` DTOs are defined for Epic 3/6 to import; they are NOT wired to any route here.

### Review Findings

Code review run 2026-06-24 — 3 parallel layers (Blind Hunter · Edge Case Hunter · Acceptance Auditor). 3 patch · 10 deferred · 11 dismissed.

- [x] [Review][Patch] **P1 — revokeConsent TOCTOU: concurrent double-revoke bypasses ConsentStateError; 0-row UPDATE throws wrong error type** [`packages/domain/src/consent/write.ts:139-166`] — `resolveConsentById` (SELECT) and the `UPDATE` are two separate DB round-trips. Two concurrent revokeConsent calls both read `revokedAt: null`, both pass the guard, and the second UPDATE silently overwrites the first reason instead of throwing `ConsentStateError`. Additionally, if the UPDATE returns 0 rows (RLS or race), the code throws a generic `Error('[revokeConsent] update returned no row')` instead of a typed error. Fix: add `and(isNull(consentRecords.revokedAt))` to the UPDATE WHERE clause; if 0 rows returned, re-read the row to throw `ConsentStateError` (row found, already revoked) vs. `ConsentNotFoundError` (row gone — impossible under current grants but defensive).
- [x] [Review][Patch] **P2 — listConsents negative `limit` bypasses the 200-row cap** [`packages/domain/src/consent/read.ts:98`] — `Math.min(opts.limit ?? 50, 200)` does not clamp the lower bound. `opts.limit = -1` yields `-1`; Postgres treats `LIMIT -1` as no limit, returning all rows. Fix: `Math.max(1, Math.min(opts.limit ?? 50, 200))`.
- [x] [Review][Patch] **P3 — `seedConsentRecord` can produce semantically invalid rows when `revokedAt` is set without `grantedAt`** [`packages/domain/tests/integration/_helpers.ts:253`] — If a future test passes `{ revokedAt: new Date('2020-01-01') }` without specifying `grantedAt`, the DB sets `grantedAt = now()` (2026), creating a row where `revokedAt < grantedAt` — an invalid row that would corrupt time-travel assertions. Fix: add a guard: `if (opts.revokedAt && !opts.grantedAt) throw new Error('seedConsentRecord: revokedAt without grantedAt produces an invalid row')`.

- [x] [Review][Defer] **W1 — listConsents shows future-dated not-yet-effective grants** [`packages/domain/src/consent/read.ts:89-111`] — deferred, pre-existing; a row with `grantedAt` in the future (only reachable via explicit future-dating) passes `isNull(revokedAt)` and appears in results as "active" even though the consent hasn't taken effect. `consentExists` handles this correctly via the `granted_at <= validAt` lower bound. No current consumer produces future-dated grants.
- [x] [Review][Defer] **W2 — `validAt` exact-boundary is exclusive: consent invalid AT the revocation instant** [`packages/domain/src/consent/read.ts:44-51`] — deferred, intentional by design; `gt(revokedAt, validAt)` means `validAt === revokedAt` returns false. The spec says "at a pre-revocation timestamp returns true" without specifying the boundary. If "at the revocation instant" should be valid, change to `gte`.
- [x] [Review][Defer] **W3 — No conditional `consentArtifactRef` validation per `consentType`** [`packages/contracts/src/consent/consent-record.ts:97-105`] — deferred, consumer-route concern; `RecordConsentRequest` accepts any non-empty string or omits the field, for all consent types. For `tc_acceptance`/DPDPA, the ref presumably carries a T&C version ID, but nothing enforces format. The primitive trusts its consumer; Epic 3/6 routes own per-type validation.
- [x] [Review][Defer] **W4 — `inherited` grant channel has no domain-level authorization guard** [`packages/domain/src/consent/write.ts`] — deferred, consumer-route concern; `grantedViaActor: 'inherited'` is accepted without any check on caller authority. The Epic 3/6 route owns the actor session and RBAC — flagged for those implementers.
- [x] [Review][Defer] **W5 — FOR ALL write policy makes the SELECT tenant-isolation policy a redundant orphan** [`packages/domain/src/policies/consent-records-rls.ts:42-51`] — deferred, intentional per spec pattern; PERMISSIVE FOR ALL already covers SELECT. The dedicated SELECT policy is technically redundant today but acts as a safety net if the write policy is ever narrowed. Consistent with the clause_versions precedent.
- [x] [Review][Defer] **W6 — DO NOT REGENERATE banner is advisory-only; no toolchain enforcement** [`packages/domain/migrations/0017_bumpy_norman_osborn.sql:1`] — deferred, pre-existing pattern; `pnpm --filter @twt/domain db:generate` is not blocked from creating a new migration tag. Pre-existing pattern from migrations 0014/0015/0016.
- [x] [Review][Defer] **W7 — `revokeConsent` does not guard empty-string reason at the domain level** [`packages/domain/src/consent/write.ts:133`] — deferred, HTTP boundary guards it; `RevokeConsentInput.reason: string` accepts `''`. The consumer contract (`RevokeConsentRequest.reason: z.string().min(1)`) prevents an empty reason at the HTTP boundary. Direct domain callers are unguarded but currently there are none.
- [x] [Review][Defer] **W8 — No co-constraint: `revocationReason`/`revokedAuditId` nullable even when `revokedAt` is set** [`packages/domain/src/schema/consent_records.ts`] — deferred, domain write path enforces it; both columns are nullable at the schema level, so a direct DB write could leave a revoked row without a reason. The `revokeConsent` write path always sets reason (required param). A `.refine()` co-constraint would make this explicit at the DTO level.
- [x] [Review][Defer] **W9 — WireProjection assignability is one-directional** [`packages/contracts/tests/consent.test.ts:48`] — deferred, low severity; test asserts `WireProjection extends ConsentRecordResponseType` but not the reverse. A future DTO field removal would be uncaught by this test. The enum lockstep and `.strict()` test provide substantial coverage. Verify if the T&C precedent also omits the reverse direction.
- [x] [Review][Defer] **W10 — `listConsents` default/cap are magic numbers without named constants** [`packages/domain/src/consent/read.ts:98`] — deferred, style concern; `50` and `200` are inline with no reference to Story 1.14.
