# Story 5.8: Pariwar-Degraded-Mode Cycle-Open SMS Bridge

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Pariwar undergoing a degraded-mode event (in-app push infrastructure down, WA Business API unavailable system-wide, or a trustee-declared "treat all cycle-open as critical"),
I want a cycle-open SMS bridge that bypasses the normal cost-optimization layer and delivers cycle-open alerts to all eligible members via SMS,
so that no member misses a cycle-open alert during infrastructure degradation.

## Acceptance Criteria

> **Scope framing (read before the ACs — this is the load-bearing decision).** This is a `[GOVERNANCE]` story with a real admin **surface** (like Story 5.3's "config table + minimal admin form"), NOT a pure-policy story like 5.7. Three facts fix its shape:
>
> 1. **The degraded-mode declaration IS this story's own artifact** — the AC explicitly requires trustees to *declare degraded mode via admin UI* and records six fields. Unlike Story 5.7's cost-optimization TOGGLE (deferred to Epic 10's FR-58C subsystem because that flag substrate lands there), the degraded-mode *declaration table + declare/revoke admin surface + permission + audit + banner* are built **here** — exactly as Story 5.3 built the WA config table + minimal admin form in-story.
> 2. **`dispatch.ts` explicitly RESERVES the degraded-mode bridge as an external WRAPPER** — *"cost-optimization (5.7) and the degraded-mode SMS bridge (5.8) WRAP `dispatch`, they do not live inside it"* (`dispatch.ts` L4-7). So the **bypass DECISION** is a pure primitive (mirror `cost-optimization.ts`), composed by the future live fan-out — never code inside `dispatch`.
> 3. **There is still NO live `dispatch` call site** ([[project_channels_no_live_dispatch_yet]]). So the **live application** of the bridge — the actual "SMS fires for every eligible member" enumeration + fan-out during a real dispatch — is **deferred to the story that first drives a live fan-out**, exactly as Story 5.7 deferred its live suppression application. This story builds the declaration substrate + the pure bypass-decision primitive + the admin surface + the composition read-seam, shaped so the future live wrapper is thin.
>
> Net: build the **declaration persistence + admin declare/revoke/read surface + permission + audit + banner** (in-story, real, mirroring 5.3) **AND** the **pure bypass-decision primitive + composition read-seam** (mirroring 5.7's `evaluateCostOptimization` + `resolveCostOptimizationToggle`). **Defer** only the live fan-out application (member enumeration + the wrap-`dispatch` send). Do **NOT** change the frozen `dispatch` / `ChannelProvider` / `CANONICAL_CHANNEL_LADDER` / `DeliveryResolver` / `render.ts` / `LifecycleSuppressionHook` surfaces, and do **NOT** add a live `dispatch` call site.

**AC1 — degraded-mode declaration persistence (AR-20; the six recorded fields):**
1. A new tenant-isolated table `pariwar_degraded_mode_declarations` (migration `0050`, hand-authored — **do NOT `db:generate`**, see Dev Notes) records a declaration with **all six AC fields**: `pariwar_id` (tenant/RLS key), `mode` (v1 CHECK `IN ('cycle_open_sms_bridge')` — extensible), `effective_from` (timestamptz), `expires_at` (timestamptz **nullable** — null ⇒ open-ended until manual revocation), `declared_by_actor` (uuid, nullable = system/seed), `reason` (text). Add `id` (uuid PK `gen_random_uuid()`), `revoked_at` + `revoked_by_actor` (both nullable — manual revocation is a state transition, NOT a row delete), and `created_at`. **Standard inline tenant-isolation RLS** (mirror migration `0038_pariwar-wa-config` / `0037_member-device-tokens`: `pariwar_id = nullif(current_setting('app.pariwar_id', true), '')::uuid`, `ENABLE`+`FORCE` RLS, `GRANT SELECT,INSERT,UPDATE,DELETE TO twt_app`) — a Pariwar's degraded-mode state must NOT be cross-tenant readable. **No** `pariwar_passport` public carve-out.
2. **"Active" is a computed predicate, never a stored boolean**: a declaration is active for `pariwar_id` at instant `at` **iff** `revoked_at IS NULL AND effective_from <= at AND (expires_at IS NULL OR expires_at > at)`. **A Pariwar has at most ONE active declaration at a time** — degraded mode is a single governance state, not a stack. `declareDegradedMode(db, { pariwarId, ... })`, within **one transaction on `db`**: (a) **`SELECT pg_advisory_xact_lock(hashtext(pariwarId))`** first (mirror the existing advisory-lock convention in `packages/domain/src/idempotency/keyed-store.ts` and `packages/domain/src/device-token/registration.ts` — both use `hashtext(key)`; do not introduce a different hashing function) — a transaction-scoped advisory lock keyed on `pariwarId`, serializing concurrent `declareDegradedMode` calls for the **same** Pariwar (auto-released at commit/rollback; a different Pariwar's declare is never blocked); (b) **auto-revokes any currently-active declaration for that `pariwarId`** (`revokedByActor = declaredByActor`, `at` = the new declaration's `effectiveFrom`); then (c) inserts the new row. **The application transaction (auto-revoke + advisory lock) is the canonical enforcement of single-active-per-Pariwar — not a database constraint.** A Postgres `EXCLUDE USING gist` range-overlap constraint could express this, but was deliberately NOT added: it would enforce a *stronger* rule ("no overlapping scheduled windows, ever, for any reason") than this story defines, and the app-level UPDATE-then-INSERT already implements the actual intended behavior (superseding, not rejecting, an overlapping declare). If race protection beyond the advisory lock is ever needed, extend it (e.g. also serialize revokes) — do not introduce a temporal exclusion constraint. `revokeDegradedMode(db, { declarationId, revokedByActor, at })` (sets `revoked_at`/`revoked_by_actor`; idempotent — revoking an already-revoked/expired row is a no-op, never an error) revokes **only** the row it's given — it does NOT search for or revoke any other declaration. `getActiveDegradedMode(db, pariwarId, at): Promise<Row | null>` returns the single active declaration (or null) — with the auto-revoke-on-declare invariant in place, "most recent" and "the" active declaration are always the same row, so revoking the currently-displayed declaration can never silently fall back to an older still-active one. Provide these pure-domain accessors in `packages/domain/src/degraded-mode/`, mirroring `channel-config/wa-config.ts`'s accessor posture (transport-free, runs on the passed scoped `Db`, RLS enforces the tenant match — signature carries **no** `pariwarId` on `revoke`/reads beyond what the query needs; RLS is the boundary, matching `getMemberStateAt`'s RLS-only convention).

**AC2 — the pure bypass-decision primitive (AR-20 + Story 5.1 policy-agnostic dispatcher + Story 5.7 cost-optimization):**
3. A pure, deterministically-testable **bypass-decision primitive** `packages/channels/src/degraded-mode.ts` (mirror the shape of `cost-optimization.ts`) evaluates: given `{ category: AlertCategory, degradedModeActive: boolean }`, does a cycle-open alert bypass the cost-optimization layer and bridge to SMS? Decision order: (1) `!degradedModeActive` → `{ bridged: false, reason: 'no_active_declaration' }`; (2) `category !== 'alert_published'` (cycle-open = `alert_published`, per AC + `alert.ts` enum) → `{ bridged: false, reason: 'category_not_cycle_open' }`; else → `{ bridged: true, channels: [...DEGRADED_MODE_BRIDGE_CHANNELS], reason }`. **Pure function** — every impure input is injected (no clock/DB/IO of its own — `degradedModeActive` is resolved by the composition seam, exactly as 5.7 injects `toggleEnabled`) — no live `dispatch` call site (canonical statement: Dev Notes "Load-bearing constraints").
4. The bridged `channels` are **exactly `['sms']`** (a `DEGRADED_MODE_BRIDGE_CHANNELS = ['sms'] as const` tuple). The bridge is a **direct-to-SMS** path: when bridged, SMS is force-sent to **every eligible member regardless of in-app engagement AND regardless of the normal channel-tier fallback ladder** (it does not wait for push/WA to fail — that is the whole point of a "bridge" during degradation). The primitive **never re-sequences** `CANONICAL_CHANNEL_LADDER`, **never changes** `dispatch`'s public shape, and is **distinct from bulk-alert SMS** (banned per RA-29) — this is the AR-20 cycle-open + time-critical carve-out, not general bulk SMS.
5. **Composition with cost-optimization (5.7) is a FUTURE-fan-out concern — this story owns neither the call nor the ordering.** The degraded-mode primitive is *designed so that* the future live fan-out composes it **ahead of** `evaluateCostOptimization`: when `evaluateDegradedModeBridge` returns `bridged: true`, that future live fan-out bypasses cost-optimization suppression for that alert (`epics.md` L4272: *"Story 5.7 cost-optimization persists during disaster mode … but Story 5.8 degraded-mode bridge remains available for trustee declaration if infrastructure is also degraded"*). **This story does NOT perform that composition and does NOT invoke either primitive** — `evaluateDegradedModeBridge` neither calls nor imports `evaluateCostOptimization`, and 5.8 owns no ordering between them. Both stay pure and independently testable (5.7 left this seam clean on purpose — 5.7 Dev Notes "Story 5.8 interaction"). The only obligation here is that the primitive's *shape* (a standalone `bridged` decision) lets the future fan-out sequence them; wiring that sequence is the live-fan-out story's job.

- [x] [Review][Patch] **`revokeDegradedMode` returns `void`, so the `revoke` handler audits a `pariwar.degraded_mode.revoked` line unconditionally — even when zero rows were actually updated** (a stale/nonexistent/already-revoked/cross-tenant `id`). If additional race protection is ever needed beyond the transaction-scoped advisory lock, extend the locking (e.g. also serialize revokes against the same lock key) — do not reach for a temporal exclusion constraint as the fix.
