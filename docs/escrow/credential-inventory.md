# Credential Inventory

The canonical list of credential domains under the escrow framework. Authority: PRD §9.1.1 (the seven credential domains), AR-67 (framework commitment), architecture §2.10a (audit independence invariant — envelope-class separation), architecture §5.9 (high-sensitivity tier), Story 0.2 (the framework + inventory commitment).

**This file is the structural anchor for the §2.10a invariant.** Every row carries an explicit `envelope_class`; the sealing-procedure runbook (§1 Prerequisites) verifies that proposed sealings honor the class assignment recorded here. A sealing operation that proposes a different `envelope_class` than the row commits is a P0 framework violation and MUST be aborted; raise the gap as a `.decision-log.md` `[CONTINUITY]` entry.

## Inventory schema

Every row records the following columns:

- **Credential class** — the named credential (matches the `credential_class` field of the envelope template).
- **PRD §9.1.1 domain** — which of the seven PRD-named domains this row belongs to (or `out-of-scope-for-§9.1.1` for envelope classes the framework tracks beyond the seven, such as KEK roots and audit-mirror credentials).
- **Owning Story** — the Story (epic-story-name) that introduces or operationally instantiates this credential. The re-evaluation trigger for `pending-system-availability` rows is the owning Story's closure.
- **Envelope class** — one of `prod-credential` | `audit-mirror-credential` | `high-sensitivity-tier-credential`. **Load-bearing per §2.10a.**
- **Availability status** — one of:
  - `sealable-now` — the credential exists and can be sealed today; awaiting Trustee Panel sealing mechanism selection + sealing event.
  - `sealed` — the envelope has been sealed; ledger has the sealing row; custodial location holds the envelope.
  - `pending-system-availability` — the credential does not yet exist because the owning Story has not closed; the envelope is reserved but not yet sealable.
  - `pending-separation-mechanism` — applies only to `audit-mirror-credential` and `high-sensitivity-tier-credential` rows. Pre-ADR sealing of these envelope classes is FORBIDDEN per the `README.md` "Audit independence invariant" pre-ADR sealing rule + the Solo-Builder credential-exposure structural concern (Story 0.2 review Decision 3). These rows wait for: (a) credential-escrow-mechanism ADR landing, AND (b) Story 1.10 closure (provisions the audit-mirror chain) + Story 0.6 closure (provides a non-Solo-Builder principal for credential retrieval), as applicable to the envelope class.
  - `pending-rotation-completion` — applies during the window between rotation start (per `docs/runbooks/secret-rotation.md` execution) and re-seal completion. The envelope is operationally stale; the re-seal log entry will flip it back to `sealed`.
  - `deferred-with-ADR` — the credential domain has no current concrete instances and won't until a contractual or regulatory event; the deferral rationale is recorded.
  - `pending-task-7-sealing-event` — the substrate (Terraform IaC + Secret Manager secret) has landed at Story closure but the substantive sealing event requires Story 0.2 Task 7 trustee execution after live provisioning.

Closure-language precision per `[[feedback_closure_language_precision]]`: never collapse `pending-system-availability`, `pending-separation-mechanism`, or `pending-rotation-completion` with `sealed`. Each carries a distinct re-evaluation trigger.
- **Envelope reference** — the `envelope_id` from `_envelope-template.md` once sealed, OR the owning Story / contractual-event trigger that will instantiate the credential.
- **Re-seal trigger** — the architectural / contractual source of the rotation event that will cause re-seal.
- **Last-seal date** — the date the envelope was last sealed (blank for `pending-system-availability` and `deferred-with-ADR`).
- **Notes** — cross-references, caveats, or §2.10a-related discipline notes.

## Re-evaluation cadence

Per `README.md` "Review cadence", this inventory is reviewed at the same cadence as the threat-actor inventory (architecture §2.1) and the data-class retention matrix (§2.12). The review confirms:

- Every `pending-system-availability` row's owning Story is still in scope (not removed by sprint correct-course; not renumbered).
- Every `sealable-now` row's credential still exists operationally (not deprecated by substrate change).
- Every `sealed` row's last-seal date is within the rotation cadence for that credential class.
- Every `envelope_class` assignment still preserves §2.10a (no row silently demoted from `audit-mirror-credential` to `prod-credential`).
- No row has drifted between this inventory and `escrow-ledger.md` (per `README.md` "Ledger-vs-inventory reconciliation").

**Substrate-pivot trigger.** A substrate pivot (e.g., Cloudflare → self-hosted WAF per architecture §5.8a; Dokploy → K8s per FR-62; bank provider replacement under Story 9.2) MUST trigger affected inventory rows' re-evaluation within **10 business days** of the pivot decision being recorded in `.decision-log.md`. The re-evaluation:

- Re-assigns `Credential class` to the post-pivot credential identity (e.g., from `cloudflare-account-admin` to `self-hosted-waf-admin`).
- Re-confirms `Envelope class` against §2.10a (pivots that change trust boundaries may flip a row's class).
- Re-seals any `sealed` row whose underlying credential changed at the pivot — old envelope invalidated; new envelope sealed per the sealing-procedure re-seal path.
- Records the re-evaluation in `escrow-ledger.md`'s "Periodic re-attestation log" with `Drift findings` = "substrate pivot per <decision-log entry>".

The review event itself is logged in `escrow-ledger.md`'s "Periodic re-attestation log" section.
