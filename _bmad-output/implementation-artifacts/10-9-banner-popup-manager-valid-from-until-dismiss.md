# Story 10.9: Banner/Popup Manager — Valid-From/Until + Dismiss `[SURFACE]`

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Pariwar admin or trustee surfacing time-bounded communications (e.g. a Niyamavali amendment notice, a system maintenance window, an urgent helpline redirect),
I want a banner/popup manager with valid-from/until windows + per-member dismiss state,
so that timely messages reach members inside the app without permanent UI clutter, and no member is ever trapped by an undismissable surface.

## Scope Boundary (read first — prevents over-build AND under-build)

**10.9 is the SECOND `[SURFACE]` in the Epic-10 "authored member-facing copy" family, and it is deliberately LIGHTER than 10.5.** Story 10.5 (News/Blog) built the pattern you are following: a **mutable-`status` content table** (NOT event-derived-state), a thin domain workflow module, ONE RBAC key, a tone-review gate at the publish moment, an admin authoring console, and a member-facing read. **Read `_bmad-output/implementation-artifacts/10-5-news-blog-dual-surface-*.md` before writing a line** — 10.9 reuses its shape almost verbatim and inherits its Decision 1 (mutable column) wholesale and Decision 4's **audience seam pattern** (NOT its literal `public` polarity — 10.5's `audience.ts` resolves `public` to an *empty dispatch list*; 10.9's Decision 4 resolves `public` to `true`, since this is a read-time visibility predicate, not a dispatch resolver — see Decision 4 below).

**Three things 10.5 needed that 10.9 does NOT — do not build them:**

1. **NO pg-boss scheduler, NO worker, NO `QUEUE_NAMES` entry.** 10.5 needed a delayed publish job because "publish" is an event that must *fire*. A banner's activation and auto-archive are **pure read-time window predicates** over `valid_from`/`valid_until` — a published banner becomes visible when the clock passes `valid_from` and disappears when it passes `valid_until`, with **no job, no transition, no writer**. If you find yourself enqueuing anything, stop.
2. **NO channel dispatch, NO `alert_published`, NO `fanOutAlertToMembers`, NO notification of any kind.** The epic AC is explicit: *"Story 5.1 channel dispatcher (**banners are in-app, not channel-dispatched**)"*. There is therefore **no crypto-boundary concern** here (the 10.4/10.5 "fan-out belongs in apps/jobs" lesson does not apply — nothing fans out). `apps/jobs` is **untouched by this story**.
3. **NO `apps/public` surface.** FR-58B is an **in-app** manager. The public/`<NoticeboardStrip>` consumption of this data is **Story 11a.5's** job (`epics.md:3782` — *"the component consumes Story 10.9 banner/popup data; respects tier visibility"*). 10.9 ships the data + the member-app render; 11a.5 later reads the same rows for the public strip. Do not build a public page.

**What 10.9 adds that 10.5 did not have:** a **per-member dismissal record** (the first per-member acknowledgement table in the codebase — `pool-onboarding`'s tutorial outcome is audit-only + client-local, not a durable per-member row), and a **deterministic collision resolver** that closes a PRD gap the adversarial review flagged as unspecified (`prds/.../review-adversarial.md:238`).

## Acceptance Criteria

**AC1 — The banner data model + the admin authoring surface.**
Given FR-58B + Story 1.8 RBAC,
When the banner/popup manager is implemented,
Then a `banners` model exists (NEW migration `0090` + `schema/banners.ts`) carrying bilingual `title`/`body`/`title_hi`/`body_hi`, `audience_scope` (`public | members-all | state | role | cohort`) + `audience_scope_value`, `valid_from` + `valid_until` (**both NOT NULL**, with a `CHECK (valid_until > valid_from)`), `display_mode` (`banner | popup`), `dismissible`, `display_once_per_member`, `severity` (`info | warning | critical`), `revision` (**`NOT NULL DEFAULT 1` — revisions start at 1, never 0**), `status` (`draft | published | retracted`), `created_by_actor_id`, the three tone-signoff columns, `published_at`, `retracted_at`, `pariwar_id` (RLS) and a `(pariwar_id, status, valid_from)` index;
And a holder of `banner.manage` opens `/p/:pariwarId/banners`, sees the Pariwar's banners (paginated, filterable by **derived** display state via a real `listBannersForPariwar` with `clampLimit`), creates + edits drafts, and publishes / retracts;
And **`status` is a plain mutable column, NOT event-derived-state** (Decision 1) — no projector, no state-writer trigger, no `events_log` stream, no CI state-invariant gate; every create / edit / publish / retract writes a Story 1.10 audit line with actor attribution (FR-58B: *"Audit-logged (publish, edit, retract)"*);
And a pure `nextBannerStatus(status, action)` reducer defines the legal transitions (`draft --publish--> published`, `published --retract--> retracted`; `draft --retract--> retracted` is legal as a discard; everything else illegal) and the API rejects an illegal transition with a typed **409 BEFORE any write** (the 10.4 `nextTicketState` / 10.5 `nextPostStatus` discipline).

**AC2 — Valid-from/until is a pure read-time window; the display state is DERIVED, never stored.**
Given a published banner with `valid_from` / `valid_until`,
When the member surface and the admin list read it,
Then visibility is computed **entirely at read time** — `status = 'published' ∧ valid_from <= now ∧ valid_until > now` — with **no scheduler, no pg-boss job, no worker, and no state transition at activation or expiry** (a banner "auto-archives" by the clock passing `valid_until`, per FR-58B, not by anything running);
And a pure `deriveBannerDisplayState(row, now)` returns `draft | scheduled | live | expired | retracted` for the admin list/preview — a **derivation over stored fields**, never a persisted column (the [[project_yogdaan_status_derivation_convention]] discipline);
And `now` is **injected** into every derivation and read (no `new Date()` inside the pure functions) so the resolver is deterministic and unit-testable across window boundaries.

**AC3 — Per-member dismissal is durable, cross-device, and re-surfaces on update.**
Given a dismissible banner rendered to a member,
When the member dismisses it,
Then a `banner_dismissals` row is written under the member's RLS scope keyed `(pariwar_id, banner_id, member_id)` recording `dismissed_revision = banners.revision` at the moment of dismissal, `dismissal_kind = 'dismissed'`, and `dismissed_at` — persisted **server-side, not in MMKV** (a reinstall or a second device must not resurrect a dismissed banner);
And the member read suppresses a banner **iff** a dismissal row exists with `dismissed_revision >= banners.revision`; a banner whose **member-visible copy is later revised** (`revision` bumped — Decision 5) therefore **re-appears** for members who had dismissed the prior revision, which is exactly AC's *"dismissed banners don't re-appear **unless updated**"*;
And `display_once_per_member = true` records the same row with `dismissal_kind = 'shown'` on first render (the PRD's *"configurable display-once-per-member rule"*), so a display-once popup never renders twice — the two kinds share one table and one suppression predicate;
And the dismiss write is **idempotent** — a replayed dismiss for the same `(banner, member, revision)` is a clean no-op returning success, never a 500 or a duplicate row (upsert on the composite PK).

**AC4 — "No member trapped": a popup is always dismissible, structurally.**
Given the PRD's FR-58B consequence *"Popup has a dismiss action (no member trapped by an undismissable surface)"*,
When a banner is created or updated with `display_mode = 'popup'`,
Then `dismissible = false` is **rejected with a typed 422**, and the same rule is enforced as a DB `CHECK` constraint (`display_mode <> 'popup' OR dismissible`) so it cannot be bypassed by any write path — an undismissable popup is structurally impossible, not merely discouraged;
And a **non**-dismissible `banner` (`display_mode = 'banner' ∧ dismissible = false`) IS permitted — the UX spec's Pattern 9 explicitly allows a non-dismissible banner for blocking system state (`ux-design-specification.md:2417`), and it carries no dismiss affordance in the member render;
And a revert-sanity test proves the teeth: removing the domain guard flips a test, and removing the CHECK flips a live-DB test.

**AC5 — Deterministic collision resolution: at most one banner and one popup, replayably.**
Given the PRD's *"one at a time per surface"* and the adversarial review's flagged gap (collision between a maintenance banner and an urgent helpdesk redirect is unspecified),
When more than one banner is simultaneously visible to a member,
Then — reading *"one at a time per surface"* precisely — a surface means **≤1 `banner` AND ≤1 `popup`, which may be on screen SIMULTANEOUSLY**. The two display modes are resolved in **separate, independent lanes**: a winning popup does **not** suppress the banner, and a winning banner does **not** suppress the popup. "One at a time" bounds each mode, not the surface's total;
And a PURE `resolveVisibleBanners(candidates, now)` returns **at most one `banner` and at most one `popup`**, ordered within each lane by a **total, deterministic** comparator: `severity` (`critical ≻ warning ≻ info`), then `valid_from` **DESC** (the most recently activated wins), then `banner_id` **ASC** (the total tiebreak);
And the resolver is **replayable** — the same candidate set at the same `now` yields the same choice on every run; hash-map iteration order, array input order, clock ties, and parallel execution cannot vary the outcome (a CI test shuffles the input set N times and asserts an identical result — the Story 10.1 routing-determinism / Story 4.6 rule-order precedent);
And the admin editor **surfaces the VISIBILITY VERDICT**, not an overlap notice — developers reason in logic, admins reason in "will anyone see this?". When a draft's window overlaps an already-published banner of the same `display_mode` and audience, the editor renders a two-row comparison naming the current winner, this draft, and each one's resulting **Visible / Hidden** verdict:

| | Severity | Title | Verdict |
|---|---|---|---|
| **Current winner** | Critical | Maintenance window | **Visible** |
| **This draft** | Warning | Rule update | **Hidden** |

And when the draft loses, the warning states the consequence in those words — *"this banner will never be seen while 'Maintenance window' is live"* — plus the deciding rule (severity, then recency, then id) and the earliest instant the draft would become visible. It is a read-only warning, **not a block** — overlapping windows are legitimate;
And the verdict is computed by calling the SAME pure `resolveVisibleBanners` the server uses, with the draft spliced into the currently-published candidate set — never a second, re-implemented comparison.

**AC6 — Tone review (Story 2.2) gates publish; a copy revision re-binds it.**
Given the shipped pure `evaluateToneReviewGate` (`packages/domain/src/tone-review/gate.ts`, default-deny: absent / author-authored / wrong-resource sign-off → deny),
When a banner is published,
Then `publish` builds a `ToneReviewSignoff` (`reviewedBy` = the publishing actor, `resourceLocator = banner:<bannerId>`, `contentHash` = SHA-256 hex of the RFC-8785 `canonicalJsonStringify` of `{title, body, title_hi, body_hi}` — **never the raw copy**), injects it into the gate, and transitions to `published` **only if the gate allows**; a deny is a typed 409 with the status unchanged;
And the sign-off is persisted on the row (`tone_signoff_content_hash` / `tone_signoff_reviewed_at` / `tone_signoff_reviewed_by`) and its recording routes through the dedicated `ToneReviewAuditSink` (`tone_review.signoff`) — **not** the auth taxonomy, **no** raw copy in the audit line;
And because the gate is already default-deny on `reviewedBy === authoredBy`, **the non-author rule needs no separate identity check** — a single-actor Pariwar therefore cannot publish a banner, which is the same known, PO-ratified consequence 10.5 recorded (see Dev Notes);
And all four copy fields must be non-empty at publish (FR-58B/FR-68 Hindi + English variants) — a missing Hindi field → typed 422.

## Load-Bearing Decisions

Decisions 1, 2, 4 and 6 are **direct inheritances** from shipped, PO-ratified precedent (10.5 Decision 1, 10.5 Decision 4, the 10.3/10.4/10.5/10.8 RBAC deferral chain) — they are settled; implement to them. **Decisions 3 and 5 are NEW calls this story makes, and each closes a documented gap in the source artifacts** — they carry a firm recommendation and a rejected alternative, and should be confirmed at review if the PO wants to weigh in, but dev may proceed on the recommendation.

1. **Data model — a mutable `status` column + audit-logged transitions, NOT event-derived-state.** Identical reasoning to 10.5 Decision 1 and the same shape: a banner is **mutable authored content** with an admin workflow, not a legal/audit-critical lifecycle like a claim or a contribution, and the `[SURFACE]` label signals "don't stand up a new primitive." → a plain `status` pgEnum transitioned in the caller's scope tx, with every create/edit/publish/retract written to the Story 1.10 audit log. **No projector, no `app.*_state_writer` trigger, no CI state-invariant gate, no `events_log` stream, no `packages/events` registration.** *Rejected:* event-sourcing to match `helpdesk_tickets`/`alerts` — over-build for mutable content with no replay requirement.

2. **Valid-from/until is a READ-TIME predicate — there is no scheduler.** The strongest anti-over-build call in this story. 10.5 needed pg-boss because publishing *fires* a dispatch; a banner's activation is purely "is `now` inside the window", evaluated on every read. Adding a job to "activate" or "archive" a banner would introduce a second source of truth for visibility, a drift class (job missed → banner never appears), and an idempotency problem — all for zero behavioural gain. → **`apps/jobs` is untouched; `QUEUE_NAMES` gains nothing.** *Rejected:* a sweep job that flips `status` to `expired` — rejected; `expired` is a **derivation**, and a stored one would be wrong for exactly as long as the sweep lagged.

3. **NEW — collision resolution: a pure total-order precedence resolver returning at most one banner + one popup, in two independent lanes.** *"One at a time per surface"* bounds each **display mode**, not the surface's total: a member can legitimately see a banner and a popup at the same moment, and the resolver never lets one mode suppress the other. The PRD says *"one at a time per surface"* but never says **which** one, and `prds/prd-TWT-2026-05-22/review-adversarial.md:238` calls this out by name: *"collision behavior between a 'scheduled maintenance' banner and an 'urgent helpdesk redirect' banner not specified."* Leaving it to `ORDER BY` in a query would make the choice depend on plan/iteration order — non-replayable, and exactly the failure mode Story 10.1's routing-determinism AC and Story 4.6's rule-order AC exist to prevent. → **`severity` DESC (`critical ≻ warning ≻ info`), then `valid_from` DESC, then `banner_id` ASC**, as a PURE function over a candidate array, with a shuffled-input CI test. Severity first because an urgent helpline redirect must beat a maintenance notice; recency second because the newer of two equal-severity notices is the live one; `banner_id` last because a total order must never tie. *Rejected:* an explicit `priority` integer authored per banner — rejected as an extra authoring burden that admins would leave at the default, re-creating the tie; severity already carries the operator's urgency intent. **Note:** this `severity` precedence is an **eligibility/selection** order — do not confuse it with the niyamavali `precedence` field, which is *provenance* ([[project_niyamavali_precedence_is_provenance]]); different concept, same word.

4. **Audience is a PREDICATE with the same seam 10.5 shipped.** `members-all` → true; `public` → true — **members are always eligible to view banners targeted at `public`; Story 11a.5 later extends the same rows to unauthenticated users** (`public` widens who *else* can see a banner, it never narrows it away from members); `state`/`role`/`cohort` → **false** + a logged "audience selector not yet resolvable" note. The `members` table (`schema/members.ts`) carries only `state` (LIFECYCLE — *not* geography) and `pariwar_id`; fabricating a district/designation/cohort attribute now would collide with Epic-3 geo. A `state`/`role`/`cohort` banner is therefore accepted, tone-reviewed, listed in the admin console with an explicit "not yet targetable" indicator, and visible to nobody — the identical, deliberate, documented seam 10.5 shipped for dispatch, and it lights up for free when the selection primitive lands.

5. **NEW — one unified `updateBanner`, where the CONTENT HASH decides whether a re-review and a `revision` bump are required.** AC's *"dismissed banners don't re-appear unless updated"* only means something if copy can change after publish; but a copy change after a tone-review sign-off must not ride the old sign-off. Rather than two endpoints with a hand-drawn line between "copy" and "not copy", `updateBanner` recomputes the content hash over `{title, body, title_hi, body_hi}` and branches: **hash unchanged** (e.g. extending `valid_until`, flipping `display_once_per_member`) → apply, **no** re-review, **no** `revision` bump, dismissals stand; **hash changed** on a *published* banner → require a **fresh** non-author sign-off (gate → 409 without one), bump `revision`, and every prior dismissal stops suppressing. On a *draft*, copy edits are free (no sign-off exists yet). This makes the sign-off's content-binding do real work and makes the "unless updated" rule mechanical rather than judgemental. *Rejected:* forbidding copy edits post-publish and forcing retract-and-recreate — rejected because it strands the dismissal-invalidation rule with nothing to trigger it, and it loses the banner's identity (and its dismissal history) over a typo fix.

6. **RBAC — ONE `banner.manage` key, pariwar dimension, district_admin deferred.** The unbroken Epic-10 pattern (`helpdesk.create` 22→23, `helpdesk.respond` 23→24, `news.manage` 24→25, `member.export_roster` 25→26, `feature_flag.*` 26→27). Read and write fold under one key in v1 (no `banner.view` split — unlike 10.8's flags, there is no transparency property forcing the read to be broader than the write). *Rejected:* granting `district_admin` — it would be **inert**: a district-ceiling grant can never satisfy a pariwar-dimension check, and the ceiling check also forbids a district_admin from holding a pariwar-scoped grant ([[project_rbac_geo_scope_containment]]).

## Dev Notes

### The single most important fact: this is 10.5's shape minus the scheduler and minus dispatch

`apps/admin/src/modules/news-blog/`, `apps/api/src/modules/news-blog/`, `packages/domain/src/news-blog/`, `packages/contracts/src/news-blog/` and `packages/domain/src/schema/news_posts.ts` are your five templates. 10.9 is the same five-layer composition with a simpler workflow (`draft → published → retracted`, no `submitted`/`approved`/`scheduled`), a *derived* rather than *fired* activation, and **zero** notification wiring. If you find yourself writing a pg-boss worker, an `alert_published` builder, a `fanOutAlertToMembers` call, or a `packages/events` registration, you have left this story's scope.

### `valid_from`/`valid_until` — the two boundary conventions, pinned

`valid_from` is **inclusive** and `valid_until` is **exclusive** (`valid_from <= now < valid_until`). Both columns are `NOT NULL` — FR-58B's *"auto-archives"* is only meaningful with a mandatory end, and a nullable `valid_until` would silently create permanent clutter, which is exactly what this feature exists to prevent. `now` is injected everywhere; never call `new Date()` inside a pure derivation.

### Dismissal suppression: `dismissed_revision >= revision`, and why `revision` (not a timestamp)

`revision` starts at 1 and increments **only** when the member-visible copy hash changes (Decision 5). The suppression predicate is `dismissed_revision >= banners.revision`. This is deliberately **not** `dismissed_at >= updated_at`: `updated_at` moves on every write including non-copy ones, and a timestamp comparison is exposed to instance clock skew (the Story 10.8 Pass-2 finding: a DB-clock write path vs an app-clock read path resolved different versions for the same real instant). A monotonic integer compared against a stored integer has neither problem.

### The tone-review gate already gives you the non-author rule — do not add a second check

`evaluateToneReviewGate` (`packages/domain/src/tone-review/gate.ts`) is PURE and default-deny on three invariants: sign-off present, resource-bound, **and non-author** (`reviewedBy === authoredBy` → deny). 10.5 added an explicit author≠reviewer identity check because it also had a *reviewer assignment* step (`submitForReview` records a `reviewer_actor_id`, and `approve` locks to that actor). 10.9 has no assignment step and no `submitted` state, so the gate's own non-author invariant IS the rule. Build the sign-off, inject it, honour the deny.

**Known consequence, already ratified elsewhere:** because `banner.manage` is granted to `pariwar_admin` only, a **single-admin Pariwar cannot publish a banner** (nobody else can be the non-author reviewer). This is the identical consequence 10.5's review recorded and the PO deferred on 2026-07-30 (`media_comms` deliberately kept dormant). Do **not** "fix" it by weakening the gate or by minting a second role grant — if it comes up, it is a deferral with an existing precedent, not a bug in this story.

### Member routes: session-gated, own scope tx, 404-not-403

There is **no** `scopeResolutionHook` on a member route (that middleware also computes RBAC grants, which members do not have). The handler opens its own RLS-scoped tx via `openScopeTx` and passes `scopeTx.client`/`scopeTx.tx` to the domain — it **never** persists through an unscoped pool. Ownership/tenancy mismatches are **404, not 403** (a 403 leaks that the resource exists). Both rules are 10.2's, verbatim ([[project_helpdesk_member_surface_102]]); `apps/api/src/modules/helpdesk/member-handlers.ts:12-17` is the header that states them.

### Where `<BannerHost>` mounts, and why not the root layout

`architecture.md:4215` reserves `apps/mobile/app/_layout.tsx  # Banner rendering at layout level`. The **root** `_layout.tsx` (read it — `apps/mobile/app/_layout.tsx:100-226`) also wraps the `(auth)` group and runs the login-wall redirect guard; a banner host there would mount before any member session exists and would need to no-op through the entire unauthenticated flow. `(tabs)/_layout.tsx` is the authenticated layout level and is where every member-facing surface actually lives. **Recommendation: mount in `(tabs)/_layout.tsx`** and note the substitution in the Dev Agent Record. If the popup needs true modal presentation, the in-repo precedent is an Expo-Router route group with `presentation: 'modal'` (`(pool-onboarding)`, wired at `app/_layout.tsx:193-199`) — but a Tamagui overlay inside `<BannerHost>` is simpler and keeps the host self-contained; prefer it unless it fights the tab bar.

### The member surface has no `announcements` screen — do not assume one

10.5's Dev Notes describe an `announcements/:alert_id` deep-link landing as "already wired". The **deep-link mapping** exists (`packages/contracts/src/deep-links/deep-link.ts:83-89` — `alert_published` → `{resource: 'announcements'}`); a grep of `apps/mobile` for `announcements` returns **no screen**. This does not affect 10.9 (banners are not deep-linked and not dispatched), but do not build 10.9's render "next to" a screen that isn't there, and do not treat that landing as an existing host for banner copy.

### Do NOT extract a shared banner component into `packages/ui`

`packages/ui` currently holds exactly three components (`status-pill`, `member-status`, `pool-progress`), each with a real cross-package consumer. `<BannerHost>` and its strip have **one** consumer today (the member app). Story 11a.5's `<NoticeboardStrip>` is the eventual second — extract **then**, not now ([[project_no_premature_package]]: don't extract before a second consumer package exists today). Build it under `apps/mobile/components/banners/`.

### Admin app stack facts (don't re-derive)

- **Routing:** TanStack Router, code-based tree in `apps/admin/src/router.tsx`.
- **Session gate:** pure `GateView` (`useSession()` → loading / error(→`/login`) / success); the SERVER permission hook is the real boundary.
- **API client:** hand-written same-origin **cookie-bearing** `apiFetch` (`apps/admin/src/api/client.ts`), schema-validated; hooks via `@tanstack/react-query`.
- **Styling:** Tailwind + `status-*` tokens. **Tamagui is mobile-only.**
- **i18n:** per-module `i18n-en.ts` `resolveEn` (en-only chrome). The banner's own bilingual copy is member-facing *content*, validated in the domain — not an i18n catalog key.

### Audit: names, and what must never enter a line

Audit actions follow the `news.*` shape: `banner.created` / `banner.updated` / `banner.revised` / `banner.published` / `banner.retracted`, `resourceLocator = banner:<bannerId>`, and `requestPayloadHash` over the **locator + action** — the authored copy is **never** audited (`news-blog/handlers.ts:89-99` is the template). The tone-review sign-off records through its **own** `ToneReviewAuditSink` (`tone_review.signoff`), not the auth taxonomy.

### No new event vocabulary

There is no `banner.*` **events_log** vocabulary and there must not be one (Decision 1 — banners are not event-sourced). The dotted names above are **audit actions**, not domain events. Do not add anything to `packages/events/src/registry.ts`; do not create a projector or a state-writer trigger. The [[project_contribution_event_name_contract]] 8.10 fence is about the contribution family and is not implicated here — but the "a green-but-vacuous read is worse than a red one" lesson is.

### Completion Notes List

**1. ARCHITECTURE DEVIATION (the one decision this story had to make on its own): the pure read-time policy lives in `@twt/contracts`, not `@twt/domain`.**

> `resolveVisibleBanners` and `deriveBannerDisplayState` were relocated from `packages/domain` to `packages/contracts` because they are pure, read-time presentation policy shared by both the API/domain layer and the browser-based admin UI. Keeping them in Domain would violate the browser bundle boundary; duplicating them would violate the single-implementation requirement of AC5.

That sentence is repeated verbatim at the head of `packages/contracts/src/banners/{precedence,display-state}.ts` and in `packages/domain/src/banners/{index,read}.ts`, so a maintainer who goes looking for either function in the domain module finds the reason where they looked, not only here.

In detail — AC5 requires the admin editor to call *"the SAME pure `resolveVisibleBanners` the server uses — never a second, re-implemented comparison"*, and Task 1 placed that function at `packages/domain/src/banners/precedence.ts`. Those two requirements are not simultaneously satisfiable as written: **`apps/admin` does not depend on `@twt/domain` and must not** — it is a browser bundle and `@twt/domain` pulls in `pg`, `drizzle` and `@google-cloud/kms` (the same class of boundary [[project_contracts_domain_bundle_boundary]] enforces for the RN bundle). The reverse edge is also closed: `@twt/contracts` already depends on `@twt/domain` for its test-only sync-guards, so `domain → contracts` would be a hard cycle.
Resolution: `precedence.ts` and `display-state.ts` moved to `packages/contracts/src/banners/` — the only package both `apps/api` and `apps/admin` can reach. `@twt/domain` keeps the DATA and the WRITE invariants (the legality reducer, the tone gate, the content-hash revision rule, the accessors); `@twt/contracts` keeps the read-time PRESENTATION policy. The `BANNER_DISPLAY_STATES` spelling authority stays on `schema/banners.ts` so the sync-guard still has a domain-side target. Consequence: `resolveMemberBanners` no longer exists in the domain — `read.ts` exposes `listMemberBannerCandidates` (SQL ∧ audience) and `apps/api`'s member handler applies the resolver. **AC5's property is now literally true** (one implementation, three consumers: apps/api, apps/admin, the tests) rather than nominally true with a duplicate.

**2. `deriveBannerDisplayState` moved with it, for the same reason** — the admin preview must distinguish `scheduled` from `live` before a draft is saved, so it needs the derivation client-side. `apps/api` imports it from `@twt/contracts` to stamp `display_state` onto every admin DTO.

**3. `dismissal_kind` is a text column + a DB CHECK, not a fifth pgEnum.** Task 1 budgeted `CREATE TYPE × 4` (display_mode / severity / status / audience_scope) and the sync-guard covers exactly those four tuples. `dismissal_kind` is never an admin-authored choice and never sync-guarded, so it rides a `text` column with `CHECK (dismissal_kind IN ('dismissed','shown'))`. A canonical `BANNER_DISMISSAL_KINDS` tuple still exists in the schema file as the spelling authority.

**4. The `revision` bump requires a NON-AUTHOR — including for a typo fix.** Decision 5 says a copy change on a published banner needs a *fresh non-author sign-off*; mechanically that means the acting admin becomes the sign-off's `reviewedBy`, and the shipped gate is default-deny on `reviewedBy === authoredBy`. So a banner's own author cannot fix their own published wording — another admin must. This is the *same* consequence as the publish gate, and the same PO-ratified deferral 10.5 recorded on 2026-07-30 (a single-admin Pariwar cannot publish a banner). Recorded, not "fixed".

**5. ARCHITECTURE SUBSTITUTION (noted per the [[project_mmkv_asyncstorage_equivalent]] discipline):** `architecture.md:4215` places banner rendering in the ROOT `apps/mobile/app/_layout.tsx`. `<BannerHost>` mounts in `app/(tabs)/_layout.tsx` instead — the root layout also wraps the unauthenticated `(auth)` group and runs the login-wall redirect guard, so a host there would mount before any member session exists. A test pins both halves: it IS in the tabs layout above `<Tabs>`, and it is NOT in the root layout.

**6. `status-warn-*` / `status-info-*` do not exist in `@twt/tokens`.** Several sibling admin modules reference those class names and therefore render **unstyled**. The banner console uses only real registry names (`status-fail-*`, `status-pending`, `status-held`, `status-muted-bg`), and a test asserts every emitted `status-*` token is one that exists. The pre-existing sibling-module breakage is **not** fixed here (out of scope) but is flagged for a follow-up.

**7. `makeClient(...).inject` had no `PATCH` in its method union** (`apps/api/tests/integration/_setup.ts`). The banner console's one unified edit is a PATCH, and this cookie-jar client is the only way an E2E spec can drive an admin-session route. Widened — a helper gap, not a policy; Fastify's `inject` always accepted PATCH. The tests passed at runtime before this and failed only under `tsc`, which is exactly the class of gap a typecheck job exists to catch.

**8. The DB-CHECK tests assert the CONSTRAINT NAME, via `err.cause`.** Drizzle wraps the pg error ("Failed query: …"), so `constraint` lives on `err.cause`, not `err.message` (the same shape the 23505 savepoint-retry path relies on — [[project_domain_limit_clamp_and_savepoint_retry]]). Asserting the *name* rather than "it threw" is what makes these the revert-sanity teeth: drop a CHECK from migration 0090 and the write succeeds, so the assertion fails rather than passing on some unrelated error.

**9. What was deliberately NOT built** (Decisions 1 + 2, and the epic's in-app-only AC): no pg-boss job, no worker, no `QUEUE_NAMES` entry — `apps/jobs` and `packages/queue` are untouched; no projector, no state-writer trigger, no CI state-invariant gate, no `events_log` stream, no `packages/events` registration; no channel dispatch, no `alert_published`, no `fanOutAlertToMembers` (so no crypto-boundary concern arises — nothing fans out); no `apps/public` surface (11a.5 owns the `<NoticeboardStrip>`); no `link_cta` / deep-link target; no per-screen targeting; no `banner.view` read key; no `packages/ui` extraction (one consumer today — [[project_no_premature_package]]).

**10. `district_admin` DEFERRED again** (the fifth Epic-10 instance) with the standard acceptance condition: a district-ceiling grant can never satisfy a pariwar-dimension check, so granting it would seed an inert capability. Pinned by a revert-sanity pair (`pariwar_admin` allowed / district-ceiling holder denied) plus a fail-closed no-grant case.

**11. Test totals:** 207 new tests — 36 domain unit + 32 domain live-DB + 61 contracts + 26 API E2E + 32 admin + 20 mobile. RBAC catalog v27 → v28 (38 keys).

**12. `ci:local`'s `integration-tests` job reports 4 failures that are a HARNESS ARTIFACT, not a regression — diagnosed, not waved through.** The four are `cross-pariwar-leak.spec.ts` (×2), `rls/policy-regression.spec.ts` and `pool/active-contribution-read.spec.ts` — all EXACT-COUNT assertions on `events_log` / `alerts` for `PARIWAR_A`. None of them touch a banner, and **this story writes no `events_log` rows at all** (Decision 1 — banners are not event-sourced), so it cannot be their cause. Three independent checks, in the order run:
- **Baseline reproduction.** Checked out `509477e` (this story's `baseline_commit`) into a throwaway `git worktree` and ran the same three specs against the same database: **identical 4 failures on unchanged code.**
- **Fresh database, full `ci:local`.** Still 4 failures — so it is NOT accumulated residue from earlier sessions (the pre-existing `twt_dev` pollution is real and dated 07-31 → 08-01 06:24, but it is not the mechanism).
- **Fresh database, SINGLE PASS** (the `integration-tests` command alone): **exit 0, 3738 tests, 0 failures.**

The mechanism is the one [[project_ci_local_double_run_pollution]] already records: `ci:local` exports `DATABASE_URL` globally, so `test (unit)`'s `pnpm turbo run test` ALREADY runs `@twt/domain`'s integration specs (they share the vitest `include`) and commits rows; `integration-tests` then re-runs them against that residue and the count assertions see two passes' worth. The live-DB attestation for this story is therefore the single-pass run above, not the in-`ci:local` job.

⚠ **Two things left for whoever picks this up:** (a) the `twt_dev` test database carries 61 committed `events_log` rows from prior sessions and will keep those 4 specs red until it is recreated — deliberately NOT done here, since recreating the container is destructive to a shared local environment and is the owner's call; (b) the double-run itself is a real `ci:local` defect worth fixing at the harness level (scope `test (unit)` away from the integration globs, or run the two jobs against separate databases) — it makes the merge gate unable to report green on an unmodified tree, which is corrosive exactly the way [[feedback_record_unattested_no_backfill]] warns about.
