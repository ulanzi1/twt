# Story 5.2: In-App Push Channel (FCM + APNs) — Primary, 7 Categories `[CONSUMER]`

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As any member or admin receiving time-critical notifications,
I want in-app push notifications via FCM (Android) + APNs (iOS) as the **primary** channel of the three-tier hierarchy, supporting the 7 push alert categories,
so that members receive immediate, free-to-deliver notifications without depending on WhatsApp or SMS for normal-priority traffic.

**This is the SECOND story of Epic 5 and the FIRST `[CONSUMER]`.** It turns Story 5.1's two `push` provider **stubs** (`fcm`, `apns`) into **real** transports behind the unchanged `ChannelProvider` port, ships the **per-member/per-admin device-token registration substrate** the push channel needs, adds the **7-category push renderers with deep-link targets**, and wires **push-token invalidation + rebuild** (architecture §3.3). It does **NOT** touch the dispatcher's public shape, the canonical ladder, or any other channel.

## Acceptance Criteria (at a glance)

1. Real FCM + APNs transports behind the unchanged `ChannelProvider` port.
2. Per-Pariwar FCM credentials via Secret Manager, fixture fallback when unprovisioned.
3. Device-token registration substrate (member + admin), tokens as Tier-1 PII.
4. 7-category push renderers with title + body + deep-link target, derived from `payload_data`.
5. Push-token invalidation on unrecoverable send failure + stale-token cleanup job.
6. Determinism + escaping gates extended to the push deep-link output.
7. Audit + AI-4-3 access-wrapper walk for the new caller-facing registration paths.

**AC1 — Real FCM + APNs push transports behind the unchanged `ChannelProvider` port.**
Replace the Story 5.1 `fcm`/`apns` **stubs** (`packages/channels/src/providers/{fcm,apns}.ts`) with **real** implementations of the SAME `ChannelProvider` interface (`send`, `getStatus`) — the dispatcher, `CANONICAL_CHANNEL_LADDER`, and `provider.ts` port do NOT change (architecture §3.4 "Providers are swappable"). Both transports go through **Firebase Admin SDK** (`firebase-admin`): FCM HTTP v1 for Android tokens, APNs **via the Firebase Admin SDK** for iOS tokens (architecture §3.4 line 1935 — **BigDev CONFIRMED 2026-07-05: single SDK for both; no native APNs `.p8` path**; see Dev Notes "Push-transport decision"). `send` returns a well-formed `SendResult` (`accepted` on Firebase acceptance; `rejected` with a mapped `detail` on a Firebase error) — it **NEVER throws into `dispatch`** (the dispatcher isolates per-channel faults, but the provider must still resolve to a `SendResult`, not a rejected promise, for the non-error path). `getStatus` returns the honest `unknown` state (FCM/APNs give no post-accept delivery receipt for silent/data pushes at v1 — do NOT fabricate `delivered`).

**AC2 — Per-Pariwar FCM project credentials via Secret Manager; fixture fallback when unprovisioned (AR-17).**
Per-Pariwar FCM **service-account** credentials load via `resolveSecretValue` (Story 1.5, `@twt/domain`) — a Secret-Manager **NAME** per Pariwar, never the value; a local-dev env fallback var mirrors argon2/turnstile/digilocker. The `push` provider `scope` becomes `'per-pariwar'` (Story 5.1 `provider.ts` already declares the field). **Follow the repo's opt-in-real convention (Turnstile/DigiLocker/KYC, `apps/api/src/deps.ts`): an absent secret NAME resolves the push provider to a `fixturePushProvider` (log-only, no network), so the stack boots with ZERO Firebase config in dev/CI/not-yet-provisioned.** Setting the secret NAME opts into real Firebase sends. Per-Pariwar Firebase `App` instances are initialized lazily and cached by `pariwar_id` (never re-`initializeApp` per send). APNs uses the Apple Push key configured **inside** the per-Pariwar Firebase project (tied to the TWT app bundle id) — no separate APNs credential path in this story.

**AC3 — Device-token registration substrate (member + admin), tokens as Tier-1 PII.**
Ship a `member_device_tokens` table (+ RLS mirroring the existing tenant-scoped tables) and its repo. Columns: token identity, `pariwar_id`, the owning principal (member **or** admin actor), `platform` (`android | ios`), the **encrypted** token (`encryptTier1`, Story 1.5 — device tokens are **Tier-1 PII**, architecture §3.4 line 1937), a `blindIndex` of the token for dedup/lookup-without-decrypt, `status` (`active | stale | invalid`), `registered_at`, `last_seen_at`.
- **Member registration endpoint** (member-session-gated, `requireMemberSession`) — the **Story 3.2 consumer**: the mobile app registers the current device token on app open.
- **Admin registration endpoint** (admin-session-gated, `requireAdminSession`) — the **Story 1.9 consumer**: admin device tokens register on admin auth.
- **App-open rebuild (architecture §3.3):** registering a token upserts it `active` and marks the principal's OTHER tokens for that platform `stale` (next-open rebuilds the active-token set). Registration is idempotent on `(pariwar_id, principal, token_blind_index)`.

**AC4 — 7-category push renderers with title + body + deep-link target (pure, deterministic).**
Each of the 7 FR-71 push categories (`alert_published`, `deadline_reminder`, `contribution_confirmed`, `contribution_mismatch`, `claim_status_change`, `helpdesk_reply`, `module_new`) renders a push notification with **title + body + deep-link target**. The renderer stays a **pure function of the immutable `Readonly<Alert>`** (AC5/AC4 of 5.1 — NO clock, NO randomness, NO I/O). Extend the render **output** (`RenderedMessage`) with an optional deep-link/data field (this is render *output*, not the frozen `Alert` — adding it does not violate the immutability invariant); the push renderer derives the deep-link from `alert_category` + **`payload_data`** (NOT `provenance_refs` — `ProvenanceRefs` fields (`alert.ts:63-71`) are all optional and unpopulated until Epic 6/8 producers land; the IDs that actually exist today per category — `claim_id`, `pool_id`, `ticket_id`, `module_id` — live in `payload_data`) via a new **deep-link URI grammar** in `packages/contracts/src/deep-links/` (finally landing the substantive contract the scaffold README reserved). `alert_published`'s `payload_data` is `{ title, body }` only — no content-specific id — so its deep-link target is the `alert_id` (announcement/feed entry), not a claim/pool/ticket/module id. The **push eligibility gate = every category except `step_up_otp`** — the full taxonomy-vs-eligibility distinction (FR-71's 7 vs. `niyamavali_amended`'s broadcast routing) is canonical in Dev Notes "Push category eligibility"; don't re-derive it here. Plaintext push needs no HTML-entity encoding — this story **owns push's escaping semantics** per the 5.1 deferral (deferred-work.md, decision D1 2026-07-05), which requires restructuring `render.ts`'s escaping to be channel-parameterized (see Task 6).

**AC5 — Push-token invalidation on unrecoverable send failure (architecture §3.3 push-token rotation).**
When Firebase returns an **unrecoverable token error** (`messaging/registration-token-not-registered`, `messaging/invalid-registration-token`, `messaging/invalid-argument` for the token), the offending device token is marked `invalid` (not merely a transient send error). Transient/quota errors do NOT invalidate the token. The provider reports the failure honestly as `SendResult.status: 'rejected'` with a stable `detail`, and the invalidation write is a **best-effort, isolated write** (never the caller's tx — AI-4-3(d); the dispatcher holds no request tx). A **Class C pg-boss stale-token cleanup job** (`apps/jobs/`) prunes `stale`/`invalid` tokens on a cadence (mirror an existing Class C job — e.g. `digilocker-cert-refresh.ts` boot wiring).

**AC6 — Determinism + escaping gates extended to the push deep-link output.**
The Story 5.1 per-channel byte-identical determinism gate (`packages/channels/tests/determinism.test.ts`) and escaping gate (`escaping.test.ts`) are extended to cover the new push deep-link/data field: replaying a fixed `alert_id` yields byte-identical push output **including the deep-link**, and injection payloads in a name-like field remain inert in the push title/body. The gate still exercises **`render` only — never `send`** (AC5 of 5.1 — Firebase sends are non-deterministic and outside the guarantee).

**AC7 — Audit + AI-4-3 access-wrapper walk for the NEW caller-facing paths.**
The two device-token **registration endpoints** are caller-facing access/write paths — so the AI-4-3 checklist items that were **N/A in 5.1 are now LIVE**: **(a)** caller-auth verified independently (session guard), **(b)** an omitted/failed caller fails **closed** (no session ⇒ 401, never a silent register), **(c)** any audit line over a token uses the **HMAC/blind index**, never raw token or `sha256(token)` (tokens are Tier-1 PII), **(d)** best-effort writes isolated on `servicePool`, **(e)** any new RBAC/route scope matches the guard. Registration + invalidation emit audit lines via `writeAuditEntry` (`@twt/domain`). The `access-wrapper:check` AST gate still scans only `packages/validity-service` — so these paths are carried by the **checklist walk + required tests** (record the walk in the Dev Agent Record).

### What this story IS (and is NOT)
- **IS:** real FCM + APNs transports (firebase-admin) behind the unchanged 5.1 port; per-Pariwar credential loading with a fixture fallback; the device-token registration substrate (table + RLS + repo + member/admin endpoints + app-open rebuild); the 7 push renderers with deep-link targets; push-token invalidation + a Class C cleanup job; extended determinism/escaping gates; the AI-4-3 walk for the new caller-facing paths.
- **IS NOT:** WhatsApp (5.3), the WA opt-in webhook (5.4), Telegram real send (5.5), SMS-DLT (5.6), cost-optimization (5.7), the degraded-mode SMS bridge (5.8), step-up-OTP delivery (5.9), and — critically — **the push→WA→SMS cascade/retry ladder (5.6)**. 5.2 does NOT add cascade-on-failure: the dispatcher still attempts `push` independently and records the honest outcome; when push fails, 5.2 records it (and invalidates dead tokens) but does NOT escalate to another channel — that policy WRAPS the dispatcher in 5.6 (5.1 Dev Notes "Dispatch execution vs. delivery policy"). **CONFIRMED by BigDev 2026-07-05:** epics.md's own Story 5.2 AC (line 2117, "failures... the dispatcher's fallback ladder advances to next channel per AR-19") reads as if 5.2 owns the cascade — it does NOT; AR-19's fallback ladder is implemented in 5.6, and 5.2's job is only to record the honest per-channel outcome the ladder will later consume. Also NOT: lifecycle-suppression implementation (the member-state read model is still absent — the 5.1 `LifecycleSuppressionHook` default stays; do not implement suppression here).
