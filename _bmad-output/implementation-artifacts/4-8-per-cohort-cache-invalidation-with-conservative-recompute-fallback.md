# Story 4.8: Per-Cohort Cache Invalidation with Conservative-Recompute Fallback (≤ 60s Freshness Invariant)

Status: done

`[GOVERNANCE]` — the THIRD and final `[SURFACE]`/`[GOVERNANCE]` beat of Epic 4. Adds the caching layer in front of Story 4.6's Member Validity Service that *delivers* the FR-12A `p95 < 200ms @ 4L` budget (Story 4.6 measured-and-recorded the uncached path; 4.6 D3-A explicitly handed the 200ms target here), while making **stale validity structurally impossible** under degraded conditions via a conservative-recompute fallback.

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the Member Validity Service caching layer,
I want a per-cohort cache invalidation strategy with an **explicit conservative-recompute fallback** — if cache freshness cannot be guaranteed within the ≤60s invariant window, fall back to direct recomputation rather than serve potentially stale validity state,
So that trust-corrupting stale validity (contribution eligibility, claim validity, lock-in status, concealment flags) is **structurally impossible** under degraded cache conditions.

## Acceptance Criteria

Transcribed verbatim from `epics.md#Story 4.8` (lines 2036–2057). The four AC groups are the contract; the Tasks below decompose them.

**AC1 — Cache key composition + per-cohort buckets**
**Given** Sprint Change Proposal Item 5 + architectural-freeze row 11 + FR-12A freshness invariant
**When** the caching layer is implemented for the Validity Service
**Then** cache key composition is `(member_id, member_state_hash, rule_registry_version, cohort_invalidation_epoch)`; per-cohort buckets are: (a) `pariwar_id × niyamavali_version` (invalidates when Niyamavali amendments publish), (b) `member_id × member_state_hash` (invalidates when member-state events change), (c) explicit invalidation broadcast (trustee-triggered "invalidate all" for emergency posture changes)
**And** any Niyamavali amendment publish (Story 2.4) triggers the affected cohort's invalidation broadcast within seconds, satisfying the ≤ 60s freshness invariant
**And** any member-state change (Story 3.1 event append) invalidates that member's per-member cohort entry

**AC2 — Conservative-recompute fallback (this story's load-bearing commitment)**
**Given** the **conservative-recompute fallback behavior** (this story's load-bearing commitment)
**When** the cache layer cannot guarantee freshness within the ≤60s invariant window — examples: (a) cohort invalidation broadcast delivery is delayed; (b) cohort-scope confidence is insufficient (e.g., a member-state change happened but its cohort attribution is ambiguous); (c) cache backend is degraded; (d) clock skew or system-state anomaly detected
**Then** the system **MUST fall back to direct recomputation** rather than serve potentially stale validity state — no cached value is returned; the request triggers a fresh evaluation through Story 4.6's Validity Service
**And** the fallback is logged for observability (every fallback is recorded with reason); a sustained fallback rate above a threshold (e.g., 5% over a 10-min window) fires an alert
**And** the operational stance is explicit and load-bearing: **stale validity is trust-corrupting in this system. We accept higher latency or higher recomputation load over serving cached values whose freshness cannot be guaranteed.**

**AC3 — All-members emergency invalidation**
**Given** an "all-members" emergency invalidation (e.g., a rule registry change with broad scope)
**When** the trustee triggers it
**Then** the cache is fully invalidated for the affected `pariwar_id × niyamavali_version` cohort; subsequent calls hit direct recomputation until the cache repopulates organically; performance degradation during the invalidation window is acceptable because the alternative (serving stale validity) is unacceptable

**AC4 — Freshness-invariant + degraded-cache assertion tests**
**Given** the freshness invariant assertion test
**When** integration tests run
**Then** a synthetic Niyamavali amendment + member-state change scenario is asserted: within ≤60s of the change, every Validity Service call must reflect the new state; any call returning stale state within that window fails the test
**And** a synthetic degraded-cache scenario is asserted: when the cache cannot guarantee freshness, every Validity Service call must fall back to direct recomputation; no cached value is returned

## Task 0: Settle the load-bearing decisions (READ FIRST — do not skip)

This is a `[GOVERNANCE]` story whose ACs commit *properties*, not a mechanism. Architecture §1.10 (`architecture.md:1042–1081`) explicitly states: *"Specific mechanisms (e.g., singleflight pattern, lease coordination, exact threshold values) committed in an implementation ADR."* So the mechanism is yours to choose **within the committed properties** — this is exactly the [[feedback_architecture_vs_adr_boundary]] discipline (architecture commits properties; the mechanism is an implementation/ADR control).

**Task 0 is settled. BigDev CONFIRMED all five decisions on 2026-07-04: D1→A, D2→A, D3→A, D4→A, D5→A** — plus three refinements that HARDEN the fail-open stance (now the "Cache participation is optional; correctness is mandatory" operational invariant in Dev Notes — best-effort cache writes + the cache warmer is performance-only, never correctness). Take the decisions as written below; do not re-open them. The rejected alternatives are retained only so the dev agent understands *why*.

The committed **properties** you must not violate (architecture §1.10 + the ACs):
- 60s freshness invariant (a change is reflected within ≤60s — see D2 for why *event-driven* changes become synchronous, not just ≤60s).
- **60s TTL** (§1.10's first committed line: *"60s TTL per UX commitment"*). The TTL is NOT redundant with D2-A key-based invalidation — it is the ONLY bound on **time-derived** payload drift (see the "Three change vectors" note in Dev Notes): `daysUntilGraceEnds`/`graceRemainingDays` count down daily with no event, and `projectLockInStatus` flips `in-lock-in → unlocked` by pure date comparison (`payload.ts:61-76`) — no event fires at that boundary. A cache hit requires `computed_at` within 60s of DB-authoritative `now()` (§1.11); an expired row ≡ miss.
- Cache-aside read semantics.
- Per-cohort invalidation with a conservative all-members fallback when scope confidence is insufficient.
- Stampede protection (stale-while-revalidate / bounded recompute — but see the AC2 nuance below).
- Redis is a **future** trigger only (`architecture.md:1079-1081`) — v1 is **in-Postgres**. Do NOT add Redis, an in-memory LRU, or any external cache store.

### D1 — Cache substrate: Postgres cache-aside **table** vs. literal materialized view

- **D1-A (RECOMMENDED): a Postgres cache-aside key/value table** (`member_validity_cache`) keyed by the AC1 composite `(member_id, member_state_hash, rule_registry_version, cohort_invalidation_epoch)`, storing the **full unredacted** `MemberValidityPayload` (jsonb) + its `validity_payload_hash` + a `computed_at` freshness timestamp (**load-bearing** — the read path enforces the §1.10 60s TTL against it, not decorative); plus a small `cohort_invalidation_epoch` table (one row per `(pariwar_id, niyamavali_version)` cohort, an integer epoch bumped on invalidation). Cache-aside read: resolve the key from **cheap** metadata reads → `SELECT` the row → hit returns the payload, miss recomputes via 4.6 and `INSERT … ON CONFLICT`. This is the shape the AC1 key composition + per-cohort epoch + per-member conservative recompute actually describe.
- **D1-B (architecture's literal word): a Postgres MATERIALIZED VIEW.** §1.10 says "materialized view + cache-aside read," and Story 4.7's D1-B recorded (`4-7-*.md:51`) that *"MV full-refresh is Story 4.8's mechanism for the validity cache and does not fit incremental per-member update."* **That is the problem:** an MV `REFRESH` is all-or-nothing (or CONCURRENTLY, still full-scan) — it cannot express per-member conservative recompute, per-cohort epoch invalidation, or the "no cached value returned on freshness-uncertainty" AC2 commitment. An MV also cannot store per-caller-redactable full payloads with a cache-aside miss path cleanly. **Rejected** unless BigDev insists on the literal word over the committed properties.
- **Why D1-A honors the architecture:** §1.10 commits the *properties* (cache-aside, 60s, per-cohort invalidation, conservative fallback, stampede protection) and defers the *mechanism* to an ADR. A keyed cache-aside table satisfies every property and fits the AC1 key composition natively; "materialized view" is the architecture's illustrative mechanism, not a frozen invariant. Record this as a documented mechanism choice (an ADR-class decision), citing §1.10's own "committed in an implementation ADR" clause. Pairs with [[feedback_architecture_vs_adr_boundary]].

### D2 — Invalidation propagation: **transactional epoch-bump** vs. async pg-boss broadcast

- **D2-A (RECOMMENDED): bump the cohort/per-member epoch in the SAME transaction as the triggering write.** On amendment publish (Story 2.4 `amendClause` path), bump the `(pariwar_id, niyamavali_version)` cohort epoch in the publish transaction. On member-state change, advance the per-member cache watermark in the append transaction (see D3). Because the cache key includes `cohort_invalidation_epoch` and `member_state_hash`, a bumped epoch / changed state means **every subsequent read resolves a new key → guaranteed cache miss → recompute**. Freshness becomes **synchronous**, not merely ≤60s — stale validity is *structurally impossible* the instant the triggering write commits. This is the strongest possible realization of the story's load-bearing goal, and it needs **no** pg-boss delivery-timing dependency for correctness.
- **D2-B (async broadcast via pg-boss):** enqueue an "invalidate cohort" job (`@twt/queue`, new `QUEUE_NAMES.VALIDITY_CACHE_INVALIDATE`). **Only needed if the cache were in-memory / cross-instance** (it is not — D1-A is Postgres, shared by all instances). An async broadcast reintroduces exactly the "delivery delayed" freshness-uncertainty window AC2(a) is written to defend against. Keep pg-boss **out of the correctness path**; reserve it only for the optional cache-**warmer** (repopulating hot entries after an all-members invalidation) and the fallback-rate alert emitter, where late delivery is harmless.
- **AC1(c) explicit "invalidate all" broadcast:** implement as a **trustee-triggered epoch bump** (bump the cohort epoch, or a global `all` epoch) written transactionally — same mechanism, admin-initiated. The word "broadcast" (which the AC uses in AC1(a), AC1(c), and AC2(a)) is satisfied by "every reader observes the new epoch"; it does not mandate a message bus — and D2-A makes AC2(a)'s "broadcast delivery is delayed" case structurally unreachable for event-driven changes, which is strictly stronger than handling it.

### D3 — Per-member invalidation hook: **DB trigger on `events_log`** vs. application-level

- **D3-A (RECOMMENDED): an `AFTER INSERT` trigger on `events_log`** (filtered to member-stream events) that **`DELETE`s that member's `member_validity_cache` rows** (the DELETE is REQUIRED, not an optional alternative to a watermark — see the RTBF note in Task 4; a watermark alone leaves unaddressable-but-present rows holding the member's full payload). This is **can't-forget** and works **regardless of which package writes the event** — critical because [[project_member_lifecycle_domain_substrate]] records that `@twt/domain` writes `events_log` **directly** (it cannot import `@twt/events` — turbo cycle), so there is no single `appendEvent()` application choke point for member lifecycle. `events_log` has `stream_id` / `event_type` / `pariwar_id` (`schema/events_log.ts:48,54,84`) — enough to scope the trigger to member streams. This mirrors the existing precedent: [[project_member_lifecycle_domain_substrate]] notes `members.state` is already **projector-only via a DB trigger + CI gate**, so a second invalidation trigger is idiomatic here.
- **D3-B (application-level hook):** invalidate inside each member-lifecycle write path. **Rejected** — N call sites, every future writer must remember, and domain writes `events_log` directly from many modules (`member/project.ts`, `member/renewal-*.ts`, etc.). Fragile; a forgotten call = silent stale validity = the exact trust corruption this story forbids.
- **Migration note:** the trigger + function ship as a new drizzle migration (raw SQL — drizzle-kit does not emit trigger DDL). See Task 5 + the migration discipline in Dev Notes.

### D4 — Cohort invalidation granularity: **conservative whole-cohort bump** vs. scope-narrowed

- **D4-A (RECOMMENDED): bump the whole `pariwar_id × niyamavali_version` cohort epoch on ANY amendment publish; treat Story 2.4's `affectedMemberScope` as an OPTIMIZATION signal only.** Story 2.4 already ships a mandatory `affectedMemberScope` declaration on every amendment (`domain/niyamavali/scope.ts`, kinds: `all_members | past_lockin | rule_subclause | named_cohort`). Use it as follows: `rule_subclause` (precise) → *may* narrow later; `all_members` / `named_cohort` / `past_lockin` (broad or opaque → **scope confidence insufficient**) → **conservative whole-cohort invalidation**. For v1, default EVERY publish to the whole-cohort bump (correct + simple); wire narrowing as a documented, deferred optimization. This is the literal implementation of AC2(b) "cohort-scope confidence insufficient → fall back" and architecture §1.10's "Conservative fallback (all-members invalidation) fires when scope confidence is insufficient to guarantee completeness."
- **D4-B (narrow by `affectedMemberScope` now):** compute the exact affected member set per amendment and invalidate only those per-member entries. **Deferred** — requires a scope→member-set resolver that does not exist, and any bug under-invalidates (serves stale to a member whose validity actually changed) = trust corruption. The conservative whole-cohort bump is strictly safer and the AC endorses it. Record the narrowing as a tracked optimization CR.

### D5 — Refactor shape so audit + redaction stay correct on a cache HIT (load-bearing)

The current `getValidityAt` (`validity-service/src/service.ts:63-134`) does, in order: (0) require `caller` XOR `internal`, (1–4) read + evaluate + assemble the FULL payload, (5) **write the admin `validity.evaluate` access-audit line for non-self callers**, (6) **redact per caller**. A naïve cache that wraps the whole function would **skip the access-audit on a hit** and could cache a **redacted** payload — both are correctness defects.

- **D5-A (RECOMMENDED): split compute from access.** Extract the cacheable core = steps 1–4 (produces the FULL, unredacted, unaudited payload; this is exactly what `getValidity(..., { internal: true })` already returns — the service *already anticipates the Story 4.8 cache warmer* at `service.ts:52-56,73-76`). The cache stores **only the full payload**. The per-access wrapper (in `apps/api`'s member-validity handlers, or a new `getValidityCached` in the service) does: access-check → **cache-aside over the full-payload core** → **access-audit MUST fire here on hit AND miss** (it is a per-READ access record, not a per-compute record) → **redact per caller**. Never cache a redacted payload; never skip the admin audit on a hit.
- **Invariant this protects:** the admin `validity.evaluate` audit line (`service.ts:167-183`) records *who read whose validity* — an access record. It must fire once per admin read regardless of cache state. The engine's lower-level per-clause `rule.evaluate` **compute**-audit correctly does NOT fire on a hit (nothing was computed) — that asymmetry is intended (`service.ts:159-166`).
- **D5-B (cache the redacted payload per caller):** **Rejected** — multiplies cache entries per caller-role, risks serving one caller's redaction to another, and still doesn't solve the audit-on-hit problem.

All five are CONFIRMED (see the "Task 0 is settled" banner above). Implement them as written; the Dev Agent Record's ledger already records the confirmation + the three fail-open refinements.

### Three change vectors — and why the 60s TTL is load-bearing, not decorative
A cached payload can go stale via THREE vectors, and D2-A's key-based invalidation only covers the first two:
1. **Niyamavali amendment** (AC1a) — covered synchronously by the cohort-epoch component of the key (D2-A/D4-A).
2. **Member-state event** (AC1b) — covered synchronously by the state-hash/watermark component + the D3-A trigger DELETE.
3. **Pure time passage — NO event fires.** The payload is a function of the evaluation *instant*, not just member state: `daysUntilGraceEnds`/`graceRemainingDays` count down daily (`member/renewal-read.ts:37-45`); `projectLockInStatus` flips `in-lock-in → unlocked` by comparing `evaluatedAt` to the unlock date (`validity-service/src/payload.ts:61-76`); retirement-coverage dates are projected the same way. The scheduler's boundary events (`member.grace_expired`, `member.lock_in_expired`, `member.valid_through_reached`) land on cron cadence — *after* the real boundary — and the countdown fields drift with no event at all. Lock-in status is one of the four trust-critical facts in this story's own So-that clause: serving `in-lock-in` after the unlock date from a key-fresh cache row is exactly the staleness this story exists to forbid.

**The §1.10 60s TTL is the bound on vector 3.** A hit requires `computed_at` within 60s of DB `now()`; expired ≡ miss. This is also what makes the hit≡recompute oracle honest: within the TTL window the payloads agree to within the FR-12A UX freshness commitment; across it, they may legitimately differ, so the entry must not be served. Do NOT "optimize away" the TTL because D2-A looks synchronous — synchronous only covers evented changes.

### Stampede protection nuance (architecture §1.10 vs. AC2)
Architecture §1.10 lists "stale-while-revalidate — readers don't block; last-known-good served with `revalidating:true`." **But AC2 is more conservative and WINS for the freshness-uncertain case:** when freshness *cannot be guaranteed*, you must NOT serve last-known-good — you recompute. Reconcile: SWR/last-known-good is acceptable ONLY while the cached entry's freshness IS assured (its key still matches the current epoch + state watermark AND its `computed_at` is within the 60s TTL — key-match alone is NOT freshness, per the "Three change vectors" note above). The moment the key would change (invalidation happened) the entry no longer matches → miss → recompute; the moment the TTL lapses the entry is unservable regardless of key. So with D1-A/D2-A + the TTL there is no "stale-but-served" window for evented changes, and time-drift is bounded at 60s. Bounded-recompute (cap fan-out, singleflight via the keyed-store) still applies to protect the DB during an all-members invalidation (AC3). Document this reconciliation.

### THE load-bearing invariant — Cache participation is optional; correctness is mandatory (BigDev-confirmed 2026-07-04)
**The cache must never become a dependency for serving validity.** State it operationally, not as an example:

> If the cache **table**, the **epoch lookup**, the **invalidation mechanism**, the **integrity verification** (hash check), or the **cache write path** fails — for ANY reason — the request MUST still succeed by direct recomputation through Story 4.6's `getValidity`. The cache is a latency optimization layered *beside* the correctness path, never *on* it.

Concretely, the dev agent must guarantee:
- **Reads are best-effort.** A failed/absent/uncertain cache read → direct recompute. Never propagate a cache error to the caller; never serve stale (AC2). ("Cache backend degraded" is not merely one example among four — it is the general rule of which the four AC2 cases are instances.)
- **Writes are best-effort — and NON-BLOCKING to success.** After a cache MISS recomputes the correct payload, the request has already succeeded logically. The subsequent `INSERT … ON CONFLICT` is a side effect: **if the cache write throws, log it and return the freshly-computed payload anyway.** A write failure must NEVER turn a successful validity computation into a failed request. (Wrap the write in its own try/catch; the return value is the recomputed payload, decided before the write is attempted.)
- **Integrity failure is a poisoned-entry signal, not a request failure.** If a hit's stored `validity_payload_hash` disagrees with a recompute (the D1-A integrity check), the request still succeeds on the recomputed value — the cache entry is overwritten/deleted and the divergence logged. A corrupt cache never corrupts a response.
- **The cache WARMER is a performance concern ONLY — never correctness.** The optional warmer (repopulating hot entries after an all-members invalidation, D2-A/AC3) exists solely to reduce post-invalidation recompute load. Its success/failure/latency has ZERO bearing on whether any request returns correct validity — an un-warmed cache simply means the next reader takes the (correct) recompute path. Do NOT let any request-path read block on, wait for, or depend on the warmer. Keep this boundary explicit in code + comments (mirror the `internal: true` warmer seam's intent in `service.ts:52-56`).

### Other correctness invariants (non-negotiable)
- **Cache-hit ≡ fresh-recompute within the 60s TTL window** (byte-identical `validityPayloadHash` for a pinned instant; equal-to-within-the-UX-freshness-commitment across the window — time-derived fields may lawfully drift inside 60s, never beyond, because an expired row is unservable). A cache that can diverge from truth is worse than no cache — this is why the integrity check, the TTL guard, and the poisoned-entry handling exist. The hit-path check is the cheap embedded-hash-vs-column self-consistency check only — never a recompute-per-hit.
- **Audit-on-access, not on-compute:** the admin `validity.evaluate` line fires per read (hit AND miss); the per-clause compute-audit fires only on compute (miss). Do not merge these.
- **Full payload cached, redaction per-caller on read:** never cache a redacted payload; never leak one caller's view to another.
- **Tenant isolation:** the cache table is RLS-scoped by `pariwar_id` exactly like the source data.

Both tenant-isolated (RLS + FORCE), migration `0036` hand-authored (snapshots stop at 0020; [[project_live_db_test_gotchas]]). **Grants go to BOTH `twt_app` AND `twt_service`** — the D3-A trigger runs as the INVOKER, so a background SIE job (renewal-lifecycle) appending a `member.%` event via the `twt_service` pool would fail the trigger's cache DELETE without the `twt_service` grant (a silent stale-validity hole; mirrors the 0013 idempotency-keys twt_service-grant rationale).
- **D2-A — transactional epoch bump.** `amendClause` bumps the cohort epoch in the SAME publish tx (domain-level can't-forget hook); the create-publish branch bumps in the route. Freshness is SYNCHRONOUS for evented rule changes → AC2(a) "broadcast delayed" is structurally unreachable. No pg-boss on the correctness path.
- **D3-A — `AFTER INSERT` trigger on `events_log`** scoped `WHEN (event_type LIKE 'member.%')`, a single indexed DELETE of the member's rows. REQUIRED (not orphaning) for the RTBF retention purge. Verified it correctly resolves the member's rows under both twt_app-RLS-scoped (events_log's own write-withCheck guarantees `app.pariwar_id` = the event's pariwar) AND BYPASSRLS writers — no SECURITY DEFINER needed.
- **D4-A — conservative whole-cohort bump on ANY publish;** `affectedMemberScope` recorded (on the amendment ledger row) but NEVER gated on for correctness.
- **D5-A — split compute-core from access.** `getValidityCached` caches only the full unredacted payload (`getValidity(..., {internal:true})`); the admin `validity.evaluate` access-audit fires on HIT **and** miss, and redaction is per-caller on the returned full payload — both OUTSIDE the cached core. Verified by the audit-on-hit test.
- **Cache participation optional / correctness mandatory (the load-bearing invariant).** `getValidityCached` is fully fail-open: key-resolve + fresh-read run in a guarded phase that degrades to direct recompute on ANY error/uncertainty (classified into the AC2 reason enum); writes are best-effort in their own try/catch AFTER the return value is fixed (a write throw is swallowed + observed, never surfaced); a poisoned hit (stored hash ≠ embedded hash) → recompute + overwrite, never a failure. All three proven by tests (degraded/fallback, best-effort-write, poisoned-entry).
- **§1.10 60s TTL is load-bearing.** The read guard is `computed_at > now() - 60s` evaluated in the DB (neutralises the AC2(d) clock-skew case). The TTL test warms then ages a row past 60s with NO event → the next read misses → fresh recompute (proves key-based invalidation alone is insufficient for the pure-time-passage vector).
- **Cheap key resolution** (Task 2 crux): `member_state_hash` = SHA-256 over the member's latest-`event_version` **watermark** (one index-only `max` on `events_log`) — advances on EVERY `member.%` event (incl. identity-transition `member.medical_disclosed`), so the key shifts synchronously; the key is resolved BEFORE recompute so a cached payload can only be ≥ as fresh as its key (forecloses the read-through stale-write race). `rule_registry_version` = the cohort's `niyamavali_version` sentinel; `cohort_invalidation_epoch` = one `SELECT` on the epoch table.
- **Stampede protection — DEFERRED with recorded rationale (§1.10 mechanism = an ADR-class decision, so recorded not skipped).** (1) AC3 explicitly accepts post-invalidation degradation; (2) a keyed-store singleflight adds an advisory-lock round-trip to EVERY miss, taxing the p95<200ms budget the cache exists to protect; (3) the recompute path is already correct + idempotent (the engine per-clause memo dedupes). **Revisit trigger:** if production p95 during all-members invalidation windows exceeds the FR-12A budget, add per-key singleflight via `domain/src/idempotency/keyed-store.ts`.
- **Observability (Task 5):** every fallback logs a structured line with its reason enum (`backend_error | cohort_ambiguous | broadcast_delayed | clock_anomaly | scope_low_confidence`), no PII/payload (§1.12). `FallbackRateMonitor` = a sliding-window (10 min) rate + threshold (5%) evaluator that returns/fires the snapshot on a crossing (unit-tested). The alert TRANSPORT is a documented hook surfaced on the request logger — the real metrics/alert sink is a tracked Category-5 ops CR.
- **GC sweep (Task 4):** `VALIDITY_CACHE_GC` cron (every 15 min IST) DELETEs rows older than 10× the TTL on the BYPASSRLS `pool` — storage hygiene only (expired rows already unservable). The cleanup responsibility matrix (trigger-DELETE / epoch-bump-only / GC) is preserved as three distinct mechanisms.
- **Trustee "invalidate all" (AC1c/AC3):** `validityCache.invalidateAllForPariwar` + `POST …/admin/validity-cache/invalidate-all` (audited `validity_cache.invalidate_all`). v1 reuses the `member.view_validity` gate (a dedicated `validity.invalidate` key + a UI surface are Epic-10 admin-polish; the epic AC only says "the trustee triggers it").

**Variances / drift surfaced (per the story's "record any drift"):**
- No per-Pariwar Niyamavali version counter exists (the engine's `niyamavaliVersionHash` is a per-EVALUATION hash, not a cheap cohort key), so v1 uses ONE cohort per Pariwar under the `CURRENT_NIYAMAVALI_VERSION = 'v1'` sentinel; invalidation rides the epoch. A forward seam — activates unchanged when real niyamavali versioning lands. Documented in `cohort_invalidation_epochs.ts`.
- `member_validity_cache` has NO FK to `members` (unlike `member_search_projection`): the RTBF concern is the D3-A trigger DELETE (not an FK cascade), orphaned rows are harmless + GC'd, and an FK would break events-only test members. Story-aligned (Task 1 did not specify an FK).
- The payload contract, redaction contract, and rule engine are UNCHANGED — the D5-A split is a restructure of the ACCESS wrapper, not a payload change. R7/R8 contribution + claim producers stay `producer_unavailable` (Epic 6/8/9). No Redis (future §1.10 trigger). D4-B scope-narrowing optimizer deferred.
- **4.6 CR-4.6-D9 (100×-thread determinism gate → DB-backed):** DEFERRED with rationale. Story 4.8's freshness/hit≡recompute tests ARE DB-backed and exercise the real cache path end-to-end; expanding the separate 100×-thread WORKER determinism gate to a DB-backed path is an orthogonal perf-harness change. Revisit trigger: if a determinism divergence is ever observed on the DB path.
