# Story 7.6: Pool-Bound Payment Enforcement (Wrong-Pool Rejected, No Refund, Facilitated Recovery)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As **the contribution-receiving pipeline** (the consumer that Epic 8's `<UPIIntentButton>` pre-fills from and Epic 9 reconciliation matches against),
I want **pool-bound payment enforcement — a primitive that resolves a member-cycle's assigned pool + its collection binding from the persisted spawn snapshot, classifies any deposit to a non-assigned pool as an invalid `wrong_pool` contribution, and structurally forbids any silent remap / auto-reassign / cross-pool fund movement (facilitated recovery via helpdesk only)**,
so that **the deterministic assignment model (`hash(member_id + cycle_id) % N`) is preserved by construction and no recovery path can ever falsify audit lineage or corrupt replay**.

## Context & Scope (read this first)

This story is `[PRIMITIVE]`. It commits the **domain-layer building blocks** that three later epics consume — it does **not** build those consumers:

## Acceptance Criteria

**AC1 — Pool-bound VPA / collection-binding resolution (Given FR-16 + architectural-freeze row 7 + Story 7.4 assignment + Story 6.8 nominee bank)**

1. A domain primitive resolves, for a **member-cycle**, the member's **assigned pool** by reading the **persisted `pool_snapshots.member_assignments`** — the source of truth per the `assign.ts` D1 contract — **never a naive `hash % N` recompute** (balancing means a redistributed member's final pool depends on the whole frozen roster; only the snapshot is authoritative).
2. Resolution returns the assigned pool **plus its collection binding**: the pool's originating claim's **nominee bank accounts #1 (primary) / #2 (secondary)** via `getClaimNomineeBankAccountsCiphertext` — **ciphertext AS STORED, transport-free, decryption-free** (the consumer decrypts under its own context; the "assigned pool's VPA" `pa=` string is built by Epic 8, not here).
3. The **VPA → pool mapping is unique per pool per cycle**: the resolver **guards + a test asserts** that no two pools within a cycle share the same collection binding (i.e. distinct `claim_case_id` per pool ⇒ disjoint collection accounts). If two pools in a cycle resolve to the same collection accounts, wrong-pool detection is ambiguous → **fail loud** with a typed error, never silently pick one.
4. Absence is a **first-class signal**, never a throw-as-flow: a member with **no** assignment in the cycle (not active-at-freeze / not in any pool's latest snapshot) returns a typed "not assigned" result; a member appearing in **more than one** pool's latest snapshot for the cycle is an **integrity violation** → fail loud.

**AC2 — Wrong-pool classification (Given the same, consumed by Epic 9 reconciliation)**

5. A **pure** classification predicate takes `{ assignedPoolId, depositedToPoolId }` (both resolved by the caller) and returns a typed verdict `valid | wrong_pool` with a reason code; `wrong_pool` iff `depositedToPoolId !== assignedPoolId`. Deterministic, no clock / no DB / no I/O.
6. The verdict type + reason-code is a **contracts-layer `.strict()` type** (a Zod/TS union — **not** a DB enum: enum-width discipline, no dead surface until Epic 9's contribution record inserts it), homed for consumption by Epic 8 (button state) + Epic 9 (matcher) + Epic 10 (helpdesk).
7. The member-facing message for a wrong-pool deposit is the **UX-DR55 dignified copy** — semantically: *"We received your payment but it went to a different pool than your assigned one. We can't auto-move it. Tap 'Get help' to talk to our helpdesk."* — committed as an **i18n catalog entry with Hindi parity** (freeze row 10; the `i18n:check-parity` gate covers it).
8. Wrong-pool contributions are **NOT auto-refunded**; recovery is **helpdesk-mediated only** (Epic 10). This story commits the *policy in types + copy + gate*, not the helpdesk flow.

**AC3 — Facilitated-recovery invariant (this story's load-bearing commitment)**

9. The recovery guidance + helpdesk resolution **MUST NOT silently remap or auto-reassign** a payment in any way that breaks deterministic assignment or audit lineage. The system **structurally prevents** all three unsafe operations:
   - (a) auto-**moving** the payment to the member's assigned pool (falsifies audit history — the payment was made to pool X);
   - (b) auto-**reassigning** the member to the pool they paid into (breaks determinism — retroactively changing `hash(member_id + cycle_id) % N` corrupts replay);
   - (c) auto-**creating a phantom** contribution record in the assigned pool (distorts the pool's actual collection state).
10. The helpdesk operator's **allowed** actions are exactly, and only: (i) confirm the wrong-pool record as `invalid` with a reason; (ii) facilitate a manual refund discussion **off-band** (logged, not automated); (iii) document the family/member conversation; (iv) close the case with a documented outcome. Modeled as a **typed, closed action set** (a `.strict()` enum).
11. The helpdesk operator **cannot** change the original payment record, change the member's assignment, or move funds between pools *through the system*. Any such correction requires a **separate trustee-attestable correction event** — rare, audit-logged, signed by **≥ 2 trustees** (modeled as a typed seam on the `claim.correct_nominee_bank` / Story 7.5 emergency-attestation precedent; **no live route in Epic 7** — the seam + the invariant + the gate, the live surface lands with the Epic-9 record it would correct).
12. A **CI gate** (green-with-teeth, wired into `ci:local`) statically asserts **no API endpoint / handler exists that takes a `(wrong-pool-payment, target-pool)` pair and modifies records**. The only modifications allowed anywhere are to the **wrong-pool record itself** (its validity flag + helpdesk-case linkage), never **cross-pool data movement**. Teeth proven by a known-bad fixture that goes RED (a green scan over new files alone proves nothing — [[feedback_gate_scope_semantic_coverage]]).

**AC4 — Audit / regulator traceability**

13. Every wrong-pool payment + its facilitated recovery is **traceable**: original deposit (with the wrong pool's collection VPA), the invalid flag, the helpdesk-case linkage, the resolution outcome. The **deterministic assignment record for the member-cycle remains untouched** — a regulator can re-derive the exact assignment from `(cycle_id, member-state-at-freeze, N)` + the version pin at any time, unaffected by any recovery action. (The *record* is Epic 9's; 7.6 asserts the assignment-immutability property + the classification/linkage shape that makes traceability possible.)

### D1 — Source of truth for "which pool is this member in" is the SNAPSHOT, never a recompute (DECIDED — load-bearing)

`assign.ts` is explicit (lines 24–27): *"The PERSISTED snapshot (`pool_snapshots.member_assignments`) is the source of truth Story 7.6 reads for VPA resolution — never a naive recompute."* The balancing pass ([[project_pool_assignment_engine]] D1) means a redistributed member's **final** pool depends on the whole frozen roster; `hashMemberToBucket(member, cycle, N)` gives only the **base** bucket, which the balancing pass may have moved off. So resolution **must** read `pool_snapshots` (the latest per pool in the cycle) and find which pool's `member_assignments` contains the member. Do **not** call `assignMembersToPools` at resolution time.

- The snapshot shape: `pool_snapshots.snapshot` (JSONB, `PoolSnapshotV1`) carries `member_assignments: [{ member_id }]` (see `pool/snapshot.ts`). Validate/parse via `snapshot-adapters/pool-v1.ts::readPoolSnapshot` if you need the typed body; for a containment query you can hit the JSONB directly.
- "Latest snapshot per pool" = `pool_snapshots_pool_id_created_at_idx` (`pool_id, created_at DESC`). A pool accrues many snapshot rows over its life; use the latest.

### D2 — Resolution returns the BINDING (accounts, ciphertext), not a `pa=` VPA string (DECIDED)

FR-16 says "UPI Intent pre-fills the assigned pool's **nominee VPA**"; FR-31 (prd L608) says the intent **defaults to nominee account #1** with a "Switch account" link to **#2**. But the collection destination in the substrate is a **bank account (account# + IFSC), stored as Tier-1 ciphertext** on `claim_nominee_bank_accounts` (Story 6.8) — there is **no `@upi` VPA column**. The existing ₹110 flow builds `upi://pay?pa=${vpa}&am=…` **server-side, VPA never client-named** (`apps/api/.../vyawastha-shulk/handlers.ts:104`, R4) from a single **config** VPA (`vyawasthaShulkVpa`). Per-pool nominee VPAs are different: they come from the family's accounts.

**7.6's seam:** resolve the **binding** (assigned pool + the claim's nominee accounts, ciphertext AS STORED, #1/#2). The literal `pa=` construction + decryption is **Epic 8's `<UPIIntentButton>`** (Story 8.6) — it decrypts under its own encryption context (the `getClaimNomineeBankAccountsCiphertext` "consumer decrypts at disbursement time" discipline). 7.6 stays transport-free + decryption-free.

⚠ **Cross-epic risk to carry forward (flag in the Dev Agent Record, do not solve here):** NPCI's `upi://pay?pa=…` targets a **VPA**, not an account#+IFSC. If nominees only ever provide account#+IFSC (Story 6.8 collects exactly that), Epic 8 may be unable to deep-link a pre-filled payee and may fall back to manual "pay to bank account" entry — which weakens FR-16's "structurally unlikely wrong-pool" claim (UX-DR55/onboarding leans on the pre-fill). This is an **Epic-8 design question** (does the nominee also provide a VPA? does the account get a derived VPA?), surfaced here so it is not lost. It does not change 7.6's binding-resolution scope.

### D3 — Wrong-pool is CLASSIFIED here, RECORDED in Epic 9 (DECIDED — the primitive/consumer seam)

The epic body says *"Wrong-pool deposits (**Epic 9**) detected and treated as invalid"* and AC1 says *"**reconciliation (Epic 9)** matches deposits … recorded as invalid `wrong-pool`."* The `contributions/` + `reconciliation/` contract dirs are explicitly reserved for Stories 9.1/9.2/9.4; `ContributionId` is a pre-reserved-but-unused brand. So **7.6 does not create a contributions table or a persisted wrong-pool record.** It ships:

- the **verdict/reason type** (contracts `.strict()` union — a TS/Zod type, mapped to a DB enum by Epic 9 when the record lands; **no DB enum now** — enum-width/no-dead-surface discipline, the `pools.support_category` precedent),
- the **constrained-action model + trustee-correction seam + CI gate** that Epic 9/10 MUST obey.

This mirrors [[project_channels_no_live_dispatch_yet]]: a real primitive with the gate/seam in place before the live consumer exists.

### D4 — The facilitated-recovery invariant is enforced by ABSENCE + a gate, not by a feature (DECIDED — load-bearing)

AC3 is a **negative** commitment: the unsafe operations (auto-move / auto-reassign / auto-phantom / cross-pool fund movement) must be **structurally impossible**. The enforcement is: (a) do not build a remap endpoint; (b) a CI gate (Task 4) that fails if one ever appears; (c) a **typed closed action set** for the helpdesk (only the four allowed actions type-check); (d) the **trustee-attestable-correction seam** as the *only* sanctioned alteration path (≥2 trustees, audited — the `claim.correct_nominee_bank` tier-2-correction precedent + the Story 7.5 emergency-attestation-record shape). The gate's teeth are proven by a **known-bad fixture** (a handler that takes `(payment, targetPool)` and writes to `targetPool`) that must go RED — a green scan over new files proves nothing ([[feedback_gate_scope_semantic_coverage]]).

### D5 — Uniqueness of collection binding per cycle is a real correctness guard (DECIDED)

"VPA → pool mapping is unique per pool per cycle" makes wrong-pool detection well-defined: Epic 9 maps a deposit's destination account → pool; that must be unambiguous. Pool→claim is 1:1 (one pool per approved claim) and accounts are claim-scoped, so bindings are naturally disjoint **unless two claims in one cycle reuse the same bank account** (e.g. two deaths in one family — rare, not impossible; there is no `(cycle_id, claim_case_id)` uniqueness constraint on `pools` today, only `(pariwar, cycle, pool_index)`). Resolution must **guard** this and **fail loud** (`WrongPoolBindingAmbiguousError`) rather than silently pick a pool — a naive implementation would miss it. Cover with a test that spawns two pools sharing a claim/account and asserts the guard fires.
