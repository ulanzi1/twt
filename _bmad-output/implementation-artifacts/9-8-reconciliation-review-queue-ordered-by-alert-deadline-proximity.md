# Story 9.8: Reconciliation Review Queue — Ordered by Alert-Deadline Proximity

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As **a trustee or designated reconciliation reviewer working a heavy cycle**,
I want **a reconciliation review queue that gathers every open case — UTR mismatches, wrong-pool payments, self-verify screenshot uploads, and staff-transcription requests — ordered by how close each case's cycle is to its reconciliation deadline, with the full case context on one screen and the sanctioned actions (confirm / reject / facilitate-recovery) each gated by step-up OTP + reason-code + an attributed audit line**,
so that **I work the most time-sensitive cases first and resolve them while preserving the two load-bearing invariants: `contribution.confirmed` stays the sole canonical financial truth (Story 9.5) and reconciliation is never silently remapped (Story 7.6 facilitated-recovery)**.

> **What does NOT yet exist — 9.8's actual job (the four things to build):**
> 1. **The cross-member queue READ (the crux).** Every existing reconciliation/history read is single-scope (one `alertId`, one `cycleId`, or one `memberId`). There is **no** `contributions`/`reconciliation_cases` projection table (`history.ts:26`) and **no** cross-member reader — `reconciliation/read.ts` exports only `resolveLivePoolByClaim`. 9.8 builds a bounded, pariwar-scoped, deadline-ordered scan of `events_log` across **alert streams AND pool streams**, deduping open-vs-resolved with the existing `hasLiveConfirmation` chain.

This is the **same drafting-drift class** the Epic-8 retro corrected for the mismatch event name ([[project_contribution_event_name_contract]]). The substrate already has an opinion: `history.ts:69-73` explicitly distinguishes FR-50's `invalid` (the human-triage **reject verdict**) from the auto-detected red mismatch, and the codebase's established move is the `reconciliation.*` namespace (9.3 D6). **Decision D1 (below): reject emits a `reconciliation.*` event, `invalid` is the outcome word, not a `contribution.*` type. The 8.10 fence stays GREEN verbatim.**

## Acceptance Criteria

*(From epics.md §Story 9.8 L3281–3294, anchored on FR-50 [prd.md L791-797], FR-30 mismatch, Story 7.6 facilitated-recovery invariant, Story 9.5 canonical-financial-truth invariant, Story 5.9 step-up OTP, Story 6.11 attributed-decision pattern.)*

**AC1 — The queue lists every open reconciliation case in the trustee's Pariwar, ordered by deadline proximity (closest first).**
**Given** open cases exist across the reserved seams — red `contribution.reconciliation-mismatch` events (mismatch + `reason='wrong_pool'`), `reconciliation.self-verify-screenshot-uploaded`, `reconciliation.manual_transcription_requested`, and `computeStaffTakeover`-eligible pools
**When** a `reconciliation.review`-permitted actor opens the queue for their Pariwar
**Then** the queue returns one row per OPEN case (a case is OPEN iff it has no live confirmation AND no reject/close marker — computed via the existing `hasLiveConfirmation` chain), each carrying its case-type + member id + pool/alert id + machine reason-code + a derived deadline instant; rows are ordered by **deadline proximity ascending** (the cycle's reconciliation-tail deadline via `resolveAlertLiveWindow` + `reconciliationTailDeadline`; FR-50 "closer to Day-15 = higher priority"); the read is hard-scoped to the actor's `pariwarId` (RLS + explicit predicate) and bounded (`clampLimit`, scan restricted to reconciling cycles).

**AC2 — Each case shows the full review context on one screen.**
**When** the trustee opens a case
**Then** the detail panel shows: **member identity** (name + mobile via `searchMembers({by:'memberId'})` ciphertext → Tier-1 boundary decrypt with fail-soft `safeDecrypt`; the contributor is the LIVING member, not the deceased); **attestation details** (`utr`, `tr`, attested-at from `events_log.occurred_at`; expected amount from the pool's snapshotted `fixedAmount` via `getPoolContributionContext`); **bank statement entries near the relevant date** (`listEntriesForPools` for the case's pool, filtered/sorted in-memory against the alert window — amounts are integer **paise**, pool fixed-amount is whole-INR ⇒ compare ×100); **the screenshot if uploaded** (mint `SelfVerifyScreenshotStorage.signedReadUrl(objectKey, 300s)` on demand — the event stores only the key); and **contextual notes** (statement-upload / manual-transcription provenance from the pool stream). Missing/undecryptable optional data degrades to an explicit "unavailable", never a 500 and never a silent blank (the 6.10 AC7 compound-read posture).

**AC3 — Confirm emits `contribution.confirmed` — the ONLY manual confirmation path — gated by step-up OTP + reason-code + attributed audit.**
**Given** an open mismatch/pending case
**When** the trustee confirms (having satisfied step-up OTP for the `reconciliation_review_confirm` action context)
**Then** the action calls the EXISTING `appendConfirmedContribution` (no re-implementation, no re-spelled string) on the case's alert stream → the member flips to **green** everywhere via the already-wired 9.5 reads (contributor list adds them, Yogdaan Bahi/pill green, the 9.7 `<SelfVerifySurface>` `resolved`), the case leaves the OPEN queue, and a NON-PII audit line is emitted (`emitAuthAudit`, `admin_reconciliation.confirmed`, context = ids + district-free + `reason_code`, never rationale); the trustee's `display_name` is resolved server-side FIRST and fail-closed (`AdminDisplayNameMissingError` 409 — no event, no audit, no fallback — [[project_admin_display_name_attribution]]). The 8.10 `contribution.*` fence stays GREEN (no new type).

**AC4 — Reject emits a `reconciliation.*` event (NOT `contribution.invalid`), notifies the member, and closes the case.**
**Given** an open case the trustee determines is invalid
**When** the trustee rejects (step-up OTP for `reconciliation_review_reject` satisfied; a reason-code selected)
**Then** a NEW `reconciliation.*` reject event (D1) is appended on the alert stream carrying ids + machine `reasonCode` + `attestedByActorIds` (NON-PII) — the member's pill stays **red** (red already conveys mismatch/invalid; no new derivation arm), the case is marked CLOSED (drops from the OPEN queue via the reject marker), a best-effort member notification is enqueued (FR-50 "member notified"; D9 posture — never fails the committed verdict), and the attributed NON-PII audit line (`admin_reconciliation.rejected`, with `reason_code`) is written; display-name fail-closed as AC3. The 8.10 fence stays GREEN (reject is `reconciliation.*`, not a fourth `contribution.*`).

**AC5 — Facilitate-recovery leaves the case OPEN and changes NO reconciliation outcome (Story 7.6 — LOAD-BEARING).**
**Given** a case that needs off-band human resolution
**When** the trustee chooses facilitate-recovery (step-up OTP for `reconciliation_review_recover`; reason-code)
**Then** the action writes ONLY an attributed audit line (`admin_reconciliation.recovery_facilitated`, reason-code) and routes the case to helpdesk via a **reserved Epic-10 seam** (no live ticket UI) — it emits **no** `contribution.confirmed`, **no** reject/reverse event, **no** remap, **no** matcher re-run; the case stays OPEN in the queue (flagged in-recovery so it isn't re-worked blindly), and the member's status is unchanged. **Structurally** no code path in this action reassigns a pool, moves funds, or edits the original payment record — the `scripts/pool-bound-payment-invariant/` gate stays GREEN. A test asserts facilitate-recovery is outcome-inert.

**AC6 — Review-and-reverse (rare) walks back an already-confirmed contribution to `held` via `reconciliation.confirmation-reversed` (the substrate-committed 9.8 producer). — IN SCOPE (D3 ratified by BigDev 2026-07-27).**
**Given** a green (confirmed) contribution a trustee must re-open (the rare monotonic exception)
**When** the trustee reverses (step-up OTP for `reconciliation_review_reverse`; reason-code; ≥1 attesting actor)
**Then** a `reconciliation.confirmation-reversed` event (already defined + registered, `reconciliation/events.ts:120-137`) is appended naming the exact `reversedConfirmedEventId` → the 9.5 reversal-consumer reads back the confirmation out everywhere (contributor-list removal; pill green→**held**), a best-effort member notification is enqueued (D9), and the attributed NON-PII audit line (`admin_reconciliation.confirmation_reversed`, reason-code) is written; a subsequent fresh `contribution.confirmed` (new event id) **re-greens** (monotonic forward — a reversal never permanently poisons). Display-name fail-closed as AC3.

**AC7 — Auth, scope, audit, friction-budget, accessibility.**
**Then** every action requires step-up OTP bound to its own action context (an elevation for confirm never satisfies reject); the read + all actions are gated by the new `reconciliation.review` key at `dimension: 'pariwar'` (a cross-Pariwar actor cannot see or act on another Pariwar's cases — tested); all audit context is NON-PII (ids + reason-code, never UTR-in-the-clear beyond where load-bearing, never rationale/PII); the decision gate is declared in `friction-budget.md` (payer = trustee, protected = canonical financial truth + reconciliation integrity; no page-weight ratchet — Tier-2 admin, not the public bundle — [[project_friction_budget_baseline_ratchet]]); the surface targets WCAG-AA (a named, tracked gap is acceptable for this Tier-2 surface); `pnpm ci:local` green incl. the 8.10 fence + the pool-bound-payment gate + PII-scrape + i18n parity.

### The `contribution.invalid` trap — reject is a `reconciliation.*` event (LOAD-BEARING; Decision D1)

The epics AC and FR-50 say "reject → `contribution.invalid`." **Do not create a `contribution.invalid` event type.** It is a fourth `contribution.*` literal and trips the shipped Story 8.10 fence (`packages/domain/tests/contribution/no-ingest-path.test.ts:88-130`) at build time, with revert-sanity already proven. This is the exact drafting-drift class the Epic-8 retro corrected for the mismatch event name ([[project_contribution_event_name_contract]]). The substrate already draws the line: `contribution/history.ts:69-73` says FR-50's `invalid` is the human-**triage reject verdict**, distinct from the auto-detected red **mismatch** — and the codebase's established move (9.3 D6, 9.7 D2) is the `reconciliation.*` namespace. So: **the word `invalid` is the OUTCOME; the EVENT is `reconciliation.*`.** The member's pill stays **red** after a reject (red already conveys mismatch/invalid — there is no separate `invalid` arm in `deriveContributionStatus`, and none is needed); the reject event's jobs are (1) mark the case CLOSED for the open-vs-resolved computation, (2) carry the reason-code for audit, (3) trigger the "member notified" push. Follow the source contract, not the prose ([[project_calendar_aware_tail_not_window_extension]]).

**A second, unflagged instance of the same drift — the reversal event (D3).** epics.md's own AC prose for Story 9.4 (L3218) and Story 9.5 (L3248) names the review-and-reverse event `contribution.confirmation.reversed` — wrong namespace (`contribution.*`), wrong dot-notation — and attributes the producer role to Story 9.4, not 9.8. The shipped code already corrects this: `reconciliation/events.ts:110` carries an explicit comment that the event "lives in the `reconciliation.*` namespace DELIBERATELY (NOT `contribution.confirmation.reversed`)." Treat this the same way as D1: the source code is the contract, epics.md's prose here is stale drafting, not a second event to build.

### The crux — there is NO cross-member reconciliation read; 9.8 builds it

Every existing reconciliation/history read is single-scope (one `alertId`, `cycleId`, or `memberId`); there is no `contributions`/`reconciliation_cases` projection (`history.ts:26`) and no cross-member reader. A case also spans **two streams** — mismatch/confirmed/reversed/self-verify ride the **alert stream** (`stream_id = alertId`), while statement-upload/manual-transcription ride the **pool stream** (`stream_id = poolId`). And the `alerts` table has **no deadline column** (`schema/alerts.ts:77-144`). So Task 3 is genuinely new engineering: a bounded, pariwar-scoped `events_log` scan across both stream families, deduped open-vs-resolved with the existing `hasLiveConfirmation` chain, ordered by a **derived** deadline. The single most important design guard: **bound the scan to currently-reconciling cycles** (alerts in `live`/closed-within-tail) — that keeps the working set to the handful of live cycles per Pariwar and makes a `clampLimit` safe (it can't hide the most-urgent case because the urgent cases are exactly the ones in-window). Mirror the `getR9VotingQueue`/`getCycleFreezePending` structure (scope-safe leading `pariwar_id`, `clampLimit`, no-N+1 LEFT JOINs, denormalized provenance); add the cross-stream dedup + the deadline sort.

### Deadline proximity — a derivation, not a field (Decision D4)

FR-50: "closer to Day-15 = higher priority." There is no stored deadline. The reconciliation deadline is the **calendar-aware tail** (`cycle-calendar/holiday-resolver.ts:311` `reconciliationTailDeadline(closeInstant, holidayCalendar)` → `tailDeadlineAt`), which is a pure post-close derivation off the cycle's `alert.live → alert.closed` instants (`resolveAlertLiveWindow`, `matcher-reads.ts:301-327`). For a cycle still live (mismatches arise during matcher runs, before close), sort by the expected Day-15/close proximity; once closed, by the tail deadline. Compute per case in memory over the bounded set. Note that `alert.closed` (Story 8.9) may not be wired for all cycles yet — the grey/closed arm is still described as unreachable (`history.ts:39-41`); resolve gracefully (a live cycle sorts by its expected close, not a null tail).
