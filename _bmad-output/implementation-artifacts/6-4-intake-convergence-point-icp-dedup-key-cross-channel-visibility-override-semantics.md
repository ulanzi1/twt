# Story 6.4: Intake Convergence Point (ICP) — Dedup Key + Cross-Channel Visibility + Override Semantics

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As Solo Builder authoring the convergence primitive,
I want an Intake Convergence Point that deduplicates intakes arriving from member-app + helpline paths and **establishes a single canonical `claim_case_id`** that all downstream flows reference,
so that audit / replay / publication / notification are unambiguous and no hidden secondary IDs persist after convergence.

`[PRIMITIVE]` — substrate building block. The claim-lifecycle substrate (Story 6.1), both intake surfaces (6.2 member-app / 6.3 helpline), and the shared `initiateIntake` core already exist and are green. **6.4 formalizes the crude same-member convergence that 6.2/6.3 already do into a first-class, auditable, override-aware ICP primitive — and closes the one load-bearing gap it leaves open.**

## Acceptance Criteria

> Verbatim from `epics.md` §Epic 6 → Story 6.4 (lines 2343–2367). AC numbering added for task traceability; wording unchanged.

**AC1 — ICP primitive + dedup key** — *Given* AR-62 (ICP — dedup + cross-channel + override) + UX-DR75 + UX-DR41 `<IntakeDecisionStrip>`, *when* the ICP primitive is authored, *then* the ICP exposes `tryConverge(intake_attempt)` with a dedup key composed of `(pariwar_id, deceased_member_id, narrow time window e.g., ±30 days)`; duplicate intakes within the window are flagged for convergence.

**AC2 — `<IntakeDecisionStrip>` merge/override surface** — *And* the `<IntakeDecisionStrip>` admin UI surface shows pending intakes with potential matches; trustee or operator can confirm convergence (merge) or override (treat as separate cases).

**AC3 — cross-channel visibility** — *And* cross-channel visibility: when both paths exist within the dedup window, the ICP shell shows both to the resolving actor; both are linked under the canonical `claim_case_id`.

**AC4 — override semantics** — *And* override semantics: explicit "do not converge" decisions are recorded with reason + actor + audit log line; future intakes do not re-attempt convergence with cases that were explicitly overridden apart.

**AC5 — canonical case identity invariant (load-bearing)** — *Given* the **canonical case identity invariant** (this story's load-bearing commitment), *when* intakes have converged through the ICP, *then* all paths resolve to a **single canonical `claim_case_id`** — there is exactly one claim case object for the converged claim.

**AC6 — downstream references canonical id only** — *And* every downstream flow MUST reference the canonical `claim_case_id`, NOT channel-originating intake identifiers: verification (Stories 6.6/6.7/6.10/6.11), appeal (Story 6.16), audit (Story 1.10 entries reference `claim_case_id`), notification (Story 5.1 alerts carry `claim_case_id` in `provenance_refs`), publication (Epic 11b Sahyog Vivran references `claim_case_id`).

**AC7 — secondary ids discarded post-convergence** — *And* channel-originating intake identifiers (e.g., temporary `intake_attempt_id` from member-app or helpline systems) are **discarded post-convergence** — no hidden secondary IDs persist; intake-attempt records are retained for audit but explicitly marked `superseded_by_claim_case_id: <canonical>` and never referenced by downstream flows.

**AC8 — CI gate on non-canonical lookup keys** — *And* a CI test asserts no downstream code path (verification, appeal, publication, notification) accepts a non-canonical intake identifier as a lookup key; all such code paths take `claim_case_id` only.

**AC9 — unambiguous audit lineage** — *Given* an audit / regulator / dispute query, *when* the history of any converged claim is traced, *then* the lineage is unambiguous: both intake attempts (with their channel-originating context) are recorded as pre-convergence events; the convergence transition is its own audit line; everything after references only the canonical `claim_case_id`.

> **⚠ RECONCILIATION (AC1/AC2 cite `<IntakeDecisionStrip>` — do not build a component with this name):** `epics.md`'s Story 6.4 AC2 misattributes `<IntakeDecisionStrip>` to ICP merge/override semantics. ## Dev Notes

### The two load-bearing insights (read these first)

**1. `claim.intake_converged` is currently NEVER emitted — the `intake_converged` state is unreachable, and it silently blocks the 6.5 documents chain.** The reducer (`claim/state.ts:104-107`) only advances `intake_converged → documents_pending` on `claim.documents_received`, and only from `intake_converged`. But nothing in the codebase emits `claim.intake_converged` (grep confirms: the only hits are in the minified `dist` bundle). So today every claim is stuck at `intake_pending` forever. **6.4 owns this transition** — emitting `claim.intake_converged` is the ICP's job (the event's own doc comment says so: `events.ts:99` "ICP dedup picked the canonical claim → `intake_converged`. Owner: Story 6.4"). This is not optional polish; it is the mechanism that makes the claim lifecycle progress past intake.

**2. 6.2/6.3 already do crude same-member convergence — do NOT rebuild it, formalize it, and do NOT regress it.** `initiateIntake` (`claims.service.ts:234`) already: (a) takes a tx-scoped advisory lock on `(pariwarId, deceasedMemberId)`; (b) reads `getClaimByDeceasedMember` (non-terminal, most-recent) and returns the existing claim with `created: false` if one exists — so a member-app filing and a helpline filing for the same death **already resolve to one `claim_case_id` with one freeze.** The shipped 6.3 Dev Agent Record calls this "crude cross-channel convergence; the RICH ICP visibility/override is Story 6.4." So the substrate is right; 6.4 adds: the `±30-day window`, the first-class `intake_attempts` ledger (so the second-channel "attempt" is a durable audited artifact awaiting resolution, not just an ephemeral `created:false` return), the `claim.intake_converged` emission (once, on the lone-intake auto-converge), the operator-driven merge (which unions the channel — see Task 5), the override ledger + separate-case path, the `<ConvergenceDecisionStrip>`, and the AC8 gate.

> **The single, coherent convergence model** (do not mix pre-merge and post-merge semantics):
> - **Lone intake** → immediately canonical + `intake_converged`. With an exact-`deceased_member_id` dedup key a lone intake is unambiguously the canonical case — nothing to disambiguate — and holding every single-channel death `intake_pending` awaiting a manual step would strand the common path (and block the 6.5 documents chain).
> - **Later exact cross-channel match** → **preserve** the existing canonical claim + single freeze; record the second attempt as `pending`; expose both channels on the `<ConvergenceDecisionStrip>`. **Do NOT auto-merge.**
> - **Authorized merge** (operator/trustee on the strip) → mark the attempt `converged`, union the channel, emit the convergence AUDIT line. No lifecycle event.
> - **Authorized override** → mint the distinct canonical claim + record the `convergence_overrides` ledger row.
>
> The `<ConvergenceDecisionStrip>` is therefore a genuine **pre-merge decision** surface — "confirm merge" *performs* the merge (it was not auto-done); "override" records the separation. This is exactly AC2 verbatim ("trustee or operator can confirm convergence (merge) or override"). Do NOT eager-auto-merge cross-channel matches — that would demote the strip to a post-hoc correction surface and contradict AC2/AC4's decision language.

> **Convergence establishes identity, NOT merit — do not conflate the two.** Auto-convergence (and merge) establishes only the **canonical claim-case identity**: which `claim_case_id` this intake belongs to. It does **not** verify the death, the claimant relationship, nominee entitlement, documents, eligibility, or claim merit — all of which remain subject to the downstream human verification + adjudication workflow (OCR parity 6.5 · peer mesh 6.6 · ground inspection 6.7 · verifier console 6.10/6.11 · State Trustee freeze 6.13 · appeal 6.16). The lifecycle states past `intake_converged` exist precisely because identity-resolution and merit-adjudication are separate concerns. A reader must never treat "converged" as "validated."

## Open Questions (surfaced for SM/PO — do not block dev; recommended defaults noted)

1. **Convergence model — DECIDED (not open), stated here so it isn't re-litigated:** lone intake → auto-converge to `intake_converged`; cross-channel second intake → recorded `pending`, resolved by an authorized operator/trustee **merge** or **override** on the `<ConvergenceDecisionStrip>` (a genuine pre-merge decision — nothing is auto-merged). Matches AC2/AC4 verbatim. **Lone-intake auto-convergence is kept** (BigDev 2026-07-09): there is no competing intake to adjudicate, and forcing every bereaved family through a human ICP queue would convert a *deduplication* mechanism into a *mandatory operational approval stage*.
