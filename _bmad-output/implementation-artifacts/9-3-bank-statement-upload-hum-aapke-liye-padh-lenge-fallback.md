# Story 9.3: `<BankStatementUpload>` + "Hum aapke liye padh lenge" Fallback `[SURFACE]`

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As Sunita (a bereaved nominee) uploading her daily bank statement into the Nominee Console,
I want a forgiving upload surface that accepts a bank-allowlisted file, runs the Story 9.2 parser inline, gives me an immediate parse-success summary or a dignified parse-failure explanation, and offers **"Hum aapke liye padh lenge"** (we'll read it for you) — a staff-mediated fallback — whenever the file cannot be parsed,
so that I am **never stranded** with an unparseable statement, and donors never sit at false-yellow because a statement silently failed to land.

## Scope — what belongs to 9.3 vs what is a reserved seam

> **Build-order reality (READ THIS FIRST).** Story 9.3 is the `[SURFACE]` + **transport** that Story 9.2 (the `[PRIMITIVE]` pure parser) explicitly deferred to it. 9.2 built the pure parse engine (`parseStatement`), the canonical `BankStatementEntry` schema, the 250 golden files, the `bank-allowlist.yaml` governance, and the `ParseResultSummary` contract — but **NO upload endpoint, NO object storage, NO virus-scan, NO DB write, NO AR-45 wiring** (9.2 Decisions D1/D2/D3; ADR-0034 "storage WIRING resolved via explicit deferral to Story 9.3"). 9.3 builds exactly that transport + the member/staff surfaces on top of it. It does **NOT** build the matcher (9.4), the pill flip (9.5), the `<StatusPill>` (9.6), the mismatch/screenshot surface (9.7), or the review-queue render (9.8). Same house discipline as 9.1/9.2: build honestly, leave first-class `{available:false}` / reserved-seam shapes for the unbuilt consumers, never fake a downstream ([[project_nominee_vpa_deferred_seam]], [[project_channels_no_live_dispatch_yet]], [[feedback_record_unattested_no_backfill]]).

## Acceptance Criteria

Adapted from epics.md §Story 9.3 (lines 3187–3199) and decomposed for the dev. **AC1 is not a verbatim carry-over**: epics.md's prose says the surface "accepts PDF or CSV" — Decision D1 (below) resolves that to the CSV-first-with-human-fallback shape below; see "The PDF-vs-CSV reconciliation" in Dev Notes for the full reasoning.

**AC1 — Forgiving upload surface: allowlisted file in, parser runs inline, ~5s feedback.**
**Given** UX-DR36 (`<BankStatementUpload>` — Sunita's daily upload surface)
**When** the upload surface is implemented
**Then** it **accepts a file from the 5-bank allowlist** (SBI / PNB / BoB / BoI / the named Bihar cooperative), **runs the Story 9.2 `parseStatement` inline** over the uploaded buffer, and returns **feedback within ~5s**: either a **parse-success summary** (the `ParseResultSummary` — rows parsed / rows rejected + per-reason breakdown / bank + parser version) OR a **parse-failure explanation** (dignified, Pattern-4 grammar — never "Error/Invalid/Failed").
> **CSV-only v1 (9.2 D2 carries forward).** The 5 v1 banks are CSV; a **non-CSV upload (PDF/image) or an unknown-bank file is NOT parsed** — it is routed to the AC2 fallback (or rejected with dignified helpdesk routing per `UnsupportedBankError`), not crashed and not silently accepted. The epics "accepts PDF or CSV" prose reconciles to **"the surface accepts the file the nominee has; a CSV from an allowlisted bank parses inline, everything else takes the human fallback path"** — the fallback is precisely the path that makes "accepts PDF" true without a v1 OCR engine. See **Decision D1**.

**AC2 — Parse failure offers two paths, one of which is the staff fallback.**
**And** parse failure offers **two paths**: (a) **retry** with a corrected format (re-pick the file; the surface stays; no data lost); (b) **"Hum aapke liye padh lenge"** — a **staff-mediated manual-entry request** with a **24–48h SLA**, where staff transcribes the statement from their side.

**AC3 — The fallback creates an audit-logged, attributed District-Admin task that feeds the matcher.**
**And** the fallback **creates an audit-logged task in the District-Admin queue with attribution** (who requested it, which pool/claim, which nominee, when) — the audit line + a **reserved-seam event/derivation** the Story 9.8 review queue / Epic-10 helpdesk will consume; and its **resolution feeds back into the matcher** (a resolved manual-entry produces `BankStatementEntry` rows the Story 9.4 matcher consumes — the feedback path is a documented seam, not a live matcher call in 9.3).

**AC4 (cross-cutting — AR-45, inherited via 9.2 seam) — external-call resilience at the storage/scanner boundary.**
**Given** AR-45 external-call resilience (the seam 9.2 recorded in ADR-0033 / bank-parsers README as owned by the 9.3 transport)
**When** the upload pipeline makes an external call (object-storage `put`/signed-URL, the virus-scan step)
**Then** each external call is wrapped with **retry-with-backoff (3× exp), an enforced timeout, and a circuit-breaker**; **all failures are audit-logged**; a storage/scanner outage yields a **dignified retry-or-defer** to the nominee, never a 500 wall.

**AC5 (cross-cutting — grief-paced UX + a11y + save-and-resume) — inherited from Story 9.1 AC2/AC4.**
**Given** the Story 9.1 "fursat" invariant + the Story 0.10 accessibility gate + Story 0.9 grief-context findings + UX-DR50
**When** the upload surface renders
**Then** all copy passes the `fursat-pressure` tone gate + tone-review (no urgency/gamification/pre-threshold pressure); it is **screen-reader-accessible** (role/label/hint on every affordance; upload + processing announce progress; the failure path is dignified, not "error"); **Hindi-first with English parity** (Story 2.1); and **save-and-resume** (UX-DR50) preserves a paused/partial upload across app restarts (MMKV, extending the 9.1 `console-resume.ts` shape), offers a **resume-link delivery option (SMS · email)** so the nominee can resume from elsewhere, and falls back to a **resume-failed (helpline fallback)** state when local restore isn't possible (ux-spec L2134–2141).
