# Story 7.7: Idempotent Payment Reference + Amount-Lock at UPI Intent

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As **the contribution-receiving pipeline** (the consumer that Epic 8's `<UPIIntentButton>` pre-fills from and Epic 9 reconciliation dedupes/validates against),
I want **an idempotent payment-reference primitive — a deterministic, bounded, version-pinned `tr=` derived from `(member_id, alert_id)` that is stable across repeated attempts, plus an amount-lock primitive that surfaces the assigned pool's snapshotted `fixed_amount` and a pure `amount_mismatch` classifier extending the 7.6 contribution-validity union**,
so that **repeated payments for one member×alert reconcile as a single valid contribution (idempotent by construction) and any deposit whose amount ≠ the locked `fixed_amount` is classified invalid — never silently auto-corrected — exactly as wrong-pool is**.

## Context & Scope (read this first)

This story is `[PRIMITIVE]`. It is the amount/idempotency sibling of Story 7.6 (pool-bound enforcement) and follows the **same primitive/consumer seam discipline** — it commits the domain + contracts building blocks that Epic 8 and Epic 9 consume; it does **not** build those consumers.

## Acceptance Criteria

**AC1 — Deterministic, bounded, version-pinned `tr=` derivation (Given FR-17 + Story 1.12 idempotency keyed store)**

1. A **pure** `deriveContributionReference({ memberId, alertId })` returns a deterministic `tr=` string that is **stable across repeated attempts** for the same `(member_id, alert_id)` — so a repeated payment carries the **same** `tr=` and reconciles as the **same** contribution (idempotency by construction, AC1 of the epic). No clock, no DB, no randomness — the "nonce" in the epic's `tr=contrib-{member_id}-{alert_id}-{nonce}` sketch is a **deterministic derived component**, never a per-attempt random value (a random nonce would defeat idempotency).
2. The derivation is **VERSION-PINNED as a whole** — a single `CONTRIBUTION_REF_VERSION` (the `POOL_ASSIGNMENT_HASH_VERSION` precedent, [[project_pool_assignment_engine]] D0) gates the entire contract: `{ prefix, hash function, preimage delimiter/encoding, truncation width }`. Epic 9's reconciler must reproduce the **identical** `tr=` from `(member_id, alert_id)` + the version pin at any time — replay identity. **Frozen seeded vectors** pin the exact bytes so a silent algorithm drift is caught (the 7.4 frozen-vector discipline).
3. The reference is **bounded** to a safe UPI `tr=` length (see **D1** — recommend ≤ 35 chars, the NPCI transaction-reference ceiling). A `tr=` that some UPI app truncates would **collide** and silently break the idempotency guarantee, so length is a first-class correctness property, not cosmetic — asserted by a test over the derivation output.
4. `alertId` is an **opaque branded `AlertId`** parameter. **No live alert exists in Epic 7** — the alert engine + `alert_id` are Epic 8 ([[project_pool_spawn_saga_atomicity]]). The derivation ships with **no live call site**: Epic 8's `<UPIIntentButton>` (Story 8.6) is the producer, Epic 9 the dedupe consumer. `member_id` is a branded `MemberId`.

**AC2 — Amount-lock resolution + `amount_mismatch` classification (Given FR-18 + Story 7.5 fixed-amount snapshot)**

5. The locked `am=` is the **assigned pool's snapshotted `fixed_amount`** (Story 7.5) — the value **already persisted on the pool at spawn** (`pools.fixed_amount` / `pool_snapshots…fixed_amount`), **never a live `getEffectiveFixedAmount` recompute at intent time** (the snapshot is truth for replay, exactly as 7.6 reads the assignment snapshot, not `assignMembersToPools`). Surface it as a field on the member-cycle collection binding ({@link resolveMemberContributionBinding}) so the Epic-8 consumer reads one authoritative amount alongside the accounts.
6. A **pure** `classifyContributionAmount({ expectedFixedAmount, depositedAmount })` returns a typed verdict `valid | amount_mismatch` + a reason code; `amount_mismatch` iff `depositedAmount !== expectedFixedAmount`. Deterministic — no clock, no DB, no I/O. (Amounts are whole INR integers, mirroring `fixed_amount`; the classifier does not do currency/paise arithmetic — Epic 9 normalizes a deposit to whole INR before calling.)
7. **Extend** the 7.6 contribution-validity union with `amount_mismatch` + its reason code (`amount_does_not_match_fixed_amount`) in **BOTH** layers: the canonical `CONTRIBUTION_VALIDITY_VERDICTS` / `CONTRIBUTION_VALIDITY_REASON_CODES` tuples in `@twt/domain`, and the `.strict()` Zod `ContributionValidityVerdict` / `ContributionValidityReasonCode` in `@twt/contracts` (re-declared value-aligned — contracts cannot import `@twt/domain`). Extend `VERDICT_REASON_PAIRING` + the `ContributionValidityResult` `.refine()` **in lockstep** so a mismatched pair still cannot parse. The cross-package lockstep test must cover the new value.
8. `amount_mismatch` is **NOT auto-corrected** — no auto-topup, no silent amount rewrite, no "round to fixed_amount" — recovery is **helpdesk-mediated only**, analogous to wrong-pool (FR-18 consequence + FR-36 facilitated path). The dignified member-facing message is committed as an **i18n catalog entry with Hindi parity** — a sibling of 7.6's `wrong_pool.*` in `packages/i18n/locales/{en,hi}/contribution.json` (the `i18n:check-parity` gate covers it; no-blame tone per UX-DR55/UX-DR76).

**AC3 — Reconciler-dedup contract + verdict composition + facilitated-recovery reuse (Given Story 1.12)**

9. **Document the reconciler-dedup contract** that Epic 9 obeys: reconciliation dedupes by `tr=` → **one valid contribution per `(member, alert)`** regardless of repeated payment attempts; a **duplicate payment with the same `tr=`** returns the **previously-recorded outcome** (no double-credit; audit log shows a duplicate was detected) — implemented via the **Story 1.12 keyed store** keyed on the `tr=` (or a `contrib:{tr}` key). 7.7 supplies the deterministic `tr=` that makes this dedupe well-defined; **it does not build the reconciler or call `keyedStore.claim`** (the primitive/consumer seam, mirroring 7.6 D3).
10. **Verdict composition/precedence is documented** (Epic 9 composes, 7.7 provides the orthogonal predicates): destination is classified **first** ({@link classifyContributionDestination}); the **amount check applies only to a deposit that reached the CORRECT (assigned) pool** — a `wrong_pool` deposit is `wrong_pool` regardless of amount (you never compare a deposit against a non-assigned pool's `fixed_amount`). So `wrong_pool` takes precedence over `amount_mismatch`; the two pure predicates stay single-responsibility and independently testable.
11. `amount_mismatch` recovery **reuses the 7.6 facilitated-recovery machinery** — the CLOSED `HelpdeskWrongPoolAction` set + the `TrusteeAttestableCorrectionRequest` seam — and introduces **no new auto-correct / auto-topup surface**. The existing `pool-bound-payment-invariant` CI gate already forbids the analogous cross-record mutation; assess whether its **semantic coverage** must extend to any new amount-mutating surface (per [[feedback_gate_scope_semantic_coverage]] / [[project_access_wrapper_gate_pending_scope]]). If 7.7 adds no new mutable surface (expected — the closed-action model makes auto-correct unrepresentable, the 7.6 D4 posture), **do not add a redundant gate**; record the decision explicitly rather than over-gate a reliably-caught family ([[feedback_mechanization_split_commitment]]).

**AC4 — Audit / regulator traceability**

12. The lock + the reference are **replay-traceable**: the pool's snapshotted `fixed_amount` (the `am=` source) is **immutable and re-derivable** from the spawn snapshot; the `tr=` is **reproducible** from `(member_id, alert_id)` + the version pin at any time; an `amount_mismatch` deposit + its facilitated recovery is traceable (the deposit's actual amount, the invalid flag, the helpdesk-case linkage, the outcome) with the **assignment and amount records untouched** by any recovery action — the 7.6 assignment-immutability property, extended to the amount. (The *record* is Epic 9's; 7.7 asserts the immutability + reproducibility properties that make traceability possible.)

### D1 — The `tr=` is a bounded, version-pinned DERIVATION, not the raw `{member_id}-{alert_id}-{nonce}` string (DECIDED — recommended, flag the alternative)

The epic sketches `tr=contrib-{member_id}-{alert_id}-{nonce}`. Read **literally**, with UUID `member_id` + `alert_id`, that is ~90 characters — well past the **NPCI `tr` (transaction reference) ceiling of ~35 chars**. A UPI app that truncates a too-long `tr=` would produce a **collision** (two different member×alert pairs sharing a truncated prefix) that silently breaks the one-valid-contribution-per-alert guarantee — a correctness failure, not cosmetics. So the recommended design **honors the AC's INTENT** (deterministic, stable-per-`(member,alert)`, dedupe-able) while producing a **bounded** reference:

- `tr = "contrib-" + <version tag> + <base32(SHA-256(`${memberId}:${alertId}`))[:N]>`, version-pinned exactly like `POOL_ASSIGNMENT_HASH_VERSION` gates the whole assignment algorithm. The "nonce" of the sketch = this **deterministic derived digest component** (same for repeats → idempotent; it is NOT a random per-attempt value).
- **Alternative (record, don't silently drop):** the literal `contrib-{member_id}-{alert_id}` verbatim. Simpler and self-evidently unique, but risks the truncation-collision above and puts raw internal UUIDs in the payment reference. If the dev/reviewer/PM prefers the literal, the length-ceiling AC (AC1.3) must be relaxed or NPCI's actual `tr` handling confirmed for the target UPI apps first.
- **Sub-decision — plain hash vs keyed HMAC:** a plain SHA-256 digest is enumerable (anyone with `member_id`+`alert_id` can compute the `tr=`), but both are internal UUIDs never exposed to members, so enumerability is low-risk. A **keyed HMAC** (secret via Secret Manager, AR-13) buys non-guessability but introduces a **key-rotation hazard**: rotating the key changes every `tr=` → breaks idempotency for in-flight alerts, so the key would itself need pinning/versioning. **Recommend the plain version-pinned hash** for replay-safety + simplicity; note HMAC as a deferred hardening if a threat model ever demands non-enumerability. **Flag this to review** the way 7.6 flagged its D2 VPA/account risk.

⚠ **Carry forward to Epic 8/9 (flag in the Dev Agent Record, do not solve here):** the exact NPCI `tr` length + charset the target UPI apps accept (BHIM/PhonePe/GPay/Paytm) should be confirmed when Story 8.6 builds the live `<UPIIntentButton>` — the pinned truncation width in AC1.3 is chosen conservatively but is a real UPI-app-behavior dependency.
