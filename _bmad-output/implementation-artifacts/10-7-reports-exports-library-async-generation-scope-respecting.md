# Story 10.7: Reports & Exports Library — Async Generation + Scope-Respecting `[SURFACE]`

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Pariwar admin or trustee needing data exports for reporting / audit / regulator submission,
I want a reports & exports library with async generation + scope-respecting output + standard report templates in CSV and JSON,
so that I can pull the numbers I need without crashing the system, without leaking a single out-of-scope row, and without exfiltrating raw Tier-1 PII I have no standing to decrypt.

## Scope Boundary (read first — prevents over-build AND under-build)

**This is a `[SURFACE]`, not a `[PRIMITIVE]`.** Unlike Story 10.6 (which shipped a pure domain harness with NO `apps/api` route and NO real operation), 10.7 ships an **end-to-end operator surface**: a lifecycle table + migration, a domain report-template registry + assembly core, contracts DTOs, a pg-boss build worker, `apps/api` request/poll/download routes, a minimal `apps/admin` console, and a "report ready" readiness signal. The reason it is still tractable on solo-build cadence is that **almost all of the async-export machinery already exists** — Story 3.11 (member DPDPA data-export) built the exact `pending → ready|failed → consumed|expired` lifecycle, envelope-encrypt-at-rest, one-time 24h authenticated download, and hygiene-vacuum you are about to build the admin analog of. **You are cloning a proven shape and swapping its audience semantics, not inventing async export.**

**The single load-bearing semantic difference from 3.11 is the requestor's standing.** In 3.11 the *member* exports their *own* data → the assembler **decrypts** their Tier-1 PII because the member is the legitimate audience (architecture §2.7). In 10.7 an *admin/trustee* exports *other members'* data → the report is **scope-respecting** (out-of-scope rows excluded, per-row RBAC) **and PII-masked** (Tier-1 fields are NOT decrypted into a report in v1). This is the whole reason 10.7 is its own story and not "run data-export for a district." Get this wrong and you have built a bulk PII-exfiltration tool with an audit line on it — exactly what FR-58A's "scope-respecting, no cross-scope leakage" and the epics' **bulk-export prohibition** (epics.md:3731, 3835 — "bulk download / CSV export of member-directory data PROHIBITED outside explicitly authorized operator workflows … scope-respecting + audit-logged") exist to prevent. 10.7 *is* that "explicitly authorized operator workflow"; it earns that status by masking, by scoping, and by auditing every pull.

## Acceptance Criteria

**AC1 — Standard report templates exist in a registry; custom read-authority gated per template (Decision 1, 6).**
Given FR-58A + Story 1.8 RBAC,
When the reports library is authored in `packages/domain/src/reports/`,
Then a **report-template registry** (`createReportRegistry()` → keyed by `reportType`) is seeded with the v1 template set, and a `ReportTemplate` contract defines what each template contributes: `reportType` (string id), `permissionKey` (RBAC key), `scopeDimension` (`ScopeDimension`), a `columns` declaration (each `{ key, header, piiTier: 1|2|3, decryptIfPermitted?: false }`), and a PURE `query(scopeCtx, client) → Promise<Row[]>` that pushes the actor's resolved scope into its SQL;
And the **v1 seed set** ships at least three templates chosen to exercise every distinct axis (NOT all ~10 FR-58A reports — the rest register in follow-ups, Decision 1): (a) a **member roster** (Tier-3-clear + masked columns only; a district-scoped read); (b) a **scope-filtered aggregate** (e.g. monthly contribution-rate by district — proves the scope-as-predicate narrowing on a GROUP BY); (c) the **audit-log report** (Auditor-only, reusing the existing `audit.export` key);
And an unknown `reportType` fails closed with a typed `UnknownReportTypeError`; the assembly harness references ONLY the `ReportTemplate` contract + the registry lookup — **zero comparison against a specific `reportType` literal** (inherits 10.6 Decision 5 / AC7b; a harness `reportType ===` branch is a review-blocking regression).

**AC2 — Async generation via pg-boss; poll-status; notify-when-ready (Decision 5, 7).**
Given a caller `POST …/admin/reports` with `{ report_type, format, params }`,
When the request is authorized,
Then the API inserts a `pending` `report_exports` row (idempotent: a second request while one is in flight for the same `(requested_by_actor_id, report_type, params_hash)` returns the in-flight row, the 3.11 `findActiveExport` guard shape) and enqueues a `REPORT_EXPORT_BUILD` job carrying a `JobEnvelope { pariwarId, actorId, traceId, payload: { reportExportId } }`;
And the `apps/jobs` worker assembles the report OFF the request path (large reports take minutes — the async rationale), and the requestor watches `pending → ready|failed` via `GET …/admin/reports/:id`;
And on flip-to-`ready` the poll-status route is the mandatory readiness signal; an in-app push to the requesting admin is best-effort on the existing dispatch seam (Decision 7).

**AC3 — Scope-respecting output: every row RBAC-validated, out-of-scope excluded (Decision 3).**
Given the requesting actor's resolved scope (`scopeCtx`: `{ actorId, grants, pariwarId, resolvedScope }`),
When a template's `query(scopeCtx, client)` runs,
Then the actor's scope is pushed into the SQL predicate so out-of-scope rows are **never fetched** (a District Admin's roster query filters to their district; an Auditor's audit-log report spans the full log; RLS tenant-isolates `pariwar_id` underneath);
And the deny-deeper geo asymmetry holds ([[project_rbac_geo_scope_containment]]): until the Epic-3 geo-tree resolver, a `state`-scoped actor's `district`-granular report resolves nothing below its ceiling — documented, the same asymmetry 10.3/10.4/10.5/10.6 shipped, not a defect;
And a live-DB test seeds rows across two districts and asserts a district-scoped actor's report contains ONLY their district's rows (no cross-scope leakage — FR-58A / FR-59) and a cross-Pariwar actor sees zero (RLS).

**AC4 — CSV + JSON formats; PII masked per AR-12 tier unless RBAC permits (Decision 2).**
Given `format ∈ { csv, json }`,
When the worker serializes the assembled rows,
Then CSV is produced via the reused `toCsv` (`packages/domain/src/bulk-operations/csv.ts` — formula-injection-safe, RFC-4180) and JSON via canonical serialization; the format is a request param;
And **Tier-1 PII is masked, never decrypted into the report in v1** (Decision 2): report templates emit only Tier-3 clear + Tier-2 hashes + already-stored masked derivations (e.g. `aadhaar_masked_id`); a test asserts no seeded template's `columns` project a Tier-1 ciphertext column as plaintext;
And the **decrypt-if-permitted** path is a first-class deferred seam: `ReportColumn.decryptIfPermitted` resolves `false`/masked in v1; the `reports.view_pii`-style capability + gate + its audit are a named forward commitment ([[project_nominee_vpa_deferred_seam]] discipline — the worker HAS the crypto like the 3.11 worker, the *authorization* is what's deferred).

**AC5 — One-time, 24h, authenticated download; envelope-encrypted at rest; audit per operation (Decision 4).**
Given a `ready` report export,
When the requestor `GET …/admin/reports/:id/download`,
Then the artifact is streamed via the 3.11 handler shape — guards in order: owned-by-actor → not-consumed (`410`) → `ready` (`409` if not) → not-expired (`410`); `consumed_at` is stamped conditionally BEFORE streaming (a concurrent double-download loses → `410`); the stream sets the format's content-type (`text/csv` / `application/json`), never JSON-embeds the artifact;
And the artifact is **envelope-encrypted at rest** in `artifact_ciphertext` (the 3.11 posture — even masked, scope-restricted admin aggregates are sensitive, and the deferred Tier-1 path will put real PII here) and decrypted in-memory only during the gated stream; a `REPORT_EXPORT_VACUUM` cron zeroes `artifact_ciphertext` for consumed/expired rows + flips past-window → `expired` (the 3.11 vacuum);
And **one audit line per export operation** (FR-47): the build writes a `report.generated` (or per-report-type) audit line with NON-PII context (`report_export_id`, `report_type`, `row_count`, `artifact_bytes`, `status`), and the download writes a `report.downloaded` line; both carry the export's `traceId`, `actorId`/`actorRole` from the requestor ([[project_admin_display_name_attribution]]), `requestPayloadHash` = a sha256 digest (never the raw params).

**AC6 — Tests + gates green.**
Given `pnpm ci:local` (`--concurrency=4`, DB on :5433) is the primary sanctioned merge gate ([[project_ci_actions_suspension_local_mirror]], [[project_ci_local_concurrency_oversubscription]]),
Then domain unit tests cover: the registry (unknown-type fail-closed; the Open/Closed proof — two divergent fixture templates flow through the unchanged `assembleReport`, no `reportType` branch); the masking invariant (no seeded template projects Tier-1 plaintext); `toCsv` reuse (the serializer is imported, not re-implemented); per-template `permissionKey`/`scopeDimension` declared;
And live-DB integration tests cover: scope-respecting narrowing (two-district seed, district-scoped actor sees only their rows, cross-Pariwar sees zero — AC3); the full lifecycle (`pending → ready` build → one-time download `410`-on-replay → expiry/vacuum) against a real `report_exports` row and the real `writeAuditEntry` (assert `traceId` grouping / membership, not absolute counts — the audit chain self-commits + accumulates, [[project_live_db_test_gotchas]]); the idempotent-request guard;
And contracts tests cover the DTO round-trip + a domain↔contracts enum/shape sync-guard (test-only cross-import, [[project_contracts_domain_bundle_boundary]]); `emit-openapi.ts` + `openapi/v1.yaml` regenerated; the new migration trips no determinism/schema-diff/pii-scrape gate; `pnpm ci:local` green.

## Load-Bearing Decisions

Each is surfaced with a firm recommendation + the rejected alternative (the 10.4/10.5/10.6 house style). **All seven decisions are CONFIRMED by the product owner (2026-07-30) — implement the recommendation as written; the rejected alternatives are closed.** The per-decision text is retained as the rationale of record (why the harness is shaped this way), not as an open question.

1. **Template scope — RECOMMEND ship the registry + harness + a 3-template representative seed set, NOT all ~10 epic/FR-58A reports.** FR-58A names 8 report types (contribution-rate, under-collection watch, new-member funnel, reconciliation throughput, claim cycle-time, field-worker payout, helpdesk SLA, audit-log query); the epic's AC prose (epics.md:3496) adds 2 more (member roster, claim outcomes) to round out the ~10-report target set. The adversarial PRD review flagged exactly this: "FR-58A alone is ~10 distinct report types — solo-build will under-deliver … the gap surfaces mid-claim-cycle." The honest move is to build the **mechanism** (registry + Open/Closed harness + async + download + masking + scoping) once, prove it with a seed set that exercises every distinct axis (a Tier-3-only roster; a scope-narrowed GROUP BY aggregate; the Auditor-only audit-log report), and let the remaining types register via the same contract in cheap follow-ups. *Rejected alternative:* implement all ten now — rejected as the classic under-deliver trap; ten hand-built report queries with no shared harness is what FR-58A's review warned against, and most of the ten read from Epics (8/9/6/field-worker) whose shapes are still settling.

2. **PII posture — RECOMMEND reports NEVER decrypt Tier-1 in v1; mask-by-default is the load-bearing guarantee, decrypt-if-permitted is a deferred seam.** This is the semantic that makes 10.7 ≠ 3.11. 3.11 decrypts because the member is the legitimate audience of their OWN data; a 10.7 report reads OTHER members' rows for an admin. Admin-side Tier-1 decryption is its own crypto-boundary concern ([[project_helpdesk_responder_surface_104]]: the admin request path carries ADMIN-identity keys, not member field-crypto — and even in the worker, decrypting a *district's worth* of members' mobiles into a downloadable file is a materially different privacy act than a member reading their own). So v1 emits Tier-3 + Tier-2-hash + stored-masked columns only; the `decryptIfPermitted` marker + a `reports.view_pii`-class gate + its audit are a named follow-up ([[project_nominee_vpa_deferred_seam]] first-class-absent-seam discipline). *Rejected alternative:* implement decrypt-if-permitted now — rejected for v1: it needs a new permission, a per-field-class decrypt in the worker, and a privacy/DPDPA review of "bulk admin PII export" that shouldn't gate the mechanism shipping. The epic's "unless the requestor's RBAC scope permits" is honored as a *seam*, recorded openly as un-shipped, not faked ([[feedback_record_unattested_no_backfill]]).

3. **Scope enforcement — RECOMMEND scope-as-query-predicate (narrow in SQL), NOT over-fetch-then-per-row-drop.** The epic says "every row is RBAC-validated; out-of-scope rows excluded." Express that set-wise: the template's `query(scopeCtx)` receives the actor's resolved scope and pushes it into the WHERE/HAVING, so out-of-scope rows are never read (RLS tenant-isolates `pariwar_id` underneath as the backstop). This is correct, efficient at report scale, and avoids materializing a whole tenant in memory. Deny-deeper geo until Epic 3 applies ([[project_rbac_geo_scope_containment]]). *Rejected alternative:* fetch broadly, then `checkPermission` per row and drop — rejected: O(N) permission evals over a large report, and it briefly holds out-of-scope rows in process memory (the thing we're preventing). A per-row assertion is fine as *defense-in-depth*, not as the mechanism.

4. **Storage — RECOMMEND reuse the 3.11 DB-column envelope-encrypted artifact + authenticated one-time route, NOT GCS signed URLs.** The epic's "downloadable URL is one-time-use, time-limited (24h), authenticated" is EXACTLY what 3.11 already implements: an authenticated GET route + a conditional consume-guard (`410` on replay) + a 24h `expires_at` + a hygiene vacuum, streaming from `artifact_ciphertext`. Clone it for `report_exports`. *Rejected alternative:* the Story 6.5 `ClaimDocumentStorage` GCS port + signed URLs — rejected as over-build ([[project_claim_document_storage_port]] is for member-uploaded blobs with a real vendor need); a signed object-store URL is *less* controllable than an authenticated one-time API route (a signed URL, once minted, is a bearer token that survives consume), and adds a storage adapter for zero gain over the proven pattern.

5. **Async cadence — RECOMMEND async-always (every report → pg-boss), NOT threshold-gated sync/async.** The epic states "report generation runs as a pg-boss job (async) … member receives a notification when ready" — async is the default, unconditionally. The PRD's FR-58A softer wording ("above a configurable size threshold queue for async") is reconciled toward the epic: **async-always** is one code path, matches 3.11, and removes a size-heuristic to tune. *Rejected alternative:* a synchronous fast-path for small reports gated on a threshold — rejected for v1: two code paths (sync + async) to keep in parity, a threshold constant to bikeshed, and the request-path sync branch reintroduces the "big report crashes the request" risk the async design exists to kill. A fast-path is a later optimization if latency data warrants it. **This is a reconciliation of an epic-vs-PRD wording gap — confirm before dev.**

6. **Authorization — RECOMMEND per-template permission keys, NO umbrella `reports.generate` key.** FR-58A gates reports differently by type ("audit log query (Auditor only)"; a district roster vs. a reconciliation-throughput report are different read authorities). So each `ReportTemplate` declares its own `permissionKey` + `scopeDimension`, and the harness `checkPermission`s against it — the exact 10.6 Decision-2 posture. The audit-log report REUSES the already-seeded `audit.export` (Auditor role, `roles.ts:73/334`); new keys mint only for templates whose read-authority isn't already covered by an existing key (e.g. a roster read may reuse `member.view_validity` or need a new `member.export_roster` — decide per seed template; catalog v25→v26 only if a new key is genuinely needed). *Rejected alternative:* one `reports.generate` umbrella key — rejected: it over-grants (a helpdesk-SLA-report viewer would inherit audit-log-export authority), collapsing FR-58A's per-type authorization into one bit, and repeats the umbrella-key mistake 10.6 Decision 2 rejected.

7. **Readiness signal — RECOMMEND poll-status as mandatory, in-app push as best-effort/deferred.** The requestor is an admin; the reliable readiness signal is the poll-status route the admin UI already watches (the 3.11 member-client pattern). FR-58A's "notify via in-app push when ready" is honored best-effort: if an admin notification/device-token channel already exists, the worker fans out a single "your report is ready" nudge to the requesting actor from apps/jobs (the news-publish crypto-boundary shape); if no admin push channel exists yet, poll-status stands alone and the push is a recorded seam. *Rejected alternative:* block the story on building an admin push channel — rejected: poll-status fully satisfies "watch pending → ready," and standing up admin device-token infrastructure is a separate concern that shouldn't gate the reports library.

## Dev Notes

### This is a [SURFACE] — but you are cloning 3.11, not inventing async export

The single most important orientation: **Story 3.11 (member DPDPA data-export) already built every mechanical piece of async export** — the `pending → ready|failed → consumed|expired` lifecycle, the tenant-isolated `data_exports` table + RLS policies, the envelope-encrypt-at-rest artifact, the one-time 24h authenticated download with the conditional consume-guard, the hygiene vacuum, the pg-boss build worker with JobEnvelope explicit-threading, the request/poll/download route trio. Read `apps/jobs/src/data-export.ts`, `packages/domain/src/data-export/store.ts`, `apps/api/src/modules/data-export/handlers.ts`, and `migrations/0033_data-exports.sql` FIRST and clone their shapes for `report_exports`. Your net-new code is: the report-template registry + assembly harness (Task 2/3), the masking posture (Decision 2), the scope-as-predicate queries (Decision 3), and the per-template RBAC (Decision 6). Everything else is a rename of a proven thing.

### The one semantic that makes 10.7 ≠ 3.11: audience standing (read this twice)

3.11 **decrypts** Tier-1 PII because the member is exporting their OWN data (the legitimate audience, architecture §2.7). 10.7 exports OTHER members' data for an admin. Therefore: **(a) scope-respecting** — the report only ever contains rows within the actor's RBAC scope (push scope into the query, Decision 3); **(b) PII-masked** — Tier-1 is NEVER decrypted into a v1 report (Decision 2). If you find yourself calling `decryptTier1` on a member's mobile/DOB/address/nominee-bank inside a report template, STOP — that is the deferred `decryptIfPermitted` path, not v1. The epics' bulk-export prohibition (epics.md:3731/3835) treats un-masked, un-scoped bulk member-data export as a P0-class leak; 10.7 is the *sanctioned* operator workflow precisely because it masks + scopes + audits. A masked, district-scoped roster CSV is the product; a decrypted all-members dump is the anti-product.

### Inherit 10.6's Open/Closed invariant — the harness never branches on report identity

`assembleReport` depends ONLY on the `ReportTemplate` contract methods + the registry lookup — **zero** `if (reportType === 'roster')` branches, now or ever ([[project_bulk_operations_open_closed_invariant]]). A future report type extends the contract / adds a template, never a harness branch. Enforce with the 10.6 twin: a behavioral Open/Closed proof (two divergent fixture templates flow through the unchanged harness) + a source-text regex asserting the harness references no `reportType` string literal. This is why the ~10 FR-58A reports can register in cheap follow-ups without touching the spine.

### Scope-as-predicate, not over-fetch-then-drop (Decision 3) + the deny-deeper geo pin

The template's `query(scopeCtx, client)` receives the actor's resolved scope and narrows the SQL — a District Admin's roster is `WHERE district = <actor.district>`, an Auditor's audit-log report spans the log, RLS tenant-isolates `pariwar_id` beneath. Do NOT fetch a whole tenant then `checkPermission` per row (O(N) + holds out-of-scope rows in memory). The geo resolver is **deny-deeper until Epic 3** ([[project_rbac_geo_scope_containment]]): a `state`-scoped actor's `district`-granular report resolves nothing below its ceiling — document it as the same asymmetry 10.3/10.4/10.5/10.6 shipped. A per-row assertion is acceptable as defense-in-depth, never as the mechanism.

### Storage: DB-column envelope-encrypted artifact + authenticated one-time route (Decision 4)

Reuse the 3.11 posture: the artifact bytes (CSV/JSON string) are `encryptTier1`-wrapped + `serializeEnvelope`'d into `report_exports.artifact_ciphertext`, decrypted in-memory only during the authenticated one-time download stream, zeroed by the vacuum once consumed/expired. Do NOT reach for the Story 6.5 GCS `ClaimDocumentStorage` port / signed URLs ([[project_claim_document_storage_port]] is for member-uploaded blobs) — a signed URL is a bearer token that survives the consume-guard, weaker than the authenticated one-time API route. Encrypt-at-rest even though v1 rows are masked: scope-restricted aggregates are sensitive, the pattern is free, and the deferred Tier-1 path will put real PII here.

### Audit: one line per operation, injected/service-pool at the composition root

`writeAuditEntry` takes the SERVICE (BYPASSRLS) pool + self-commits its own tx (`audit/write.ts` — cannot be rolled back by a per-test ROLLBACK). The build worker writes `report.generated` AFTER the row flip; the download handler writes `report.downloaded` AFTER streaming; both NON-PII (`report_export_id`, `report_type`, `row_count`, `artifact_bytes`, `status` — never the params or any row content), `traceId` correlating the one export's request→build→download, `actorId`/`actorRole` from the requestor ([[project_admin_display_name_attribution]] — the admin's `display_name` is the attribution source; a missing name blocks with a typed error, no email-derived fallback), `requestPayloadHash` = sha256 of canonical params (never raw — the `.strict()` boundary). Live-DB tests assert `traceId` grouping / membership, not counts (the chain self-commits + accumulates, [[project_live_db_test_gotchas]]).

### CSV: reuse 10.6's `toCsv`, do NOT write a second serializer

`packages/domain/src/bulk-operations/csv.ts` (`toCsv`) is the repo's ONE CSV writer — RFC-4180 quoting, stable first-seen column order, OWASP formula-injection neutralization. 10.6 explicitly built it content-only and deferred durable async download to THIS story. Import it; a second CSV serializer is a review-blocking duplication ([[feedback_no_premature_package]] in reverse — the consumer exists now, reuse the shared util). JSON output is canonical serialization of the same rows.

### No decrypt in v1 = no member-field-crypto complexity in the worker (but keep the seam)

Because v1 masks (Decision 2), the build worker does NOT need per-field-class member decrypt — it only `encryptTier1`s the finished artifact (like 3.11 encrypts the finished ZIP; the worker already has KMS deps). The `decryptIfPermitted` marker on `ReportColumn` resolves `false` everywhere in v1; the worker HAS the crypto to honor it later (the 3.11 worker proves apps/jobs can decrypt), so the deferred path is a capability+gate+audit addition, not a crypto-plumbing one. Record it as a first-class forward commitment ([[project_nominee_vpa_deferred_seam]]) — do NOT silently omit it.
