# Story 8.4: UPI Intent Flow + `<UPIIntentButton>` + UTR Self-Attestation + Yellow Pill

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As Sushil tapping "Contribute →" on the My Pool card,
I want a UPI Intent flow that pre-fills the nominee VPA + amount + `tr=` + `tn=`, opens my preferred UPI app,
accepts my pasted UTR on return, and shows the **yellow pill** state on my card,
So that I complete the contribution loop in seconds — with idempotency + amount-lock + a clear
**unconfirmed-but-attested** status that never pretends to be a confirmed payment.

## Scope — what belongs to 8.4 vs what is a reserved seam

> **Story 8.4 is the PRODUCER of yellow.** It is the first Epic-8 WRITE path (every prior 8.x surface —
> 8.2 card, 8.3 list — is read-only). It builds the UPI Intent construction + the UTR self-attestation
> write (`contribution.utr-attested`) + the member's own yellow-pill state. It **closes the loop at
> yellow** — it never confirms, never flips green, never counts toward "raised so far." Green is Epic 9's
> exclusive `contribution.confirmed` flip (`epics.md:2855`). 8.3 already made yellow **structurally unable**
> to reach the confirmed list/meter; 8.4 introduces the yellow that 8.3's teeth were built to exclude — so
> the two must be verified as a pair (the attestation this story emits must not appear on any confirmed
> surface, ever).

8.4 is `[SURFACE]`. It reuses 8.2/8.3's `member-pool/` **read** seam (`resolveMemberLivePool`) to resolve
the member's assigned live pool, then adds the **write** half the 8.2 card left as a `TODO(8.4)` stub
(`apps/mobile/components/active-contribution/ActiveContributionCard.tsx:92`).

## Acceptance Criteria

**AC1 — UPI Intent is server-authoritative, amount-locked, and idempotent by construction.**
Given FR-27 + FR-28 + UX-DR26 (`<UPIIntentButton>` ≥ 56pt) + Story 7.6 pool binding + Story 7.7 `deriveContributionReference` + amount-lock (`epics.md:2929-2931`),
When the member taps the ≥ 56pt `<UPIIntentButton>` and the flow builds the intent,
Then the `upi://pay` URL is constructed **entirely server-side** (the vyawastha-shulk `intent` R4 precedent — the client NEVER names the payee or the amount) with: `pa=` (the nominee VPA — see AC2/D1), `am=` (the assigned pool's SNAPSHOTTED `fixed_amount` from the Story 7.6 binding, read-only, whole-INR positive integer — the amount-lock), `cu=INR`, `tn=` (a note carrying the pool letter/name + cycle ref, the FR-27 grammar "Pool Karna — Sahyog Alert #78"), and `tr=` = `deriveContributionReference({ memberId, alertId })` (Story 7.7, DETERMINISTIC per `(member_id, alert_id)` — the SAME member+alert always yields the SAME `tr=`, so repeated payments reconcile as ONE valid contribution — idempotency by construction);
And the flow resolves the member's assigned live pool through the SAME `resolveMemberLivePool` seam 8.2/8.3 use (member `active` × `live` alert × assigned pool) — it does not re-implement pool resolution;
And every URL component is `encodeURIComponent`-escaped (the vyawastha-shulk precedent — an unencoded reserved char corrupts the intent, and a malformed URL is "₹310 to the wrong VPA with no recourse", architecture `:90-91`);
And the `intent` endpoint meets the architecture's **UPI Intent launch < 1s p95** budget (architecture.md:36).

**AC2 — The nominee VPA is server-resolved; its ABSENCE is a first-class fail-soft state, never a broken intent (D1 — the load-bearing substrate decision).**
Given FR-16 ("UPI Intent pre-fills the assigned pool's **nominee VPA**", `prd.md:470`) + FR-27 (`pa=` = VPA, `prd.md:573`) + the money-flows-member→nominee-directly PMLA posture (`prd.md:1165`) + the CONFIRMED substrate gap (there is **no VPA column anywhere** — Story 6.8 collected nominee bank accounts as account#+IFSC **ciphertext only**, `claim_nominee_bank_accounts.ts`; `grep -rni vpa packages/domain/src/schema` returns nothing),
When the intent is built,
Then `pa=` sources from a **server-side nominee-VPA resolution** (default account #1, with a "Switch account" affordance to #2 per FR-27, `prd.md:608`);
And because the VPA is **not present in the substrate today**, this resolution legitimately returns **absent**, and the flow treats absence as a **first-class state** (the 8.2 `{ assigned:false }` / 8.3 "honestly empty" discipline, `[[feedback_record_unattested_no_backfill]]`): the `<UPIIntentButton>` is disabled/replaced with a calm "UPI contribution isn't available for this pool yet — tap Get help" path (Story 8.11 helpline / Story 8.5 coach seam), NEVER a `upi://pay?pa=undefined` URL and NEVER a fabricated VPA;
And **the VPA-resolution seam is built so that when the VPA-collection substrate lands, the flow lights up with zero changes to this story's surface code** — exactly how 8.3's confirmed list populates when Epic 9 lands;
And the D1 decision is **SETTLED (BigDev, 2026-07-21): path (b) — defer VPA collection to a dedicated story; 8.4 ships with the seam ABSENT.** So the VPA resolver returning absent is the EXPECTED, shipped v1 state — the `{ available:false, reason:'vpa_not_collected' }` fail-soft path is a first-class, tested surface, not a temporary stub. Do NOT extend Story 6.8 or add a VPA column in 8.4 (`[[feedback_closure_language_precision]]` — *Resolved via explicit deferral*, not "not addressed"; the dedicated VPA-collection story is a forward commitment, see D1).

**AC3 — UTR self-attestation records a member CLAIM only, as `contribution.utr-attested` with a schema-level `attestation_only: true` (the load-bearing invariant).**
Given the epic's **UTR-attestation-is-member-claim-not-confirmation invariant** (`epics.md:2935-2941`) + Story 9.4's primary-match dependency on this event's `utr` field (`epics.md:3163`, PRD FR-30),
When the member returns from the UPI app and pastes a UTR,
Then the UTR is **format-validated against the shipped precedent** — reuse the exact `packages/contracts/src/payments/vyawastha-shulk.ts:58` regex (`/^\d{12}$|^[A-Za-z0-9]{22}$/`, "12-digit numeric or 22-char alphanumeric", matching PRD FR-28's stated shape exactly) — do NOT invent a new bounded-string validator; and, on success, persisted **as-entered** as a **`contribution.utr-attested`** event on the alert's event stream (`stream_id = alert_id`), with a payload carrying `poolId` + `memberId` + the deterministic `tr` + the **raw `utr` value itself** (this is what Story 9.4's matcher exact-matches against `BankStatementEntry.transaction_id_utr` — omitting it breaks Epic 9's primary match path) + a **schema-level `attestation_only: true`** flag + the audit shape;
And the persisted event represents a **member-declared payment claim ONLY** — NOT a reconciliation-confirmed contribution, NOT fund receipt, NOT payout eligibility; the `attestation_only: true` flag is a REQUIRED literal in the payload schema (`z.literal(true)`), so a downstream consumer can never mistake a yellow event for a confirmed one, and an event that omits/negates it does not validate;
And the write is **idempotent on the deterministic `tr`** — a re-paste / retry for the same `(member, alert)` records ONE attestation (a UNIQUE guard on the derived `tr`, or an append-then-dedupe-on-read that keys on `tr`), never a second yellow claim (the FR-17 one-valid-contribution-per-`(member,alert)` guarantee);
And the UTR is **masked** in any audit/log line (last-4 only — the vyawastha-shulk `maskUtr` precedent), never logged in full.

**AC4 — The yellow pill is the MEMBER'S OWN state; it never pollutes any confirmed/aggregate surface (this story's teeth).**
Given the epic's "downstream surfaces must NOT treat yellow as quasi-confirmed / must NOT count yellow toward raised-so-far / must NOT imply payment success" (`epics.md:2939-2941`) + 8.2's confirmed-only meter + 8.3's confirmed-only list,
When the member's My Pool card renders after attestation,
Then the card shows a **yellow-pill state for THIS member** — a per-member `myContribution` status (`none` → `attested`) whose copy carries the explicit semantics "you have told us you paid; we are still verifying with our bank-statement reconciliation" (never "confirmed", "received", "success", or "paid ✓");
And the **8.2 confirmed-only aggregate progress meter is UNCHANGED** — no yellow/attested count is added to `progress`; the meter still reads `confirmedCount of rosterSize` sourced ONLY from `contribution.confirmed` (yellow is a member self-state, NOT an aggregate — `epics.md:2939`);
And **CI teeth assert**: (a) **no API surface promotes yellow → green** without an Epic-9 `contribution.confirmed` event in the stream (extend the 8.3 confirmed-only test to seed a `contribution.utr-attested` and assert it appears on NO confirmed surface — the card meter, the 8.3 contributor list, any count); (b) **public/aggregate counts source from confirmed only** (the 8.2/8.3 shape tests already forbid a yellow field — re-assert after 8.4 makes the event real); (c) the **`contribution.utr-attested` schema carries `attestation_only: true`** as a required literal (a `.strict()` shape test), and a downstream `.strict()` read rejects any attempt to surface it as confirmed;
And 8.3's live-DB yellow-exclusion spec (which currently seeds a **hand-crafted** `contribution.utr-attested`) is updated to seed via **8.4's real producer/schema** — closing the "invariant bites before the producer exists" seam into "invariant bites against the real producer."

**AC5 — Failure and no-app paths are handled without stranding the member.**
Given FR-27's "per-app guidance if no UPI app installed" (`epics.md:2932`) + the Story 8.5 failure-coach linkage (`epics.md:2947-2958`, backlog),
When the member has no UPI app, or returns from the UPI app WITHOUT a UTR (cancel/failure) or pastes an INVALID UTR,
Then the flow offers **per-app guidance** (the member can still complete manually / switch apps) and the **failure path links the Story 8.5 UPI failure-coach seam** (8.5 is backlog — 8.4 leaves the navigable link/affordance, not the coach surface itself);
And no failure path emits a `contribution.utr-attested` event (only a valid, format-passing UTR does) — a cancel/failure leaves the member in `myContribution: 'none'`, free to retry (the idempotent `tr=` means a retry after a real payment still reconciles as one).

**AC6 — Accessibility (inherited Story 0.10 P0-2c gate).**
Given the inherited accessibility gate (Story 0.10 P0-2c) + the 8.2/8.3 a11y posture,
When the flow renders for assistive-tech users,
Then the `<UPIIntentButton>` touch-target is **≥ 56pt** (UX-DR26); the UTR paste field has a **clear ARIA label**; the **yellow-pill state is announced** with the explicit "pending reconciliation" semantics (`accessibilityLiveRegion="polite"` — ambient status, never `assertive`); Devanagari renders without clipping at 360px; grade-6 reading level; and **operational figures (amount, `tr` if shown, UTR) render in Latin numerals even in Hindi** (amendment-A2 — the 8.2/8.3 D6 discipline), NOT `toHindiNumeral`.
