## Story

As a Trustee Panel,
I want the TWT repository auto-mirrored to ≥1 trustee-controlled location on every release-branch push, with the pipeline, restoration drill, and bus-factor recovery posture verifiable end-to-end,
So that the codebase survives if Solo Builder's primary repo access is lost — and a contracted external engineer can take over from the mirror within the AR-67 / PRD §9.1.1 30-day window without Solo Builder consultation.

## Acceptance Criteria

1. **AC-1 — Mirror pipeline auto-replicates release-branch commits to a trustee-controlled destination within 10 minutes, with read-access verified by ≥2 trustees and a successful restoration drill on record**

   **Given** the AR-67 + PRD §9.1.1 commitment to code-escrow with auto-mirror on every release-branch push, AND the architecture §5.4 commitment that "Source-code host: GitHub primary; escrow mirror to trustee-controlled location per Step 2 §9.1.1"
   **When** Solo Builder authors the code-escrow framework, the mirror pipeline (a GitHub Actions workflow), and the mirror-destination scaffolding
   **Then** `docs/escrow/code-escrow/` exists alongside `docs/escrow/` per the Story 0.2 escrow-framework symmetry, with the artifacts listed in Project Structure Notes (README, mirror-destination-inventory, code-escrow-ledger, mirror-procedure runbook, restoration-drill runbook, mirror-workflow specification)
   **And** the GitHub Actions workflow `.github/workflows/code-escrow-mirror.yml` is authored to fire on every push to the release-branch set (release-branch set definition committed per Project Structure Notes; see [Cross-Story Dependency Note] for the Story 1.1 alignment requirement), push the full git history (refs + tags + LFS objects if any) to the mirror destination via `git push --mirror`, and report success/failure to the code-escrow-ledger via a structured artifact
   **And** the workflow targets the **10-minute replication SLA** (per AC-1 text); the SLA is measured as wall-clock time from `pushed` event timestamp on GitHub to the corresponding ref's appearance at the mirror destination; the workflow itself runs under a job-timeout shorter than the SLA so a hung workflow surfaces as a failure rather than masking the breach
   **And** the **mirror destination is a property commitment** (trustee-controlled, non-Solo-Builder admin, geographically separate from the primary repo's hosting region per [[feedback_architecture_vs_adr_boundary]] — the architecture commits the property, the ADR records the specific destination); the candidate destinations (GitLab.com under a trustee-owned account, Codeberg, self-hosted Gitea on trustee infrastructure, Bitbucket under trustee-foundation account, hybrid dual-mirror) are ADR territory and recorded in `docs/escrow/code-escrow/mirror-destination-inventory.md` as `pending-ADR` until the Trustee Panel + Solo Builder selection lands
   **And** the workflow **does NOT push secrets or build artifacts** — the mirror receives only the repository source (refs, tags, LFS pointers); GitHub Actions secrets, GCP Secret Manager references, container images, and Artifact Registry artifacts are explicitly out of scope per architecture §5.4 + §5.9 (the mirror is a code-survival surface, not a deployment-substrate replacement)
   **And** **read-access verification** is recorded in `code-escrow-ledger.md` "Read-access verification log" with each verifying trustee, date, scope verified (repo readable; ref list current; HEAD matches primary at verification time), and method (`git clone` to local + `git log` cross-check is the documented method; alternatives recorded per attempt)
   **And** the **restoration drill** is recorded in `code-escrow-ledger.md` "Restoration drill log" with executing trustee-authorized engineer (Solo Builder is permitted as the executor only when no backup engineer is yet contracted per Story 0.6; otherwise the backup engineer or another trustee-authorized non-Solo-Builder engineer executes), drill date, scope (`git clone` from mirror + `pnpm install` + at least one apps/* workspace build + deployment to a **non-production environment** per AC-1 text — local Docker, an ephemeral dev environment, or a sandbox Dokploy instance — explicitly NOT prod or staging), outcome, gaps discovered, follow-up procedure revisions
   **And** **closure precision** (per [[feedback_closure_language_precision]]): each AC-1 closure leg is one of three states — **Closed by [edit]** (workflow authored + mirror destination scaffolded with concrete inventory row + ledger entry committed), **Resolved via explicit deferral** (mirror destination selection awaiting ADR; restoration drill awaiting Story 0.6 backup engineer contract or trustee-authorized substitute; ≥2-trustee read-access verification awaiting destination provisioning), or **Not addressed** (in scope but neither edited nor explicitly deferred — this state should not occur and triggers an open question). Never collapse "deferred" with "closed."

2. **AC-2 — Bus-factor switch-to-mirror scenario: development resumes from the mirror without data loss**

   **Given** the mirror destination is provisioned and at least one release-branch push has replicated successfully (AC-1 partial closure); AND Solo Builder is silent for the duration of the exercise (bus-factor simulation discipline inherited from Story 0.1 AC-4 and Story 0.2 AC-3)
   **When** the Trustee Panel + trustee-authorized engineer execute the **switch-to-mirror procedure** documented in `docs/escrow/code-escrow/restoration-procedure.md` (built on the restoration-drill scaffolding from AC-1)
   **Then** the trustee-authorized engineer obtains read+write access to the mirror destination under the mirror's own access-control model (the ADR-recorded credential model — deploy key, SSH cert, OAuth token, or platform-native invite); verifies the mirror's HEAD matches the last-known-good primary HEAD at the time of primary inaccessibility (via cross-checked ledger entries from the GitHub Actions workflow run records, the periodic read-access verification entries, and any out-of-band trustee-held SHAs); branches a working ref from the mirror and demonstrates the ability to build at least one apps/* workspace, push a commit to the mirror, and queue a hypothetical release (the deployment itself is out of scope for AC-2; the **continuity-of-development** property is the AC-2 test, not continuity-of-deployment)
   **And** **data-loss check** is performed by comparing the mirror's ref set + tag set + commit SHAs against the last successful mirror-workflow run's recorded SHAs (the workflow emits the pushed SHA range to the ledger; the comparison is the verification check); a divergence between the workflow's last-recorded SHA and the mirror's current HEAD is a **gap** — the missing commits are the data loss; the exercise records the gap and the recovery path (re-push from any out-of-band trustee-held clone; pull from backup engineer's local clone per Story 0.6; or accept the loss if the missing window is within the 10-minute SLA gap and the trust accepts the residual risk)
   **And** every step is logged in `code-escrow-ledger.md` "Bus-factor switch-to-mirror log" with executing trustee + engineer, exercise date, primary-inaccessibility-simulation method (revoked Solo Builder GitHub access; deleted primary repo; "pretend Solo Builder is unreachable"), mirror state at switch time, verification outcome, gaps discovered
   **And** AC-2 is **provisionally closed** when at least one bus-factor switch-to-mirror exercise demonstrates the continuity property under simulated primary-inaccessibility, OR when the trust-authorized substitute path is exercised (Solo Builder is permitted as the executor for the first switch-to-mirror only when Story 0.6 has not yet contracted a backup engineer — the substitute path is recorded explicitly per [[feedback_closure_language_precision]]); **fully closed** only when a non-Solo-Builder engineer (the contracted backup engineer per Story 0.6) executes the switch-to-mirror under full bus-factor silence. AC-2 full closure has a hard dependency on Story 0.6 closure
   **And** the **30-day takeover property** committed by PRD §9.1.1 is partially evidenced by AC-2 — the restoration drill (AC-1) demonstrates code accessibility; AC-2 demonstrates continuity of development; the **end-to-end 30-day takeover** is evidenced when Story 0.5 (KT pack), Story 0.6 (backup engineer contract), and AC-2 close together. AC-2 alone does not discharge the 30-day takeover property — record this dependency explicitly in the ledger when closing

### §2.10a-adjacent property — mirror surface separation is structural, not policy

The §2.10a audit independence invariant is about the **audit-mirror** (`twt-audit-mirror-prod`). The **code-mirror** Story 0.3 owns is a separate surface that serves a different invariant — code survival, not audit independence. The two MUST NOT be conflated:

- The audit-mirror credentials are sealed under Story 0.2's framework with envelope-class `audit-mirror-credential` and structurally separated from `prod-credential` (per §2.10a). Story 0.3 does NOT touch audit-mirror credentials.
- The code-mirror destination is its own platform with its own credentials (sealed under Story 0.2's `prod-credential` envelope class — see Task 8 inventory-row-addition). Compromise of the code-mirror credentials grants the attacker a clone of the source code, but does NOT grant access to audit-mirror data (it's a different platform with different credentials).
- The workflow YAML committed to the primary repo references secret NAMES (`MIRROR_PUSH_CREDENTIAL`, `MIRROR_DESTINATION_URL`); the workflow YAML itself is part of the source code and therefore mirrored. **This is acceptable** because the YAML carries no secret VALUES — the names are integration contracts, not secret material. Solo Builder MUST NOT inline secret values in the YAML or in any committed file.

The **structural** anchor for surface separation: the mirror destination is administered by trustees (not Solo Builder); the WIF binding for prod-deploy is scoped to the **primary** repo + production-release branch + production-deploy workflow file (per architecture §5.4 — the mirror destination is not in the trust binding, so a malicious mirror push cannot trigger a prod deploy).
