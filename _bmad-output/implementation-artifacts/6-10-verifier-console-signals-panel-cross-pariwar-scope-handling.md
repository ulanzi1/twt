# Story 6.10: Verifier Console Signals Panel ~5s Load + Cross-Pariwar Scope Handling (UX-DR39 — ₹50L Design Budget)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story Classification

**`[SURFACE]`** — the **read-only** verifier console. 6.10 assembles a **bounded compound read model** across every signal Epic 6 already produces and renders the **signals panel** + **cross-Pariwar scope chrome** for a single claim, plus the **human-adjudication invariant** (runtime enforcement + a CI gate). It is **READ-ONLY**: it emits **no `claim.*` lifecycle event** and takes **no adjudication decision** — Approve / Deny / Escalate + their events are Story 6.11's `<VerificationDecisionStrip>`, which mounts into a sticky-bottom slot this shell provides. This is the twin-consumer of the accessors five prior stories deliberately shipped *for 6.10 to mount*: 6.5's `<VerifierReviewPanel>` (Decision D2 there), 6.6's peer-mesh reads (D3), 6.7's `getClaimGroundInspection` (D4), 4.6/4.8's Validity payload, 4.4's R14 concealment rule.

All ten seam decisions (D1–D10) below were **ratified by BigDev 2026-07-11** and are firm. The four residuals that follow are the only genuinely open calls; each has a recommended default already wired into the tasks.

## Story

As **Anita** (a verifier at the District-Admin level) reviewing a claim case,
I want **a signals panel that loads in ~5 seconds and surfaces every relevant signal — peer-mesh responses, ground-inspection notes/photos, OCR parity, the Member Validity Service payload, a concealment-review indicator, and recent in-scope precedents — all on one screen with the active cross-Pariwar scope unmistakable**,
so that **I can make an informed ₹50L disbursement judgment in minutes rather than spending hours digging through linked records.**

## Acceptance Criteria

**AC1 — Bounded compound read model, ~5s load, no N+1 (FR-42 + AR-65 + UX-DR39 + Story 4.6 Validity Service + Story 0.11 operator-shadowing findings).**
The signals panel is served by **one API request** backed by a **bounded compound assembler** — a **fixed number of data-source reads independent of signal-row count** (**no N+1**). A named per-request read-count ceiling is asserted (Task 1/6). p95 ≤ 5s at 4L-member-scale Pariwar is met by the bounded fan-out + the Story 4.8 validity cache + existing claim indices; the story does **not** claim a full-scale 4L load measurement (D9).

**AC2 — Signals in clearly-labeled sections.** The panel displays:
- **(a)** deceased-member identity + Validity Service payload + **a concealment-review indicator** (a request-time, scope-safe tri-state — **see D10**; **not** the redacted validity `specialFlags` array);
- **(b)** OCR parity from Story 6.5 with `<DocumentPreview>` (embed the existing `<VerifierReviewPanel>`);
- **(c)** peer-mesh responses — **transcripts (responder + response), not just counts** — per Story 6.6; a non-response is an **absence**, never inferred `denied`. **AMENDED (code review 2026-07-11):** peer responses ship as specified; **verifier annotations are explicitly `not_available_yet`** (the `PeerMeshTranscript.verifierAnnotations` field — the D6/D10 not_available_yet precedent) until an owning producer story adds real capture — Story 6.6's `ClaimPeerMeshRespondedPayloadSchema` carries only `responder_member_id` + `response` today, no verifier-added note/annotation field exists. This is a genuine capability gap, not a wording error — never fabricated, never silently dropped;
- **(d)** ground-inspection notes + photos per Story 6.7;
- **(e)** prior verifier comments (**full rationale transcript**, sourced from 6.11's decision read model — **see D6**);
- **(f)** recent in-scope resolved precedents (**latest 3, scope-respecting** — deterministic recency rule, **see D6**).

**AC3 — Cross-Pariwar scope handling (server + client).** When Anita has access to multiple Pariwars:
- the **active scope is displayed prominently** in console chrome;
- **the API resolves tenant + district authorization on every request** — a claim from Pariwar A **cannot** be fetched while the effective scope is Pariwar B (RLS + explicit `pariwar_id` predicates);
- **switching scope is an explicit navigation** to the target Pariwar's safe landing route; it **clears the current console packet immediately**, does **not** carry the current `claimCaseId` across Pariwars, shows a loading/blank state during transition, and **never renders the old Pariwar's evidence beneath new-scope chrome** (D8);
- each scoped request is **audit-logged** (the per-request `scope.change` access audit — D8 documents the exact evidence available);
- client query keys include the **effective `pariwarId` + `claimCaseId`** so cache-disabled server behavior is matched by cache-key isolation (no stale cross-scope data lingers in client state).

**AC4 — Signals are advisory, not auto-adjudicating (this story's load-bearing invariant).** The panel surfaces signals as **decision-support artifacts for human judgment, never as automated decisions**. Final adjudication authority remains **human and audit-attributable**; the panel **never** auto-approves/auto-denies on any signal combination. Concealment indicators, Validity payloads, peer signals, OCR mismatches, and combinations thereof are **assistive** — they highlight, recommend, prioritize, but never decide. Structurally, 6.10 ships **no decision endpoint**, so nothing here *can* auto-decide.

**AC5 — Human-actor: runtime enforcement + CI gate.** The **runtime route is the security control**: the verifier-console read independently requires an authenticated **human** actor, `claim.verify`, resolved district (or global) scope, tenant match, and the required session posture — fail-closed, audited. **In addition**, a CI invariant gate prevents future machine/service principals from being wired into claim-adjudication routes: it inspects **structured route/permission registration** (not brittle source-text grep) for the human-auth composition, ships with a known-bad fixture, and defines an explicit coverage set that **Story 6.11 must extend** with its approve/deny/escalate routes.

**AC6 — AR-61 staff-fallback / escalation (read-only affordance).** The console provides the **designated escalation-action slot** and clearly communicates the higher-scope (District → State) escalation path. **Story 6.10 performs no escalation write, no reassignment, and no lifecycle transition.** The actionable escalation control + its audit/routing behavior are owned by Stories 6.11/6.12. *(The Epic's original AC6 — "they can escalate; the case advances; escalation is audit-logged" — is **partially realized** here: 6.10 ships the affordance only; the emitting action + state effect land with the downstream owner. The claim state machine has no `escalated` state/event, so escalation is a routing/reassignment concern, not a lifecycle advance.)*

**AC7 — Compound-read failure posture + the four-state section vocabulary.** No silently-degraded panel. A **whole-request failure** on: tenant/scope/permission denial, or a failure of the claim-identity core read. Otherwise each section carries an explicit status from a **four-state vocabulary that must NEVER be collapsed**:
- **`present`** — data present;
- **`empty`** — the producer exists and genuinely found **no records** (e.g. no inspection scheduled → a meaningful `[]`);
- **`unavailable`** — an **existing** dependency **failed** transiently (validity, peer-mesh, inspection, OCR, signed-media);
- **`not_available_yet`** — the **downstream producer has not shipped** (sections (e)/(f) until Story 6.11; the concealment `not_evaluated` state is this category's spelling for section (a)).

A dependency failure is **never** converted into `empty`; a not-yet-built producer is **never** rendered as `empty` or `present`. These three (`empty` / `unavailable` / `not_available_yet`) are distinct and independently tested.

### Freshness (D7 — ratified) — cache-disabled, ₹50L stakes

### Cross-Pariwar client-state safety (D8 — ratified; the easy-to-miss half)

Server-side freshness does **not** prevent **stale cross-scope data in client state**. Two things must hold:
1. **The switch destination is safe.** Switching to Pariwar B must **not** substitute B's id while keeping A's `claimCaseId` (a predictable cross-tenant 404 + a window where A's evidence sits under B's chrome). Switch → clear packet → navigate to B's safe landing/queue route → loading state → no carry of `claimCaseId`.
2. **Query-key isolation.** Keys include the effective `pariwarId`+`claimCaseId`; a pending/failed new-scope request renders **no** prior-scope evidence.
- **Scope-audit accuracy:** the `scope-resolution` middleware emits `scope.change` on **every** `/p/:pariwarId/` request (`middleware/scope-resolution/index.ts:56-64`), with `context: { newScope, roles }` — it is a **per-request scope-access audit**, **not** a distinct "switched from A to B" record (it does not compare to a previous scope). The audit trail therefore shows the *sequence* of scope accesses (A-line then B-line), from which a switch is inferable. AC3 is satisfied by that access audit; if a **distinct** switch record is later required, add explicit switch context at the console — do **not** claim a distinct transition record exists today.

### Concealment indicator — the redaction trap, resolved (D10 — ratified; most important)

**Do not derive the district indicator from `payload.specialFlags`.** The Validity Service **redacts** at its boundary (`types.ts:185-191`, `redaction.ts`): a narrower-than-State-Trustee caller gets `pendingConcealmentFlag` forced `false` **and internal `specialFlags` stripped**. So for Anita (`district_admin`) the array is empty — and **absence of a visible flag cannot distinguish "no flag exists" from "a flag exists but was redacted."** Wiring AC2(a) to that array silently hides concealment on exactly the ₹50L cases it must flag.

**Two more facts (VERIFIED):**
- **No claim-linked concealment producer exists today.** The only concealment code is `packages/domain/src/medical/concealment.ts` (Story 3.5, member-standing `niy.concealment.r14`) + the validity payload's member-standing flag. `types.ts:76-78` is explicit that the **true C7 concealment** (an undeclared IMA-listed illness surfaced by a *death claim*) is **claim-linked and stays in Epic 6 (R14)** — there is no claim at member-standing validity time. The **claim-scoped** producer is a **future story** (6.15 routes it; 4.4's claim-scoped R14 evaluation produces it).
- The member-standing validity flag is a **different signal** — do **not** substitute it for the claim-linked one.

**Resolution — a request-time, scope-safe tri-state owned by the 6.10 assembler (no new store):**
```
concealment_signal: {
  status: 'flagged' | 'not_flagged' | 'not_evaluated';

}
```
- District actors receive **`indicator_only`** — presence status only, never flag names / notes / evidence text / author identity / hidden counts.

- **Until the claim-scoped producer lands, `status` is `not_evaluated`** — never `not_flagged`, never a green/clear. This is the honest v1 posture (the D6 absence-is-signal principle): a redacted/absent read must not collapse "not evaluated" into "evaluated and clear."

- **Producer ownership DEFERRED (ratified):** the concrete producer is deferred to **whichever story first owns claim-linked R14 evaluation — likely Story 6.15**. **Do NOT add a new validity-service presence accessor merely to manufacture a signal before the claim-linked evaluation exists.** Until the producer lands, 6.10 emits **`not_evaluated`**.
