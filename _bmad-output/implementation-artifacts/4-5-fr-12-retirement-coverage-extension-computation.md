# Story 4.5: FR-12 Retirement Coverage Extension Computation `[CONSUMER]`

Status: done

## Story

As the rule evaluation engine processing retirement-coverage eligibility,
I want FR-12's "+1 year per 5 years of valid membership" logic computed on-the-fly from `joined_at` + `retired_at`,
so that retirement-extended members have their post-retirement coverage window correctly calculated.

## Acceptance Criteria

> Verbatim from `epics.md` §Story 4.5 (lines 1964–1980). This is the FOURTH `[CONSUMER]` of the Story 4.1 engine primitive after R7 (4.2), R8 (4.3), and R5/R9/R14 (4.4).

**AC1 — the R12 clause is authored as interpretable DATA + the engine computes the window on-the-fly**

**Given** FR-12 + Story 4.1 engine
**When** the retirement coverage rule clause is authored
**Then** clause `niy.retirement-coverage.r12` carries the rule (≥5 years valid membership → +1 year post-retirement; +1 additional year per 5 additional years, so 15 years → +3 years) in structured JSONB
**And** the engine computes the coverage window on-the-fly from the member's `joined_at` (signup event), `retired_at` (Life Events `posting.updated` with retirement flag, or admin trustee-marked retirement event), and the rule's parameters
**And** the evaluation result identifies whether the member is currently within their post-retirement coverage window and how many days remain

**AC2 — a retired, still-covered member is returned eligible with the extension payload**

**Given** a member who retired but has not yet exhausted the retirement coverage window
**When** Epic 4 Validity Service evaluates them
**Then** they are returned as eligible with `retirement_coverage_extension: { active: true, days_remaining, granted_years }` in the canonical payload

- **Retirement coverage is an EXTENSION of eligibility, never a denial.** A non-retired member or one below the `min_years` threshold yields `granted_years: 0` / not-applicable — NOT an ineligible/deny verdict. Consistent with the Epic 4 never-auto-deny posture and `pool` benefit-mechanism.

### The rule semantics (from FR-12 — provisional, `policy_review_required`)

FR-12 (`prd.md:373-379`): "After 5 years of valid membership, member retains **+1 year post-retirement coverage**. Each additional 5 years adds another year. (15 years → +3 years.)" Consequences: "Engine computes post-retirement coverage on-the-fly from `joined_at` and `retired_at` (when set)"; "retired members continue receiving alerts and contributing during their covered extension."

The grant ladder as parameters: `granted_years = min(cap?, floor(valid_membership_years / grant_every_years) * years_per_grant)`, gated by `valid_membership_years >= min_years`. With `grant_every_years=5`, `years_per_grant=1`, `min_years=5`: 5→1, 10→2, 15→3, 4→0. No cap implied by the addendum (confirm with BigDev in D2).

**Content is PROVISIONAL** (final legally-reviewed copy lands via Story 0.13). The "valid membership" lapse-netting question (D4) is a genuine policy ambiguity — flag it `policy_review_required` on the clause; the producer's `valid_membership_years` derivation applies whatever the Trustee Panel settles. Encode faithfully, do not resolve in code (the 4.2/4.3/4.4 discipline).

### Decisions — CONFIRMED by BigDev 2026-07-03 (rationale for the record)

All four confirmed as written in Task 0 (D1-A + namespaced channel, D2-i + fact-vocabulary narrowing, D3, D4). Rationale retained so the dev agent understands *why*:

1. **D1-A + namespaced channel.** The interpreter was explicitly designed to be extended by 4.2–4.5 (`interpret.ts:27` names R12). A boolean-only engine cannot deliver FR-12's computed output without pushing the rule into 4.6 service code, which breaks FR-12A's "adding a rule = zero code change to the service" (`prd.md:422`). Additive: `conditional` clauses unchanged; `computed` absent for them. **Refinement:** the channel is `computed?: { values: … }`, not a bare top-level `Record` — the `{ values }` wrapper reserves the `computed.*` namespace so a later computed rule can add sibling metadata (units, per-value provenance) without a breaking result-shape change. D1-B (boolean-only + 4.6 arithmetic) rejected.
2. **D2-i — producer derives the calendar span; engine does the integer grant ladder; 4.6 does the date projection.** Honors the Date-free pure core + AI-3-1 (calendar math in the producer), keeps the FR-12 rule as registry DATA, and mirrors Story 4.4's D4 (narrow the engine surface to what its channel cleanly carries; push the rest to 4.6). The engine's "on-the-fly computation" is the grant-ladder integer arithmetic — the part that IS the rule. **Refinement:** raw `member.retired_at`/`member.joined_at` are deliberately NOT added to the engine fact vocabulary — the engine reads exactly two `member.*` facts (`valid_membership_years`, `is_retired`); the dates live in the producer + the 4.6 projection only. D2-ii (engine epoch-ms date math) rejected.
3. **D3 — engine emits raw values under `computed.values`, 4.6 maps names + does the date projection.** Single source of the raw numbers; resolves the PRD↔epic variance without engine-side dual-naming.
4. **D4 — lapse-netting is `policy_review_required`, resolved in the producer's derivation, not engine branching.** Same flag-don't-resolve discipline as 4.2/4.3/4.4.
