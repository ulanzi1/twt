# Question 1 — an ending was wrong: can it be undone, and who decides?

**In one sentence:** when an ending turns out to be wrong — the officer ended the wrong worker or gave the wrong reason, or the worker says
they were ended unfairly — can it be undone, and who decides?

**Why it cannot be decided without you:** it is what the Trust owes a person it ended wrongly — and, as built, one officer can end a worker
alone, and the ending is final.

## The one fact that decides it

**As built, nothing can undo an ending — not even an officer's own slip.** The only repair is to register the person again, which gives
them a new code and a new record: teachers holding the old code can no longer credit them, and their history is split. There are two
different cases inside "wrong": **a slip** (the worker may never even know) and **a dispute** (the worker says it was unfair). For members,
you already have both a way back and an appeal.

## What you are choosing between (Question 1)

| | Option | What changes for a person | Cost |
|---|---|---|---|
| **A** | **Undo for a slip; an appeal for a dispute.** The Pariwar Admin may undo any ending made by mistake, restoring the worker as they were, with the same code; both the ending and the undo stay in the history. A worker who says an ending was unfair may appeal: the Pariwar Admin hears it — or, if a Pariwar Admin ended them, the Trustee Panel. *Our suggestion.* | A slip is put right at once; a worker ended unfairly has someone else to turn to. | A way back and an appeal record must be built before go-live. Field workers have no login yet, so an appeal is made by phone or in person and recorded by the officer who hears it. Teachers who joined with the code while it was ended were not credited; whether that is made up follows your answer to Question 6. |
| **B** | **Final** (as built). | Nothing more is built. | A slip by one officer cannot be put right except by a new registration, with a new code and a split history. |
| **C** | **Undo only, no appeal.** The Pariwar Admin may undo any ending, at anyone's request. | Slips are put right; a dispute depends on the Pariwar Admin agreeing. | The worker has no recognised way to be heard by someone other than the officers who manage them. A way back must still be built. |

**Our reading:** **A** — **because** a slip should cost nobody anything, one officer can end a worker alone, and an appeal heard by someone
other than the officer who ended them is the cheapest guard against a mistake.

# Question 2 — a worker who left comes back: same record and code, or a fresh start?

**In one sentence:** a worker who left, or was ended for not working, wants to come back — or the Trust itself wants them back; do they
return on their old record with their old code, or start again?

**Why it cannot be decided without you:** it decides what a returning person keeps — above all their code, which teachers may still hold.

## The one fact that decides it

**Who asks for the return — the worker or the Trust — makes no difference; what matters is whether the old code comes back.** Today they
are registered again: a District Admin registers them and a Pariwar Admin approves them, as you ruled for every worker. They get a new code
and a new record, and nothing links them to the old one. Teachers still holding the old code can no longer credit them. This question is
about a person who **left**; a person ended **wrongly** is Question 1, and a person ended for **conduct** is the anti-fraud story's.

## What you are choosing between (Question 2)

| | Option | What changes for a person | Cost |
|---|---|---|---|
| **A** | **Back on the old record, with the old code,** once a second officer approves, exactly as a new worker is approved. *Our suggestion.* | One person, one code, one history; teachers who still hold the code can credit them again. | A "rejoin" step must be built, and "an ending is final" changes. Teachers who joined with the code while they were away were not credited (the code was not working). |
| **B** | **A new registration and a new code, linked to the old record.** | The history reads as one person's; the old code stays dead. | A link to build; teachers holding the old code can never credit them again. |
| **C** | **A new registration and a new code, with no link** (as built). | Nothing more is built. | Two unconnected records for one person; the officer may not know they worked before. |

**Our reading:** **A** — **because** it is how a returning employee is usually treated (same person, same record), and the code is the
worker's working tool: teachers keep it long after it is handed out.

# Question 3 — a returning number: is the officer told?

**In one sentence:** when an officer registers a field worker whose phone number belonged to a worker this Pariwar has ended, should the
screen say so?

**Why it cannot be decided without you:** it discloses to a second officer that a person was once ended, and why.

## The one fact that decides it

**As built, nothing tells the officer.** Once a worker is ended, their number is free to be registered again in the same Pariwar — that is
how a worker registered with a misspelt name is corrected. So a worker ended because they stopped working can be registered again by
another District Admin, with a new code, and nobody sees the link. (Across Pariwars you already decided that a link comes later; this
question is only about one Pariwar.) If you choose Question 2 A, this is also how an officer learns to bring the person back on their old
record instead.

## What you are choosing between (Question 3)

| | Option | What changes for a person | Cost |
|---|---|---|---|
| **A** | **Shown, as information only.** The screen says the number belonged to a worker ended on a date, for a reason; the officer still decides. *Our suggestion.* | The registering officer knows the history before deciding. | A second officer learns of an earlier ending and its reason. A small piece of work on the register screen. |
| **B** | **Not shown** (as built). | Nothing changes. | A worker can be ended in one district and registered in another with no one aware. |
| **C** | **Refused without the Pariwar Admin.** | Re-engaging an ended worker needs the Pariwar Admin. | A typo correction would also need the Pariwar Admin unless excepted; more to build; a block where information may be enough. |

**Our reading:** **A** — **because** the officer is deciding whether to take the person on, the reasons on record today are neutral, and
the decision stays with the officer.

# Question 4 — a worker goes silent: when, and how, may they be ended?

**In one sentence:** a worker stops recruiting and cannot be reached — for weeks or months — and nobody knows why; when may the Trust end
them for not working, and does the system warn anyone?

**Why it cannot be decided without you:** ending a person for "not working" is a judgement about them, and it switches off their code.

## The one fact that decides it

**Today nothing notices a silent worker, and their code keeps working.** The system does not yet record which teachers a worker brings in,
so it cannot see that a worker has gone quiet. Until an officer acts, a teacher who got the code before the worker went silent can still
join with it and credit them — credit for work the worker did before going quiet. The officer's only tools are a suspension "under
review" (which does not describe silence) or an ending for "stopped working" — on the officer's own judgement, with no rule on how long
to wait, and the officer cannot reach the worker to tell them.

## What you are choosing between (Question 4)

| | Option | What changes for a person | Cost |
|---|---|---|---|
| **A** | **A warning, then the officer decides.** If a worker brings in no teacher for a set time (we suggest 90 days), their District Admin is told; the officer tries to reach them, and only then may end them for "stopped working". Until then they stay as they are. *Our suggestion.* | No one is ended for silence without an officer looking first; a quiet worker is noticed. | The warning needs the system to record which teachers a worker brings in, which a later story builds — until then, it is the officer's judgement alone. A worker in a slow area may be flagged though still working; the officer decides. |
| **B** | **The officer's judgement only** (as built). | Nothing more is built. | Silent workers are noticed only if an officer remembers to check; one District Admin may end a worker after a week, another never. |
| **C** | **Automatic.** After the set time, the system suspends the worker by itself. | Silence is dealt with without anyone acting. | The system would act against a person on its own; as built, every act on a worker must be done by a named officer, and the anti-fraud plan forbids ending a worker by a machine rule alone. A worker away for a good reason is suspended without anyone asking. |

**Our reading:** **A** — **because** a warning gets silence noticed while keeping the decision with an officer who has tried to reach the
person. We also suggest a reason **"could not be reached"** for a suspension, so the record says what actually happened.

# Question 5 — a worker dies: how is it recorded?

**In one sentence:** when a field worker dies, how does the Trust record it, and on whose word?

**Why it cannot be decided without you:** it is what the Trust records about a person's death, and the record is what the family would
rely on later for anything the worker was owed.

## The one fact that decides it

**Today no reason fits.** An officer can only choose "left", "stopped working" or "registered by mistake" — each of them untrue for a
death. Field workers are not members, so the Trust's process for a member's death does not apply to them. Nothing is owed to any worker
today; but once workers are paid, the family's claim will start from this record.

## What you are choosing between (Question 5)

| | Option | What changes for a person | Cost |
|---|---|---|---|
| **A** | **Its own reason, "died", recorded by the District Admin or the Pariwar Admin on what they have been told** (by the family, a colleague or the community), with the date of death. *Our suggestion.* | The record says what happened. | A new reason needs a small database change. It rests on the officer's word; a death recorded wrongly is put right under Question 1. |
| **B** | **As A, but only on a document** (for example a death certificate) that the officer has seen. | The record is backed by proof. | Families wait; the Trust handles a document about a non-member (a question for counsel); something to store and protect. |
| **C** | **Recorded as "stopped working"** (as built). | Nothing more is built. | The record is untrue, and a family's later claim starts from a record that says the worker simply stopped. |

**Our reading:** **A** — **because** the record should say what happened, field workers are known personally to their officers, and a
mistake can be undone (Question 1 A). **Not decided here:** whether money a worker had already earned is paid to their family, and to whom;
that is for the story that first pays field workers, and this question makes it pressing.

# Question 6 — a teacher joins with a suspended worker's code: is the worker ever credited?

**In one sentence:** while a field worker is suspended — under review, or at their own request — a teacher who joins with their code is a
member in full; is the worker credited for that teacher, now or if the suspension is lifted?

**Why it cannot be decided without you:** it is what the Trust owes a field worker, and you said what a suspension does to money is not yet
ruled.

## The one fact that decides it

**As built, the worker is never credited for that teacher — not during the suspension, and not afterwards, even if a review clears them.**
That follows the rule you confirmed for a worker **not yet approved** ("not credited and cannot be credited afterwards"); you were not
asked then about a worker who is suspended. The teacher is not affected in any option: they are a member in full either way. Nothing is
lost today: no credit is recorded for any field worker yet, and the first story that records it waits for this answer.

## What you are choosing between (Question 6)

| | Option | What changes for a person | Cost |
|---|---|---|---|
| **A** | **Never credited** (as built). | A worker suspended and later cleared loses the teachers who joined meanwhile, for good. | It costs a worker something permanent for a suspension that may turn out unjustified. Simplest to build. |
| **B** | **Held, and credited if the suspension is lifted;** lost if the worker is then ended. | A cleared worker loses nothing. | The credit story must keep "held" credits. A worker suspended at their own request (for example, on leave) would also be credited for anyone who used their code while they were not working. |
| **C** | **By reason:** under review — held, and credited if cleared; at the worker's own request — not credited. *Our suggestion.* | A cleared worker loses nothing; a worker who asked for a break is not credited for it. | Two rules instead of one, and the reason is the officer's word. The credit story must keep "held" credits. |

**Our reading:** **C** — **because** a review that clears a worker should not cost them, while a worker who asked to stop is not working
for the Trust in that time. (The same reasoning would apply to a worker ended wrongly and restored under Question 1.)

# Question 7 — five field-worker permissions: do you confirm them?

**In one sentence:** do you confirm five new permissions — **move** a worker to another district directly, **suspend**, **reactivate**,
**end**, and **read the full history** of a worker — held as below?

**Why it cannot be decided without you:** your earlier decision says permissions for field workers are confirmed by you once the feature
that uses them is built. This is that feature.

## The one fact that decides it

**You have already said who manages field workers; these permissions turn that into switches.** You ruled that the Pariwar Admin may move a
worker directly, that the District Admin will manage field workers with the Pariwar Admin filling in, and that the full log of a field
worker is kept. You said "manage" was a direction for suspending and ending, not yet a ruling — so this asks you to rule it. Every act is
written to the worker's history with the officer, their role and the permission that allowed it. Nobody sees a name or a phone number
through these permissions.

## What you are choosing between (Question 7)

| | Option | What changes for a person | Cost |
|---|---|---|---|
| **A** | **Confirm all five, as built.** Move: the Pariwar Admin only. Suspend, reactivate, end and read the history: the District Admin of the worker's current district, and the Pariwar Admin. *Our suggestion.* | A District Admin can suspend, reactivate or end a worker in their own district, alone, and read their history. | One officer alone can end a worker — and, until Question 1 is answered, an ending cannot be undone. If you want something stricter, we change who holds a permission before go-live; nothing is rebuilt. |
| **B** | **Suspend and end: the Pariwar Admin only.** The District Admin may still reactivate and read the history. | Every suspension and ending goes through the Pariwar Admin. | Against your direction that the District Admin manages field workers; the Pariwar Admin carries every case, including a typo correction. |
| **C** | **As A, but ending needs the Pariwar Admin.** | A District Admin may suspend; only a Pariwar Admin ends a worker. | A District Admin waits on the Pariwar Admin for every ending, including a typo correction and a death; fewer endings made by one officer alone. |

**Our reading:** **A** — **because** it follows your direction, every act names its officer in the history, and Question 1 (A) gives a way
back for an ending made wrongly. If you prefer C, it is a change of who holds one permission.

# In plain English

We are building the screens that let officers move a field worker to another district, suspend them, bring them back, record that their
work has ended, and read everything that has happened to their record. As built, an ending is final and a returning person starts again
with a new code. We ask seven things. **One:** if an ending was a mistake or unfair, we suggest the Pariwar Admin can undo a mistake, and
a worker can appeal — to the Pariwar Admin, or to you if a Pariwar Admin ended them. **Two:** a worker who left and comes back — whether
they ask or the Trust asks — should, we suggest, return on their old record with their old code, once a second officer approves. **Three:**
when an officer registers a number that belonged to an ended worker, we suggest the screen tells them, as information only. **Four:** a
worker who goes silent should be flagged to their District Admin after 90 days without a new teacher, and ended only after the officer has
tried to reach them — never automatically. **Five:** a death should be recorded as a death, on the officer's word, with the date. **Six:**
a teacher who joins with a suspended worker's code is always a member in full; we suggest the worker is credited for that teacher if a
review clears them, but not if they had asked to stop. **Seven:** please confirm five permissions — only the Pariwar Admin moves a worker
directly; the District Admin of the worker's district and the Pariwar Admin suspend, bring back, end and read the history. Nothing is live
today. The building goes ahead; ending a real worker, crediting any worker, and going live with these permissions wait for your answers.
If this section and the evidence below disagree, the evidence is the record.

## E3 — What the code actually does

- **At `bb4d8620` (re-checked by E4):** the suspend, reactivate and terminate commands exist in the domain package with **no caller** in any
  app; none of the five permissions is in the catalog (v60, 81 keys); a worker's state machine makes `terminated` final (no transition
  leaves it, and the database refuses any update of a terminated row).
- **Reasons:** suspend — `under_review`, `at_worker_request`; terminate — `left_voluntarily`, `inactive`, `registered_in_error`. No reason
  for death or for a worker who cannot be reached; nothing in the field-worker code mentions a death. A new reason is a database enum change.
- **Credit and silence:** a field worker's code accepts a new signup only while the worker is `active`; no code records a signup's credit to
  a worker yet (the attribution door has no caller) — so Question 6 costs nothing today, and the system cannot see a silent worker
  (Question 4). *Inference from the code, re-checkable by E4.*
- **Only a named officer acts:** every lifecycle event refuses a `system` or `member` actor — "A later automated actor is a new decision"
  (`packages/domain/src/field-worker/events.ts`, the header) — so Question 4 C needs a new decision.
- **A returning number:** the database's uniqueness on a worker's number skips terminated rows, so an ended worker's number can be
  registered again in the same Pariwar; nothing tells the officer. A worker's name and number cannot be changed once registered.
- **Members, for comparison:** a terminated member can be restored (`member.restore_terminated`, Story 10.19) and a moderation decision
  appealed (`member.decide_moderation_appeal`, Story 10.22); nothing of the kind exists for field workers.
- **What Story 13.1c will build (from the story, not yet code):** routes and screens for move, suspend, reactivate, end (any of the three
  neutral reasons, from any state but ended) and the history; each event carries the authorization that allowed it.
