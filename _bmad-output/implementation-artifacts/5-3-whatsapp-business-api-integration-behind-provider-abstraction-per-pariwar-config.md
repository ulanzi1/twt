# Story 5.3: WhatsApp Business API Integration Behind Provider Abstraction + Per-Pariwar Config `[CONSUMER]`

Status: done

## Story

As any member who has opted into WhatsApp delivery (Story 5.4) for a Pariwar that has WA Business enabled,
I want notifications delivered via WhatsApp Business using a UTILITY template registered with Meta, per a per-Pariwar WA Business number configured by the trustee,
so that high-trust, dual-gated notifications reach me on the channel I already use daily.

**This is the THIRD story of Epic 5 and the SECOND `[CONSUMER]`.** It turns Story 5.1's `whatsapp-business` provider **stub** into a **real** transport behind the unchanged `ChannelProvider` port — sending Meta-approved **UTILITY templates** via **Meta's WhatsApp Business Cloud API** with per-Pariwar credentials — and ships the **per-Pariwar WA config substrate** (config table + templates + minimal trustee admin form) the channel needs. It follows the exact factory + fixture + opt-in-real shape Story 5.2 established for `push`. It does **NOT** touch the dispatcher's public shape, the canonical ladder, `ChannelProvider`, `DeliveryResolver`, or any other channel. It does **NOT** build the fallback-to-SMS ladder (5.6 wraps the dispatcher), the inbound opt-in webhook (5.4), or member opt-in state (5.4).

## Acceptance Criteria (at a glance)

1. Real WA Business transport (Meta Cloud API, UTILITY templates) behind the unchanged `ChannelProvider` port.
2. Per-Pariwar WA credentials via Secret Manager NAME; fixture fallback when unprovisioned.
3. Per-Pariwar WA config substrate: config table (number + phone-number-id + toggle + credential NAME) + per-category UTILITY template registry + repo + RLS.
4. Minimal trustee admin form + API to configure the WA number, toggle, and per-category template names (full polish → Epic 10).
5. WA-correct escaping semantics owned by this channel (deferred-work.md D1 re-trigger); WA send-status mapping seam (delivered/read/failed/blocked) for the 5.4 webhook to feed.
6. Honest failure classification (template-not-approved, Meta API unavailable, 24h-window-expired, member-blocked) surfaced as `SendResult` — no fabricated success, no cascade here.
7. Determinism + escaping gates extended to the WA template render; audit + AI-4-3 walk for the new caller-facing config paths + the send path; AR-53 single-module-swap discipline documented.

**AC1 — Real WA Business transport behind the unchanged `ChannelProvider` port (FR-72, AR-53, Story 5.1 dispatcher).**
Replace the Story 5.1 `whatsappBusinessProvider` **stub** (`packages/channels/src/providers/whatsapp-business.ts`) with a **real** implementation of the SAME `ChannelProvider` interface (`send`, `getStatus`) — the dispatcher, `CANONICAL_CHANNEL_LADDER`, `provider.ts` port, and `DeliveryResolver` do NOT change (architecture §3.4 "Providers are swappable"; [[project_channels_no_live_dispatch_yet]]). The provider is a **FACTORY** bound to a per-Pariwar messaging handle — mirror `createFcmProvider` (`fcm.ts`) EXACTLY: the frozen `send(rendered, target)` carries no `pariwar_id`, so the composition layer resolves the Pariwar's WA credentials + config and builds a provider bound to them. `scope: 'per-pariwar'` (5.1 declared the field). The provider calls **Meta's WhatsApp Business Cloud API** `POST https://graph.facebook.com/<version>/<phone_number_id>/messages` with a **`type: "template"`** message body (UTILITY category template). `send` returns a well-formed `SendResult` (`accepted` on Meta acceptance — Meta returns a `messages[0].id` wamid; `rejected` with a mapped, PII-free `detail` on a Meta error) — it **NEVER throws into `dispatch`** (resolve to a `SendResult`, never a rejected promise, on the normal error path — the `fcm.ts` try/catch template). `getStatus` returns honest `unknown` at accept time (Meta gives no synchronous delivery receipt — delivered/read status arrives asynchronously via the 5.4 webhook; do NOT fabricate `delivered`).

**AC2 — Per-Pariwar WA credentials via Secret Manager NAME; fixture fallback when unprovisioned (AR-17, AR-53).**
Per-Pariwar WA Business **access token** (Meta system-user token) loads via `resolveSecretValue` (Story 1.5, `@twt/domain`) — a Secret-Manager **NAME** referenced from the per-Pariwar config row (AC3), never the value; a local-dev env fallback var mirrors argon2/turnstile/digilocker/FCM. **Follow the repo's opt-in-real convention EXACTLY (Turnstile/DigiLocker/KYC in `apps/api/src/deps.ts`, and 5.2's `fixture-push`): an absent/blank credential NAME (or an absent config row, or `enabled=false`) resolves the WA channel to a `fixtureWhatsappProvider` (log-only, no network), so the stack boots with ZERO Meta config in dev/CI/not-yet-provisioned.** Setting the credential NAME + `enabled=true` opts into real Meta sends. Per-Pariwar WA API clients are built lazily and cached by `pariwar_id` (never rebuild the client per send) — mirror `firebase-app.ts`'s per-Pariwar cache, and inherit its **documented cache-staleness gap**: `resolveSecretValue` re-fetches fresh each call, but an in-process client cache has no TTL/eviction, so a rotated Meta token is picked up only on process restart (restart-required-on-rotation; document, do NOT build eviction — same call 5.2 made).

**AC5 — WA-correct escaping owned by this channel (deferred-work.md D1) + WA send-status mapping seam (AC of the epic; webhook receiver is 5.4).**
This story **owns WhatsApp's escaping semantics** per the 5.1 deferral (deferred-work.md:1812 — "each provider story MUST own its channel's escaping"). Today `render.ts`'s `whatsapp` arm passes `escapeText` (HTML-entity + backslash-markdown escaping) — but **WA UTILITY templates are parameterized, not free-text**: the payload-derived values are **template body PARAMETERS** (`components[].parameters[].text`), and Meta's rule is that a template parameter may **NOT contain newlines, tabs, or 4+ consecutive spaces** (Meta rejects the send otherwise), and does NOT interpret HTML/markdown. So WA's correct escaping is NOT `escapeText`'s HTML-entity encoding (that would garble `&`→`&amp;` in the member's WA message) — it is **whitespace-normalization** (collapse runs of whitespace, strip newlines/tabs) so the send is Meta-valid, with injection kept inert by the value never being interpreted as markup. **Render shape (Q1 — CONFIRMED by BigDev 2026-07-05: option A, pre-composed body string for v1):** the WA renderer emits ONE whitespace-normalized `body` string (the existing `RenderedMessage.body`, no shape change), which the provider sends as the template's single body parameter (`{{1}}`). Add a `whatsapp` transform distinct from `escapeText` and `identity` to `render.ts`'s already-parameterized escaping seam (5.2 D1). Structured multi-parameter templates (an additive `RenderedMessage.templateParams`) are the **Epic-10 evolution — explicitly NOT v1** (see Dev Notes "Template-param render shape decision"). Separately, define the **WA delivery-status mapping seam**: a pure `mapMetaStatus(metaStatus) → SendStatus['state']` (`sent | delivered | read → delivered/sent`, `failed`, `deleted/blocked → failed`). **Ownership split (Q2 — CONFIRMED by BigDev 2026-07-05):** 5.3 EXPORTS the pure `mapMetaStatus(metaStatus)` function AND a status-update service/repository seam (persist per-send WA status keyed by wamid). Story 5.4 OWNS the HTTP webhook receiver, Meta signature verification, payload parsing, retries, and the 5s acknowledgement timing, and CONSUMES those exported seams. 5.3 builds NO webhook route, NO signature verification, NO endpoint ([[project_channels_no_live_dispatch_yet]] boundary).

**AC6 — Honest failure classification; NO cascade in this story (AR-19 ladder is 5.6).**
Classify Meta send failures into a stable, PII-free `detail` the (future 5.6) fallback ladder + observability can read: `template_not_approved` (Meta error 132xxx template errors), `api_unavailable` (5xx / network / rate-limit 131xxx), `window_expired` (the member's 24h customer-service window closed — around 131047/131051), `recipient_blocked` / `invalid_recipient` (around 131026/131052), `auth` (190/system-user token invalid). **These exact numeric codes are indicative, not settled — verify each one against the current Meta WhatsApp Cloud API error-code reference at implement time (do NOT hardcode the class↔code mapping from memory; the same caveat AC1 gives the graph version/template shape applies here).** Mirror `push-errors.ts`'s `classify* → detail` shape (`<class>:<code>`) so the invalidation/fallback seam reads it back WITHOUT any `SendResult` shape change. **This story adds NO push→WA→SMS cascade and NO retry ladder** — the dispatcher still attempts `whatsapp` independently and records the honest outcome; AR-19's fallback-to-SMS is implemented in Story 5.6 which WRAPS the dispatcher (5.1 Dev Notes "Dispatch execution vs. delivery policy"; epics.md line 2140 reads as if 5.3 owns the fallback — it does NOT, same clarification as 5.2's line-2117 note). Dual-gating (admin toggle AND member opt-in) is enforced by the `DeliveryResolver` composition seam (whatsapp-business.ts's own header comment: "dual-gated ... enforced by the delivery resolver, not here") — the config `enabled` toggle is the admin gate this story ships; member opt-in ACTIVE is Story 5.4's gate. The provider itself never gates — it sends what it's handed.

### Meta WhatsApp Business Cloud API — the concrete integration facts (verify current at implement time)
- **Send endpoint:** `POST https://graph.facebook.com/<graph_api_version>/<phone_number_id>/messages`, `Authorization: Bearer <access_token>`, JSON body `{ messaging_product: "whatsapp", to: "<E.164-no-plus>", type: "template", template: { name, language: { code }, components: [...] } }`. Success → HTTP `200` with `{ messages: [{ id: "wamid...." }] }` (the wamid is the `providerMessageId`). **Use Context7 / the live Meta Cloud API docs to confirm the current graph version + template component shape at implement time — do NOT hardcode from memory; Meta versions the API and template rules change.**
- **UTILITY templates only** (architecture §3.4 line 1940-1941): payment reminder, payout issued, claim accepted, expiry warning, membership lapse — NOT MARKETING. The category maps from `alert_category` → the Pariwar's registered `template_name` via `resolveApprovedTemplate`.
- **Template parameters** carry the payload-derived variables (`components[].parameters[].text`). Meta rejects a parameter containing newlines/tabs/4+ consecutive spaces → the AC5 whitespace-normalization is a CORRECTNESS requirement, not cosmetic.
- **24h customer-service window:** a UTILITY template CAN be sent outside the 24h window (templates are the mechanism for re-engagement), but a member who never opted in / blocked the number / has an invalid number fails with a stable Meta error code → AC6 classification. The 24h window primarily matters for free-form (non-template) messages, which v1 does NOT send.
- **Status callbacks** (delivered/read/failed) arrive **asynchronously** on Meta's webhook — the SAME webhook Story 5.4 stands up for inbound opt-in messages. 5.3's `mapMetaStatus` + status-update seam is the consumer contract; 5.4 owns the receiver. This split is the Q2 boundary — do NOT build a webhook route in 5.3.

### Template-param render shape decision (Q1 — CONFIRMED by BigDev 2026-07-05: option A for v1)
**Locked: (A) pre-composed body string.** The WA renderer emits one whitespace-normalized `body` string (like today) and the provider sends it as the template's single `{{1}}` body parameter. Keeps `RenderedMessage` unchanged; single-body-parameter UTILITY templates satisfy the five named use-cases (payment reminder, payout issued, claim accepted, expiry warning, membership lapse); aligns with the epic's "minimal admin form ... full polish lives in Epic 10". **(B) structured template parameters** (the WA renderer emitting an ordered `{{1}}, {{2}}, …` list via an additive optional `RenderedMessage.templateParams` field — render OUTPUT, like 5.2's additive `deepLink`, NOT touching the frozen `Alert`) is the **Epic-10 evolution — explicitly out of scope for v1**. Do NOT add `templateParams` in this story.

### WA send-status webhook — ownership split (Q2 — CONFIRMED by BigDev 2026-07-05)
Epic AC (line 2139) says WA "send status (delivered, read, failed, blocked) is captured from Meta webhook callbacks." The **webhook ingress primitive** is explicitly Story 5.4's deliverable (`apps/api/modules/channel-webhooks/`, AR-44 persist-and-ack-within-5s). The boundary is a clean separation of concerns:
- **5.3 OWNS (this story):** the outbound WA transport, Meta request construction, the pure `mapMetaStatus(metaStatus)` status-mapping function, and a per-send **status-update service/repository seam** (persist WA delivery status keyed by wamid). 5.3 EXPORTS `mapMetaStatus` + the status-update seam.
- **5.4 OWNS (next story):** the HTTP webhook receiver/endpoint, Meta signature verification, payload parsing, retries, and the 5s acknowledgement timing — and it CONSUMES 5.3's exported `mapMetaStatus` + status-update seam to persist the mapped status.

This keeps 5.3 free of any webhook route/endpoint/verification (consistent with the no-live-dispatch boundary — [[project_channels_no_live_dispatch_yet]]) and avoids 5.3/5.4 both standing up webhook infra. No ambiguity: if it's an HTTP receiver, verification, parsing, retry, or ack, it is 5.4; if it's the mapping function or the persistence seam, it is 5.3.

### Escaping: WA is whitespace-normalization, NOT `escapeText` (the D1 re-trigger)
deferred-work.md:1812 (decision 2026-07-05) requires each provider story to own its channel's escaping. 5.2 gave push the `identity` transform (plaintext tray renders no markup). WA's correct transform is **whitespace-normalization of template parameters** — because (a) template params are not markup-interpreted (so HTML-entity encoding `&`→`&amp;` would GARBLE the member's message, the exact bug the deferral flags), and (b) Meta rejects params with newlines/tabs/4+ spaces (so normalization is required for the send to succeed). Add a `whatsapp` transform alongside `escapeText`/`identity` in `render.ts` (5.2 already parameterized the escaping seam — this is a third arm, not a rewrite). Keep injection inert by the param never being interpreted, and assert it in the split escaping test.

### AR-53 external-dependency abstraction — the single-module-swap discipline
AR-53 commits that "the abstraction allows future Meta API changes or alternate WA Business providers to be a single-module change." Structurally: (1) the `ChannelProvider` port is the swap boundary — a BSP swap is a new `providers/<bsp>.ts` + a registry change, nothing else; (2) Meta-specific facts (graph version, endpoint shape, error codes, template-param rules) live INSIDE `whatsapp-business.ts` + `whatsapp-app.ts` + `whatsapp-errors.ts`, never leaking into `dispatch`/`render`/contracts; (3) the config table stores provider-agnostic intent (number, toggle, template names) + a credential NAME, so a BSP swap re-points the credential + client without a schema change. ADR-0028 records the v1 = direct Meta Cloud API decision + this swap surface. This is a cloud-control/vendor decision → an ADR, not only Dev Notes. [[feedback_architecture_vs_adr_boundary]]
