# Story 6.7: Ground Inspection Scheduling + Notes + Photos

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a **District Admin** (or, later, a designated field worker) conducting the physical verification of a claim,
I want a ground-inspection workflow to **schedule** an inspection, **record notes** (structured + free-text), and **upload photos**,
so that physical verification is captured **alongside** the peer mesh — **both signals, not either** (PRD §4.6 / FR-40) — and the verifier can weigh the presence or **absence** of each.

## Story Classification

`[SURFACE]` — this story adds a first-class admin surface (schedule + notes + photos) on top of the Story 6.1 claim state machine and the Story 6.5 object-storage substrate. It **owns + first-emits** `claim.ground_inspection_scheduled` (enriches the 6.1 placeholder payload) and **adds** the 22nd claim event `claim.ground_inspection_completed` (a new annotation/identity event). It **consumes** the Story 6.5 `ClaimDocumentStorage` port for the photo bytes (**not** the OCR-shaped `claim_documents` row — see **Decision D2**) and the Story 6.1 `projectClaimState` single-writer for the two annotation events. Both events are **identity transitions** — ground inspection does **not** advance the primary lifecycle state (it gathers during `verification_in_progress`, exactly like peer-mesh responses). It ships the read accessor the Story 6.10 verifier console consumes; it does **not** build the console mount (**Decision D4**).

## Six seam decisions — surfaced for confirmation

Like Story 6.6's D1/D2, these decisions touch frozen contracts / cross-story boundaries / business invariants. Recommendations are given; confirm or override before/at dev-time. **D5 and D6 are correctness invariants, not just seams** — get them wrong and a district admin acts outside their district, a claim ends up with two live inspections, or a completion tears.

- **Decision D1 (permission key) — RECOMMENDED: single-dot `claim.conduct_ground_inspection`, granted to `district_admin` AND `block_admin` (+ `super_admin` auto).** The epic AC's two-dot `claim.ground_inspection.conduct` **VIOLATES `PERMISSION_KEY_REGEX`** (`/^[a-z_]+\.[a-z_]+$/`, `packages/domain/src/rbac/permissions.ts:41`) — the **exact** reconciliation Story 5.8 made for `pariwar.degraded_mode.declare` → `pariwar.declare_degraded_mode`. The correct ADR-0008 `<resource>.<action>` form is single-dot. PRD FR-40 names the scheduling actor as "a **block-/district-level** admin" (not district-only), so grant to BOTH `district_admin` (`scopeCeiling: 'district'`, already holds `claim.approve`) AND `block_admin` (`scopeCeiling: 'block'`, currently holds only `[member.suspend, member.view_validity]`). **Verify before relying on the `block_admin` grant:** the D6 permission gate runs at `{ dimension: 'district', resolveValue }` — confirm (against `packages/domain/src/rbac/scope.ts`'s scope-resolution logic and the `check.test.ts` patterns) that a grant scoped to a `block` node actually satisfies a `dimension: 'district'` check for that block's parent district. If the scope model requires an exact-node match rather than containment, a block-scoped grant may never authorize anything under a district-dimension check, and the gate/grant would need to resolve district from the block's parent instead — add a test asserting this explicitly (Task 7). (Catalog bump is **7 → 9** combined with the D6 `claim.override_ground_inspection` key — see Task 1.) **`field_worker` grant is DEFERRED** to Epic 12 — its role is `scopeCeiling: 'self'` and its comment says "Dispatch keys land Epic 12; scope `self` = `field_worker_self`" (`roles.ts:155`): a field worker conducting an inspection on an arbitrary claim needs the Epic-12 dispatch/assignment substrate that does not exist yet. Record that as an acceptance condition (mirrors 6.6's deferral discipline). The two-dot form may survive only as an **audit action** string if one is emitted.

- **Decision D2 (photo storage seam) — RECOMMENDED: reuse the Story 6.5 `ClaimDocumentStorage` PORT, NOT the `claim_documents` ROW.** The epic says "consume Story 6.5's `<ClaimDocumentUpload>` for the photo path." Two hard reasons the OCR-shaped `claim_documents` row is the wrong vessel for inspection photos: (1) it has a **UNIQUE `(claim_case_id, document_type)`** index (`claim_documents.ts:136`) → only **ONE** `ground_inspection_photo` per claim, but an inspection has **many** photos; (2) its `parity_outcome` / `parity_flags` / `ocr_confidence` / `verifier_review_required` columns are **NOT NULL OCR concepts** irrelevant to a field photo, and its single-writer is the OCR job. So: store the photo **bytes** via the reusable `ClaimDocumentStorage` port (GCS/in-memory/local-fs adapters already exist — `packages/platform-adapters/src/claim-document-storage/`), and persist the **object keys** in a ground-inspection-owned child table (Task 3), **NOT** a `claim_documents` row, and enqueue **NO OCR/parity job** for these. Note also that `<ClaimDocumentUpload>` = the **mobile** RN screen (`apps/mobile/app/(claim)/document.tsx`); ground inspection is an **admin** surface, so the reusable asset is the **port + the upload-endpoint pattern**, not the RN component itself.

- **Decision D3 (upload lifecycle guard) — RECOMMENDED: a NEW admin ground-inspection upload endpoint, not reuse of `uploadClaimDocument`.** The shared 6.5 upload core (`claims.documents.handlers.ts`) runs a lifecycle guard that accepts a document **only** when the claim is `intake_converged` or `documents_pending` (`UPLOADABLE_STATES`, handlers.ts:44) and otherwise returns `409 claim_document.upload_not_allowed`. A ground inspection runs during **`verification_in_progress`** (peer-mesh already advanced the state), so the 6.5 endpoint would **409** every inspection photo. Add a dedicated admin endpoint with its own guard (accepting `verification_in_progress` — and any later pre-terminal state where inspection is still meaningful; see Dev Notes "State posture").

- **Decision D4 (verifier-console mount) — DEFERRED to Story 6.10/6.11.** AC2 ("verifier console evaluates the case → both signals presented; absence of either is itself a signal") is a **6.10 consumer** concern. 6.7 ships the **read accessor** (`getClaimGroundInspection` / bundle read) that 6.10 consumes and **records** both the presence and the absence signal; it does **not** build the console mount (same boundary as 6.5's `<DocumentTypeChooser>` and 6.6's operator-queue deferral). **Flagged for 6.10 to resolve (not addressed here):** epics.md's Story 6.10 AC (line 2475) and PRD FR-42 both require the verifier console to load all signals from **one** denormalized query with **no N+1**. 6.7 ships `getClaimGroundInspection()` as a standalone accessor — 6.10 must decide whether to call it as a separate round-trip (acceptable only if 6.10's "one query" language tolerates a bounded, small number of per-claim reads) or fold a joinable query fragment from `ground-inspection-read.ts` into its own compound query. This is a genuine open cross-story data-contract question, not resolved by this story.

- **Decision D5 (assignment lifecycle + concurrency) — CONFIRMED: the ASSIGNMENT is the addressable unit; a claim may hold MULTIPLE assignments — sequential or parallel, within the SAME district or across DIFFERENT districts; reschedule SUPERSEDES a SPECIFIC assignment under a row lock — NOT read-side "latest row", and NO active-uniqueness of any kind.** Corroboration/additional-evidence flows legitimately create **several concurrent** ground-inspection assignments on one claim (D6), so there is **no** "one active inspection per claim" invariant — a claim-wide `UNIQUE (claim_case_id) WHERE status='scheduled'` would be **wrong** (it forbids the parallel assignments D6 requires). Each `claim_ground_inspections` row is one **assignment**, addressed by its own `ground_inspection_id`. The concurrency discipline still holds **per assignment**: a reschedule targets a **specific** `ground_inspection_id`, `SELECT … FOR UPDATE` that row → set it `superseded` → insert the replacement, in ONE scope-tx — never `ORDER BY created_at LIMIT 1` to guess "the current one". `ground_inspection_status` = `scheduled | completed | superseded | photo_refused | evidence_unavailable` (the last two are D6's refusal disposition). **NO `(claim_case_id, district)` active-uniqueness — decided OFF.** District is an **authorization boundary, not an inspection identity**; two active same-district assignments are legitimately concurrent (residence + workplace verification; a second corroboration visit by another inspector; separate sites under different purposes; a supervisor-requested additional-evidence visit while the first is still open). A claim+district uniqueness constraint would encode an operational assumption as a business invariant and could **reject valid evidence collection**. Duplicate/accidental scheduling is controlled by **request idempotency + operator visibility**, not a DB uniqueness constraint; the per-assignment row lock is sufficient for reschedule races.

- **Decision D6 (assignment-specific jurisdiction + inspector identity + mandatory-photo/refusal) — CONFIRMED.** Each assignment records **its own** `district` (structured, non-null — the authz anchor), `inspection_stage` (`initial|corroboration|additional_evidence` — why) + `inspection_site_type` (`family_residence|current_residence|permanent_residence|workplace|school_or_office|incident_location|other` — what/where; two separate bounded fields), the encrypted `location_ciphertext` (exact address/landmark/contact/free-text site detail — Tier-1), and `inspector_actor_id`. **Authorization is evaluated against THAT ASSIGNMENT's district** — *not* the deceased's posting district, *not* a single claim-wide district. So the district is a **stored, non-null column on the assignment** (plaintext non-PII, the `member_postings.district` posture), supplied at schedule time. The permission gate runs at `{ dimension: 'district', resolveValue }` (`apps/api/src/modules/rbac/index.ts:96,106` — the default `pariwar` dimension is insufficient): for **schedule**, `resolveValue` reads the assignment **district from the request body** (so an admin can only open an assignment in a district their grant covers); for **reschedule/findings/complete/refusal/photo/read**, `resolveValue` reads the **assignment row's `district`**. Multiple parallel assignments — in the **same or different** districts — are each independently gated to a district-scoped admin. (This supersedes the earlier deceased-posting-district idea; the null-posting edge disappears — district is an explicit assignment attribute, required at schedule.) **Inspector identity:** persist `inspector_actor_id`; thread it into the `scheduled`/`completed` events + audit; **completion (and photo upload, findings, refusal) rejects an acting actor ≠ the assigned inspector** unless an explicit **supervisor-override permission key** is held. The override is a **defined RBAC key** — `claim.override_ground_inspection` (single-dot, Task 1), granted to a supervisory `pariwar`-ceiling role (`pariwar_admin` + `super_admin`), checked via `requirePermission` at the assignment's district when `acting_actor ≠ inspector_actor_id`. It is never implicit, never "any district admin" — a district admin cannot silently act on a peer's assignment; only the assigned inspector or an explicit override-holder can. The override action is stamped into the event/audit (who overrode whom). **Scheduling and rescheduling are district-AUTHORITY operations, not evidence-AUTHORING ones — they do NOT require the acting admin to be the currently assigned inspector** (only the district-scoped `claim.conduct_ground_inspection`); rescheduling stays district-scoped, row-locked, idempotent, and audited, and the replacement **may assign a different `inspector_actor_id`** (reassignment is a normal reason to reschedule). The inspector-identity guard applies to the evidence-authoring verbs — `complete`, `refusal`, `findings`, `photos` — not to `schedule`/`reschedule`/`read`. **Mandatory photo (overrides the earlier "no photo required"):** an inspection **cannot** be `completed` without **≥ 1 valid persisted photo** on the active assignment — the photo is **mandatory completion evidence**, and `completeGroundInspection` verifies the count **transactionally** before appending `claim.ground_inspection_completed`. **Refusal path:** if the family refuses all permitted photography, the assignment is recorded `photo_refused` (or `evidence_unavailable`) with a **mandatory encrypted note** + an audit line; it is **NOT completed successfully** (no `completed` event); the claim is **escalated to the verifier/adjudicator** (a signal the 6.10 console reads), who may deny under the applicable Niyamavali rule after reviewing the refusal + other evidence (adjudication stays 6.10/6.11 + niyamavali — Decision D4 boundary).

## Acceptance Criteria

> Lifted from epics.md §Story 6.7 (lines 2415–2431). Event naming reconciled to the codebase single-dot `resource.action` snake_case convention + the Story 6.1 frozen vocabulary (never the epics.md illustrative `claim.ground-inspection.scheduled` hyphen/double-dot form). Permission key reconciled per Decision D1. FR/AR provenance: PRD §4.6 FR-40 (peer-mesh + ground-inspection are **both, not either**).

**AC1 — Schedule a ground-inspection ASSIGNMENT (permission-gated at the assignment's district).**
**Given** FR-40 and a claim in an inspectable state (`verification_in_progress`; see Dev Notes "State posture")
**When** an admin holding **`claim.conduct_ground_inspection`** (Decision D1) **at the target assignment's district** (Decision D6 — `dimension: 'district'` with the district taken from the schedule request, not the default pariwar-wide check and not the deceased's posting district) schedules an inspection assignment
**Then** the assignment is persisted in a new tenant-isolated `claim_ground_inspections` row with: **date/time** (`scheduled_at`), **`district`** (the assignment's jurisdiction — structured non-null plaintext, the authorization anchor), **`inspection_stage`** (`initial | corroboration | additional_evidence` — why), **`inspection_site_type`** (`family_residence | current_residence | permanent_residence | workplace | school_or_office | incident_location | other` — what/where), **assigned inspector identity** (`inspector_actor_id` — persisted, threaded into events + audit), and a **family contact** — with PII fields (family contact; the exact address/landmark/contact instructions/free-text site description in `location_ciphertext`; any free-text notes) stored as **Tier-1 envelope ciphertext** (AR-12 / Story 1.5), and the bounded operational metadata (`district`, `inspection_stage`, `inspection_site_type`, `scheduled_at`, `status`) in plain columns. `inspection_site_type = 'other'` requires a non-null `location_ciphertext` description.
**And** a claim MAY hold **multiple assignments** — sequential or parallel, **within the same district or across different districts** (D5/D6, for corroboration/additional evidence; e.g. a family-residence visit and a workplace visit in one district); there is **no** active-uniqueness of any kind. The assignment is addressed by its own `ground_inspection_id`; a **reschedule supersedes that specific assignment** (`SELECT … FOR UPDATE` the row → `superseded` → insert the replacement, one scope-tx — never a read-side "latest row" pick). A retried schedule/reschedule POST is de-duplicated by the **idempotency contract** (Dev Notes "Schedule + reschedule idempotency"), not by a DB uniqueness constraint.
**And** a single `claim.ground_inspection_scheduled` event is emitted via `claim.projectClaimState` (the ONLY legal writer to `claims.current_state`) as an **annotation/identity transition** (`from_state === to_state === 'verification_in_progress'` — it does **not** advance state); 6.7 **owns** this event and is its **first emitter**, so **enriching** the 6.1 placeholder payload with `ground_inspection_id` + `inspector_actor_id` + non-PII assignment metadata (`district`) is safe and correct (see Dev Notes "Event naming"). The event payload carries **NO PII** (ids + non-PII metadata only — the peer-mesh precedent).

**AC2 — Record notes (structured + free-text).**
**Given** a scheduled inspection
**When** the inspector records findings
**Then** **structured fields** (a bounded enum set — e.g. `residence_confirmed`, `neighbours_confirmed`, `death_confirmed_visually` — see Dev Notes "Notes model") persist as non-PII columns/jsonb, and **free-text notes** persist as **Tier-1 ciphertext** (free text may name the deceased / bystanders — treat as PII, encrypt-before-insert, never logged/echoed — the `claim_documents` extracted-field precedent).

**AC3 — Upload photos (consume the 6.5 storage port; bounded; orphan-safe).**
**Given** a scheduled (active) inspection
**When** the inspector uploads one or more photos
**Then** the upload is authorized as the **assigned inspector's evidence** (#8/D6 — `acting_actor === inspector_actor_id` or a checked `claim.override_ground_inspection`; NOT open to any in-district admin) on an assignment still in `status = 'scheduled'`; **MIME allowlist** (`image/jpeg`, `image/png`, `image/webp` — NOT the death-cert PDF allowlist) + **per-file byte cap** are checked **before** the storage `put`.
**And** the **max-photo-count per assignment = 20 (LOCKED, a named const — NOT a configurable registry**; a byte cap independently bounds total payload, so 20 is a simple storage-abuse boundary, generous for residence/workplace evidence). The (21st) photo is rejected, enforced in the domain writer **under the parent-assignment row lock** (count-then-insert while `SELECT … FOR UPDATE` holds — a route-level pre-check would race, #7).
**And** each photo's **bytes** are stored via the Story 6.5 `ClaimDocumentStorage` port (Decision D2); its **object key** + non-PII object metadata (`content_type`, `byte_size`) + the **encrypted `caption_ciphertext`** (nullable, Tier-1 — #11, a free-text caption can name a person/place) persist as **one row per photo** in a `claim_ground_inspection_photos` child table (**many** photos per inspection — NOT a `claim_documents` row, NOT unique-per-type, NO OCR/parity job). Access is a short-lived **signed URL** minted from the object key (never the bytes, never a public URL) — the 6.5 access pattern.
**And** the write is **orphan-safe**: `put`-then-persist, and if the DB photo-row insert fails after a successful `put`, the object is **deleted best-effort** (`storage.delete?.(key)`) before rethrowing — never a dangling GCS object with no row. This is **structurally modeled on** the 6.5 upload's `put`→try/catch→best-effort-delete→rethrow shape (`claims.documents.handlers.ts`), but is not identical: that handler's compensation guards a **queue-enqueue** failure (6.5 never inserts a `claim_documents` row synchronously — the async job does), so 6.7 is the first caller to apply this shape to a real synchronous DB-insert failure.
**And** at least one valid photo is **MANDATORY completion evidence** (Decision D6 — overrides the earlier optional posture): a `completed` inspection MUST carry ≥ 1 persisted photo on its active assignment. The absence-of-photography case is NOT "complete without a photo" — it is the **refusal disposition** (AC4a), a distinct, non-successful outcome.

**AC4 — Completion event (atomic; guarded; by the assigned inspector; photo-mandatory).**
**Given** an active assignment with notes and **≥ 1 persisted photo**
**When** the **assigned inspector** (Decision D6 — acting actor === `inspector_actor_id`, or an explicit supervisor override) marks it **complete**
**Then** completion is **atomic in ONE DB scope-tx**: (1) `SELECT … FOR UPDATE` the assignment row + assert `status = 'scheduled'`, (2) **verify ≥ 1 photo** under that lock (`SELECT count(*)` — reject with `GroundInspectionPhotoRequiredError` if zero; the photo is mandatory evidence, D6), (3) update the assignment row (`status = 'completed'`, `completed_at`, final notes/findings), (4) append `claim.ground_inspection_completed` via `claim.projectClaimState` — all-or-nothing, no partially-completed inspection. Object storage is **NOT** in this transaction (completion only counts already-durable photo rows), and the **audit line is a post-commit sink emission, NOT part of this tx** (#10 — the durable record is the `events_log` event; see Dev Notes "Audit boundary"). The atom is `{ photo-check + row update + event append }`.
**And** `claim.ground_inspection_completed` is the **22nd** claim event, **NEW** (NOT in the 6.1 or 6.6 vocabulary), an **annotation** transition that is **identity only from `verification_in_progress`**; its payload carries `ground_inspection_id` + non-PII completion metadata, **NO PII**. It is a **material evidentiary fact** — the reducer stays total (never throws — replay-robustness), but the **write path GUARDS the claim state**: emission is rejected (a new `GroundInspectionClaimNotInVerificationError`) when the claim is terminal or pre-verification, so a `completed` event is **never appended** to a resolved or not-yet-verifying claim (the exact hazard Story 6.6 fixed with `PeerMeshClaimNotInVerificationError` — unconditional identity-event append is unsafe). Both `scheduled` and `completed` events exist on the claim's `events_log` stream (epics.md:2427 "emit both").

**AC4a — Photo-refusal / evidence-unavailable disposition (NOT a successful completion).**
**Given** an active assignment where the family **refuses all permitted photography** (or evidence is otherwise unobtainable)
**When** the inspector records the refusal
**Then** the assignment takes the **semantically correct disposition (#12), not a free caller pick**, with a **bounded `refusal_reason`** from the v1 closed set paired to the disposition: `photo_refused` ⇔ `family_refused_photography` (the family actively refused permitted photography); `evidence_unavailable` ⇔ one of `premises_inaccessible | responsible_person_absent | site_no_longer_exists | inspector_safety_risk | other_evidence_unavailable`. A mismatched status/reason pair is rejected. A **MANDATORY encrypted note** (`notes_ciphertext` non-null — Tier-1, the human detail) is required for every refusal, and remains required for `other_evidence_unavailable` (never a bare "other"), in one scope-tx under the assignment row lock. It is **NOT** completed successfully: **no `claim.ground_inspection_completed` event is emitted** (the completion path's photo guard is exactly what this disposition routes around). The claim is **escalated to the verifier/adjudicator** — a signal the Story 6.10 console reads (via the AC5 accessor); the verifier may **deny under the applicable Niyamavali rule** after reviewing the refusal + other evidence. Adjudication (the deny decision + the niyamavali binding) is 6.10/6.11's job (Decision D4 boundary); 6.7 records the disposition + mandatory note + audit + the escalation signal, exactly as 6.6 recorded the AR-61 peer-mesh fallback disposition (no auto-deny, no state advance).

**⚠️ Open planning-doc tension (flagged for PM, not resolved by this story):** PRD FR-40's testable consequence states both peer-mesh AND ground-inspection **must** pass for the claim to advance — no exception clause. epics.md's own Story 6.7 AC (line 2429-2431) softens this to verifier discretion ("the verifier may still approve with only one signal"). AC5 below follows epics.md's softer framing (consistent with how this story has been drafted throughout), but the two source documents disagree and that disagreement has not been reconciled — confirm the intended policy with product before/during 6.10, since 6.10 is where the discretion is actually exercised.

**AC5 — Both-not-either signal is recorded + readable (verifier console consumes; Decision D4).**
**Given** the architectural commitment that peer-mesh + ground-inspection are **both, not either** (PRD §4.6, epics.md:2429)
**When** the verifier console (Story 6.10) evaluates the case
**Then** 6.7 provides a **read accessor** (`getClaimGroundInspection(db, pariwarId, claimCaseId)` — ciphertext AS STORED, the caller decrypts + mints signed URLs) that surfaces the assignments + notes + photo keys + dispositions (including any `photo_refused`/`evidence_unavailable`); **absence of a completed inspection is itself a first-class signal** the verifier must explicitly acknowledge — a null/incomplete read is not neutral. "Both, not either" (PRD §4.6) means **both signals are always pursued and presented**: 6.7 does not relax that — it makes the ground-inspection signal (present, refused, unavailable, or absent) legible. Whether the verifier may proceed on a single positive signal is a **documented verifier-discretion exception** owned by 6.10/6.11 (epics.md:2431), exercised case-by-case with the absence recorded — NOT a standing rule that "one is enough", and NOT something 6.7 grants. Ground inspection **NEVER** auto-advances state and **NEVER** adjudicates. The console mount + the discretion policy are 6.10's job (Decision D4); 6.7 ships the accessor + records the signal.

**AC6 — Tenant isolation + permission gating enforced (chains DIFFER per endpoint).**
**Given** multi-tenant substrate
**When** any read/write runs
**Then** both new tables are RLS-isolated (`app.pariwar_id`, the `claims-rls.ts` construct) with an explicit `pariwar_id` predicate for defense-in-depth; a cross-tenant `claimCaseId`/`ground_inspection_id` guess resolves to empty/`404`, never another Pariwar's data.
**And** the permission chains are **not uniform** (#14): all write endpoints share `[requireAdminSession, scopeResolutionHook, requirePermissionHook('claim.conduct_ground_inspection', { dimension: 'district', resolveValue })]`, but the **district resolver source differs** (`schedule` = request body; all other verbs = the assignment row), and `complete`/`refusal`/`findings`/`photos` **add the inspector-identity guard** (`acting_actor === inspector_actor_id`, or a checked `claim.override_ground_inspection` at that district). `schedule`/`reschedule`/`read` are **district-scoped only** — no inspector guard (scheduling/rescheduling are district-AUTHORITY operations, D6; the replacement may reassign the inspector). There is no single copy-paste chain — each route composes the pieces its verb requires.

### State posture — inspection gathers during `verification_in_progress`, never advances

| From | Event | To | Note |
|---|---|---|---|
| `verification_in_progress` | `claim.ground_inspection_scheduled` | `verification_in_progress` | 6.7 — annotation (both, not either) |
| `verification_in_progress` | `claim.ground_inspection_completed` | `verification_in_progress` | 6.7 — **NEW annotation, identity (22nd event)** |

The claim reaches `verification_in_progress` when Story 6.6's `claim.peer_mesh_pinged` fires (`documents_pending → verification_in_progress`). Ground inspection + peer mesh **gather in parallel** during that state (PRD §4.6 "both, not either"); neither advances the claim — the verifier (6.10/6.11) opens `verifier_reviewing` when ready. For Task 5's D3 guard, `verification_in_progress` is the canonical inspectable state; if the product wants inspections to remain addable during `verifier_review` too, widen the guard set (confirm — but the epic frames inspection as pre-verifier). **Never** let an inspection event advance state.

**Reducer identity ≠ unconditional append (the 6.6 lesson).** `ground_inspection_completed` is a **material evidentiary fact**, not just a no-op. The reducer must stay **total** (return identity from any state, never throw — a historical annotation event must replay cleanly; the AC3 replay-robustness contract). But that total-reducer property is exactly why an **unguarded write is unsafe**: identity-from-any-state means the reducer will happily append a `completed` event onto a `settled` or `denied` claim and re-write the same terminal state, minting a false "inspection completed" audit fact on a resolved claim. Story 6.6 hit this and added `PeerMeshClaimNotInVerificationError` at the writer. 6.7 mirrors it: the reducer is identity, the **writer guards** (`GroundInspectionClaimNotInVerificationError`) — reject the emission unless the claim is `verification_in_progress`, re-read inside the tx. Identity is correct **only from `verification_in_progress`**; the guard is what enforces that at write time.

### Assignment state-transition matrix (a SEPARATE machine from the claim reducer)

Each assignment carries its own lifecycle on the `claim_ground_inspections.status` column — **distinct** from the claim state machine (`claims.current_state`). This matrix is enforced by the **writers under the assignment row lock** (Task 4), NOT by `claim.projectClaimState`/the claim reducer (the claim stream only ever sees the two identity annotation events). `scheduled` is the sole non-terminal state; all others are terminal.

| From | Action (verb) | To | Guard |
|---|---|---|---|
| — | `schedule` | `scheduled` | claim === `verification_in_progress`; district-scoped permission |
| `scheduled` | `recordFindings` | `scheduled` | row-lock; assigned inspector or override |
| `scheduled` | `addPhoto` | `scheduled` | row-lock; assigned inspector or override; under max-count |
| `scheduled` | `complete` | `completed` | row-lock; ≥1 photo; assigned inspector or override |
| `scheduled` | `reschedule` | `superseded` (+ new `scheduled` row) | row-lock; district-scoped permission |
| `scheduled` | `refusal` (family refused) | `photo_refused` | row-lock; bounded reason + mandatory note; inspector or override |
| `scheduled` | `refusal` (unobtainable) | `evidence_unavailable` | row-lock; bounded reason + mandatory note; inspector or override |
| terminal (`completed`/`superseded`/`photo_refused`/`evidence_unavailable`) | any mutating verb | — (reject) | `GroundInspectionNotActiveError` |

A terminal assignment is immutable. Because `scheduled` is the only mutable state and the row lock is taken first, complete-vs-refuse-vs-reschedule on one assignment can never both win.

### Schedule + reschedule idempotency (#3/#4 — the D5 substitute for a uniqueness constraint)

With no DB uniqueness on `(claim_case_id, …)`, a retried `POST …/ground-inspection` or `…/reschedule` (client retry, double-submit, at-least-once proxy, post-commit timeout) must not mint a duplicate assignment or re-run a mutation. Contract: the client supplies an **`Idempotency-Key`**; the writer records it in the domain `idempotency` **KeyedStore** (`idempotency_keys` — the niyamavali/validity precedent). Scope the key per `(pariwar_id, claim_case_id)` to avoid cross-claim collision. Distinct from AR-58 event re-append (`projectClaimState.eventId`), which dedupes the *event*, not the *assignment row*.

**Claim-key-FIRST, not lookup-then-insert (the High-severity race).** A plain "look up key → insert assignment → persist key" lets two concurrent same-key requests BOTH miss the lookup and BOTH insert — and with no assignment-uniqueness the loser orphans a second row. Instead the key row's **unique index is the serialization point**: the writer generates the new `ground_inspection_id` app-side, then **INSERTs the `(scoped_key → id)` row as its FIRST write**. Under READ COMMITTED the second tx blocks on the first's uncommitted key row, then on the first's commit gets `23505` → **raw `SAVEPOINT`-rollback that statement** (`[[project_domain_limit_clamp_and_savepoint_retry]]` — `db.transaction()` would commit the caller's tx early), **re-read the bound id, return it, and persist NOTHING** (no assignment, no event). The winner's key-claim + assignment insert + event all share the tx, so any later failure rolls the key back too (no orphan key). The loser leaving zero rows behind is the whole point — it is why there is no duplicate despite the absent uniqueness constraint.

**Reschedule** uses the identical mechanism, keyed to `{ old_ground_inspection_id → replacement_ground_inspection_id }`: a same-key replay returns the bound **replacement** assignment with no second supersede and no second event (so a post-commit-timeout retry doesn't hit `GroundInspectionNotActiveError` on the now-`superseded` old row, and a manual operator retry can't mint an unintended extra assignment). Both contracts need **concurrent same-key** coverage, not just sequential replay.

This is also operator-visible (the UI lists existing assignments) — idempotency guards the machine retry, operator visibility guards the human duplicate.

### Audit boundary (#10 — sink, not a tx participant)

`emitAuthAudit` is an **injectable SINK** (`apps/api/src/audit/audit-sink.ts` — "THE SEAM, NOT THE SINK"; default = a structured log line; the FR-47 hash-chain + `events_log` sink is Story 1.10, swapped via DI). It is therefore **NOT** a participant in the writer's DB transaction. The **durable, replayable evidentiary record** of a scheduled/completed inspection is the `events_log` event appended by `claim.projectClaimState` *inside* the writer tx; the audit-sink line is the route's **post-commit** emission. "Completion atomicity" (AC4) is over `{ ≥1-photo check + row update + events_log append }` in one DB tx — the audit line is emitted after commit and is explicitly out of that atom. Do not write "the audit is in the same tx" anywhere — it contradicts the sink model. (Refusal/reschedule/findings/photo have no `events_log` event; their durable record is the assignment row state + the post-commit audit line.)

### Correctness invariants (the four scrutiny areas — read before Task 4/5)

1. **Assignment lifecycle + concurrency (D5) — the assignment is the unit; no claim-wide uniqueness.** A claim may hold **multiple** active assignments (parallel/sequential, different districts — corroboration/additional evidence, D6), so there is **no** "one active per claim" invariant and **no** `UNIQUE (claim_case_id) WHERE status='scheduled'`. Each row is one assignment, addressed by `ground_inspection_id`. Concurrency discipline is **per assignment**: a reschedule locks a **specific** row (`SELECT … FOR UPDATE` by `ground_inspection_id`) → `superseded` → insert replacement, one scope-tx. **Never** `ORDER BY created_at DESC LIMIT 1` to guess "the current" assignment — address it by id. Historical `completed`/`superseded`/`photo_refused` rows are unbounded.

2. **Completion atomicity (AC4) — one DB tx; storage AND the audit sink are out of it.** Object storage cannot join a DB transaction, so the design keeps it out of the completion path entirely: photos are uploaded in **prior** AC3 calls (their rows already durable), so `completeGroundInspection` is a pure DB scope-tx — the atom is exactly `{ row-lock + verify ≥1 photo (count) + update row + projectClaimState(completed) }`. The `emitAuthAudit` line is **NOT** in this atom — it is a post-commit **sink** call and is excluded on purpose (#10; see Dev Notes "Audit boundary"). Do NOT list "+ audit" inside the completion tx anywhere — it reintroduces a false all-or-nothing guarantee (the durable record is the `events_log` event, not the audit line). There is no "storage succeeds, DB fails" window at completion because completion writes no bytes (it only COUNTS existing rows). The only put-then-persist boundary is the **photo upload** (invariant 3), isolated to that one call.

3. **Photo lifecycle — bounded, orphan-safe, MANDATORY for completion.** MIME allowlist + per-file byte cap enforced **before** `put`; max-count-per-inspection enforced in the writer **under the parent-assignment row lock** (count-then-insert while `SELECT … FOR UPDATE` holds — a route/bare-count pre-check races, so the lock is what makes the cap real, #7). Orphan cleanup: `put`→insert; on insert failure after a successful `put`, best-effort `storage.delete?.(key)` before rethrow (the 6.5 compensation patch) — never a dangling object. **≥ 1 photo is MANDATORY completion evidence (D6):** `completeGroundInspection` verifies the count under the same row lock and rejects zero (`GroundInspectionPhotoRequiredError`). The no-photo case is NOT "complete anyway" — it is the **refusal disposition** (invariant 5).

4. **Assignment-specific jurisdiction + inspector identity (D6) — authz against the ASSIGNMENT's district.** The gate runs at `dimension: 'district'` against the **assignment's own `district`** (a stored non-null column; from the request body at schedule, from the row thereafter) — NOT the deceased's posting district and NOT a claim-wide district; the default pariwar-wide check is insufficient (any district admin would act on any claim). District is an **authz boundary**, not an inspection identity — the assignment's *what/where* is the separate `inspection_site_type` + encrypted `location_ciphertext`. Persist `inspector_actor_id`; thread it into events + audit; `complete`/`refusal`/`findings`/`photos` reject an acting actor ≠ the assigned inspector unless the actor holds the **defined `claim.override_ground_inspection` key** at that district (Task 1 — an explicit, checked, recorded capability, never "any district admin"). Parallel assignments (even same-district) are each gated to their own district-scoped admin.

5. **Photo-refusal / evidence-unavailable (D6/AC4a) — a distinct non-successful disposition.** Family refuses all permitted photography → the assignment is `photo_refused`/`evidence_unavailable` with a **mandatory non-null encrypted reason note** + an audit line. It is **NOT** a successful completion: **no `claim.ground_inspection_completed` event**, no state advance, no auto-deny. It **escalates to the verifier** (a readable disposition signal, the 6.6 AR-61-fallback pattern); the verifier may deny under the applicable Niyamavali rule (adjudication is 6.10/6.11 + niyamavali — the D4 boundary). This is the sanctioned path around the mandatory-photo completion guard.

### PII posture (AR-12 / Story 1.5 / 1.16b gate)

- **PII (Tier-1 ciphertext):** family contact (phone), free-text inspection notes, the mandatory refusal reason note, the photo **`caption_ciphertext`** (free-text — can name a person/place, #11), and the **exact address / landmark / contact instructions / free-text site description** (`location_ciphertext` — always encrypted, not "only if precise"; the ambiguous plain `location`/`caption` were renamed for exactly this reason).
