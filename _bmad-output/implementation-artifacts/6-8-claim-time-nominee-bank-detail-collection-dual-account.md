# Story 6.8: Claim-Time Nominee Bank Detail Collection (Dual Account)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a **claim filer** (Ravi-mode member-app proxy, or a helpline operator during intake),
I want to provide **both nominee bank accounts** upfront at claim-time — a **primary (#1)** and a **secondary (#2)**, each with account-holder name + account number + IFSC — with IFSC pre-validated before submission,
so that when the pool settles (Epic 7/9) **disbursement is never blocked** by a single account hitting the RBI UPI per-payee-per-day limit or failing, because the second pre-validated account is already on file.

## Story Classification

`[SURFACE]` — this story adds a first-class claim-filing surface (`<NomineeDetailEditor>` dual-bank collection) on top of the Story 6.1 claim state machine and the Story 1.5 PII-encryption substrate. It **owns + first-emits** a NEW annotation claim event `claim.nominee_bank_recorded`, lands a NEW tenant-isolated child table `claim_nominee_bank_accounts` (one row per account, ranked #1/#2), and ships a NEW **abstraction-first `BankIfscLookup` port** (cached) for IFSC pre-validation — the 6.5 `OcrProvider` "no boundary gate until a real vendor exists" precedent. It **consumes** the Story 6.1 `projectClaimState` single-writer for the annotation event and the Story 1.5 `encryptTier1`/`decryptTier1` helpers for the bank PII. It ships the **read accessor** (`getClaimNomineeBankAccounts`) that the Epic 7 pool spawn (Story 7.4 `nominee_bank_accounts` refs, epics.md:2627) and the Epic 9 dual-account disbursement (Story 9.5, epics.md:3254-3258) consume; it does **NOT** build the disbursement split logic, the RBI-limit arithmetic, penny-drop verification, or any payment rail (all downstream). Bank collection is an **annotation** — it does **NOT** advance the claim lifecycle state (Decision D2), exactly as ground-inspection scheduling and peer-mesh pinging gather signals without advancing state.

## Seam decisions — surfaced for confirmation

Like Story 6.7's D1–D6, these touch frozen contracts / cross-story data boundaries / business invariants. Recommendations are given; **confirm or override before/at dev-time.** D1 (the account model) and D6 (PII tiers) are correctness-and-schema-shaping — get D1 wrong and Epic 9's disbursement reads the wrong beneficiary structure.

- **Decision D1 (account model) — ✅ APPROVED (BigDev, 2026-07-10): two claim-scoped disbursement accounts; NO mapping to nominee rank or 75/25 entitlement.** `claim_nominee_bank_accounts` is **claim-scoped**, keyed `(claim_case_id, account_rank)` with `account_rank ∈ {1,2}` (#1 primary / #2 secondary), each row carrying its OWN encrypted `account_holder_name`. The two accounts are a **dual-account disbursement channel for the claim** — a **RBI-UPI-per-payee-per-day-limit workaround + failover** (story goal + FR-37 + Epic 9.5, epics.md:3254-3258) — **NOT** one-account-per-declared-nominee and **NOT** a beneficiary-share split. The 75/25 nominee split lives on `member_nominees.split_pct` (Story 3.4) and is an entirely **separate concept** this story does not touch or reference. **DO NOT add a `nominee_rank` column, an FK to `member_nominees`, or any holder-name-must-match-nominee validation** — the filer types a holder name per account, full stop; there is no nominee linkage on the schema, the writer, or the contract.

- **Decision D2 (state posture) — ✅ APPROVED (BigDev, 2026-07-10): bank recording is annotation-only and causes NO claim-state transition (the 6.7 ground-inspection posture).** FR-37's line "Claim enters `under_verification`" describes the **overall** claim-filing progression (intake → documents → verification), **not** a transition this collection triggers. (Note: the literal string `under_verification` does not exist in the state enum — the actual state is `verification_in_progress`, `schema/claims.ts`; FR-37 is using loose prose, not the enum name — don't grep for `under_verification` expecting a hit.) Bank collection is claim-time data capture that can happen (and be re-edited via `<NomineeDetailEditor>`) across the pre-adjudication window; it must **never** auto-advance or adjudicate. So emit `claim.nominee_bank_recorded` as an **identity transition** (`from_state === to_state`) via `projectClaimState` (the ONLY legal `claims.current_state` writer), and the **write path GUARDS the claim state** (Decision D3) — collection is accepted only in the pre-decision window and rejected on a terminal/post-approval claim, so an account is never recorded onto a settled/denied claim. The reducer STAYS total (identity from any state — replay-robustness), exactly the 6.6/6.7 lesson: correctness lives in the write-path guard, not the reducer.

- **Decision D3 (allowed collection window) — ✅ RESOLVED (BigDev, 2026-07-11): THREE-TIER edit governance.**
  1. **Nominee** (member-app Ravi-mode + helpline-as-proxy): editable only **before `verifier_approved`** — the tier-1 window `{intake_converged, documents_pending, verification_in_progress, verifier_review}`; **permanently read-only for the nominee once the claim reaches `verifier_approved`.**
  2. **Authorized admin correction**: after `verifier_approved` but **before the claim/cycle freeze (`state_trustee_freeze`)** — the tier-2 window `{verifier_approved}` — an admin (helpline) may make an **audited, reason-required, step-up-protected** correction (a mandatory `correctionReason`, `NomineeBankCorrectionReasonRequiredError` if absent; the event carries a non-PII `corrected: true` flag, the reason rides the AUDIT sink only — the convergence-override "audited reason" precedent — NEVER `events_log`). NOT open to the nominee.
  3. **After the claim/cycle freeze or publication — AND the `reversed` / `appeal_stage_*` states**: no ordinary edit and no routine admin correction. Any bank-detail change there requires the **separately governed emergency or appeal-remediation workflow** (OUT OF SCOPE here; the writer rejects with `NomineeBankClaimNotCollectableError`). **✅ SETTLED (BigDev, 2026-07-11):** `reversed`/appeal are v1-closed, NOT correction windows. A future story may reopen correction on those states ONLY after defining re-verification, approval-invalidation, downstream-readiness-invalidation, audit, and notification semantics — so `NOMINEE_BANK_ADMIN_CORRECTION_STATES` must NOT be widened without them (pinned by a lock-in test for `appeal_stage_1` + `reversed`).
  Implemented as two constant windows (`NOMINEE_BANK_COLLECTABLE_STATES` + `NOMINEE_BANK_ADMIN_CORRECTION_STATES`) + an `allowCorrection` authority flag on the writer (member route passes `false`, helpline `true`).

- **Decision D4 (IFSC lookup) — RECOMMENDED: an abstraction-first `BankIfscLookup` PORT + a cached adapter, format-validation always-on, NO vendor boundary gate yet (the 6.5 `OcrProvider` precedent).** AC "pre-validation hits a bank-IFSC lookup (cached) before submission" needs (a) **format validation** — the RBI IFSC shape `^[A-Z]{4}0[A-Z0-9]{6}$` (4-letter bank code, a literal `0`, 6-char branch code), enforced in the contract + re-asserted server-side; and (b) an **existence/branch lookup** returning `{ bankName, branch }` for a valid IFSC, cache-first. Define `BankIfscLookup` as a domain port (like `ClaimDocumentStorage`/`OcrProvider`) with an **in-memory/stub adapter** for v1 + tests, and leave the real-vendor adapter (e.g. a bundled IFSC dataset or a public IFSC API) as a seam — **no CI boundary gate until a real vendor lands** (6.5 discipline). **Penny-drop / account-holder-name verification is DEFERRED `[v1-S]`** (FR-37 explicit) — do **NOT** build name-match; "account-holder validated against bank IFSC lookup" in v1 means the IFSC resolves to a real bank/branch, and the holder name is captured verbatim, not verified against the bank. `bank_name`/`branch` are **public, non-PII, IFSC-derived** → Tier-3 plaintext (D6).

- **Decision D5 (dual surface / dual route) — RECOMMENDED: two thin routes over one shared domain writer — a member-app (Ravi-mode) route + a helpline/operator (admin) route (the 6.2/6.3 split precedent).** `<NomineeDetailEditor>` is consumed by BOTH the member-app claim flow (Story 6.2 `nominee-review.tsx` — which today is read-only and **explicitly defers dual-bank collection to "Story 6.8"**, see `apps/mobile/app/(claim)/nominee-review.tsx:1-7`) and the helpline console (Story 6.3, Priya-path). Mirror the intake split: a member-session-gated `POST /api/v1/member/claims/:claimCaseId/nominee-bank` (Ravi-mode, deceased derived from session, claim ownership asserted) **AND** an admin/scope-gated helpline route, both calling the SAME `recordClaimNomineeBankAccounts` domain writer. The IFSC-lookup read endpoint is shared/public-ish (returns only public bank/branch data). **Bank-account entry is a member-side FINANCIAL action** (architecture §1.14:1352 lists "bank-account / IFSC change" as member-side financial) → the member route runs behind **step-up** (`requireMemberStepUp` — the claim-filing handover-trust elevation is already present in the 6.2 flow; confirm it covers this write or add a `nominee_bank` step-up context). The helpline route runs behind the operator's existing admin step-up + the claim-filing permission (Decision D5a).

- **Decision D5a (permission key) — RECOMMENDED: reuse the existing claim-filing permission the helpline uses; do NOT mint a new key.** The operator recording nominee bank during intake is part of filing a claim — reuse whatever `claims.helpline.routes.ts` gates intake with (verify the exact key in that file; the 6.3 intake route). If it is cleaner to scope separately, a single-dot `claim.record_nominee_bank` is the fallback — but prefer reuse (no catalog bump) unless the reviewer disagrees. **Verify the actual key before Task 5.**

- **Decision D6 (PII tiers) — CONFIRMED by architecture §2.7:1504-1505 (nominee bank account + nominee IFSC are explicitly Tier-1).** `account_holder_name` (a person's name), `account_number`, and `ifsc` → **Tier-1 envelope ciphertext** (`piiColumn(1, 'claim_nominee_bank')`), encrypted app-layer BEFORE insert / decrypted on the read path (the 3.4 nominee-crypto + 6.7 ground-inspection-crypto precedent). `bank_name` + `branch` (public, IFSC-derived, non-identifying) → **Tier-3 plaintext text**. `account_rank` (1/2) + `ifsc_validated` (bool) → non-PII plain columns (**no `nominee_rank` — D1 APPROVED**). NEVER log a decrypted bank field; NEVER put account number / holder name / IFSC in an event payload or an audit line (the payload carries `account_rank` presence + `ifsc_validated` only — the peer-mesh/ground-inspection NO-PII-in-payload discipline).

**AC1 — Dual-account collection with per-account fields, ranked #1/#2, PII-encrypted (D1, D2, D6).**
**Given** FR-37 (dual-account claim-time nominee bank collection) + UX-DR34 `<NomineeDetailEditor>` and a claim in a collectable state (D3: `intake_converged | documents_pending | verification_in_progress`)
**When** a claim filer submits nominee bank details
**Then** **two** accounts are collected — `account_rank = 1` (primary) and `account_rank = 2` (secondary) — each with `account_holder_name`, `account_number`, `ifsc`, and the IFSC-derived `bank_name` (+ `branch`); the three sensitive fields (`account_holder_name`, `account_number`, `ifsc`) persist as **Tier-1 envelope ciphertext** (`piiColumn(1, 'claim_nominee_bank')`, encrypted app-layer BEFORE insert — Story 1.5 / AR-12), while `bank_name`/`branch`/`account_rank` are non-PII plain columns
**And** the request carries **exactly two complete accounts** (Task 5 RESOLVED — no single-account partial, no "add #2 later"), and the collection is **latest-wins replace** on the account set for the claim (the `member_nominees` re-declaration precedent — delete-then-insert **both rows** under a per-claim lock in ONE scope-tx), so an edit via `<NomineeDetailEditor>` cleanly replaces the prior two accounts, never appends orphan rows
**And** a single `claim.nominee_bank_recorded` annotation event is emitted via `projectClaimState` as an **identity transition** (`from_state === to_state`; D2 — it does NOT advance state); its payload carries `account_ranks_present` + `ifsc_validated` flags only, **NO PII** (no account number, no holder name, no IFSC)

**AC2 — IFSC format validation + cached bank lookup pre-validation; penny-drop deferred (D4).**
**Given** the `<NomineeDetailEditor>` pre-validation requirement
**When** an IFSC is entered / a submission is validated
**Then** IFSC **format** is validated against the RBI shape `^[A-Z]{4}0[A-Z0-9]{6}$` (contract-level in the request DTO **and** re-asserted server-side — never trust the client)
**And** a **cached** `BankIfscLookup` port resolves a valid IFSC to `{ bankName, branch }` (cache-first; the adapter is abstraction-first with an in-memory/stub v1 implementation — no real-vendor CI boundary gate yet, the 6.5 `OcrProvider` precedent); an IFSC that fails format or lookup is rejected with **Pattern-4 dignified copy** (UX-DR55 — "we couldn't recognize that IFSC, please check it," never a raw validation error), and the account is not persisted
**And** **penny-drop / account-holder-name verification is NOT built** (FR-37 `[v1-S]` deferred) — the holder name is captured verbatim; `ifsc_validated = true` records only that the IFSC format + branch lookup passed at claim time

**AC3 — Read accessor for the Epic 7/9 consumers (ciphertext AS STORED).**
**Given** the Epic 7 pool spawn (Story 7.4 `nominee_bank_accounts` refs, epics.md:2627) and the Epic 9 dual-account disbursement (Story 9.5, epics.md:3254-3258 — both accounts "pre-validated at claim time per Story 6.8")
**When** a downstream consumer needs the claim's nominee bank accounts
**Then** 6.8 provides `getClaimNomineeBankAccounts(db, pariwarId, claimCaseId)` returning the account rows (empty when not yet collected, **both rows** when collected — never a single-account partial, per Task 5) **ciphertext AS STORED** (the ROUTE/consumer decrypts under its own encryption context — the `getClaimGroundInspection`/`getClaimDocuments` precedent), tenant-scoped (RLS + explicit `pariwar_id` predicate); a claim with no accounts returns `[]` (a first-class "not yet collected" signal a consumer must handle, never a throw)

**AC4 — Dual surface: member-app (Ravi-mode) + helpline (operator) (D5).**
**Given** UX-DR34 `<NomineeDetailEditor>` is consumed by both the Story 6.2 member-app claim flow and the Story 6.3 helpline console
**When** the collection endpoints are implemented
**Then** a **member-session-gated** route (`POST /api/v1/member/claims/:claimCaseId/nominee-bank`, deceased derived from the session, claim ownership asserted, behind member **step-up** — bank entry is a member-side financial action, architecture §1.14:1352) **and** a **helpline/admin scope-gated** route both call the SAME `recordClaimNomineeBankAccounts` domain writer (the 6.2/6.3 intake split precedent — two thin routes, one core); the mobile `nominee-review.tsx` read-only screen is extended (or a new step added) to render the `<NomineeDetailEditor>` dual-bank form with Pattern-4 copy

**AC5 — Tenant isolation + claim-ownership/permission gating.**
**Given** the multi-tenant substrate
**When** any nominee-bank read/write runs
**Then** `claim_nominee_bank_accounts` is RLS-isolated (`app.pariwar_id`, the `claims-rls.ts` construct) with an explicit `pariwar_id` predicate for defense-in-depth; a cross-tenant `claimCaseId` guess resolves to empty/`404`, never another Pariwar's data
**And** the member route asserts the claim's `deceased_member_id` matches the session member (a member cannot write bank details onto another member's claim); the helpline route runs the operator's admin scope + the claim-filing permission (D5a — reuse the existing key) + admin step-up; the write-path re-guards the claim state (D3) inside the scope-tx so a terminal/post-approval claim is rejected (`NomineeBankClaimNotCollectableError`), independent of the route's pre-check

### State posture & the guard (D2/D3)
`projectClaimState` is the ONLY legal `claims.current_state` writer (DB trigger + CI gate enforce it — `schema/claims.ts:11-24`). The annotation event is `from_state === to_state`. ### Audit boundary (the 6.7 discipline)
Audit is a **post-commit sink emission, NOT a same-tx DB write**. Emit `emitAuthAudit(deps, request, 'claim.nominee_bank_recorded', {...})` AFTER the writer's tx commits (call it from the route after the scope-tx closes — not inside the handler before the tx resolves). Carry NON-PII only: `claim_case_id`, `account_ranks_present`, `ifsc_validated`, acting actor. The durable evidentiary record is the `events_log` event.

### Idempotency / concurrency
Latest-wins delete-then-insert under the `claims` row lock makes concurrent edits serialize cleanly (no orphan rows — the composite PK `(claim_case_id, account_rank)` also structurally forbids a duplicate rank). A double-submit re-records the same 2 rows (idempotent-in-effect). An explicit `Idempotency-Key` is optional here (unlike 6.7's schedule/reschedule which MINT new addressable assignments) — the replace-semantics + composite PK give convergence for free. If the reviewer wants strict once-only event emission, thread an idempotency key the 6.7 claim-key-first way ([[project_domain_limit_clamp_and_savepoint_retry]]) — but latest-wins is the simpler correct default for editable data.
