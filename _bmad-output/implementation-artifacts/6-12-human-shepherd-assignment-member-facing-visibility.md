# Story 6.12: Human Shepherd Assignment + Member-Facing Visibility

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story Classification

**`[SURFACE]`** — the story that gives a grieving family a **named human** instead of an opaque state machine. When a claim starts gathering verification signals (`verification_in_progress`), a District Admin is **assigned as the claim's shepherd** and their **name + role + contact** surface to the claimant, plus a push. This is a **routing/attribution** feature — *not* a new lifecycle state and *not* an adjudication power. It sits beside the verifier: the shepherd is the family's contact; the verifier (Story 6.11) makes the ₹50L decision. They may be different people; being the shepherd grants **no** `claim.approve`.

**6.12 reuses four Epic-6 patterns almost verbatim** — do not reinvent them:
1. **The annotation-event discipline** (`claim.verifier_escalated` / `claim.ground_inspection_scheduled`): shepherd assignment is a NEW **identity-transition annotation event** `claim.shepherd_assigned` (28th claim event; `from_state === to_state`; reducer identity). Escalation's own comment already names 6.12 as the owner of "the actionable State-level queue" — this is that queue's assignment half.
2. **The decision-metadata read-model + snapshot table** (`claim_verifier_decisions`, Story 6.11): a new `claim_shepherd_assignments` table with the SAME shape (live-vs-superseded, partial-unique one-live-per-claim, atomic supersession on reassignment, actor-display snapshot).
3. **The R5 actor-display posture** ([[project_admin_display_name_attribution]] — "Binds all future admin-attribution surfaces (6.12/6.13+)"): the shepherd's name is a decision-time **snapshot of `users.display_name`**, never email-derived, never a fallback.
4. **The reschedule-as-re-emit pattern** (`claim.ground_inspection_scheduled` with `supersedes_ground_inspection_id`): **reassignment re-emits the SAME `claim.shepherd_assigned` event** with `previous_shepherd_actor_id` + `assignment_reason` + a `supersedes_assignment_id` back-reference — there is NO separate `shepherd_reassigned` event.

**The v1 scope boundary (FR-41):** "Human shepherd assigned per claim (WI-26) `[v1-M]`" is THIS story. **"Shepherd inbox/dashboard/load-balancing/handoff UI is `[v1-S]`"** — the shepherd's own work-queue surface is OUT of scope. 6.12 ships **automatic assignment + member-facing visibility + audit-logged reassignment/fallback**; workload-balancing is a *routing input* (a live-assignment count), NOT an admin dashboard.

**All six residual design forks (R1…R6) are RATIFIED by BigDev (2026-07-12) — see "Residual questions for BigDev (RATIFIED)" for the exact calls + four story corrections + one wording fix, all baked into the ACs/tasks below.** The load-bearing one, R1 (shepherd contact source), resolved to **option (a): add `users.contact_phone` + `users.contact_whatsapp` (nullable E.164) and snapshot them into the assignment row** — `users` today has **only `display_name`**, and FR-41 requires "name + phone + WhatsApp." **Eligibility is now stricter than 6.11's R5:** a shepherd is only auto-assignable if they have a `display_name` **AND at least one usable contact channel** (phone or WhatsApp) — otherwise the family gets "your point of contact" with no way to reach them.

## Story

As **a bereaved family** (Ravi filing for his father, or a helpline-mediated claimant),
I want **a named human shepherd (a District Admin) assigned to my claim, with their name + role + contact visible on my claim status surface and delivered by a push**,
so that **I have a real person to reach through the verification process — not just an opaque system deciding a ₹50L claim in the background.**

## Acceptance Criteria

**AC0 — Assignment is a routing ANNOTATION, never a lifecycle change; two authorities, one transaction (the 6.11 AC0 framing, applied to shepherding).**
Every assignment writes to **two stores with two distinct authorities, in one transaction, neither a projection of the other**:
- **The `claim.shepherd_assigned` event in `events_log` is the LIFECYCLE-TIMELINE authority** — a NEW **identity-transition annotation** (`from_state === to_state`; the reducer has **no** shepherd state and gains none, exactly like `claim.verifier_escalated`). It carries `auditShape` + **non-PII routing coordinates only** (`shepherd_actor_id`, `previous_shepherd_actor_id: uuid | null`, `assignment_reason`, `supersedes_assignment_id: uuid | null` — **the AC5 back-reference; it MUST be in the event schema or the reassignment link the event promises cannot ride the timeline**, `district`) — **never** the shepherd's name/phone/WhatsApp (AC8).
- **The `claim_shepherd_assignments` table is the ASSIGNMENT-METADATA authority** — who the live shepherd is, the display-name + contact snapshot, the reason, and the live-vs-superseded history.
Claim STATE is **always** derived from event replay, **never** from the assignment table. Any code that reads a shepherd's name from `events_log`, or a claim's state from the assignment table, is wrong.

**AC1 — Automatic assignment when a claim enters `verification_in_progress` (FR-41 core).**
A claim enters `verification_in_progress` by exactly ONE transition: `documents_pending → verification_in_progress` via `claim.peer_mesh_pinged`, emitted by the `CLAIM_PEER_MESH_SELECT` pg-boss worker (`apps/jobs/src/claim-peer-mesh.ts`). When (and only when) that transition commits, the assignment service:
- resolves the district via **`member.getMemberPostingLatest(db, pariwarId, deceasedMemberId)`** (`packages/domain/src/member/posting.ts`, exported from the domain barrel) — the SAME primitive `resolveVerifierConsoleDistrict`/`resolveDecisionDistrict` wrap for their HTTP preHandlers; those two are unexported, request-scoped preHandlers and **cannot** be called from a worker, so the worker calls the domain read directly;
- resolves the candidate pool: users holding a **`district_admin`** `role_grant` at **`scope_dimension = 'district'`, `scope_value = <that resolved district>`** within the claim's tenant (server-derived, never client-supplied), **filtered to the CONTACTABLE — active users with a non-null `display_name` AND at least one usable contact channel (`contact_phone` or `contact_whatsapp`, R1). A candidate missing the name OR both channels is INELIGIBLE (skipped) exactly like a nameless one (AC2)** — FR-41 promises a reachable human, so an un-contactable shepherd is not a valid assignment;
- applies **workload balancing**: pick the candidate with the FEWEST live (`superseded_at IS NULL`) shepherd assignments, deterministic tiebreak by `shepherd_actor_id` (the peer-mesh determinism discipline — no `Math.random()`);
- **claim category** is a routing input that in v1 collapses to the single death-support category (note it in code; no branch to build);
- emits `claim.shepherd_assigned` (identity annotation, `actor: 'system'`, `assignment_reason: 'initial'`, `previous_shepherd_actor_id: null`) AND inserts the LIVE assignment row (shepherd_actor_id + **shepherd_display snapshot** + contact snapshot per R1 + `assignment_reason`) in ONE scope-tx (AC0).
- If **no** eligible in-scope District Admin exists (empty pool, or all ineligible per AC2) → the **AR-61 fallback path** (AC4), never a silent no-shepherd.

**AC2 — Assignment read model + shepherd-display + contact snapshot (R1/R5 posture, refined for the automatic path).**
- A new **`claim_shepherd_assignments`** table (migration `0060`, mirror `claim_verifier_decisions`): `assignment_id` (uuid pk, branded `ShepherdAssignmentId`), `claim_case_id` (FK → claims, `onDelete: cascade`, branded `ClaimId`), `pariwar_id` (RLS predicate col, branded), `shepherd_actor_id` (the assigned District Admin's `users.id`; non-PII query/join key), **`shepherd_display`** (`text` NOT NULL — assignment-time SNAPSHOT of `users.display_name`; controlled staff attribution, plaintext, never email-derived), **`shepherd_contact_phone`** + **`shepherd_contact_whatsapp`** (both nullable `text`, E.164 — the assignment-time SNAPSHOT of the two `users` contact columns; R1), `assignment_reason` (enum `initial | reassignment | fallback`), `supersedes_assignment_id` (self-FK, `onDelete: set null`, NULL on the first assignment), `superseded_at` (tz, NULL = the live assignment), `assigned_at`, `created_at`. **Partial-unique invariant `UNIQUE (claim_case_id) WHERE superseded_at IS NULL`** — at most ONE live shepherd per claim.
- **Contact source (R1, RATIFIED — option (a)):** two new **`users` columns** — `contact_phone` + `contact_whatsapp`, both **nullable `text` in canonical E.164** (`+<country><subscriber>`; validate the E.164 shape on write, the `display_name` provisioning path) — controlled staff-contact personal data, plaintext by deliberate decision (their whole purpose is to be shown to the family; document the posture in the column comment for the 1.16b gate, as `display_name` did; NEVER member PII). Both nullable at the column, but the WRITE model requires the two invariants below. Snapshot BOTH into the assignment row at assignment time.
- **Contactability invariant (RATIFIED correction):** an auto-assignable shepherd MUST have `display_name` **AND ≥1 usable contact channel** (`contact_phone` OR `contact_whatsapp` non-null). A candidate missing the name OR both channels is **INELIGIBLE for auto-assignment** — skipped, fall to the next candidate; if the whole eligible pool is un-contactable, fall to the AR-61 fallback (AC4). This closes the "named but unreachable point of contact" hole FR-41 must not create.
- **Display + contact snapshot (R5, [[project_admin_display_name_attribution]]):** `shepherd_display` + the two contact columns are captured at assignment time and never re-resolved live; a later rename / number change never rewrites a historical row.
- **Manual reassignment fail-closed:** a **manual** reassignment (AC5/R6) targeting an admin without a `display_name` **OR** without a usable contact channel **blocks** with a typed error (`AdminDisplayNameMissingError` for the name; a sibling `ShepherdNotContactableError` for the contact) — the 6.11 fail-closed rule, no fallback, no placeholder/email/UUID.

**AC3 — Member-facing visibility (FR-41: name + contact on the claim status page + confirmation).**
- A **scope-safe member READ** surfaces the LIVE shepherd for a claim the member filed/owns: `GET /api/v1/member/claims/:claimCaseId/shepherd` returning `{ display_name, role_label, contact }` (contact per R1) for the current (`superseded_at IS NULL`) assignment, or a well-typed "not yet assigned" state for a claim still pre-`verification_in_progress`. Authorization: the member-claim ownership check used by the existing `/api/v1/member/claims/:claimCaseId/*` routes (the claimant/filer bond) — never a cross-claimant read.
- A mobile **`<ShepherdContactCard>`** (`apps/mobile/components/claim/`) renders the shepherd's name + role + tappable contact (phone `tel:` / WhatsApp `wa.me` deep-links off the E.164 snapshot, R1). Grief-mode copy (no countdowns; "your point of contact"). Offline: read-only cached view (UX §Offline "claim status if Ravi-mode").
- **Concrete v1 mount (R3, PINNED — do not let the dev choose):** mount the card on **`apps/mobile/app/(claim)/acknowledgement.tsx`** AND ensure that surface is **reachable AFTER filing** — the acknowledgement screen today is a one-shot terminal of the filing wizard, so add a **persistent member entry point** to it (a "your claim / point of contact" link from the member's claim/home surface that re-opens the acknowledgement/shepherd view). A card that exists only on the un-re-reachable end-of-wizard screen is **not** acceptable ongoing visibility. This stays a **scoped shepherd card, NOT a full claim-status timeline** (that broader surface is a separate story).
- **Card behavior when contact is absent (defensive — should not occur given AC2 contactability):** if a live shepherd row ever surfaces with `display_name` but **no** contact channel, the card renders the name + role + a typed "contact being arranged" affordance (e.g. the helpline CTA), never a dead "your point of contact" with no action. A `not_assigned` claim (pre-`verification_in_progress`) renders the typed not-yet-assigned state.

**AC4 — AR-61 staff-fallback via an INJECTED port (cross-cutting AC per epics.md:2280 — referenced, not re-implemented).**
- **When no eligible/contactable in-scope District Admin exists**, OR **when the assigned shepherd is unavailable**, the **fallback shepherd** is paged. **Substrate reality (RATIFIED correction):** Story 0.7's fallback-handler ledger is **documentation-only** (`docs/fallback-handler-ledger/{ledger,rota,loop-nodes/…}.md` — prose Markdown, no machine-readable rota, no runtime resolver in code). So the dev **must NOT invent runtime resolution from a document.** Instead define an **injected `ShepherdFallbackResolver` port** — `resolveFallbackShepherd(pariwarId, district, claimCaseId) → { shepherdActorId, display, contact } | null` — with a **test stub / config-backed fake** as the v1 implementation (the `NiyamavaliAmendedHook` / injected-seam precedent). Real rota integration (a persisted registry the ops rota writes to) is an explicit **follow-up**, not 6.12 scope. Wire the port's default from config/env; page = call the port.
- A fallback assignment re-emits `claim.shepherd_assigned` with `assignment_reason: 'fallback'`, `previous_shepherd_actor_id` = the superseded shepherd (or `null` if there was none), and the `supersedes_assignment_id` back-reference; **atomic supersession** (AC5). The member `<ShepherdContactCard>` updates to the new shepherd; the push re-fires (AC7).
- If neither a primary nor a fallback (port returns `null`) can be resolved, the assignment attempt is **recorded as un-resolved** (a structured `alarm()` + the pg-boss retry/DLQ path — the peer-mesh missing-scope precedent), never a claim silently left shepherd-less with the family shown nothing.

**AC5 — Reassignment is audit-logged; self-assignment prohibited (FR-41).**
- **Reassignment (fallback OR admin-initiated per R6) re-emits the SAME `claim.shepherd_assigned` event** (there is NO `shepherd_reassigned` event — the ground-inspection-reschedule precedent) with `assignment_reason ∈ {reassignment, fallback}`, `previous_shepherd_actor_id`, and `supersedes_assignment_id`.
- **Atomic supersession** (the 6.11 revise precedent): conditional `UPDATE claim_shepherd_assignments SET superseded_at = now() WHERE assignment_id = $live AND superseded_at IS NULL RETURNING` (0 rows ⇒ a concurrent reassignment already won ⇒ typed conflict), THEN insert the new live row (`supersedes_assignment_id = $live`); the partial-unique index is the backstop. One live shepherd per claim, always.
- **Every reassignment writes a post-commit audit line** (FR-41 "reassignment audit-logged") via `emitAuthAudit` — NON-PII context: `claim_case_id` + `district` + `shepherd_actor_id` + `previous_shepherd_actor_id` + `assignment_reason`. **Never the name/phone/WhatsApp.**
- **Self-assignment prohibited (FR-41, RATIFIED as actor ≠ target):** any **actor-initiated** reassignment (R6) rejects `actor_id === target_shepherd_actor_id` with a typed error (`ShepherdSelfAssignmentError`) — a District Admin cannot route a claim to themselves. The automatic path (AC1) is `actor: 'system'` and has no "self," so it satisfies this by construction. **This is NOT a shepherd/verifier role-separation rule:** a District Admin MAY hold both the shepherd and the verifier responsibilities on the same claim when separately authorized — assignment itself grants no `claim.approve` (AC6), and being the verifier does not bar being the shepherd. The only constraint is that the actor performing a manual reassignment is not its target.

**AC6 — Admin-side visibility via the verifier console (Story 6.10); the shepherd does NOT replace the verifier.**
- The verifier-console bounded compound assembler (`apps/api/src/modules/claims/claims.verifier-console.handlers.ts`) gains ONE new **isolated, fail-soft section**: the live shepherd (`shepherd_display` + `role_label` + `shepherd_actor_id`) for the claim, or an `empty`/`unavailable` state (the 6.10 four-state section vocabulary — a transient throw ⇒ `unavailable`, request still 200; the section is never converted to `empty`). Read-only.
- **Being assigned as shepherd grants neither `claim.verify` nor `claim.approve`; console access and adjudication remain independently RBAC-gated** (RATIFIED wording). Assignment adds the shepherd's identity to a console that is *already* gated by `claim.verify` (Story 6.10) — it does NOT itself grant a shepherd access to that console, and it does NOT grant `claim.approve` (Story 6.11, D-B). A shepherd who lacks those grants simply is not shown the console / cannot adjudicate. Do NOT wire any write, nor any implicit grant, off the shepherd panel.

**AC7 — Member push via Story 5.1 (a seam — `dispatch()` has NO live caller yet).**
- At assignment AND reassignment, fire an **injectable `ShepherdAssignedNotificationHook`** (the `NiyamavaliAmendedHook` / `notification-hook.ts` seam precedent) carrying **non-PII coordinates only** (`pariwarId`, `claimCaseId`, `shepherd_actor_id`, `claimant_actor_id`, `assignment_reason`). Production wires a **console-placeholder** hook; tests inject a capturing fake. It **must never** resolve targets or send bytes — `packages/channels` `dispatch()` is a `[PRIMITIVE]` with **no live call site through Story 5.4** ([[project_channels_no_live_dispatch_yet]]); 6.12 must **not** become its first live caller (R4).
- **Hook ownership (RATIFIED correction):** assignment originates in the jobs worker, so the hook lives in the **`apps/jobs` dependency graph** and is fired post-commit by the assign/fallback worker. **If the R6 manual reassignment route ships, that `apps/api` path fires the SAME hook post-commit** — one hook definition, both call sites, so every shepherd change (auto, fallback, or manual) notifies identically.
- The **durable, correctness-mandatory** member-facing path is the **pull-based `<ShepherdContactCard>`** (AC3); the push is best-effort and never blocks or fails the assignment. This mirrors FR-71's `claim-status-change` push category as a future Epic-5 fan-out.

**AC8 — PII discipline (the ground-inspection `inspector_actor_id` precedent).**
- `events_log` payloads + the audit-sink context carry **actor ids + district + reason ONLY** — **never** the shepherd's name, phone, or WhatsApp. The shepherd's display + contact live **only** in `claim_shepherd_assignments` (+ the authorized member card read).
- The contact snapshot columns (R1) are **controlled staff-contact data** deliberately shared with the claimant (that IS the feature) — document the posture in the column comments for the 1.16b PII-shielding gate reviewer, exactly as `users.display_name` did. They are **not** member PII, **not** indexed as searchable filters, and **never** copied into `events_log`.

**AC9 — Idempotency + determinism (the ₹50L discipline).**
- A transaction-scoped **advisory lock on `(pariwarId, claimCaseId)`** (a distinct namespace prefix from the intake + verifier-decision locks) serializes concurrent assignment attempts on one claim.
- A re-run of auto-assign for a claim that ALREADY has a live shepherd is a **no-op** (the partial-unique index + a pre-write live-assignment check — the 6.11 `getLiveDecision` precedent), never a second shepherd. The pg-boss at-least-once redelivery of the trigger must self-heal, not double-assign.
- Candidate selection is **deterministic** (workload count + stable tiebreak); given the same roster + workload state, the same shepherd is chosen on replay.

### D-A — Assignment is an identity annotation + a metadata table, NOT a lifecycle state (firm)

There is **no shepherd lifecycle state** and there must not be one — assignment is a routing concern (the 6.10/6.11-confirmed framing that escalation is "routing/reassignment, no lifecycle state, no queue mutation"). `claim.shepherd_assigned` is a `requireIdentityTransition` annotation (`from_state === to_state`); the reducer's case returns `state` unchanged and stays TOTAL. `CLAIM_LIFECYCLE_STATES` is **unchanged** (15 states). The assignment row is the metadata authority (who/contact/reason/live-vs-superseded); the event is the timeline authority. One tx; neither a projection of the other (AC0 — the 6.11 two-authority discipline).

### D-B — The trigger: assign when `verification_in_progress` is entered, via a worker enqueued off peer-mesh (R2)

`verification_in_progress` is entered by exactly ONE transition — `claim.peer_mesh_pinged` (`documents_pending → verification_in_progress`), emitted by the `CLAIM_PEER_MESH_SELECT` pg-boss worker. `claim-peer-mesh.ts` has two enqueue shapes: SELECT→WINDOW is same-file (direct `boss.send`, one module owns both queues); OCR→SELECT is cross-file (an **injected callback** wired in `boot.ts`, so the OCR module never imports the SELECT queue name). The **recommended trigger** for the NEW `CLAIM_SHEPHERD_ASSIGN` worker mirrors the cross-file shape (it's a separate file, like OCR→SELECT): `boot.ts` injects an enqueue callback into `claim-peer-mesh.ts`'s deps, invoked after the SELECT worker commits. This keeps 6.12 OUT of 6.6's frozen selection tx (no hardcoded queue name or direct `boss.send` inside that file) and gives the assignment its own retry/DLQ envelope. **Do NOT** inline the assignment into the peer-mesh selection tx (couples two stories' failure modes), and **do NOT** invent a generic event-reactor framework (none exists; the enqueue-chain is the codebase's idiom). Note the epics' FR-41 says "entering `under_verification`" (line 91) — that is **stale wording**; the canonical state is `verification_in_progress` (`schema/claims.ts:60,77`), and the story AC already spells it correctly.

### D-C — Shepherd = District Admin; scope-respecting via server-derived district (firm)

There is **no dedicated `shepherd` role** in `roles.ts` (the 12-role set) — the epic's "(or another designated shepherd role)" has no substrate. The shepherd IS a **`district_admin`** at the deceased member's server-derived latest posting district, resolved by calling **`member.getMemberPostingLatest(db, pariwarId, deceasedMemberId)`** (`packages/domain/src/member/posting.ts`, exported from the domain barrel) directly from the worker. **`resolveVerifierConsoleDistrict`/`resolveDecisionDistrict` are NOT importable functions** — they're unexported, per-route Fastify preHandlers (`claims.verifier-console.routes.ts`, `claims.verification-decision.routes.ts`) that call the same domain read for an HTTP request context; a pg-boss worker cannot use them and must call `member.getMemberPostingLatest` itself. Candidate pool = `role_grants` (role `district_admin`, `scope_dimension='district'`, `scope_value=<district>`, tenant) × active `users` with a `display_name`. **Do NOT** invent a shepherd role or a geo-tree resolver — the district-node exact match is all that resolves pre-Epic-3 ([[project_rbac_geo_scope_containment]] — a state-ceiling grant does NOT satisfy a district check). Workload balancing = live-assignment count with a deterministic tiebreak (the peer-mesh determinism discipline — no `Math.random()`; a pure, replayable choice).

### D-D — The R5 display-name posture, refined for an automatic actor ([[project_admin_display_name_attribution]])

The shepherd's name is a **snapshot of `users.display_name`** at assignment time — controlled staff attribution, plaintext-by-decision, NEVER email-derived, never re-resolved live (a rename never rewrites history). This is the SAME source 6.11 ratified and the memory explicitly binds 6.12 to it. **6.12 adds a contact snapshot next to it (R1 ratified):** `contact_phone` + `contact_whatsapp` (E.164), same controlled-staff-data posture. **The refinement over 6.11:** 6.11 could `AdminDisplayNameMissingError`-block a human adjudicator mid-request; 6.12's PRIMARY path is an **automatic system assignment** that cannot 4xx a grieving family. So the **contactability invariant** (name AND ≥1 channel) is enforced as **eligibility** — a candidate missing the name or both channels is **skipped** on the auto path — and block-on-missing (`AdminDisplayNameMissingError` / `ShepherdNotContactableError`) applies **only** to a manual reassignment (R6). Do not fabricate a display/contact fallback in either path; an un-contactable pool falls to AR-61 fallback, never to a nominal-but-unreachable shepherd.

### D-E — Reassignment = re-emit + atomic supersession (the reschedule + revise precedents)

Reassignment (fallback or manual) re-emits the SAME `claim.shepherd_assigned` event with `previous_shepherd_actor_id` + `assignment_reason` + `supersedes_assignment_id` — the `claim.ground_inspection_scheduled` reschedule pattern (same event, back-reference field; no separate `superseded` event). Atomic supersession is the 6.11 revise pattern verbatim: conditional `UPDATE … WHERE superseded_at IS NULL RETURNING` (0 rows ⇒ conflict 409) then INSERT the new live row; the partial-unique `(claim_case_id) WHERE superseded_at IS NULL` is the backstop. This guarantees exactly one live shepherd under concurrency and keeps the full reassignment timeline auditable.

### D-G — PII discipline (AC8, the ground-inspection precedent)
