## Story

As any surface consuming contribution status,
I want `contribution.confirmed` (Story 9.4 matcher) to be the **sole authoritative source of confirmed-contribution truth** — fenced so no surface can independently claim a contribution is "confirmed" by inferring from a yellow pill, a UTR attestation, or any other proxy — and the reversal path (`reconciliation.confirmation-reversed`, Story 9.4 Decision D1) correctly **backs out** a confirmation everywhere it was surfaced,
so that financial truth flows through exactly one event-derived state, is impossible to fake or reconstruct, and only ever moves forward except by an explicit, attested compensating event.

### Reversal semantics — the per-confirmation event-id chain (the single most subtle part)

A (member, pool) can traverse: `contribution.confirmed`(id=C1)→green ; `reconciliation.confirmation-reversed`(reversedConfirmedEventId=C1)→held ; later `contribution.confirmed`(id=C2)→green again. The correct, monotonic, replay-deterministic read is **per-confirmation-event**, NOT per-(member,pool):
- Collect the member's confirmed event ids for the pool: `C = { c.eventId }`.
- Collect the reversal-named ids: `R = { r.payload.reversedConfirmedEventId }`.
- **live-confirmed** iff `C \ R ≠ ∅` (some confirmation is un-reversed) → **green** / lists as a contributor.
- **held** iff `C ≠ ∅` AND `C \ R = ∅` (confirmations exist, all reversed) → **held** / removed from the contributor list.
- A reversal naming an id not in `C` (defensive) is ignored — it cannot un-confirm a confirmation that isn't there.
This keeps the confirmation "only ever moves forward except by an explicit compensating event" (the 9.4 monotonic invariant) TRUE on the read side: a reversal walks back exactly the confirmation it names, and a fresh confirmation re-greens. **Do NOT collapse to "any reversal for (member,pool) → held"** — that would permanently poison a re-confirmed member and break re-green. Keep the confirmed + reversal fetch ONE batched query (add the reversal type to the existing `inArray`/`or`), then reconcile by event id in JS (the set is bounded by the pool roster; no per-row round-trip).
