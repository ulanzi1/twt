## Story

As Solo Builder authoring the reconciliation matcher,
I want a UTR matching engine that runs as a cron job 6×/day during live alerts, matches member UTR attestations against uploaded bank-statement entries **idempotently** and **replayably**, and emits the canonical `contribution.confirmed` verdict under a **monotonic-confirmation invariant** (a confirmation can only ever move forward — never silently revert),
so that financial truth is computed deterministically, is auditable, and is the sole authority every downstream surface reads — with the ONLY path to un-confirm being an explicit, attested, audit-logged compensating event.

## Acceptance Criteria

Decomposed from epics.md §Story 9.4 (L3201–3224) + the Epic-9 demoable closure (L3136) + the cross-cutting Epic-9 ARs. Where the epics prose and the SHIPPED code contracts diverge, the **code contract wins** and the divergence is called out (see Dev Notes) — do not code to the prose.

**AC1 — The matcher runs as an idempotent cron 6×/day during live alerts.**
**Given** FR-30 (p95 < 4h reconciliation latency) + AR-58 (idempotent matcher) + Story 1.12 keyed store + the `reconciliation.statement-uploaded` events Story 9.3 emits
**When** the matcher is authored
**Then** it runs as a **pg-boss cron job 6×/day (every 4h), IST-scheduled**, registered in `apps/jobs/src/boot.ts` following the `cycle-open-alert` worker's **enqueue-primary + recovery-sweep** shape (Decision D4 layout); each **match attempt is idempotent** on the key `(member_id, alert_id, bank_statement_entry_id)` via `createKeyedStore().claim()`; at-least-once delivery from cron OR sweep is safe (a redelivery claims → `already_claimed` → no-op, no double confirmation).
> **Cron scope.** The matcher only does work for pools whose cycle alert is **live** (the contribution window is open). A producer-less/alert-less tick is a cheap no-op (the Story 5.6 anti-pattern is a *scheduled worker with no producer*; here the producer — statement uploads — exists, so the cron is legitimate). Make the cadence env-overridable (`MATCHER_CRON`, default `0 */4 * * *` IST) exactly as the sweep cadences are.

**AC2 — Primary UTR match + secondary verification.**
**And** the matching mechanism is: **(a) primary match** — an exact string match between a Story 8.4 `contribution.utr-attested` event's `utr` and a Story 9.2 `BankStatementEntry.transaction_id_utr` (both scoped to the same pariwar + pool/alert); **(b) secondary verification** — **destination**: the entry's provenance pool (the `poolId` its statement was uploaded against, Task 2) equals the attestation's `poolId`, via the pure `classifyContributionDestination` primitive (Dev Notes) — a mismatch here is `wrong_pool`, checked BEFORE amount (AC3.10 precedence); **amount**: the matched entry's `amount` equals the pool's `fixed_amount` (**units reconciliation: `pools.fixed_amount` is whole-INR, `BankStatementEntry.amount` is integer paise ⇒ compare `fixed_amount × 100 === amount`**; reuse the pure `classifyContributionAmount` primitive, Dev Notes) AND `transaction_date` falls within a reasonable window of the alert AND `sender_vpa` matches the member-recorded payment VPA **(the sender-VPA arm has NO data source today — the `utr-attested` payload carries no member VPA and none is collected anywhere; it is a first-class `{available:false}` seam per Decision D3, NOT a fabricated check)**; **(c) on full match** — emit `contribution.confirmed`.
> A UTR-less entry (`transaction_id_utr === null`) is never matchable — the matcher skips it (the schema documents this: "the matcher simply never confirms a UTR-less row").

**AC3 — `contribution.confirmed` emission with the exact forward-contract shape.**
**And** on a full match the matcher appends **`contribution.confirmed`** (the SHIPPED `CONFIRMED_EVENT_TYPE`) carrying **`poolId` + `memberId`** (the exact camelCase keys the Story 8.3 contributor-list read greps — `CONFIRMED_PAYLOAD_POOL_KEY`/`CONFIRMED_PAYLOAD_MEMBER_KEY`) plus `alertId`, `utr`, `confirmedAt`, and `matchProvenance` (which `bank_statement_entry_id`, which idempotency key, which matcher run); the event is append-only (Story 1.3) on the stream Decision D2 fixes. On emission the Story 8.3 contributor list, the Story 8.6 Yogdaan Bahi green arm, and the `contribution/history.ts` green passbook arm all populate **with zero code changes in those reads** — proven by a test asserting a real matcher run flips a seeded member's `history` status yellow→green.

**AC4 — The matcher is replayable (deterministic, order-invariant).**
**And** replaying the same `(bank_statement_entries, attestation_events)` set produces **identical match outcomes** regardless of input order (Story 4.6 order-invariant pattern); a re-parse of the same stored blob yields byte-identical `entry_id`s (Story 9.2 `deriveBankStatementEntryId`); a **frozen-vector test** pins a seeded statement + attestation set → a fixed confirmed/mismatch outcome set, and asserts a shuffled-input replay reproduces it exactly.

**AC5 — The monotonic-confirmation invariant (this story's load-bearing commitment).**
**Given** the monotonic-confirmation invariant
**When** a contribution has been confirmed (a `contribution.confirmed` event exists for `(member, alert/pool)`)
**Then** the confirmation **cannot silently revert**: (a) a matcher re-run over an already-confirmed `(member, alert)` is an **idempotent no-op** (a pre-read short-circuits before any re-emit); (b) **no matcher code path emits any reversal/un-confirm event** — the ONLY un-confirm path is a trustee-attested review-and-reverse (Story 9.8: step-up OTP via Story 5.9 + reason-code + State-Trustee attestation à la Story 6.14) that emits an explicit **compensating event** (Decision D1 fixes its namespace/name) with full provenance (which trustees, what reason, which original confirmation it reverses); (c) **silent reversion is structurally impossible** — a CI/unit test asserts no matcher path can transition a contribution from confirmed back to pending/unconfirmed without an attested compensating event, and the append-only events_log (Story 1.3 immutability trigger) makes a direct-mutation reversal fail at the DB layer.
> This story DEFINES + REGISTERS the compensating-event type and PROVES the matcher never emits it; Story 9.8 wires the human action that does. The reversal PRODUCER is a 9.8 seam.

**AC6 — Wrong-pool payments are never silently remapped (Story 7.6 invariant).**
**Given** the Story 7.6 facilitated-recovery invariant
**When** the matcher encounters a payment against the wrong pool (a UTR/amount that resolves to a different pool than the attestation's, or an amount-mismatch to the correct pool)
**Then** it does **NOT** silently remap: the wrong-pool/mismatched record is preserved as **invalid**, a `contribution.reconciliation-mismatch` is emitted (the pre-built red-pill reader populates), and the case is left for the Story 9.7/9.8 review queue. No `contribution.confirmed` is emitted for a wrong-pool or amount-mismatched deposit.

**AC7 (cross-cutting — the 8.10 fence must stay green).**
**Given** Story 8.10's `no-ingest-path` executable fence (the complete `contribution.*` vocabulary is EXACTLY three: `utr-attested`, `confirmed`, `reconciliation-mismatch`)
**When** 9.4 adds the compensating (reversal) event type
**Then** the reversal type MUST NOT be a fourth `contribution.*` literal that trips the fence (Decision D1 resolves this — the 9.3 D6 precedent chose a non-`contribution.*` namespace exactly to dodge this fence); `pnpm --filter @twt/domain test` keeps `packages/domain/tests/contribution/no-ingest-path.test.ts` GREEN (verify, do not assume — the fence source-scans for `contribution.*` literals).

**AC8 (cross-cutting — AR-45 external-call resilience at the storage-fetch boundary).**
**Given** AR-45 (the matcher's external call is the `BankStatementStorage.getBytes` blob fetch for re-parse)
**When** the matcher fetches a stored statement blob
**Then** the fetch is wrapped with retry-with-backoff + timeout + circuit-breaker (reuse the 9.3 `apps/api/src/modules/reconciliation/resilience.ts` `ResilientCall` pattern, or the jobs-side equivalent), all failures audit-logged; a storage outage defers the match to the next tick (the cron is self-healing), never crashes the worker or corrupts a partial confirmation.

### The units trap (paise vs whole-INR) — the single most likely wrong-data bug

`pools.fixed_amount` is **whole INR** (`integer`, e.g. `1000`). `BankStatementEntry.amount` is **integer paise** (`100000` for ₹1000). A naive `fixed_amount === amount` compares 1000 to 100000 and NEVER matches — every confirmation silently becomes a mismatch. The matcher MUST reconcile: `fixed_amount × 100 === amount` (or `amount / 100 === fixed_amount` with an integer-exactness guard — paise not divisible by 100 is itself a mismatch). The BankStatementEntry schema comment names this exactly ("the pool's whole-INR `fixed_amount` (× 100)"). Add a frozen-vector test with a real ₹-amount pair to lock it.

### Replay determinism + order-invariance (Story 4.6 pattern)

The matcher must be a pure function of its input SET, not its input ORDER. Sort attestations + entries canonically (by `entry_id` / event id) before matching; never let a Map-iteration order or a DB row order leak into the outcome. A re-parse of the same blob yields the same `entry_id`s (Story 9.2 guarantees this), so the whole `(attestations, entries) → verdicts` computation is replay-identical. Prove it with a shuffled-input test (AC4). This mirrors the pool-assignment engine's version-pinned replay identity ([[project_pool_assignment_engine]]) — the matcher is another replay-identity primitive.

### The monotonic invariant is enforced in THREE layers (defense in depth)

1. **Keyed store** (`(member, alert, entry)` claim) — prevents two concurrent ticks double-confirming.
2. **Event-level pre-read** — before emitting `confirmed` for `(member, alert)`, check none exists; a re-run is a no-op. This is what makes "confirmation only moves forward" true across runs.
3. **Append-only events_log** (Story 1.3 immutability trigger) — a direct UPDATE that would "un-confirm" fails at the DB. The matcher simply has NO reversal-emit code path (structural). The ONLY reversal is the 9.8 trustee compensating event.
All three are AC5; Task 6 tests each with revert-sanity teeth.

**Design decisions worth review attention:**
1. **`no_statement_entry` is NOT emitted by the live matcher.** The pure engine classifies it (faithful to AC2), but the worker emits mismatches ONLY for a deposit found-and-rejected (`wrong_pool`/`amount_mismatch`). During an open window a member who attested before their statement was uploaded is legitimately PENDING (yellow); a premature red would flip every fresh attester. The post-close "still no deposit" determination is a reconciliation-tail concern (a future story). Documented in the worker + ADR-0035.
2. **Standalone verdict schemas (not the write map).** To keep the Story 8.10 `no-ingest-path` fence + the 8.4 events.test GREEN verbatim (AC7's literal requirement), the confirmed/mismatch schemas ship standalone and register in the events registry directly, rather than mutating `CONTRIBUTION_EVENT_TYPES` (which would trip the exact-equality fence assertion). The enqueue-primary is wired in BOTH apps/api reconciliation routes best-effort, via an OPTIONAL `reconciliationMatchQueue` dep (omitted in tests). ~~The staff route's enqueue is technically pre-commit~~ — the code review found the staff route's enqueue actually fired BEFORE the scope-tx commit (the middleware commits in an `onSend` hook after the handler returns), and that the ADR did not in fact document this caveat as an earlier draft of this note claimed.
