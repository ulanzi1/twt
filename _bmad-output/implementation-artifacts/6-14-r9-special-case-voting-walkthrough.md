## Story Classification

`[SURFACE]` — a State-Trustee-facing R9 voting UI + its API surface + the domain write-paths + the registry-driven read model that back it. **This is the FIRST claim story since 6.6 to ADD to the claim vocabulary** — unlike 6.13 (which was a pure emitter of the pre-committed Story 6.1 vocabulary), R9 voting is genuinely greenfield: there is **no `claim.r9_outcome` event, no R9 voting state, no `claim.r9_vote` RBAC key, and no votes table anywhere in the substrate** (grep-verified). 6.14 lands all of them.

It is the CONSUMER end of the seam 6.13 opened: 6.13's `routeToR9` writer parks a claim (a live `claim_state_trustee_decisions` `phase='routing'`, `outcome='routed_to_r9'` row; the claim stays `verifier_approved`/`reversed`, durably excluded from the cycle-freeze commit) and its file explicitly says "the actual R9 panel voting + `claim.r9.outcome` is Story 6.14 (6.13 casts no R9 votes and emits no R9 events)". 6.14 is that panel. It is also the FIRST place the **niyamavali clause registry (Story 2.3 `clause_versions`) is read from the CLAIM flow** — R9 voting is "registry-driven" because it snapshots the applicable R9 sub-clause's `clause_version_id` for per-vote provenance (Story 4.4 defined the three R9 clauses as DATA; 6.14 reads them, it never re-encodes them).

## Story

As a State Trustee panel voting on an R9 special-case claim (suicide, murder, multiple-deaths-same-date, nominee-accused),
I want a registry-driven voting UI that surfaces the R9 sub-clause that applies, the rule-version snapshot (`clause_version_id`), and per-vote provenance,
So that R9 voting decisions are auditable to the exact rule + each trustee's individual vote.

**AC3 — Cast an individual R9 vote (panel-member-only; rationale required + bounded; revisable until finalize; per-vote rule snapshot).**
**Given** an open (not-yet-finalized, not-superseded) R9 voting session
**When** a State Trustee casts a vote (`POST …/admin/r9-voting/:claimCaseId/vote`, body `{ vote: 'approve' | 'deny', rationale }`)
**Then** the voter MUST be a member of the session's immutable `panel_actor_ids` (AC2) — an actor holding `claim.r9_vote` who is NOT on this panel is rejected with a typed 4xx (the panel is the eligible-voter set, not "anyone with the key")
**And** the write path inserts a `claim_r9_votes` row recording: `session_id`, `voter_actor_id`, `voter_display` (R5 snapshot, NOT NULL — AC7), `vote`, `rationale_ciphertext` (Tier-1 `piiColumn`, NOT NULL), `cast_at`, and the **`clause_version_id` snapshot COPIED from the session** (the epic's "rule-version snapshot persists with the vote")
**And** **rationale is REQUIRED, non-empty, and bounded ≤500 chars** for EVERY vote (approve and deny alike — the epic lists rationale as part of every vote record) — the ≤500-char PLAINTEXT bound is enforced ONCE, at the trusted pre-encryption boundary (the contract `superRefine` on `body.rationale`, →400), BEFORE `encryptR9VoteRationale` runs (the `verifier-decision-crypto.ts` precedent); the domain write-path receives ONLY ciphertext and cannot re-derive the plaintext's character length from it (envelope/KMS overhead means ciphertext byte length does not track plaintext char count — a ciphertext-length check would be a FALSE proxy, not a re-enforcement, of the ≤500-char rule). **Corrected 2026-07-14 (code review, story-6-14-r9-special-case-voting-walkthrough):** the domain layer's actual defense-in-depth is two narrower, DISTINCT guarantees instead — (1) a compile-time brand, `PreparedR9VoteCiphertext` (`packages/domain/src/claim/r9-voting.ts`), obtainable ONLY via `prepareR9VoteCiphertext`, which the route calls AFTER contract validation + encryption, so `castR9Vote` structurally cannot accept a raw unvalidated string; and (2) a SEPARATE storage-safety ceiling (`R9_VOTE_CIPHERTEXT_MAX_BYTES`) inside that same constructor, guarding the `piiColumn` against a pathologically oversized envelope — explicitly NOT a re-check of the 500-char business rule. The NOT-NULL column is the final backstop.
**And** one LIVE vote per panelist per session (partial-unique `(session_id, voter_actor_id) WHERE superseded_at IS NULL`); a panelist may **REVISE their own live vote any time BEFORE finalization** — the revise atomically SUPERSEDES the prior live vote (0-row conditional UPDATE ⇒ 409, the 6.11 `reviseDecision` precedent) + inserts the new one + sets `supersedes_vote_id`; the transcript keeps both, the tally counts only the live vote. **Reaching a computable tally ("quorum") does NOT lock voting — FINALIZE (AC4) is the single lock point**; there is no auto-lock-at-quorum
**And** casting/revising writes metadata ONLY (no lifecycle event, AC0); voting is illegal once the session is finalized (`outcome IS NOT NULL`) OR superseded/cancelled ⇒ typed 4xx.

**AC4 — Finalize the panel outcome (a SEPARATE, step-up-gated human action; deterministic vote-row lock; DATA-driven; strongly idempotent).**
**Given** an open (not-superseded) R9 voting session
**When** a panel trustee finalizes (`POST …/admin/r9-voting/:claimCaseId/finalize`) — a SEPARATE, explicit human action, never auto-triggered by the last vote (D-E/#1)
**Then** the route requires a FRESH ~5-min step-up elevation bound to `r9_finalize` (Story 5.9 / 1.9 `requireStepUp`, added AFTER the permission hook so an unauthorized actor never reaches step-up — D-E, ratified) and the finalizer MUST be a panel member (`panel_actor_ids`); **v1 EXPLICITLY ACCEPTS the RISK of self-finalization** — the same actor may open + vote + finalize (the single-trustee-panel reality) — recorded openly as an accepted v1 posture, NOT hidden; separation-of-duties (opener≠finalizer, a distinct minimum-panel-size rule) is DEFERRED to the Epic-3 multi-trustee panel ([[feedback_record_unattested_no_backfill]] discipline: an accepted risk is stated, not papered over)
**And** finalizing REQUIRES **QUORUM** — the number of CAST live votes must be ≥ the session's `quorum_required` (D-D: v1 default = a strict majority of the panel, `⌊N/2⌋ + 1` where `N = cardinality(panel_actor_ids)`, snapshotted at open; for a single-member panel that is `1`, preserving the no-empty-finalize rule) — a below-quorum finalize is rejected with a typed 4xx (subsumes the "no zero-vote / no-vote-self-finalization" rule)
**And** under the per-claim advisory lock, the write path LOCKS the session's live vote rows `FOR UPDATE` in a DETERMINISTIC order (by `vote_id`) BEFORE tallying (#6) — so a concurrent cast/revise cannot change the count between the read and the finalize write; it then COMPUTES the outcome against the session's snapshotted `voting_requirement` **with the PANEL SIZE `N` as the denominator** (D-D — precise, panel-based, not "of those who voted"): `majority` ⟺ `approve_count > N/2` (i.e. `approve_count ≥ ⌊N/2⌋+1`); `supermajority` ⟺ `approve_count ≥ ⌈2N/3⌉`; `unanimous` ⟺ `approve_count === N` (every panel member approved) — an absent or `deny` panelist counts AGAINST the approval threshold; the outcome is `approved` iff the threshold is met, else `denied` (v1 seed resolves all three R9 clauses to `majority`); persists `outcome` (`approved` | `denied`) + `approve_count` + `deny_count` + `finalized_at` + the finalizing actor's `actor_display` onto the session row
**And** it emits `claim.r9_outcome` (the 29th claim event — D-A) carrying the NON-PII tally + rule snapshot ONLY (`clause_id`, `clause_version_id`, `voting_requirement`, `approve_count`, `deny_count`, `outcome` — no names, AC0/AC10) AND advances the claim lifecycle (D-A: `approved` → `state_trustee_approved`; `denied` → `denied`) AND SUPERSEDES the live `routed_to_r9` routing row (so an approved claim rejoins the 6.13 cycle-freeze commit set, and a denied claim is out of it) AND writes a `claim_state_trustee_decisions` `phase='r9_outcome'` metadata row — all atomically in ONE scope-tx
**And** an `approved` R9 claim then flows through the ORDINARY 6.13 cycle-freeze commit (`state_trustee_approved → claim.approved`, the single step-up-gated milestone Epic 7 keys off — 6.14 emits NO `claim.approved`); a `denied` R9 claim lands in `denied` (eligible for the Story 6.16 3-stage appeal)
**And** **strengthened idempotency (#7):** the `outcome IS NOT NULL` short-circuit is re-checked UNDER the per-claim advisory lock (not just an up-front read) — a re-finalize returns the recorded outcome WITHOUT re-emitting `claim.r9_outcome`, re-advancing the lifecycle, or re-superseding the routing row; the `events_log (stream_id, event_version)` unique index is the structural backstop; a finalize on a SUPERSEDED (cancelled) session is a typed 4xx, NOT an idempotent success.

### D-D — Voting session + votes tables + the DATA-driven outcome + the IMMUTABLE panel (RATIFIED + hardened, BigDev 2026-07-13)

Two new tables (the 6.13 two-table precedent): `claim_r9_voting_sessions` (the panel — clause snapshot + `voting_requirement` + the immutable panel roster + `quorum_required` + computed outcome; the audit + finalize anchor) and `claim_r9_votes` (per-vote provenance). The `voting_requirement` is DATA from the clause payload: `majority` (v1 default + `R9`'s `majority_required`), with `supermajority`/`unanimous` forward-compat and DATA-driven (no per-clause hardcode).

**Hardened voting-integrity model (BigDev refinements, baked into AC2–AC5/AC9):**
- **Immutable panel + panel-based denominators + quorum (#1/#2 — BigDev, 2026-07-13).** The eligible-voter set (`panel_actor_ids`) is captured at open, every member validated to hold `claim.r9_vote` @ pariwar, and FROZEN thereafter — no adding a voter mid-vote to swing the outcome (a non-panel actor is rejected even if they hold the key, AC3). The DENOMINATOR is the **panel size `N = cardinality(panel_actor_ids)`** (NOT cast votes — corrected from the create-story draft): `majority` ⟺ `approve > N/2`; `supermajority` ⟺ `approve ≥ ⌈2N/3⌉`; `unanimous` ⟺ `approve === N` — an absent/`deny` panelist counts against the approval threshold. A **quorum** (`quorum_required`, v1 default `⌊N/2⌋+1`, snapshotted at open, forward-compat to a DATA clause field) gates finalize: below quorum → 4xx (subsumes the old "≥1 vote" rule; for N=1 quorum=1). This is the precise, panel-based model BigDev ratified.
- **Strengthened session uniqueness (#4).** At most ONE non-superseded session per claim (open OR finalized) — `(claim_case_id) WHERE superseded_at IS NULL`. A finalized session blocks re-opening; re-voting requires cancel-first (AC5).
- **Revision until finalize (#5 — ratified unchanged).** A panelist may revise their live vote (superseded transcript) any time before finalize; reaching quorum does NOT auto-lock — FINALIZE is the single lock point.
- **Deterministic finalize (#6/#7/#8).** Finalize is a SEPARATE explicit human action; requires quorum; locks the live vote rows `FOR UPDATE` (vote_id order) before tallying; is idempotent under the advisory lock (re-finalize returns the recorded outcome, never double-advances).
- **v1 self-finalization is an EXPLICIT accepted risk (#3 — ratified unchanged, with the accepted-risk statement).** A single-member panel (or one actor opening+voting+finalizing) is permitted and recorded openly as a v1 accepted risk, NOT hidden ([[feedback_record_unattested_no_backfill]]). The multi-trustee panel + separation-of-duties (opener≠finalizer, a distinct minimum-panel-size rule) is the same Epic-3 geo-tree future as the `state_trustee` grant deferral — noted, not built.
