# Story 7.2: Pool Naming Service (Culture-Rooted Curated List + Dual Identifier UX-DR72)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As any member viewing their assigned pool OR any admin auditing the pool engine,
I want pool identity as a **dual representation** — a canonical `P-YYYY-MM-###` identifier for system/audit/regulator use and a member-facing display shortform (letter codes A/B/C…) — plus a per-Pariwar curated-name **capability** so future tenants can layer culture-rooted names on top,
so that members see a simple, stable shortform, system audit uses one canonical identifier, and the mapping is deterministic + replay-reproducible + never remapped mid-cycle.

## ⚠️ READ FIRST — Scope-defining decision (culture-rooted names)

**There is a source-document conflict this story deliberately resolves. Do not start coding the names registry until you have read this section and the matching Dev Note.**

- **PRD FR-13 + epics.md Story 7.2 AC1** mandate a `pool_names` registry seeded with **≥ 30 culture-rooted (Mahabharata) names pre-launch**, shown on member surfaces.
- **The UX spec (a LATER amendment) VETOED that overlay for TWT-Bihar.** Pool columns show **letter codes only** (F, D, J, H, B…); "Mahabharata Pool Naming — Dropped" is an explicit spec section. [Source: ux-design-specification.md §8 line 1155, §11 lines 1297–1301, 1766–1770]
- **Item 13** (sprint-change-proposal 2026-05-27) left the naming **storage surface unresolved** (Niyamavali registry vs branding bundle vs separate admin list) — deferred to IR, never closed.
- **Adversarial review M-10** requires religious-balance + omen-sensitivity review of ANY Mahabharata seed list *before* it ships (Bihar's Muslim teacher population; Karna/Bhishma death-omen sensitivity). [Source: prds/…/review-adversarial.md M-10, lines 192–194, 228]
- **The dual-identifier discipline itself is NOT in conflict** — PRD §11, UX §11, and the epic all commit `P-YYYY-MM-###` canonical + letter-code shortform. That is the unambiguous core of this story.

**Resolution baked into this story (RECOMMENDED — Option B; confirm at review, the Story 7.1 pattern):**
Build the **dual-identifier service** (canonical-id allocation + letter-code derivation + resolver) as concrete, definitely-consumed work (Tasks 1–4). Build the `pool_names` registry as a **per-Pariwar structural capability** (Task 5) — the table + ordering + exhaustion service exist so a future tenant *can* populate names — but **TWT-Bihar v1 seeds ZERO culture names**; its active member-facing display shortform is the **letter code**. Do **NOT** hardcode 30 Mahabharata names as active labels; that would ship exactly what the UX amendment vetoed and what M-10 gates. This satisfies the epic's "a registry exists" while honoring the veto + Item 13 (storage surface = a dedicated per-Pariwar table, resolving Item 13) + the multi-tenant theme-layer framing (cultural motifs are branding-bundle parameters, not engine data). **The letter-code fallback (empty registry → letter code) is the explicit, TESTED launch behavior for TWT-Bihar — not an incidental default** (see AC3/AC5 + Task 4). Future Pariwars remain free to populate the registry *after* the required governance + product review (adversarial M-10: religious-balance + omen-sensitivity).

**Alternatives if BigDev overrides:** **Option A** — ship the ≥30-name seed per the literal AC (requires the M-10 sensitivity review first). **Option C** — defer the registry table entirely to a future tenant-onboarding story and ship only the dual-identifier service for v1 (leanest, matches `[[feedback_no_premature_package]]`; 7.3's "reserve N names" then reduces to letter-code derivation + canonical-id allocation, which exist either way).

## Acceptance Criteria

**AC1 — Canonical identifier generation service (`P-YYYY-MM-###`).**
Given FR-13 + UX-DR72 + UX §11 Pool Identifier Rule + Story 7.1's `pools.pool_canonical_identifier` column and its unique index `(pariwar_id, pool_canonical_identifier)`,
When the naming service is authored,
Then a deterministic, atomic **canonical-identifier allocation service** exists that produces `P-YYYY-MM-###` (default format; format is per-Pariwar configurable, TWT-Bihar uses the default): `YYYY-MM` = the cycle-freeze month, `###` = a per-`(pariwar_id, YYYY-MM)` monotonic zero-padded counter (`001` = first pool that month, per the UX example `P-2026-05-001`); allocation is transactional (the `cohort_invalidation_epochs` per-Pariwar-counter precedent) and race-safe against the 7.1 unique index; the service allocates a **contiguous range of N** identifiers in one call (7.3's parent job consumes it); it is used in audit logs, system queries, regulator exports, and error messages.

**AC2 — Letter-code derivation (member-surface shortform).**
Given the dual-representation requirement + the N > 26 boundary flagged by the epic AC and adversarial review (TSCT's A–T topped out at 20),
When the letter-code function is authored,
Then it is a **pure, total, deterministic bijective base-26 function of `pool_index`** (0→A, 1→B, …, 25→Z, 26→AA, 27→AB, … — spreadsheet-column style, never breaks at N > 26); it is presentation-only, rendered **on member surfaces only** (My Pool card, Yogdaan Bahi, Sahyog Drive contributor list); it stores nothing (derived on read from `pool_index`).

**AC3 — Dual-representation resolver + stable-mapping invariant.**
Given the canonical identifier is always the source of truth and the shortform is presentation (UX §11),
When pool identity is surfaced,
Then a single resolver exposes: the **canonical identifier** for audit/system/regulator/error surfaces, and the **display shortform** for member surfaces (letter code for TWT-Bihar; a culture name IF the registry supplies one for that Pariwar — see AC5). **The empty-registry → letter-code path is the committed, explicitly-tested TWT-Bihar launch behavior** — the resolver defaults to the letter code whenever no registry name is supplied (never a blank, never the canonical id leaking onto a member surface). The mapping (`pool_index` ↔ letter code, `pool` ↔ canonical id) is a **documented stable mapping — never renamed or remapped mid-cycle**; identity is fixed at spawn and immutable for the pool's life.

**AC4 — Naming service is engine-neutral (no death branches).**
Given Story 7.1's `pool-support-category-invariant` gate + the `support_category` discriminator,
When the naming service code is authored,
Then it contains **no death-specific branches** and no `'death'` / `'death_support'` string matches outside the enum definition file; the new naming source files are inside the gate's `SCAN_ROOT` (extend it if needed, per the per-epic scope-extension convention) and the gate stays GREEN with a revert-sanity proving teeth.

**AC5 — Curated-name registry capability (per-Pariwar; TWT-Bihar seeds ZERO names).**
Given FR-13's registry requirement, Item 13's storage-surface question, and the UX amendment veto (see "READ FIRST"),
When the registry is authored,
Then a per-Pariwar `pool_names` table exists (the `pariwar_wa_templates` precedent) with `pariwar_id`, `position_in_ordered_list`, `display_name_en`, `display_name_hi`, `cultural_lineage_note`, and audit/approval columns, RLS-scoped by `pariwar_id`; a **deterministic, replay-reproducible ordering service** assigns "next N names in `position_in_ordered_list` order" (consumed by 7.3); **TWT-Bihar's registry is empty at launch** (letter-code shortform is its active display) — no Mahabharata seed is shipped as active labels, and the empty-registry → letter-code fallback is an **explicitly-tested launch invariant** (AC3 + Task 4), not an incidental default; future Pariwars may populate the registry only *after* the governance + product review (M-10); and the reservation call distinguishes **opt-out** (registry has zero rows for the Pariwar — by design, e.g. TWT-Bihar — returns an empty result, NOT an error, signaling the caller to use letter codes) from **true exhaustion** (registry has rows but fewer than requested — a trustee configuration gap), which **fails with a clear typed error** so 7.3 can surface it and the trustee must extend the list; any registry mutation is **audit-logged** (`audit_log_entries` precedent).

### Letter-code derivation (bijective base-26 — the N>26 trap)
The epic AC and adversarial review both flag that naïve `A + pool_index` breaks past Z. Use spreadsheet-column bijective base-26 (there is no "zero digit"): repeatedly `n--; digit = n % 26; n = floor(n/26)`. Test the exact boundaries in Task 1. The UX examples "F, D, J, H, B…" are **illustrative of scattered pools in a table, not a mapping spec** — the committed rule is deterministic derivation from `pool_index` (epic AC); do not try to reproduce that specific letter sequence.

### Canonical identifier — format, month, counter
- Format is **per-Pariwar configurable, default `P-YYYY-MM-###`** (UX §11 "Format is per-Pariwar configurable"). v1 only implements the default; thread the format as a parameter so a future tenant can override without an engine change (the multi-tenant theme-layer discipline). Do NOT hardcode the literal grammar in three places — one pure formatter.
- `YYYY-MM` = the **cycle-freeze month** (from `cycle_freeze_commits`, the 7.3 handoff). 7.2's allocator takes the freeze month as input; it does NOT read the clock (determinism/replay — `[[project_measured_validation_framework]]`).
- `###` counter: recommended reset **per-`(pariwar, YYYY-MM)`** (matches `P-2026-05-001`). Flag the continuous-per-Pariwar alternative for BigDev.

### Counter allocation (the transactional precedent)
`cohort_invalidation_epochs` is the exact shape to copy: a per-Pariwar monotonic counter bumped **in the same transaction as the triggering write** (D2-A), making allocation race-safe with zero message-bus timing dependency. [Source: packages/domain/src/schema/cohort_invalidation_epochs.ts] The allocator MUST accept the caller's `tx` (7.3's parent job runs the spawn in one tx) — do not open a nested/own transaction (`db.transaction()` would commit the caller's work early — `[[project_domain_limit_clamp_and_savepoint_retry]]`). The 7.1 unique index `pools_pariwar_canonical_identifier_uq` is the correctness backstop; on `23505` map to a typed collision error (code on `err.cause.code`). Consider whether a dedicated counter table is even needed vs. `SELECT max(sequence) … FOR UPDATE` within the month partition — decide in this note with rationale, build ONE. **Recommended default: `MAX(sequence) FOR UPDATE`** within the `(pariwar_id, period)` partition — no new table/migration, and the 7.1 unique index is already the correctness backstop against a race producing a duplicate. Override with a dedicated counter table only if BigDev wants symmetry with `cohort_invalidation_epochs` or the `MAX()`-under-lock query proves awkward against the range-allocation requirement (allocating `count > 1` contiguous ids in one call).

Record this as the Item 13 resolution in the Dev Agent Record. i18n: `display_name_en` / `display_name_hi` mirror the `hi | en` v1 locale surface (`pariwar_passport.ts` `default_locale` enum, architecture §2.7) — dormant for TWT-Bihar v1 (empty registry).

**⚠ DECIDED VARIANCE #1 — counter table, NOT `MAX(sequence) FOR UPDATE` (Task 3; flagged for review).** The story recommended deriving the sequence from `MAX()` under lock. I built the **dedicated `pool_canonical_counters` table** instead — which Task 3 explicitly permits ("pick one in Dev Notes with rationale; do not build both") — because the recommended default is unsound here on three counts: (1) **it does not serialize** — `FOR UPDATE` locks only rows that ALREADY exist, so two allocators racing on a fresh month both read NULL, both pick `001`, and one dies on the 7.1 unique index, turning the backstop into the primary failure path; (2) it would require **parsing the sequence back out of a per-Pariwar-CONFIGURABLE format string**, coupling the counter to the grammar the same story makes overridable; (3) `MAX()` **recycles** sequence numbers if a pool row is ever removed, re-issuing an identifier that may already appear in an audit line. It is also what AC1 actually names (the `cohort_invalidation_epochs` per-Pariwar-counter precedent). `pool-canonical-allocator-concurrency.spec.ts` is the evidence: two concurrent allocators both **succeed with disjoint ranges** — the property `MAX()` cannot deliver. (Aside: `SELECT max(...) … FOR UPDATE` is also a Postgres error — `FOR UPDATE` is not allowed with aggregates.)

**⚠ DECIDED VARIANCE #2 — `reserveNames` returns `PoolNameReservation[]`, not `string[]` (Task 5; flagged for review).** The story specifies `string[]`. Reservation happens at **cycle freeze** (a system context with no viewer), while display happens **per member** (a locale context) — so collapsing to one string would bake a locale choice in at the wrong moment and surface the wrong language to half a bilingual Pariwar. Each reservation carries `{ poolNameId, positionInOrderedList, displayNameEn, displayNameHi }`; the caller passes the locale-appropriate name to `resolvePoolDisplay({ pariwarCultureName })`. The AC's intent ("assigns the next N names in position order") is preserved exactly. This surface is new and has no consumer yet (7.3 is first), so nothing is broken by it.

**Reset boundary DECIDED (Task 2, recorded here since Dev Notes is not a dev-editable section).** The `###` sequence resets **per `(pariwar, YYYY-MM)`**, matching the UX reference example `P-2026-05-001` (`001` = that month's first pool). The continuous-per-Pariwar alternative is flagged for BigDev: it would make identifiers globally ordered per tenant but would contradict the documented example. Covered by `the ### counter RESETS per month` in the allocator spec.

**Opt-out vs exhaustion (AC5 — the load-bearing distinction).** `reserveNames` discriminates on the Pariwar's **TOTAL** row count, not the approved count: zero rows = **opt-out** → `[]`, no throw (TWT-Bihar's launch config — throwing here would fail its every cycle freeze); rows present but too few approved = **exhaustion** → typed `PoolNameListExhaustedError` carrying `requested`/`available` (a trustee configuration gap). The subtle case is tested explicitly: an opted-in registry with **nothing approved yet** is exhaustion, NOT opt-out — the approved count alone cannot tell "never opted in" from "opted in, un-reviewed", and silently returning `[]` would hide a half-configured tenant behind letter codes.
