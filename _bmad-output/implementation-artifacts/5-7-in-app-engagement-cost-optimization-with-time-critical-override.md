# Story 5.7: In-App-Engagement Cost Optimization with Time-Critical Override

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As Solo Builder watching the WA / SMS delivery cost,
I want a cost-optimization policy layer wrapping the dispatcher that suppresses redundant WA / SMS delivery when the member has already engaged in-app within a recent staleness window — with an explicit **time-critical override** that bypasses suppression,
so that delivery cost is minimized for routine notifications without sacrificing reach for time-critical alerts.

## Acceptance Criteria

> **Scope framing (read before the ACs).** This is a `[GOVERNANCE]` policy story. Two facts fix its shape:
> (1) **`dispatch.ts` explicitly RESERVES cost-optimization as an external WRAPPER** — *"cost-optimization (5.7) and the degraded-mode SMS bridge (5.8) WRAP `dispatch`, they do not live inside it"* (`dispatch.ts` L4-7, L14-17). (2) There is still **NO live `dispatch` call site** ([[project_channels_no_live_dispatch_yet]]), and the **FR-58C feature-flag subsystem that gates this policy lands at Epic 10** (`packages/contracts/src/feature-flags/README.md` — "substantive contracts authored at Stories 10.x"). So — exactly like Story 5.6's cascade primitive — 5.7 builds the **pure cost-optimization POLICY primitive + its config + suppression audit + composition read-seams**, deterministically testable, shaped so the future live fan-out's "wrap `dispatch(alert)`" call site is thin. It does **NOT** wire a live suppression path, does **NOT** change the frozen `dispatch` / `ChannelProvider` / `CANONICAL_CHANNEL_LADDER` / `DeliveryResolver` / `render.ts` surfaces, and does **NOT** add a producer-less feature-flag/DB path (mirror 5.6's "do not wire a producer-less pg-boss worker").

**AC1 — the cost-optimization policy primitive (AR-18 + Story 5.1 policy-agnostic dispatcher):**
1. A pure, deterministically-testable **cost-optimization policy primitive** (`packages/channels/src/cost-optimization.ts`, mirroring the shape of `cascade.ts`) evaluates a suppression decision from: the alert's `alert_category` + `time_critical` flag, the member's **last in-app-engagement timestamp**, the **per-Pariwar cost-optimization toggle** state, the **per-category staleness window**, and `now`. It returns a `CostOptimizationDecision` — either `{ suppressed: false, reason }` or `{ suppressed: true, channels, reason }`. It is a **pure function** (no clock/DB/IO of its own — `now` and every input are injected), and it introduces **NO live `dispatch` call site**.
2. When suppression fires, the suppressed `channels` are **exactly the two paid cost channels** `['whatsapp', 'sms']` (a `COST_OPTIMIZED_CHANNELS` const tuple) — **in-app push is NEVER suppressed** (the policy "suppresses WA and SMS while still firing in-app push"). The Telegram side-channel is **not** a cost-optimization target (it is a free fire-and-forget mirror, out of the ladder — leave it independent, exactly as the cascade does). The primitive **never re-sequences** `CANONICAL_CHANNEL_LADDER` and **never changes** `dispatch`'s public shape.
3. The primitive computes suppression as: given the toggle ON, a non-time-critical alert, and a member whose last engagement is **within** the category's staleness window (`now − lastEngagementAt ≤ window`), suppress the cost channels; otherwise **do not suppress** (full delivery). Every non-suppression path carries a machine-readable `reason` (`'time_critical'`, `'toggle_off'`, `'no_engagement_signal'`, `'no_recent_engagement'`) so the future audit/observability layer can attribute *why* a member got the full fan-out.

**AC2 — per-category staleness window config (AR-18 + architecture §3.4):**
4. The staleness window is **configurable per alert category** (`DEFAULT_STALENESS_WINDOW_MS` + a `STALENESS_WINDOW_BY_CATEGORY` typed `const` override map + a `stalenessWindowFor(category, overrides?)` reader). The **default window is 6 hours** — the **architecture-committed** value (`architecture.md` §3.4 L2080: *"within the optimization staleness window (default 6 hours; tunable in Category 5 Observability)"*). Per-category overrides encode the epic's intent (*"shorter for `deadline_reminder`, longer for `contribution_confirmed`"*, AC L2213): `deadline_reminder` shorter (the epic's illustrative "30 min"), `contribution_confirmed` longer. **These per-category values are a v1 product-policy DEFAULT, not an architecture mandate** (exactly like Story 5.6's DLT-registry category set) — tunable via Category 5 Observability; the reader is injectable so a later config source overrides them without touching the primitive.
5. The window map is keyed by the real `AlertCategory` enum (`packages/contracts/src/alerts/alert.ts` — 9 values); a category with no explicit override falls back to `DEFAULT_STALENESS_WINDOW_MS`. Windows are plain millisecond numbers (mirror `cascade.ts`'s plain-array backoff schedule) so a later durable/observability config adapter is thin.

**AC3 — the time-critical override (AR-18):**
6. The **time-critical override is honored**: when `alert.time_critical === true` (already a first-class field on the `Alert` envelope — `alert.ts` L84-85: *"Overrides cost-optimization (AR-18 / Story 5.7): a time-critical alert is never delayed to batch"*, set by the trigger logic in Epic 6 / Epic 8), the policy **bypasses suppression entirely** and returns `{ suppressed: false, reason: 'time_critical' }` — dispatch to **all** configured channels regardless of in-app engagement. This check is **first** in the decision order (before the toggle and the window) so a time-critical alert can never be cost-suppressed by any combination of toggle/engagement state. Architecture §3.4 L2082-2086 anchors the illustrative always-send set (payment reminder within 48h of cycle close, expiry warning within 7 days, payout issued) — those are **producer-set `time_critical=true` cases**, not category literals the policy hardcodes.

**AC4 — per-Pariwar toggle + engagement read (composition seams; FR-58C-gated):**
7. The policy is **per-Pariwar admin-toggle gated, separate from the WA admin-toggle (FR-72)**, and **FR-58C-flag-gated** (`architecture.md` §3.4 L2077-2081). Because the **FR-58C feature-flag subsystem lands at Epic 10** (contracts README) and there is **no live dispatch site**, the toggle is read through a **composition SEAM** `resolveCostOptimizationToggle(deps, pariwarId): Promise<boolean>` that **defaults to `false` (OFF)** until Epic 10 wires the real flag. **OFF is the fail-safe default**: OFF ⇒ the policy suppresses nothing ⇒ **full delivery, zero risk of a missed alert** — cost-optimization can only ever *reduce* sends once explicitly enabled, never regress reach silently. **Do NOT** add a per-Pariwar toggle DB column / migration / admin form in this story (that persistence + UI belongs to the FR-58C subsystem at Epic 10 — adding a producer-less toggle column now repeats the anti-pattern 5.6 called out for pg-boss).
8. The member's **last in-app-engagement timestamp** ("last app-open timestamp from session activity", AC L2212) is read through a seam over an **existing** signal: `member_device_tokens.last_seen_at` — stamped at app-open when the client re-registers its push token (`architecture.md` §3.4 L1911-1913: *"the member's active-token set is rebuilt at app-open"*; the column exists — `member_device_tokens.ts` L72). Add a pure-domain accessor `getMemberLastEngagementAt(db, memberId)` returning `MAX(last_seen_at)` over the member's **active** device tokens (or `null`), and a thin composition seam `resolveMemberLastEngagement(deps, pariwarId, memberId)`. A member with **no engagement signal** (`null`) is **never suppressed** (`reason: 'no_engagement_signal'` — fail toward reach). This is a **building block only — still NO live `dispatch` call site**.

**AC5 — suppression audit + cost-attribution (audit / cost-attribution query):**
9. **Every suppression event is auditable with its reason** (AC L2216-2218: *"every suppression event is logged with the reason (member's last engagement timestamp + staleness window)"*). Provide a **PII-free** suppression-reason record + an audit emit helper (`auditCostSuppression`) that writes ONE audit line via the frozen `AuditPort` (`audit.ts`) with action `alert.cost_suppression`, carrying the **category, the member's last-engagement timestamp, the staleness window, and the computed age** — all non-PII (timestamps + ids + config numbers; same posture as the dispatch line, which hashes the ID-only payload). The reason record is the substrate "cost-attribution + behavioral analysis" reads to examine whether the suppression policy is well-calibrated. **No raw member PII** (no mobile / name / device token) appears in the reason or the audit line. Architecture §3.4 L2087 also names "per-Pariwar observability metrics" — the **metrics EMISSION transport is deferred to the observability epic** (Category 5); this story shapes the reason record so that emission is thin, and says so plainly (mirror 5.6's staleness-alarm-transport deferral).

**AC6 — freeze discipline + no live wiring:**
10. **Do NOT touch** the frozen channel core: `dispatch.ts`, `provider.ts` (`ChannelProvider` / `SendTarget` / `SendResult`), `CANONICAL_CHANNEL_LADDER`, `DeliveryResolver`, `render.ts`, and the `LifecycleSuppressionHook` seam — all frozen ([[project_channels_no_live_dispatch_yet]]). **Cost-optimization is NOT the `LifecycleSuppressionHook`** (that hook is the member-state/frozen-account suppression boundary — a *different* concern; `dispatch.ts` L14-17, L79-91). Do not reimplement cost-opt inside `dispatch`, do not repurpose the lifecycle hook for it, and do not add a live suppression call site. The primitive returns a decision the **future live fan-out** composes (it will omit the suppressed cost-channels' targets, or feed a combined decision, at the site that first drives a real `dispatch` fan-out); this composition + the Story 5.8 degraded-mode bypass are downstream — 5.7 leaves the seam clean and un-obstructed.

### Review Findings

- [x] [Review][Patch] **`evaluateCostOptimization`'s window-compare guard silently falls through to SUPPRESS on an invalid `Date` (`ageMs` is `NaN`).** `NaN < 0` and `NaN > window` both evaluate `false` in JS, so an invalid `lastEngagementAt`/`now` skipped the clock-skew guard entirely and reached the suppress branch — the one path in this function that didn't fail toward reach on an unknown/degenerate state. Confirmed independently by both the Blind Hunter and Edge Case Hunter review layers. Fixed: the window-compare guard now also checks `Number.isNaN(ageMs)`; added a unit test asserting an invalid Date yields `{ suppressed: false, reason: 'no_recent_engagement' }`. [packages/channels/src/cost-optimization.ts:176-183]

### The four spec tensions — surface them, resolve them (this is the story's real work)
Four places where the epic AC and architecture §3.4 use different words. Per [[feedback_architecture_vs_prd_boundary]] the architecture commits the *property*; the epic AC is the committed *acceptance surface*. Resolutions:

1. **Engagement signal — "acted on the same notification's in-app surface" (arch §3.4 L2078-2079) vs "last app-open timestamp from session activity" (epic AC L2212).** The architecture's ideal is *per-notification* engagement (a read-receipt on that specific alert); no per-notification read-receipt substrate exists yet. The epic AC pins the **v1 signal to the coarse app-open timestamp**. **Resolution: v1 = the coarse app-open proxy** (`member_device_tokens.last_seen_at`, stamped at app-open per arch §3.4 L1911-1913). Per-notification read-receipt engagement is a later refinement (record it in `deferred-work.md`). The architecture commits the property ("recent engagement suppresses redundant paid sends"); the epic pins the mechanism for v1.

2. **Suppressed channels — "suppresses WA and SMS" (epic AC L2205, L2212) vs "suppresses WA send" (arch §3.4 L2078-2079 prose).** The epic AC is broader and is the committed acceptance surface; SMS is the *more* expensive paid channel and is clearly a cost-optimization target. **Resolution: suppress BOTH `['whatsapp','sms']`** (the `COST_OPTIMIZED_CHANNELS` tuple); the architecture prose's singular "WA" is illustrative shorthand for "the paid cost channels" (it predates the SMS provider). Push always fires.

3. **Default window — 6 hours (arch §3.4 L2080, committed + "tunable in Category 5 Observability") vs 30 min (epic AC L2212, "e.g., 30 min").** The epic value is explicitly illustrative ("e.g."). **Resolution: default = 6 hours** (architecture-committed); the epic's 30 min maps to the **`deadline_reminder` per-category override** (the epic's own "shorter for `deadline_reminder`" example). Per-category values are a v1 product default, tunable.

4. **Toggle wiring — "per-Pariwar admin toggle, FR-58C-flag-gated" (arch §3.4 L2077-2081) but the FR-58C subsystem lands at Epic 10.** **Resolution:** the toggle is a **composition SEAM defaulting to OFF**; the real per-Pariwar FR-58C flag read + its admin surface + its persistence land at **Epic 10** (contracts `feature-flags/README.md`). OFF is fail-safe (suppress nothing ⇒ full reach). Building a producer-less toggle column/UI now would repeat the anti-pattern 5.6 flagged for pg-boss.

### Why "no live call site" is the correct scope, not a gap (say it plainly)
Story 5.6 built the cascade **semantics** and deferred durable **execution** because there was no producer. 5.7 is identical: it builds the cost-optimization **policy** (the decision function + config + reason + audit + read-seams) and defers the **live application** (the wrap-`dispatch(alert)` fan-out) to the story that first drives a real fan-out — which is also when the FR-58C flag (Epic 10) makes the toggle meaningful. The primitive is shaped (pure decision, injectable inputs, PII-free reason, plain-number config, fail-safe-OFF toggle) precisely so that live wrapper is thin. **A later developer must not "fix" this by wiring a producer-less live suppression path or a producer-less toggle column.**

### Story 5.8 interaction (leave the seam clean)

Shape the primitive so 5.8 wraps cleanly: 5.8's bypass is expressible either as the producer setting `time_critical=true` on the degraded cycle-open alert (the existing override path — `epics.md` L4272 confirms *"Story 5.7 cost-optimization persists during disaster mode … but Story 5.8 degraded-mode bridge remains available"*), or as the live fan-out simply not consulting the policy under an active degraded-mode declaration. **Do not** build 5.8's bypass here — just don't foreclose it (keep `evaluateCostOptimization` a pure decision the caller may skip).

### PII / audit discipline
- The **suppression reason + audit line are PII-free**: category, `last_seen_at` timestamp, window ms, age ms, `member_id`/`alert_id`/`pariwar_id` UUIDs — **never** a mobile / name / device-token / rendered message.
