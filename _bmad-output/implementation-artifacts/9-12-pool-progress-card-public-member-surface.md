# Story 9.12: `<PoolProgressCard>` Public/Member Surface (confirmed-only, no yellow leakage)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As **a member or visitor viewing pool progress**,
I want **a framework-agnostic `<PoolProgressCard>` that shows pool letter + name, confirmed contributor count, amount raised, days remaining, and the fixed amount per contribution — sourced EXCLUSIVELY from `contribution.confirmed` event-derived state, with NO yellow/pending/projected leakage**,
so that **the surface reflects Story 9.5 canonical financial truth: a low-or-zero meter is honest, never inflated by intent, and the identical confirmed-only render logic is reused unchanged by the member card today and the public Sahyog Vivran surface in Epic 11b.**

## Scope decisions (LOCKED by BigDev, 2026-07-28)

Story 9.12 is a `[SURFACE]` story. Almost everything it needs already exists and is **live**: the Story 8.2 compound read (`GET /api/v1/member/active-contribution`) already resolves pool identity + `fixedAmount` + `daysRemaining` + a **confirmed-only** `progress: { confirmedCount, rosterSize }`; Story 9.4/9.5 already made `contribution.confirmed` the sole financial-truth authority and wired that count live; Story 9.6 already established the `packages/ui` **headless-presenter** pattern (`<StatusPill>`), and the mobile `<ActiveContributionCard>` already renders a progress meter inline. So 9.12 is **not** a new read, a new endpoint, or a new event — it is the **extraction of the confirmed-only pool-progress render contract into a reusable `packages/ui` presenter**, plus the **amount-raised derivation** the epic adds, wired into the existing mobile consumer with the public consumer declared as a seam. These decisions were resolved with BigDev before authoring; they are binding.

### Decision 1 — `<PoolProgressCard>` is a headless `packages/ui` presenter, NOT a React component

Per the epic ("implemented in `packages/ui` (extends Story 1.17)") and the **frozen `packages/ui` pattern**: this package contains **zero** react/react-native — it is pure `(input) → view-model` presenters (`status-pill/`, `member-status/`) that emit **structured values + `@twt/tokens` role NAMES + i18n KEYS**, which each render layer (apps/mobile RN today, the Epic-11b public web later) resolves. 9.12 adds `packages/ui/src/pool-progress/` in the **same shape** as `status-pill/` (`view-model.ts`, `presenter.ts`, `i18n-keys.ts`, `index.ts`, barrel-exported from `packages/ui/src/index.ts`). It has NO API call, NO DB read, NO palette, NO copy strings, NO react import — asserted with **pure unit tests** (there is nothing to mock). **Do NOT** build a `.tsx` component in `packages/ui`; **do NOT** add react/react-native to `packages/ui/package.json`.

### Decision 2 — Confirmed-only is enforced STRUCTURALLY at the presenter's input boundary (the load-bearing invariant, Story 9.5)

The presenter's **input type carries no way to express yellow/pending/attested/projected money**. Mirror the Story 8.3 `pool-contributor-list` "confirmed-only as a SHAPE" discipline: the input is `{ pool identity, confirmedCount, rosterSize, fixedAmount, daysRemaining }` and DELIBERATELY has **no** `attestedCount` / `pendingCount` / `yellowCount` / `projectedTotal` / `status` field. A `.strict()`/exact-shape unit test rejects any such field as **decoy teeth** ([[feedback_gate_scope_semantic_coverage]]) — adding one is the single change this presenter exists to forbid. This is the amount-analog of the 8.2 `ActiveContributionProgress` "NO attested/pending/yellow count field — by design" rule. `rosterSize` is the meter denominator (N), NOT a pending count.

### Decision 3 — Amount raised = `confirmedCount × fixedAmount`, a PURE derivation (yellow can never inflate it)

The epic adds "amount raised (confirmed amounts only)." Derive it in the presenter as **`confirmedCount × fixedAmount`** — do NOT sum a per-`contribution.confirmed`-event amount, do NOT add an `amountRaised` field to any read. Rationale (load-bearing): **every** confirmed contribution is money at the **exact** fixed amount — an over-payment or under-payment stays a **red** `amount_mismatch` and is **never** confirmed (Story 9.11 "canonical financial-truth is preserved because an over-payment stays RED"; Story 9.5). So `confirmedCount × fixedAmount` is exact AND structurally **impossible** to inflate with yellow money (there is no yellow operand). This is the amount-analog of Decision 2. The result is an **integer amount in the same unit as `fixedAmount` (whole INR)**; the render layer applies `formatInr` at the display boundary.

### Decision 4 — Reuse the existing Story 8.2 compound read; add NO new read/endpoint. Public read is an Epic-11b seam.

The epic's "same compound read model pattern as Story 4.7 admin surfaces — denormalized projection optimized for fast render" is **already satisfied** by the Story 8.2 `GET /api/v1/member/active-contribution` read (member × `live` alert × assigned pool × snapshotted `fixedAmount` × `daysRemaining` × confirmed-only `progress`). The MEMBER surface feeds the presenter from **that** existing response — no new read, no new query, no new endpoint. The PUBLIC (Epic 11b Sahyog Vivran / Sahyog Drive) read is **not built in 9.12** — it is a **declared forward seam**; the presenter is public-safe by construction (Decision 2 + it emits only the six render fields, all already PII-safe public-tier), so Epic 11b reuses it unchanged (exactly as Story 8.3's contract reserved for the public render).

### Decision 5 — Build the EPIC's member/public card, NOT the UX-doc's nominee-console daily-delta widget (naming collision)

⚠️ The UX spec's `<PoolProgressCard>` (ux-design-specification.md §2011-2018) describes a **different** surface: a **nominee-console / trustee-dashboard operational widget** — "daily-delta fill visualization," "last-updated timestamp (always visible)," "mismatch flag count," "drill-down to mismatch list," states `just-updated / stale / complete`. That is the operational daily-reconciliation context (Story 9.1 `<NomineeConsole>` home already shows "X of Y contributed · Z reconciled · last updated"). The **epic's Story 9.12** is the **member/public confirmed-only progress card** (letter+name, confirmed count, amount raised, days remaining, fixed amount; explicitly NOT yellow/pending/projected). Build the **epic's** spec. Do **NOT** build last-updated timestamps, mismatch-flag counts, drill-down links, or daily-delta/stale states into the 9.12 presenter — they belong to the nominee-console variant and are out of scope. (A shared name across two contexts; the epic AC is the binding contract for 9.12. Same footgun class as Story 9.11's `amount_mismatch` collision and Story 9.10's epic-vs-PRD divergence.)

> ⚠️ **9.12 is a presentation-extraction story.** It adds **no** `contribution.*` event type (the Story 8.10 fourth-type fence — `contribution.*` stays exactly three), **no** read/endpoint/query, **no** new alert category, **no** react in `packages/ui`, and touches **nothing** under `packages/channels/src/**` or the matcher/reconciliation write paths. It adds one pure `packages/ui` presenter (confirmed-only input, amount-raised derivation, token/i18n-key/numeral discipline), unit-tested with anti-widening teeth, wired into the existing mobile consumer with the public consumer seamed.

3. **Amount raised is derived `confirmedCount × fixedAmount` — the single canonical definition, structurally yellow-proof (Decision 3, load-bearing).** The presenter computes `amountRaisedInr = confirmedCount × fixedAmount` (whole INR, same unit as `fixedAmount`) and exposes it on the view-model. It does **not** read, sum, or accept any per-event confirmed amount. A unit test proves: (a) `raised === confirmedCount × fixedAmount` across a matrix (0 confirmed → ₹0; N confirmed → N×fixed); (b) the meter is confirmed-only — a scenario where members have **attested (yellow) but not confirmed** yields the SAME raised amount and SAME `confirmedCount` as if they had done nothing (there is no yellow operand to leak, because the presenter never receives one). ### Amount raised = `confirmedCount × fixedAmount` is the load-bearing structural choice (Decision 3)

The temptation is to sum a per-`contribution.confirmed` amount. **Don't** — for three reasons: (1) it is unnecessary (every confirmed contribution is exactly `fixedAmount`; an over/under-payment stays a RED `amount_mismatch`, never confirmed — Story 9.11's "over-payment stays RED" + Story 9.5); (2) `confirmedCount × fixedAmount` is **structurally yellow-proof** — there is no attested/pending operand in the multiplication, so the raised figure **cannot** be inflated by intent, which is the whole point of the confirmed-only invariant expressed as arithmetic; (3) it avoids coupling the presenter to whatever the confirmed-event payload happens to carry. The multiplication is the single canonical definition of "amount raised" — like `classifyAmountMismatchDirection` is the single definition of over/under (Story 9.11). Convert to a formatted `₹` string ONLY at the render boundary (`formatInr`), never in the presenter. (Note: Story 7.5's fixed-amount transition is a FUTURE `upcomingAmountChange` — the current cycle's confirmed contributions are all at the snapshotted `fixedAmount`, so the multiplication holds for the live cycle.)

### Confirmed-only is a SHAPE, not a filter (Decision 2, the 9.5 invariant this story carries)

Story 9.5's canonical-financial-truth AC names Story 9.12 explicitly as a downstream consumer that "reads ONLY from the `contribution.confirmed` event-derived state" and mandates a CI test that "no UI surface promotes any contribution to confirmed without a `contribution.confirmed` event" and "no query counts yellow-pill or unconfirmed contributions toward raised/confirmed totals." 9.12 satisfies this **structurally**: the presenter input has no yellow/pending/projected field to begin with (so nothing to filter), and the raised amount is `count × fixed` (so no yellow operand exists). The anti-widening test (Task 3b) is the teeth — a green test is the proof the meaning cannot fork, so no reviewer has to eyeball every surface ([[feedback_gate_scope_semantic_coverage]]). This is the presentation-layer analog of the 8.3 contract's `.strict()` decoy-teeth and the 8.2 progress "the one change this contract exists to forbid."

ux-design-specification.md §2011 describes `<PoolProgressCard>` as a **nominee-console/trustee daily-delta operational widget** (last-updated timestamp, mismatch-flag count, drill-down, `just-updated`/`stale`/`complete` states). That is the operational reconciliation context — Story 9.1's `<NomineeConsole>` home already renders "X of Y contributed · Z reconciled · last updated." The **epic's Story 9.12** is the **member/public confirmed-only progress card** (letter+name, confirmed count, amount raised, days remaining, fixed amount; NOT yellow/pending/projected). The name is shared across two contexts; **the epic AC is the binding contract for 9.12**. Do NOT build last-updated timestamps, mismatch counts, drill-downs, or daily-delta/stale states into the 9.12 presenter — they are the nominee-console variant's, out of scope here. (Same footgun class as Story 9.11's `amount_mismatch` collision and 9.10's epic-vs-source divergence — flagged so the dev builds the epic's spec, not the UX-doc widget.)

### Keep the member's OWN self-state OUT of the confirmed-only meter (the 8.2 separation)

The mobile card has TWO distinct regions: (1) the **confirmed-only aggregate meter** (`progress: { confirmedCount, rosterSize }`) — this is what 9.12's presenter owns; and (2) the member's **own** contribution self-state (`myContribution: none|attested|mismatch` → `<StatusPill status="yellow|red|held">`) — a PER-MEMBER signal, DELIBERATELY separate from the aggregate. Do NOT route `myContribution` through the pool-progress presenter or let it touch the meter — that separation IS the confirmed-only invariant on the card (8.2: "Never add a yellow/red/attested count to `progress`"). 9.12 only touches region (1) + adds the amount-raised line; region (2) stays exactly as Story 9.6/9.7 left it.

### `packages/ui` stays react-free (Decision 1)

`packages/ui` depends only on `@twt/contracts` (+ dev `@twt/tokens`, `@twt/eslint-config-twt`). Adding react/react-native would break the "pure logic only, no framework" contract that lets the SAME presenter serve RN (mobile), the PDF note-template, and the Epic-11b public web. The presenter emits `@twt/tokens` role NAMES as strings (e.g. `'status-confirmed'`) — never a hex, never a resolved colour, never a `@twt/tokens` runtime import (FM-14 #2: no magic-number colours in component code). Verify `pnpm --filter @twt/ui build` produces no react import.

### Do NOT

- Do **not** build a React/`.tsx` component in `packages/ui`, or add react/react-native to `packages/ui/package.json` (Decision 1) — it is a pure presenter package.
- Do **not** add any `attestedCount` / `pendingCount` / `yellowCount` / `projectedTotal` / `status` / `utr` field to the presenter input or view-model (Decision 2; the 9.5 confirmed-only invariant; the anti-widening test fails otherwise).
- Do **not** sum a per-`contribution.confirmed`-event amount for "raised" — it is `confirmedCount × fixedAmount` (Decision 3), the only definition, structurally yellow-proof.
- Do **not** build a new read, query, endpoint, or contracts wire-DTO — the member card feeds from the existing Story 8.2 `active-contribution` response (Decision 4).
- Do **not** add a `contribution.*` event type / new alert category / matcher / reconciliation / self-verify / channels change (8.10 fence; AC7).
- Do **not** build the UX-doc's nominee-console daily-delta widget (last-updated / mismatch-flag / drill-down / stale states) into 9.12 (Decision 5) — that is a different surface.
- Do **not** route the member's own `myContribution` self-state through the pool-progress presenter or into the aggregate meter (the 8.2 separation).
- Do **not** format numerals in the presenter — emit raw integers + i18n keys; the render layer applies `formatInr` + Latin numerals at the boundary (Story 1.17; AC5).
- Do **not** apply a red/danger tone to a low meter — a low-or-zero confirmed meter is honest, never an error (the existing card's rule; Story 2.2 register).
- Do **not** let the `min(100, …)` percentage clamp silently repair `confirmedCount > rosterSize` — that impossible over-count must THROW and surface, not render as a falsely-100%-complete meter (AC2/AC3).
