# Story 13.1b: A Newly Approved Field Worker Is Sent Their Code by SMS - Only After the Approval Has Committed `[CONSUMER]`

Status: review

## WHAT THIS STORY IS, IN ONE PARAGRAPH

Story 13.1a (done) lets a Pariwar Admin approve a registered worker and lets an officer read the worker's code aloud. This story sends the worker that code by
SMS without anyone having to ask. Its shape is an **outbox**: the approval transaction records "a code SMS is due" (a row in a new table,
`field_worker_code_sms_sends`), so an approval that rolls back leaves no row and an approval that commits cannot lose one. A **jobs sweep** picks up each due
row, checks the worker is still `active`, writes one audit line, decrypts the mobile, and hands one DLT-registered text to the MSG91 gateway. It sends
**at most once**: if the outcome is unknown it does not try again, because BigDev's own recovery is the by-hand read. The row's outcome, joined to MSG91's
delivery report, becomes a **signal on the admin's worker list**, as of when that list loaded, so an officer who looks the worker up sees whether to read the code out. Nobody is alerted (Q-7). It builds no route, no permission key, no event and
no resend. Nothing goes out in production until a template is approved and its id is set: **no DLT template has been submitted yet**, and that is roster Row 49's work, outside this repo.

## Story

As a **field worker whom the Pariwar Admin has just approved**,
I want **my code sent to my phone by SMS**,
so that **I can start sharing it without waiting for an admin to read it to me.**

## Policy meaning (AI-10-1)

**This story introduces ONE predicate, and it gates a message to a field worker, not a member's access to a benefit:** *the code SMS goes only to a worker who is
`active` at the moment it is sent* (AD4). No member predicate is added or changed: no member state, no `account-frozen` source, no `member_attribution` row, no payout
field (I10). 13.1's `acceptsNewAttributions` is not touched.

*In the field worker's terms:* **"Once a Pariwar Admin approves you, the Trust texts your code once to the number on your application. If you are suspended or
ended before it goes, it does not go. If it does not reach you, nobody sends it again: ask your District Admin or Pariwar Admin and they will read it to you."**

*In the member's terms:* **nothing changes** - 13.1's sentence stands: *"Who introduced you never changes what you are covered for - if your introducer is no longer
active, you are a member in full; only the credit to them is not recorded."*

*Costs, stated so they are not found later:* (a) One text per registration. A district move changes no id and no code, so it sends nothing; a new registration after a termination, or in
another Pariwar, is a new worker, a new code and a new text. A worker whose phone was off when it arrived and who deleted it must ask an officer (AD14). (b) The number is the one an
officer typed from the form; nothing proved it, and no route corrects a stored mobile. A mistyped number sends the code to a stranger, **and the list then reads `delivered`, so the
officer sees nothing wrong** and the worker hears nothing. The text carries no name (AD9). Whether such a text is a notifiable breach is counsel's and is not judged here (section 0
edge 8, Row 49 (d), [[project_dpdp_breach_duty_not_sdf_gated]]). (c) This text is also the worker's only notice of the approval (13.1a AD14). A worker approved while the SMS is not lit,
or whose text fails, hears nothing until they ask, and never gets the text later (AD13). (d) Nobody is told of a failed text: the line shows only to an officer who opens Find and chooses the
worker's district (Q-7). (e) A suspension landing in the seconds between the state check and the gateway call does not stop the text (AD4).

**Checked against the Niyamavali** (the git-ignored private copies in the main checkout, grepped by absolute path 2026-11-06): `docs/legal/niyamavali.md` for

([[feedback_niyamavali_rulebook_not_spec]]): "silent" is a finding, not a blocker.
**Checked against the Privacy Policy** (`docs/legal/privacy-policy.md`, private copy, same date): `field.?worker|contractor` 0 hits, `sms` 0 hits. A field worker is outside its
Members / nominees / claimants scope (13.1 section 0 edge 5). So the footing for texting a worker is the physical recruitment form (13.1 Q-3) and only that: **its purposes'

## FOUND FACTS (G) - traced at `d555f75d`, 2026-11-06

- **G1 - HEADLINE: the epic's "NO sender for a recipient who is not a member" is STALE.** `sendClaimDltSms` takes an explicit E.164 and its callers text nominees and claimants; the 5.11b
  generic path `prepareDltSms` + `sendPreparedDltSms` (`apps/jobs/src/scheduler/claim-dlt-sms-send.ts`) has no claim or helpline dependency and admits every send-row kind. The real gaps are: no send row, no
  CRQID kind, no registry entry, no recorded language. The sender is NOT a new build. `dispatch()` is not usable: it is keyed on `Alert.member_id`, and targets resolve by member.
- **G2 - HEADLINE: `decryptFieldWorkerField` cannot be "reused" from a job.** It lives in `apps/api/src/modules/field-worker/field-worker-crypto.ts`, and `apps/jobs` cannot import `apps/api` (api depends on jobs; the reverse is a
  cycle). Precedent for the fix: Story 8.8 moved member field crypto into `@twt/domain` and the API module re-exported. `FIELD_WORKER_FIELD_CLASS` is already in `@twt/domain` (`encryption/field-classes.ts`); `EncryptionDeps` is API-local, so the
  domain function takes the structural `{ kms, kekRef }` it needs. `buildJobsEncryptionDeps` is a by-value parallel of the API's (same KEK reference), so an API-sealed mobile decrypts in jobs.
- **G3 - HEADLINE: 13.2's door is request-only.** `readAttributionCodeForRequest(request, scopeTx, ...)` takes the Pariwar from `requestContext`; a job has no request. The reach fence
  (`apps/api/tests/unit/attribution-code-reach-fence.test.ts`) forbids `attributionCode` and `readAttributionCodeForFieldWorker` outside the module, the door and `ALLOWED`, and a planted door in `apps/jobs` is one of its positive controls. The door's header names the
  sanctioned way: a "REVIEWED addition to the fence's allow-list with its own named Pariwar source (TR4b)"; the fence's header says the same of a new entry. 13.2 C4 names two needs for a job, and this story has both: that entry, and a jobs-login grant on the codes table (Row 49 (f)). The domain read requires a checked-out client inside a transaction scoped to the same Pariwar
  (`assertTxBoundScope`); `withPariwarScope(pool, pariwarId, (db, client) => ...)` gives exactly that. It sets NO role: the read runs as the jobs login, so the explicit `pariwar_id` predicate is the only Pariwar filter in it (13.2 TR3).
- **G4 - HEADLINE: the COMMIT sits INSIDE two nested audit wrappers.** In `approval-handlers.ts` `closeScopeTx(ctx.scopeTx, true)` runs inside the inner `mutate`. A throw after it, anywhere in `mutate`, writes both `_rolled_back` lines over a
  committed approval and `withIdempotency` releases the key. A replay returns the stored result and does not re-run `run`. So anything hung on the handler after COMMIT either lies in the log or fires twice, and a crash between COMMIT and an
  enqueue loses the send with no trace. `sms`-after-commit in the handler is the design this story must NOT use.
- **G5 - HEADLINE: nothing can "subscribe" to `field_worker.activated`.** There is no generic `events_log` fan-out subscriber (`apps/jobs/src/scheduler/cycle-open-alert.ts` says so). A sweep over `events_log` would also need its own "already handled" record, which is the table this story adds
  anyway. The event is the conceptual trigger; the row is the mechanism. `pending_kyc -> active` happens once in a worker's life; `reactivated` is a different event (`state.ts`), so a reinstated worker gets no second text.
- **G6 - A job has no actor to name.** C1's "actor-naming" is the API's shape (`actorId`, `actorRole: authorization.role`). Writers allow nulls (`actorId`, `actorRole` nullable in `audit/write.ts`). Job precedents: `module-activation.ts` (`withCompensatingAudit`, both null),
  `claim-shepherd-assign.ts` (`actorRole: 'system'`). Naming the approver as the actor would state something false: they did not decrypt anything. The row carries `activated_audit_id` so the line can be followed back to the approver (AD5).
- **G7 - Neither `field_workers` nor `events_log` can carry the signal.** A new column on `field_workers` fights the guard `field_workers_reject_unguarded_state_write` (0201): every update needs the writer variable and a strictly increasing version, and a terminated row is untouchable; a sweep would have to
  bump a version with no event. A new event fails too: actors are human-only in the schema, the commands and the projector, `packages/events/tests/field-worker-registry-coverage.test.ts` demands set equality and "Human actor only", and an event that does not bump the row breaks the head check. So: a separate table, the twin of `alert_sms_sends` (0184).
- **G8 - No language is recorded for a worker.** `0200_field-workers.sql` has no locale column. Members use `COALESCE(m.preferred_locale, pp.locale_default)`; `pariwar_passport.locale_default` is NOT NULL, enum `hi | en`, and readable by anyone (`USING (true)`).
- **G9 - One code in ten starts with zero.** `generateAttributionCode` pads: `String(randomInt(0, 10 ** 6)).padStart(6, '0')`. The sheet's numeric type says a leading zero "is ⛔ addressed by any primary source; Row 30 (d) asks". The OTP templates carry the same open question. A provider that stripped the zero would deliver a wrong code. That is a Row 49 (e) go-live leg, and the device proof must use a code starting with `0`.
- **G10 - DLT is NOT STARTED, and the sender is unknown.** Sheet line 3: "NOT STARTED"; no Record line shows a submission; Row 30 (b) has no evidence. - **AD3 - AT MOST once (the epic's open question).** The row becomes `attempting` and COMMITS before the gateway is called. Anything that MAY have reached the gateway is final: a timeout or `api_unavailable:*` -> `error`, detail `exhausted:outcome_unknown:<cause>`; a crash-left `attempting` past the lease -> the same. Anything that
  DEFINITELY did not reach it goes back to `due`: a KMS or Secret Manager transient, a failed audit write, a database fault in the read, `rate_limited:*`. Reason: "a duplicate SMS vs a missed one - a missed one is recoverable by hand" (epic), and BigDev's own process is the by-hand read. Cost: an unknown outcome is shown as `not_confirmed` even if the text arrived; the worker just has a code they did not need to ask for.
  **Settle and release** both use the twin's `finalise` loop in full (`ALERT_SMS_FINALISE_BACKOFF_MS`, `[200, 1000]`): a THROW is retried after each pause; a `false` is never retried, the row moved on; a `false` after an earlier throw is worded as unconfirmed, because that try may have committed; when every try throws, alarm with the send id and, on an accept, the gateway's request id, the only handle on that text. A row left this way lapses to `exhausted:outcome_unknown`: an accepted text reads `not_confirmed`, and a failed release turns a definite non-send into the same word. Accepted: rare, and it errs towards the officer helping.
  **The queue.** The sweep claims **one row at a time** (the lease covers one row's work, never a batch's queue time, TR6), ordered by `updated_at`, then `send_id`. A release sets `updated_at`, so a released row goes behind every waiting row, and it is not claimable again until `2^(attempt_count - 1)` minutes after that `updated_at`: 1, 2, 4 ... 256. So a row that always fails (G19) costs the queue one tick per attempt, not a day. `attempt_count` rises at each claim; a release on attempt `FIELD_WORKER_CODE_SMS_MAX_ATTEMPTS` is final instead: `error`, `exhausted:attempts`, alarm, so the ten attempts span about 8.5 hours, inside the max age. A flat one-a-minute retry would lose a lone row's text to a ten-minute blip. The ceiling bounds the decrypts and audit lines of a stuck row, and a permanent fault such as a missing grant ends here rather than as a false "may have sent". Cost: a fault outlasting 8.5 hours ends the row for good, and the by-hand read is the recovery. Until then the list reads `sending` and nothing alarms, because a release raises no alarm: a permanent fault is first alarmed about 8.5 hours after the first approval. Two clocks: the lease is judged on `updated_at`, the max age on `created_at`, which a release never moves, so a row released every tick still expires. `due` older than `FIELD_WORKER_CODE_SMS_MAX_AGE_MS` is final `error`, `exhausted:expired`: a long jobs outage ends in the by-hand path, not in a burst of day-old texts.
  **The lease** starts at the claim and covers the read, prepare, audit, KMS, send and settle. The bounded terms total about 80 s (read connect 10, Secret Manager 10, pre-flight 9, audit connect 10, send 10, settle 31) against 300 s; a unit test pins the constant above their sum, as the twin pins its lease. KMS `decrypt` and the audit advisory lock have no timeout in repo code. ## Acceptance Criteria

**AC1 - Due, in the approval's transaction.** When a Pariwar Admin approves a `pending_kyc` worker (13.1a's route, unchanged), one row exists with `outcome = 'due'`, `attempt_count = 0`, `activated_audit_id` equal to the `field_worker.activated` audit line's id, and the response, the two events, the two audit lines and the status are what 13.1a's tests pin (I4). (a) An approval that rolls back (a second-command failure; a failed COMMIT) leaves NO row. (b) A replay of the same key adds no row. (c) A lost race (the second approver, 409) adds no row. (d) `pending_kyc` workers have no row. (e) Under `twt_app` in the worker's Pariwar the insert succeeds; UPDATE and DELETE are refused; another Pariwar sees nothing.

**AC2 - The send.** Given a `due` row for an `active` worker with a provisioned template and a gateway fake, one tick makes exactly ONE gateway call for that row (filter by CRQID: a tick sweeps the whole shared test database): the template id for the Pariwar's locale, `{ code }` equal to the worker's code (a code starting with `0` keeps its zero), the worker's E.164, and CRQID `fw<send_id without dashes>`. The row ends `accepted` with `provider_message_id`, `locale`, and `attempt_count = 1`. A row committed by a REAL approval is the one sent: the API's live legs assert the row (AC1), and the jobs live leg runs the domain command `activateFieldWorker` in a real transaction, then a tick, because `apps/jobs` cannot import `apps/api`'s harness. No gateway call happens before the approval's COMMIT: a tick during an open approval transaction sees no row.

**AC3 - Never to the wrong person.** (a) A worker `suspended` or `terminated` before the tick ends `skipped_not_active`: no code or locale read, no audit line, no decrypt, no gateway call. (b) A worker reactivated later gets no second text (the row is final). (c) `pending_kyc` workers are never claimed (they have no row).

**AC4 - At most once, and the queue survives a bad row.** (a) Two ticks overlapping on one row: one send. The gateway fake holds tick A in flight until tick B has returned, on a row whose `updated_at` was past the lease before the claim, and B neither claims nor lapses it, so the overlap is real. (b) A process killed after claim leaves `attempting`; the next tick after the lease ends it `error`, `exhausted:outcome_unknown`; no re-send. (c) A gateway timeout or `api_unavailable:*`: final, no re-send. (d) `rate_limited:*`: back to `due`, sent later, one accepted text. (e) A KMS transient and a failed audit write: back to `due`, the gateway not called. (f) `due` past the max age: `error`, `exhausted:expired`, no send. (g) A finished row refuses every update at the database, for every role at default settings, and identity columns refuse change on a live row. (h) The sweep claims one row at a time and stops at `FIELD_WORKER_CODE_SMS_TICK_MAX`. (i) A release ends the tick: at most one attempt per row per tick, and one gateway call and one audit intent line per attempt. (j) A row that always releases does not hold up a younger row: behind K such rows, a younger row is delayed K ticks at most. (k) A row released on every eligible tick is not claimable before its backoff, and still ends: `exhausted:attempts` at attempt `FIELD_WORKER_CODE_SMS_MAX_ATTEMPTS` with one alarm, and `exhausted:expired` at the max age, judged on `created_at`. (l) A database fault in the read releases with `api_unavailable:db`. (m) A throw from `render`: no audit line, no gateway call, the tick resolves, no later row is touched in that tick, and the lease later ends the row `exhausted:outcome_unknown`. (n) After a final `auth:*`, a gateway `dlt_template_not_approved:*` or an unknown-outcome send, the tick ends. (o) Settle: a throw is retried; a `false` is not, and it alarms by id in the twin's two wordings; when every try throws after an accept the alarm carries the send id and the gateway's request id.

**AC5 - A failed send never undoes an approval.** For every row of the Outcomes table: the worker's state and `events_log` are unchanged by the sweep, and, except for `skipped_not_active` (not `active`, so 13.1a's 409) and `no_code` (an integrity fault, 13.1a's 500), `GET .../code` still answers 200 with an audit line.

**AC6 - Dark is honest.** With no template id: every due row ends `error`, `config:dlt_template_id_missing`, one alarm per row, no decrypt, no audit line, no gateway call, no retry; later provisioning the id sends nothing for that row. The fixture provider is never used: the row ends `error`, never `accepted`, and a source assertion shows `field-worker-code-sms.ts` does not name `createSmsProvider`.

**AC7 - The number, for this purpose only.** In a successful attempt the sequence is: the row claimed and committed, then the read (state, ciphertext, code, locale, in that order, stopping at a worker not `active`) and its scope transaction closed, then `prepareDltSms`, then exactly ONE `field_worker.code_sms_mobile_decrypted` line for that attempt (`actorId` null, `actorRole` `system`, locator `field_worker/<id>`, hash over ids only), then the decrypt of the mobile, then the gateway.
